# 独立した敵対的レビューを行う

`AGENTS.md`と`docs/develop/quality/code-review.md`を読み、適用基準と対象の版を確認する。日本語の報告前に執筆ガイドとPR運用を読む。

## 独立性と権限

重要変更では、通常レビューに加えてこの手順を実行する。ユーザーから明示的に依頼された範囲にも使用する。委譲は読み取り専用のレビューに限る。修正、Git書き込み、外部投稿、マージ、データや設定変更の権限を与えない。

原則1名を`fork_turns: none`で起動する。実装担当の結論、疑い、期待する指摘を渡さず、固定した差分・仕様・必要な関連資料から判断させる。モデルを指定せず親の設定を継承する。独立レビューを実行できない場合はその事実を報告し、コミットを止めてユーザーへ相談する。自己レビューを独立レビューとして扱わない。

## レビュー担当へ渡す情報

- リポジトリの絶対パス、ベース・headまたはHEAD・index tree ID、対象ファイルと読み取り方法
- Issueの目的・受け入れ条件・対象外、設計正本と適用する運用文書、このSKILL.md
- 通常系の成立確認に加え、失敗・境界・部分成功・競合・データ互換性の反例を探す依頼
- 差分で導入・悪化した問題を対象にすること、実行可能な安全な検証と権限の制約
- 該当行、期待と実際、具体的な成立条件、影響、一次根拠、反証の試み、確信度、修正方向を報告すること
- サブエージェント自身は再委譲しないこと。未確認の推論を確定事項にせず、指摘なしも有効な結果とすること

コミット前のtree ID取得は親が必要な権限で行う。独立担当は渡されたtree IDとindexの一致を`git diff --cached --exit-code <tree-ID>`などで読み取り確認し、`git write-tree`は実行しない。通常レビューのスキルを参考に読む場合も、この委譲先の読み取り専用・再委譲禁止の境界を維持する。

## 指摘の検証と終了

親は指摘をコード、仕様、テスト、実行結果などの一次情報で確認し、反証や前提の違いも検討する。外部仕様が必要なら公式の一次情報を確認する。重大な影響でも根拠が弱い仮説は、確定した`[must]`にせず未確認のリスクとして区別する。

重大な指摘について判断が割れた場合だけ、追加1名の独立担当へ同じ固定対象と双方の根拠を渡す。結論を誘導しない。このレビュー対象について合計2名、修正後の再確認は1回までとし、上限で未解決ならコミットを止めて相談する。修正で別の重要変更が加わった場合も上限を黙ってリセットせず相談する。

通常レビューと重複する指摘を統合し、PR運用のPrefixで報告する。採用・棄却した指摘と根拠、対象の版、独立担当の実施状況、実施・未実施の検証、未解決事項を残す。ファイルや外部サービスへの記録は親の依頼された開発工程で行い、このスキル自身は投稿しない。
