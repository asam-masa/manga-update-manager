# 復元元ZIPの受入・識別・解放契約

Issue #637、親 #378。2026-11-22に承認した初回の入力範囲を、[読取保持の方針](./restore-preparation.md#復元元zipの読取保持6342026-11-21)と[Spike #635](./verification/restore-source-hold-spike.md)に沿って具体化する。#639で取得・識別・解放、#640で保持中の読取・再確認を部品として追加した。ZIP展開・復元の通常経路は未接続である。

## 初回の対応範囲

- ローカルNTFS上の既存の通常ファイルを、ドライブ文字から始まる通常の絶対パスで受け入れる。日本語と空白を含む通常の名前は対象とする。
- 相対パス、`.`/`..`、特殊なデバイス指定、UNC/ネットワーク共有、代替データストリーム、曖昧な末尾や予約名等は、既存のパス検査と同じく補正せず拒否する。
- 親階層と対象のシンボリックリンク・ジャンクション等のリンク経由を拒否する。対象ファイルのハードリンク数も1だけを許可し、複数または確認不能を拒否する。
- exFAT/FAT32、ネットワーク共有、リンク経由の入力を直接受け入れるための追加検証は後続へ分ける。利用者が対応するローカルフォルダーへコピーして選び直すことは可能だが、アプリが自動コピーして条件を回避しない。

保存側のパス確認・親保持・識別照合を再利用し、検証済みの範囲から進める。一方、読取だけでも保存場所が制限され、未対応のUSBや共有上のZIPは直接選べない。保存先の条件を無条件に入力側へ流用した結果ではなく、初回の範囲を絞る承認内容である。

## 取得と保持

親階層を既存の条件で確認し、改名・削除を許可しない共有条件で保持する。その中の対象を読取専用・読取共有・既存ファイルだけの取得で開き、検証から展開完了まで同じハンドルを維持する。保持中は親階層の改名・削除も一時的に制限される。

書込/削除用の先行アクセス等で必要な保持を取得できなければ、検証・展開を開始しない。弱い共有条件・パス再取得・作業コピーへ自動で切り替えない。元ZIPに作成・書換え・修復・削除を行うAPIや権限を追加しない。

取得した同じハンドルから、次を確認してから所有を返す。

| 確認 | 契約 |
| --- | --- |
| 種別・属性 | ディスク上の通常ファイルだけを許可し、ディレクトリーとリパースポイント等の対象外を拒否する |
| ハードリンク数 | 1であることを確認し、複数・確認不能を拒否する |
| 名前・識別 | ハンドルの名前と要求パスを照合し、volume/file IDを基準として保持する。パスだけで同じ物と判断しない |
| サイズ | 既存ZIP入力の範囲（22バイト以上、`MaxArchiveBytes`以下）を確認する。DBコピー用の256MiB上限をZIPへ適用しない |

識別の基準は保持取得時であり、ファイル選択画面を開く前からの同一性を保証するものではない。拡張子だけで有効なZIPと扱わず、既存の形式・実量・CRC/ハッシュ・DB/画像の意味的検証を別途行う。

## 読取と再確認

所有する部品は生のハンドルや書込操作を公開せず、同じハンドルの読取・サイズ取得・再確認と解放を扱う。呼出元は借用した読取処理をすべて終えてから解放し、元ZIPを準備物の削除対象へ渡さない。

取得完了時、検証/展開へ貸す前、最終読取後に、同じハンドルから名前・ID・種別/属性・リンク数・サイズを照合する。基準との不一致や確認不能を検出した場合は準備を成功扱いにせず、退避・切替へ進まない。これは確認した時点の照合であり、全別名やメタ情報が恒久的に固定される保証ではない。

読取は件数・EOF・下位エラーを保持する。想定外の読取失敗や内容検証の失敗を部分成功へ変換しない。取消は各操作の前後で確認し、開始済みのOS I/Oを強制終了できるとは保証しない。I/OとCloseは順序付け、Close開始後は解放の成否にかかわらず新しいI/Oを拒否する。

## 失敗・取消・解放

| 状態 | 契約 |
| --- | --- |
| 取得前の失敗・取消 | 入力の所有を返さず、未取得と取得/解放未確認を区別する |
| 親の部分取得、対象取得後の確認失敗・取消 | 取得済みのファイルと親の解放を試み、元の原因と各取得/解放の観測を残す。未確認の所有を正常な入力として返さない |
| 読取中の失敗・取消 | 消費処理の終了後に解放する。元の失敗/取消と、ファイル・親の解放結果を分離する |
| Close | 一度だけ実行し、ファイルの後に親階層を解放する。途中の解放が失敗しても残りの解放を試み、結果を保存する。再度のCloseでネイティブ処理を再試行しない |
| 解放失敗・確認不能 | 成功へ丸めず、入力解放が未確認であると呼出元へ伝える。後続の退避・切替へ進まない。再取得や元ZIP削除で解消しようとしない |

入力の解放確認は、準備物の削除・アプリの通常操作再開の許可とは別である。通常操作の再開や終了案内への接続は後続で具体化し、この記録だけで再開条件を追加しない。

## 取得・識別・解放部品（#639）

`platform.OpenRestoreSource`は既存のパス検査と`HoldBackupDirectory`で親階層を確認・保持し、既存の対象を読取専用・読取共有で開く。同じハンドルから通常ファイル/属性・リンク数1・volume/file ID・名前・ZIPのサイズ範囲を確認して、`RestoreSource`の所有を返す。書込・作成・削除権限、生ハンドル、公開の読取APIは追加しない。`Path`と`Identity`は観測であり、削除や再取得の許可ではない。

取得失敗や取消では所有を返さず、`RestoreSourceError`に元の原因と`RestoreSourceReleaseResult`を残す。親の部分取得の観測も既存のエラーから引き継ぎ、未取得と解放未確認を区別する。ファイル取得とエラーが併発した場合も、その保持を解放してから返す。

CloseとReleaseResultは同じmutexで直列化する。Closeはファイルの後に親を解放し、失敗しても親の解放を試みる。結果と原因を保存してネイティブ再試行を行わず、エラーがなくても解放の観測が揃わなければ`ErrRestoreSourceRelease`を残す。解放結果だけで準備成功や通常再開を許可しない。

合成NTFSで読取権限と書込/削除権限の不在、親/対象の保持とClose後の内容保全、短小/欠損/ディレクトリー/複数ハードリンク/親と対象のシンボリックリンク/先行アクセスの拒否を確認する。故障模型では親の部分取得、取得とエラーの併発、観測/名前/サイズの不一致、取得前後の取消、ファイル/親の解放失敗・未確認、並行Closeの一度だけの実行を確認する。

サイズ境界はメタ情報の模型で確認し、ZIP上限分の実ファイルは生成していない。Close失敗の模型は実際には解放後にエラーを加える条件を含み、実OS解放故障の再現ではない。シンボリックリンクを作成できない環境の該当試験はskipとし、成功へ含めない。保持中のReadAt等と再確認は#640へ分け、App/UI・ZIP検証/展開には接続しない。

## 保持中の読取・再確認部品（#640）

`RestoreSource.Reader(ctx)`は、保持している同じファイルを読む`io.ReaderAt`を貸す。新しいハンドルを開かず、借用によって所有の寿命を延ばさない。呼出元はすべての消費処理を終えてからCloseする。

読取前後に取消を確認する。通常の読取では件数・EOF・下位エラーをそのまま返し、読取後に取消を検出した場合は件数と元の原因を残して取消を併記する。開始済みのOS I/Oを強制中断しない。失敗や取消で所有を暗黙に解放せず、呼出元が消費処理を終了してからCloseし、元の原因と解放結果を分けて扱う。

`Size(ctx)`と`VerifyIdentity(ctx)`は同じハンドルを観測し、名前・volume/file ID・通常ファイルの条件・リンク数1・取得時のサイズを再確認する。サイズ取得も未確認のキャッシュ値を返す操作ではない。不一致・確認不能では成功値を返さず、観測の下位エラーと取消も保持する。ZIPの内容が有効であることを保証する操作ではない。

呼出元は検証へ貸す前、展開へ貸す前、最終読取後に再確認し、読取・内容検証・再確認が失敗したら準備全体を成功扱いにしない。この順序と退避・切替の停止は後続の接続で実装し、部品が自動実行するとは扱わない。

読取・再確認とCloseは同じmutexで直列化する。Closeが排他を取得して開始した後は、物理ハンドルの解放に失敗していても、新しい読取・再確認を拒否する。Close要求の待ち行列の先着順までは保証しない。

合成NTFSで同じファイルの読取、位置の非変更、短い読取のEOF、Close後の拒否、元内容の保全を確認する。保持後にハードリンクを追加できた条件では、再確認でリンク数の不一致を検出した。リンクの追加そのものや全別名の変更を防ぐ保証ではない。故障模型でID・名前・サイズ・観測の不一致、読取エラーと取消の併発、解放失敗後も物理ハンドルが生存する条件でのI/O拒否を確認する。チャネルで読取・再確認・Closeを待ち合わせて順序を確認し、実OS解放故障や電源断の再現とは区別する。

## 検証範囲と実装の分割

Spikeでは、選択した名前への変更拒否と同じハンドルの読取を限定確認した。一方、別ハードリンク名は改名・削除できたため、全別名の固定を保証する根拠にはしない。今回のリンク数1の受入条件と再確認も、製品の部品・故障試験として確認してから接続する。

先行する書込/DELETEハンドルや今回の書込マッピングでは取得を拒否したが、全環境・全マッピングの結果ではない。ドライブの付替え、悪意ある属性変更、別プロセスやドライバー等を含む任意の環境変化への完全な保護を保証しない。必要な安全条件の不成立を検出したら、条件を緩めず中止する。

1. [#639](https://github.com/asam-masa/manga-update-manager/issues/639)で取得・識別・一度だけの解放と観測の保持を追加する。合成NTFSと故障模型で入力拒否、部分取得、先行アクセス、取消、解放未確認を確認する。
2. [#640](https://github.com/asam-masa/manga-update-manager/issues/640)で保持中の読取・再確認とCloseとの順序付けを追加する。件数/EOF、基準不一致、取消、Close後の拒否を確認する。

型・エラー分類・既存部品の再利用は各Issueの実装前に照合する。新しい対応範囲を実装都合で追加せず、ZIP検証/展開、DB/画像の意味的検証、App/UI、退避・切替・復旧への接続はさらに後続へ分ける。ADR-0022のValidation StatusはPendingを維持する。
