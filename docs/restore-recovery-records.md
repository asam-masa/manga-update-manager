# 復元事前記録と完了記録

Issue #684。復元の切替と再起動時の中断判定に使う記録を定める。復旧方針は[退避・切替の合意](./backup-restore.md#復元と退避保持の追加合意3852026-11-03)、観測の根拠と限界は[合成試験](./verification/restore-switch-spike.md)を参照する。

## 確定した配置と順序

アプリのデータ保存先直下の `restore-active` を進行中の復元専用とする。そこに `plan.json` と `complete.json` を置く。起動時は既存のストレージ排他を取った上で、この場所を通常DB接続・移行・画像整理より前に確認する。復元ID別の履歴から起動対象を選ばない。進行中の記録が残る場合は新しい復元を始めない。

事前記録には旧一式と準備済みの新一式を識別する情報、および予定配置を保存する。非上書き公開、公開後の同一性、必要な同期と解放が確認できてから旧一式を退避する。事前記録の公開に失敗した場合や結果を確認できない場合は、旧一式を移動しない。新画像の最終配置と同一性を照合し、作業領域の新DBへ画像管理情報を反映して接続の終了を確認した後、新DBを配置する。配置結果の確認後に、同じ復元IDに紐づけた完了記録を別ファイルとして追加する。事前記録を上書きしない。同期の確認は電源断後の耐久性の保証を表さない。

## 形式と読取契約

読取部品の入力は、取得側が区別した「取得済みのバイト列」「不在確認済み」「状態未確認」と、未公開候補の観測である。取得側が読取不能や公開結果不明を報告した場合も状態未確認とする。空の本文、nil、読取エラーだけから不在を推測しない。

本文は形式版付きのUTF-8 JSONとする。事前記録と完了記録は役割の異なるオブジェクトとして検証する。完了記録は復元IDと、取得した事前記録の元バイト列のSHA-256で対応付ける。再シリアライズ結果は比較に使わない。未知版、欠落、余分なフィールド、重複キー、末尾の別JSON、上限超過は拒否する。

### 形式v1

- 事前記録の必須キーは `version`、`restoreId`、`workspaceId`、`oldDatabase`、`oldCovers`、`newDatabase`、`newImages` とする。
- `version` は整数の `1`、`restoreId` と `workspaceId` は小文字の16進文字32桁とする。復元IDはこの切替の識別子、作業領域IDは既に準備した領域を指す識別子である。
- 物理識別のオブジェクトは `volumeSerial` と `fileId` を持つ。小文字の16進文字でそれぞれ16桁、32桁とし、後者はWindowsの128ビットIDのバイト順を保つ。ファイルとディレクトリーの種別は配置の役割で区別し、取得側でも照合する。
- `oldDatabase` は物理識別を持つ。通常パスから当該復元の退避先へ移す役割とする。 `oldCovers` は旧画像フォルダーの物理識別、または不在確認済みを表す明示的な `null` とする。キーの欠落や確認不能を `null` に変換しない。
- `newDatabase` は `stagedId` と `identity` を持つ。前者は既存の準備ファイル名から得た小文字16進文字32桁の識別子で、後者は配置前の物理識別である。 `newImages` は `imageId`、`stagedId`、`identity` を持つ要素の配列とする。画像IDは小文字16進文字32桁とし、含有画像だけを記録する。0件は空配列とする。
- 事前記録内で画像ID、準備ファイルのID、物理識別の重複を拒否する。新DBを含む準備ファイルのIDも相互に一意でなければならない。
- 完了記録の必須キーは `version`、`restoreId`、`planSha256` とする。 `planSha256` は小文字16進文字64桁。版と復元IDも事前記録と一致することを確認する。

事前記録は最大8MiB、完了記録は最大4KiBとし、バイト列の取得側は各上限+1バイトを超えて読み取らない。読取部品でも上限を検査する。新画像は既存の形式v1に合わせて最大1万件とする。この件数制限を旧画像フォルダー内のファイルに適用しない。

予定配置は固定の配置種別と、形式で検証した識別子で表現する。任意のパスをJSONから取得して保存先に連結する処理は設けない。読取部品からファイルI/O、移動、削除は行わない。

旧画像は退避・復旧の単位に合わせ、画像フォルダー一式の物理識別を記録する。旧画像の個別一覧は作らない。この照合で確認するのはフォルダーの同一性である。配下の各画像の内容は別の観測が必要となる。フォルダーの不在を確認できた状態と、確認できない状態を区別する。

| 観測 | 判定 |
| --- | --- |
| 未公開候補なし・事前と完了ともに不在確認済み | 記録なし |
| 未公開候補なし・妥当な事前記録・完了は不在確認済み | 未完了の候補 |
| 未公開候補なし・妥当な事前と完了・版と復元IDとSHA-256が一致 | 完了の候補 |
| 完了だけ存在、記録の不一致・破損・取得未確認、未公開候補ありまたは有無を確認不能 | 保全停止 |

記録が一致しても実物の照合が必要である。完了の候補では最終配置と更新後のDB管理記録を確認する。未完了の候補では旧一式を安全に特定できる場合だけ復旧へ進む。判定結果は通常起動や移動・削除の許可を表さない。

## 実装の分割

### Windowsでの記録取得（#687）

列挙と固定名のオープンは、照合済みの親ハンドルを起点とする。ドライブ文字を使って絶対パスを開き直す方法では、別の親で得た不在を区別できない。既存部品から再利用するのは祖先保持とハンドル検査であり、親ハンドルを起点とするオープンと列挙は追加の検証対象とする。

既存のストレージ排他を取得した呼び出し元から、検証済みの保存先を受け取る。排他は観測の開始から呼び出し元が判定を使い終えるまで維持する。既存の親保持とハンドル検査を再利用し、ローカルNTFS上の親を削除共有なしで保持する。固定名の対象は再解析ポイントをたどらず開き、種別、正規名、ボリュームと物理IDを保持ハンドルで確認する。

| 観測 | 取得結果 |
| --- | --- |
| 保存先を保持・照合でき、直下の完全な列挙で `restore-active` とその大小文字違いがなく、固定名のオープンが `ERROR_FILE_NOT_FOUND`、再確認も一致 | 事前・完了とも不在確認済み、未公開候補なし |
| 検証済みの `restore-active` を保持し、同じディレクトリーの完全な列挙に対象名がなく、固定名のオープンも `ERROR_FILE_NOT_FOUND` | 対象の記録が不在確認済み |
| 列挙とオープンが一致し、通常ファイルを保持・照合し、同じハンドルから上限内で全体を読み取れた | 対象の記録を取得済み |
| 親の取得失敗、アクセス拒否、共有違反、パス不明、列挙未完了、名前・種別・物理IDの不一致、再解析ポイント、読取・解放失敗、取消、観測の変化 | 状態未確認 |

専用ディレクトリーの直下には固定の公開名2つだけを許容する。列挙APIが返す自己・親の項目を除き、それ以外の項目は名前や型を問わず未公開候補ありとして扱う。大小文字違いや短縮名で固定名を開けた場合も、正規名・列挙名が一致しなければ状態未確認とする。後続の公開側は作業候補が残るとこの判定で停止する前提を守る。子の中身は再帰的に走査しない。

記録ファイルは書込み・削除共有なしで保持し、事前記録は8 MiB+1バイト、完了記録は4 KiB+1バイトまで読む。上限超過、読取エラーを伴う部分データ、取得時と再確認時の不一致では本文を採用しない。判定用の観測を渡す前に子、専用ディレクトリー、親の順に解放を試みる。元の失敗原因と解放の結果を保持し、解放未確認や取消時には取得済み・不在確認済みを返さない。

親の保持は配下の新規作成を止めない。列挙を再確認し、保持ハンドルと固定名の対応や不在が変化した場合は保全停止へ送る。列挙と再確認は単一の原子的な観測ではない。アプリ排他に従わない外部プロセスが観測間に変更を加えて元に戻す場合まで検出できるという前提は置かない。取得結果は後続の現物照合を省略する根拠にしない。

実装では、隔離したNTFS上で親・子の不在、空の専用ディレクトリー、未知項目、大小文字違い、共有違反、再解析ポイント、サイズ境界を確認する。故障試験では列挙途中の失敗、取得前後での項目追加・消失・同名差し替え、部分読取、取消、解放失敗を注入し、分類器に不在確認済みが渡らないことを確認する。ハンドル列挙の終端とIDの照合はこの試験で確認し、祖先保持や対象オープンの根拠は既存検査とWindowsの仕様を参照する。[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex)

保存先直下の列挙は `restore-active` と大小文字違いの候補だけを照合対象とする。正規名の項目が一つだけ存在して開いた実体と一致した場合に専用ディレクトリーの検査へ進む。大小文字違いだけが存在する場合や両方が存在する場合は状態未確認とする。大文字と小文字を区別する設定の親でもこの条件を合成試験で確認する。[Windowsのディレクトリーごとの大小文字区別](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)

### 実装済みの判定と後続作業

#695で、照合済みのWindowsファイルハンドルを借り、形式ごとの上限+1バイトまで同じハンドルから読む。読み取った本文は取消、上限超過、正常な終端以外の読取失敗で破棄する。取得全体の再確認と解放は呼び出し元の後続工程とする。

#693で、完全な列挙と固定名のオープンを1回分の観測として照合する。項目がある場合は名前、種別、再解析ポイントの有無、物理IDとボリュームを確認し、一致した子ハンドルを返す。列挙とオープンの両方が不在を示した場合だけ、この回の不在を確認できる。取得全体の再確認と分類器への接続は後続とする。

#691で、保持済みWindowsディレクトリーハンドルを固定サイズのバッファーで列挙し、項目の名前・属性・128ビットIDを取得する。走査途中の項目は暫定値とし、終端までの成功を確認できない場合は破棄する。隔離NTFSの複数ページ・再列挙で件数と対象IDを確認し、故障模型で途中失敗と取消を検証する。[FILE_ID_EXTD_DIR_INFO](https://learn.microsoft.com/windows/win32/api/winbase/ns-winbase-file_id_extd_dir_info)

#689で、照合済みの親ハンドルから固定名の既存子を読み取り用に開き、種別と再解析ポイント不在を確認するWindows部品を追加した。子名が見つからないという観測は、保持中の親から得た列挙結果と照合する工程に引き継ぐ。[親ハンドルを指定するWindows API](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes)

最初に取得済みの有界なバイト列から各記録を検査し、両記録の組み合わせを判定する読み取り専用部品を作る。件数・サイズの境界、未知版、フィールドの重複・欠落、誤ったID・ハッシュ、読取不能と不在の違いを合成試験で確認する。

`internal/restore.Classify` は、ファイル取得側が観測した事前記録・完了記録・未公開候補の状態を受け取り、形式と組み合わせを判定する。保全停止時には部分的な事前記録を返さない。

安全な取得と非上書き公開、現物照合、起動時の接続、正常完了した記録の退避は後続とする。ADR-0022の検証状態はPendingを維持する。
