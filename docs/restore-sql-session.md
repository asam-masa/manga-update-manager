# 復元準備DBの読取専用VFSと解放契約

Issue #655、親 #651 / #378。2026-11-22に承認した接続方式と、失敗・取消後の片付け条件を記録する。[Spike #653](./verification/restore-vfs-spike.md)は判断材料であり、この製品契約の実装・検証完了ではない。

## 採用と範囲

固定済み`modernc.org/sqlite`の公開読取専用VFSを採用し、[PreparedRestore](./restore-extraction.md#入力保持から準備成果物までの接続647)の借用ReadAtを使う。準備ファイルと親の保持を解放せず、パスからの再取得・DB一式の追加コピーを行わない。

別方式の追加調査を続ける案より、限定成立した経路で進める。既存の保持と読み取る内容を維持できる一方、借用アダプター・VFS登録・SQL資源・準備物の使用状態を管理する部品が必要になる。新規ライブラリの採用ではなく、既存依存の公開サブパッケージを使う判断である。

初回は準備DB1件を固定の論理名に対応付け、SQL接続1本で検査用の内部SQLを逐次処理する。同時追加接続は行わない。未知名・任意パス・書込用のOpenを許可せず、mode=roと対象VFSを明示する。SQLiteが要求した処理に対応できなければ失敗とし、ホストFSや書込可能な方式へ切り替えない。任意SQLの受付機能や完全なSQLサンドボックスの保証は追加しない。

## 借用と読取の原因保持

- 準備物の使用状態を確保してからVFS登録・SQL資源の取得を始める。借用を使う全処理が終わるまで、所有者を保持する。
- 論理ファイルを開くたびに独立したRead/Seek位置を作り、検証済みサイズで有界に読む。Statは同じ準備物の既知メタ情報を返す。任意の入力名から保存先を組み立てない。
- view Closeは借用viewの終了だけとし、元の準備ファイル・親を閉じない。重複した終了で参照数を重複減算しない。
- 最初の非EOF読取原因をセッション内に保持し、以後のI/Oを拒否する。EOFに別の原因を併記したエラーは単なるEOFとして捨てない。新しいクエリーでも原因をリセットしない。
- SQL結果・保持した読取原因・contextを、各検査結果の採用前と処理全体の終了時に合わせて判定する。SQLが成功しても、読取原因や取消があれば検証成功にしない。
- 一度失敗・取消になったら新しい検査へ進まない。元の原因、後処理の原因、各資源の取得/終了の観測を分離し、後の解放成功で元の失敗を消さない。

SQL用のviewやハンドルをセッション外へ貸し出さず、すべての消費処理を終えてから後処理する。取消は協調的に確認し、開始済みのOS I/OやSQLiteの処理を必ず即時停止できるとは保証しない。

## 終了とCleanupの条件

検査成功・失敗・取消のいずれでも、取得済みSQL資源の終了、DB接続のClose、VFS登録のCloseと全viewの終了を確認する。Rows・トランザクション等はDB接続より先に終了する。一部が失敗しても、消費処理の終了を確認したうえで実行できる残りの後処理を試みる。DBの終了を確認できなければ、依存するVFS登録を閉じず保全する。view数0だけでDB自体の終了を代用しない。

取消後も必要な後処理は元の取消要求で省略せず、最後まで待つ。VFS/viewの終了だけでは、準備物本体の解放が完了したことにはしない。VFSのErrInUse、Close失敗、view数の不一致、取得/終了の確認不能を成功へ丸めない。既存のコピーDB検査と同様、Rowsの走査エラー等を自動解放失敗と区別できなければ解放未確認として残す。

部分取得でも、未取得と確認できた資源・取得済み・終了済み・未確認を区別する。戻されたハンドルがnilであることだけで未取得や解放済みと推測せず、呼び出したAPIと取得段階の根拠を残す。

| 検査・解放の状態 | 準備物への扱い |
| --- | --- |
| 検査成功かつ全解放確認 | SQL使用中を解除して準備物の所有を次の検査へ戻す。切替許可や復元可能の判定にはしない |
| 検査失敗/取消かつ全解放確認 | 元の原因を残してSQL使用中を解除し、退避・切替前の既存の所有確認付きCleanupへ進める |
| 一つでも解放未確認 | 準備物を削除せず、元の保持と必要なSQL/VFS/viewの参照・原因・観測・残置候補を保全する。検証・切替を止め、終了・再起動を案内する |

検査失敗時に一律保全する案より、解放を確認できた場合に限って不要な準備物を片付ける案を採用する。未確認を保守的に判定するため、実際には解放済みでも保全となる場合がある。

SQL使用中・解放未確認では、PreparedRestoreのCleanupからネイティブ削除/Closeを始めない。未確認はその処理内では解除せず、自動再試行・別接続・再取得・再検査で削除を再開しない。既存ライブラリの終了済みオブジェクトに対する規定動作を変えず、アプリ独自のネイティブ再試行を追加しない。

通常操作の受付/再開、画面の終了案内への接続、異常終了後の保全物の扱いは別工程で具体化する。今回の保全方針だけを起動時の自動削除の許可にしない。元ZIP・現在/退避データの削除・変更や、退避/切替開始後の復旧物の片付けにも広げない。

## 実装と検証の分割

1. [#656](https://github.com/asam-masa/manga-update-manager/issues/656)：準備物の使用状態とCleanupの排他。SQL使用中/解放未確認でネイティブ処理を始めず、全解放確認時だけ借用を終了できる条件と競合を試験する。
2. [#657](https://github.com/asam-masa/manga-update-manager/issues/657)：有界な読取専用FS/viewとSQLセッション。部分取得、原因と取消の併発、SQL成功/Go原因あり、Rows/DB/VFS/viewの終了失敗、Cleanupとの接続を試験する。必要なら部品ごとに分割する。

通常・独立レビューを行い、合成の実保持DBと故障模型を使う。結果だけでなく、未取得・取得途中・終了済み・未確認の観測、後処理の順序、元のファイルを閉じないことと成功を返す時点を確認する。

#656で、PreparedRestoreへSQL使用予約とCleanupの排他を追加した。借用開始前に一意な使用予約を取得し、全解放確認時だけ終了できる。使用中または解放未確認ではネイティブCleanupを開始せず、解放未確認の原因を保持して再予約も拒否する。合成の実保持DBでCleanup拒否後も借用ReadAtが有効であることを確認し、故障模型で同時開始・終了・Cleanup、重複終了、古い終了通知、解放未確認を確認した。実VFS・SQL資源との接続と各解放観測は#657であり、この部品だけでSQL検査や製品復元が完了したとは扱わない。

DB構造/移行履歴・対応版・データ規則・画像参照の検査項目は#651で引き続き設計する。旧DB移行はこの読取専用VFSの書込経路にせず、方式と所有を別途決める。画像内容・寸法・管理記録再確立、App/UI、通常再開、退避/切替/復旧、実OS故障・電源断は対象外である。ADR-0022はPendingを維持する。
