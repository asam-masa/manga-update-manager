# タグ管理の確認と保存方針

Issue #312、親#296/#30。[ADR-0020](./adr/0020-confirm-tags-with-work-edits.md)の管理操作を具体化する。2026-10-28のgrillingで承認された設計であり、#317で管理用の内部取得、#313で改名・削除の保存処理、#320で[取得API](./tag-api.md#管理用の取得apiissue-320親314)、#314で[変更API](./tag-api.md#管理用の変更apiissue-314)を追加する。管理画面は未実装である。作品編集と削除確認の既存機能は[タグAPI](./tag-api.md)・[画面設計](./work-screen.md)を参照する。

## 操作と確定単位

一覧の「タグ管理」から専用画面を開き、未使用を含むタグと使用作品数を表示する。使用数は全作品を対象とし、漫画名検索や予定条件で絞った一覧の件数とは分ける。配置・フォーカスは管理画面の実装前にサンプルで確認する。

名前変更・削除はタグ1件ずつ確定する。改名はそのタグの「保存」、削除は確認画面の「削除する」で実行し、管理画面全体の一括保存を置かない。作品編集での複数新規タグの仮追加・一括確定とは別の操作である。

## 名前変更

固定タグIDと、編集開始時に確認した正確なタグ名を使う。現在の名前が変わっていた場合や対象がなくなった場合は、そのまま改名しない。使用作品の増減だけでは保存を拒否しない。改名は全関連作品から参照する名前を変える操作で、作品への関連自体は保持するためである。

名前の検証と同一性は既存の[タグ保存契約](./tag-storage.md)に従う。前後空白除去後の完全同名が別タグに存在する場合は拒否し、統合や付け替えはしない。候補検索の全半角・英字大小の一致を保存名の同一性へ流用しない。

## タグ削除の確認

確認画面はタグ名・使用作品数・対象作品のタイトル一覧を表示する。多数の場合は作品一覧部分をスクロールできる形にする。「作品は残り、このタグと作品との関連だけが外れる」ことを案内する。使用0件のタグも明示削除できるが、自動削除はしない。

確認後にタグ名または対象作品の組合せが変わっていれば削除せず、最新情報で再確認する。件数が同じでも対象が入れ替われば拒否する。対象作品の同一性を件数やタイトルだけで比較せず、作品IDの再利用も別作品として区別する。確認情報の型・取得と照合の境界は保存処理の着手時に具体化する。

確認した条件の照合と削除の間に別の変更を通さない保存境界が必要になる。画面での確認だけで安全な確定を保証せず、保存処理で同じ条件を照合する。失敗や競合後に自動で削除を再送しない。

## 保持するデータと失敗時の扱い

管理による改名・削除では、作品・画像・作品の全日時（updated_atを含む）・予定日・他タグを保持する。削除で外すのは指定タグの関連だけとする。作品編集で付け外しした際に作品のupdated_atを更新する既存契約とは、操作と更新範囲が異なる。

競合や取得失敗では改名入力等を保持し、最新情報を確認してから再操作する。未取得・不正値・部分取得を使用0件やタグなしの成功として扱わない。削除済みのタグを暗黙に再作成しない。

#314の追加grillingで、管理の改名・削除中も作品編集を受け付け、先行確定で確認条件が変われば後の保存を止めて入力を残し再確認する方針を承認された。同じタグへの管理操作の二重送信は拒否する。通常終了は既存の変更処理と同じく処理中を案内して止める。#320は取得だけであり、#314でこの管理用の変更受付・終了制御を接続する。画面からの再確認と入力保持は#315で接続する。

DB停止・結果不明・確定後警告・処理中の終了は既存契約に沿わせる。結果不明を未確定と断定せず、自動再送しない。確定後の再取得失敗だけで確定済みの操作を失敗へ戻さない。各段階で受付・資源解放・画面の操作可能状態を照合する。

## 管理用の内部取得（Issue #317、親#313）

`Store.ListTagUsage`は、未使用を含むタグと全作品の使用数をタグID昇順で返す。検索・予定・ページ条件は受け取らない。タグ未登録は空一覧。関連数と正のIDの参照先作品数を同じ集約SQLで照合し、参照先のない関連を使用0件として扱わない。

`Store.PreviewTagDelete`は、指定タグの正確名と作品ID・登録日時・タイトルを単一のLEFT JOINで取得する。内部型は`storage.TagDeletePreview`と`TagWork`。対象は作品ID昇順で、未使用は空の作品一覧、不存在は`ErrTagNotFound`とする。使用数はこの一覧の長さから得られ、別の使用数取得結果と組み合わせて確認情報を作らない。

作品IDと登録日時は既存画面の作品識別に合わせ、タイトルは表示用として分ける。ID再利用でも登録日時が異なれば区別できる。登録日時まで同じ値で直接再作成された行を識別する世代番号ではない。削除時の集合照合は後述の#313、取得APIの型は#320で接続する。変更APIは未接続で、この読取結果だけを削除権限にしない。

既存Storeの受付枠をRows・接続の解放まで保持する。タグ名、参照先、取得する作品ID・登録日時・タイトルを検証し、不正値は修復しない。集約一覧は作品のタイトル・日時等の全項目を検証する一覧ではない。走査・Rows解放・接続解放の失敗では全結果を破棄し、既存の取消・DB停止分類へ従う。読取メソッドはDBを書き換えない。

一時SQLiteで空一覧・未使用・不存在・共有タグの使用数と順序、作品ID再利用時の登録日時、再接続、読取前後の作品不変と`total_changes()`の不変を確認する。不正なタグ名・作品名・登録日時、参照先のない関連、取消・停止、実SQLiteのRows.Close後に故障を返す合成ドライバーで部分結果を返さないことを確認する。破損値の試験は一時DBだけでCHECK/外部キーを無効にする。WALの別接続が最初の行の読取後に改名と関連解除を確定しても、取得結果は元の名前・全対象で揃い、次の読取は変更後になることを確認する。物理障害・OSの接続解放故障・公開API・画面の実機検証ではない。

## 改名・削除の内部確定（Issue #313）

`Store.RenameTag`は確認した`manga.Tag`と新しい名前、`Store.DeleteTag`は`TagDeletePreview`を受け取る。旧名は正規化せず、新しい名前だけ既存の名前規則で前後空白を除く。ID・正確名が不正な確認、削除の未取得（Worksがnil）・重複ID・非正ID・ゼロ登録日時は`ErrTagConfirmation`で拒否する。明示的な空一覧は未使用タグの確認である。

両操作は同じStore受付枠とTxで現在のタグを取得し、不存在は`ErrTagNotFound`、旧名の変化は`ErrTagChanged`とする。改名は関連を照合せず、別タグの完全同名は`ErrTagDuplicateName`。同名への改名はUPDATE/Commitを行わず、読取TxをRollbackして返す。タグ名のID・名前以外の履歴を比較する改訂番号は追加しない。

削除はTx内で確認用取得を再実行し、作品IDと登録日時の集合を順序に依存せず比較する。登録日時は同じ瞬間かを比較し、表示タイトルは照合条件にしない。同件数の入替やID再利用による登録日時の違いは`ErrTagChanged`。照合後に同Txで指定ID/旧名のタグだけをDELETEし、外部キーのCASCADEでその関連だけ外す。SQLの変更件数は1件を要求し、0件成功を認めない。作品・全日時・予定・画像記録・他タグは更新しない。

TxのRollback、Commit、接続解放まで受付枠を保持する。確定前の失敗はRollbackし、Rollback失敗はDB停止。Commit失敗は`ErrTagChangeOutcomeUnknown`とDB停止で成功値を返さず、自動再送しない。Commit成功後の接続解放失敗は成功タグと`ErrTagChangeCommitted`を返す。確定後の追加SELECTは行わず、再取得失敗で成功を取り消さない。SQLITE_BUSY等を成功や確認競合へ読み替えず、その呼出しを再試行しない。

一時SQLiteで共有/未使用タグの改名・削除、別タグ同名の拒否、名前変化/不存在、付け外し後の改名、同件数入替・作品ID再利用・順序違い・表示タイトル差、作品/日時/予定/画像記録/他タグの保持と再接続を確認する。UPDATE/DELETE/CASCADEのABORT・IGNORE、取消・停止、実Commit後の故障応答、Rollback後の故障応答、別接続の読取ロックによるCommit拒否を区別する。WALで削除の照合中に別作品へ付与した場合は古い読取Txからの書込が失敗し、未確認対象まで削除しないことを確認する。確定後の接続解放警告は分類関数へ合成エラーを与えた検証で、OSの解放故障は再現していない。公開API・UI・実機操作、物理障害の検証は後続であり、ADR-0020はPendingを維持する。
