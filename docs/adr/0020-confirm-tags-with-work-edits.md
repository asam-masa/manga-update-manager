# ADR-0020: タグの作成と付与を作品編集の保存時に確定する

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-27
- Related: [#30](https://github.com/asam-masa/manga-update-manager/issues/30)、[#293](https://github.com/asam-masa/manga-update-manager/issues/293)

## Context

ADR-0005で複数タグ・既存候補の再利用・AND絞り込みを合意したが、作成と保存のタイミング、未使用タグ、管理の入口は未決定だった。2026-10-27のgrillingで、既存の作品編集から始め、作品とタグをまとめて保存する方針が承認された。

タグ名の変更と削除は複数作品へ影響する。一作品から外す操作とタグ自体を削除する操作を区別し、候補を使って以前の表記を再利用できることを優先する。今回の対象は操作と成功境界の設計であり、DB構造・API型・画面配置の実装は含めない。

## Decision Drivers

- 編集を取り消しただけで作りかけのタグを残さないこと
- 以前の表記を候補から探し、再利用できること
- 一作品の編集と全作品へ影響する管理を区別できること
- 検索・予定条件・既存の並び順とページ分割に統合できること
- 独立して検証可能な小さなIssue・PRへ分割できること

## Considered Options

| 問い | 候補 | 利点 | 負担・リスク |
| --- | --- | --- | --- |
| 付け外しの入口 | 既存編集から開始 | 保存・取消を作品編集へまとめられる | 登録後に編集する手間がある |
| 付け外しの入口 | 登録と編集の両方 | 登録時に分類できる | 初回に二つの入力経路の検証が必要 |
| 新規作成 | 作品保存時に作成・付与を一括確定 | 取消で作りかけが残らない | 作品更新との原子性と競合の設計が必要 |
| 新規作成 | 選んだ時点で確定 | 作品保存前から候補へ再利用できる | 取消しても未使用タグが残る |
| 未使用タグ | 明示削除まで保持 | 以前の名前を再利用できる | 不要タグの整理は手動 |
| 未使用タグ | 自動削除 | 候補を減らせる | 作品から外すだけで候補も失う |
| 候補検索 | 表記差を吸収した部分一致 | 以前の表記を正確に覚えていなくても探せる | 保存名の重複判定と別の比較が必要 |
| 候補検索 | 保存名の完全一致 | 比較が単純 | 以前の表記を思い出せないと見つけにくい |
| 管理 | 専用画面 | 全作品への影響と使用作品数を確認できる | 管理画面を開く操作が必要 |
| 管理 | 作品編集にも名前変更・削除を置く | 編集しながら管理できる | 一作品から外す操作との区別が難しい |
| 条件反映 | ボタンで候補を開き即時反映 | 上部の場所を抑え、件数を見ながら選べる | 候補を開く操作と選択ごとの再計算が必要 |
| 条件反映 | 候補を常時表示／適用時に反映 | 選択へすぐ移れる／選び終わるまで一覧が動かない | 上部の場所／適用操作が必要 |

## Decision

作品への付け外しと新規作成は、まず既存の編集画面に追加する。登録フォームには追加しない。「新しいタグを作成」の明示操作は編集内の仮追加とし、作品の保存成功時に作品更新・新規タグ作成・付与を一括確定する。取消では新規タグを保存せず、確定前の失敗で一部だけ残さない。保存結果不明を未保存と断定せず、既存編集の結果不明・停止契約との整合を実装時に確認する。

一度保存したタグは使用作品が0件でも保持し、候補に出す。名前は前後の空白を除いて1〜50 Unicodeコードポイントとし、改行・制御文字を拒否する。日本語・英字は通常1文字、一部の結合文字・絵文字は複数として数える。途中の空白は保持する。重複は保存名の完全一致で禁止し、全半角や英字大小を同一の保存名とは扱わない。

候補検索は漫画名検索と同じ全半角・英字大小の差を吸収した部分一致とする。候補検索用の比較と保存名の同一性を分け、似た名前を自動統合・置換しない。

一覧の「タグ管理」から専用画面を開き、使用作品数を示す。名前変更は全関連作品へ反映し、既存名への変更を拒否する。タグ削除は確認操作を伴い、作品を残してタグの関連だけ外すことを示す。作品編集では付け外し・新規作成だけを扱う。

一覧の「タグで絞り込み」から候補検索・複数選択を開く。選択タグは解除ボタン付きで表示し、「すべて解除」も用意する。選択・解除を即時反映し、候補欄は開いたまま複数選択できる。閉じても条件を保持する。全選択タグのANDと漫画名検索・予定条件を全件へ適用し、既存整列の後でページ分割する。明示的なタグ条件変更はページ1へ戻す。表示形式切替では保持し、再起動では解除する。

## Consequences

- 作品の確定とタグ作成の確定を一致させるため、保存の一括性と失敗・競合の検証が必要になる。
- 未使用タグは自動整理しない。候補の再利用を優先し、不要タグは利用者が管理から削除する。
- 使用作品数と管理操作の影響は一覧の現在の絞り込み件数から独立させる。
- 保存名が別でも同じ検索に一致することがある。候補が一致することは重複や統合の根拠にならない。
- #294の保存基盤、#295の編集、#296の管理、#297の絞り込みへ分ける。必要ならAPIと画面をさらに独立した単位へ分割する。
- DB/APIの型・移行・未指定更新の互換性、同名作成や古い編集との競合、削除確認・結果不明・選択中タグ削除後の整合は各着手前に具体化する。具体的な画面配置とフォーカスはUI実装前にサンプルで確認する。
- タグ階層・OR・統合・条件の再起動保持は対象外とし、将来の保存機能を先行実装しない。

## Validation

### 保存基盤の具体化（2026-10-27）

追加のgrillingで、タグ名とは別の固定IDと作品対応表を承認された。一回の編集で複数の新規タグを仮追加でき、保存時に前後空白除去後の完全同名があれば既存タグを自動再利用する。同名の重複選択は関連一つにまとめる。既存の選択済みタグの改名・削除を検出した場合は、作品とタグを保存せず入力を残して再確認する。候補検索だけで一致する別表記は自動再利用の対象にしない。

#299では名前のドメイン検証と`tags`・`work_tags`の追加構造を先行する。タグIDはINTEGER PRIMARY KEY AUTOINCREMENTとし、自動採番で削除済みIDを再利用しない。タグ名はBINARY完全一致UNIQUE、関連は作品ID・タグIDの複合主キーとする。構造と制約の範囲は[データ仕様](../データ仕様.md#タグ保存の構造issue-299)を参照する。

ドメインの名前検証、一時DBの旧8移行からの追加と再接続・再適用、作品/予定日/画像記録/アクセス/設定の保持、移行台帳への書込失敗時の構造と台帳のロールバックを確認した。外部キーを明示的に有効にしたテスト接続で、不正参照・重複拒否、タグ削除時の作品保持、作品削除時の未使用タグ保持、外部キー検査を確認した。本番接続の外部キー有効化とStore保存/取得、一括編集・自動再利用・改名削除検出は未接続であり、親#294に残す。

### 保存取得と編集の接続（Issue #301）

#301でStore専用ドライバーの各物理接続に外部キーを強制し、タグ一覧/作品タグの取得、任意のタグ編集、作品更新とタグ作成・同名再利用・関連変更の一括確定、既存選択の改名/削除検出、任意の内部削除スナップショットを接続する。[内部契約と検証範囲](../tag-storage.md)を参照する。タグを持たない従来入力はタグを保持する。公開Wails DTO・APIとUIは未変更のため、機能全体のValidation StatusはPendingを維持する。

### 公開APIと編集UIの分割（Issue #303、親#295）

#303で候補/作品タグの読取をApplication経由で公開し、編集と削除確認へ任意のID/名前集合を受け取る。タグIDは新規の公開型で正のint64の10進文字列として精度を保持し、既存作品ID/WorkDTOは変更しない。[API契約](../tag-api.md)に省略保持・明示解除・失敗分類と検証範囲を記録する。

追加grillingで、初期/再取得の失敗は入力保持・再読込成功まで保存無効、改名削除後も本文/付け外し/新規仮追加を残して変更されたタグだけ確認する方針を承認された。改名は新しい名前を確認して採用、削除済みは明示解除してから再保存する。画面は[未接続の合意](../work-screen.md#タグ編集の失敗時の合意issue-295未接続)として記録し、サンプル確認後に接続する。APIの自動試験を画面の検証済みとは扱わず、Validation StatusはPendingを維持する。

### 編集画面への接続（Issue #306）

2026-10-28のサンプル確認で、予定日とメモの間のタグ欄、通常幅のサイト名/予定日横並び、狭い幅の縦並び、下部の保存/取消を承認された。[画面契約](../work-screen.md#タグ編集の画面接続issue-306)に初回だけの選択採用、読込失敗時の入力保持、改名/削除部分だけの明示確認、検索と正確名の分離を具体化する。通常の編集保存結果と停止契約を維持し、DB/APIは変更しない。[検証記録](../verification/work-tag-editor.md)はDOMと実WebView2の範囲を区別する。管理・絞り込み等が残るためValidation StatusはPendingを維持する。

### 残る機能全体の検証条件

初回#293は承認済み設計だけの記録だった。#299の構造検証だけでタグ機能全体を完了とは扱わず、Validation StatusはPendingを維持する。以下の残る実装・検証と、先行検証の根拠の照合を子Issueで行う。

- 空名・前後/途中空白・50/51コードポイント・改行/制御文字・全半角/英字大小の検索と重複判定の区別
- 旧DB移行と再接続、既存作品・予定日・画像・アクセス・設定の保持
- 保存の一括確定、取消・確定前失敗での非作成、結果不明・停止・同名作成/名前変更/削除との競合
- 全作品への名前変更と関連のみ削除、未使用候補、使用作品数、削除後の選択条件と編集中入力の整合
- 検索・予定・AND条件、0件・ページ境界、遅い一覧応答、開始済み処理と通知の保持
- 合成保存先の実WebView2で候補選択・保存・取消・管理・キー操作・3形式と再起動時解除
