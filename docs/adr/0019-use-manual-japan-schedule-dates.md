# ADR-0019: 更新予定を日本の暦日として手入力する

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-25
- Related: [#31](https://github.com/asam-masa/manga-update-manager/issues/31)、[#29](https://github.com/asam-masa/manga-update-manager/issues/29)、[#262](https://github.com/asam-masa/manga-update-manager/issues/262)

## Context

基本の登録・タイトル・最終アクセス順は#258までで実装した。更新予定の日付を入力する方法、過去予定の保持、未来表示の適用範囲は未決定だった。利用者とのgrillingで、最初は一作品につき任意の日付を一つ手入力し、既存編集画面で設定・解除する方針を承認された。

最終アクセスや登録日時は発生した瞬間をUTCで保存する。一方、今回の予定は時刻を持たない日本の暦日であり、アクセス記録から読了やサイトの更新完了を推定するものではない。保存・編集・表示・整列をまたぐ日付の意味を固定する。具体的なDB列・API型・見直し処理は後続Issueで既存契約と照合する。

## Decision Drivers

- 手入力一日付から小さく検証できること
- 日付が過ぎた予定や未設定の作品を意図せず失わないこと
- UTCの時刻と日本の暦日を混同しないこと
- 一覧の密度と予定の確認を両立すること
- 既存の編集成功境界・ページ・検索・設定保存を維持すること

## Considered Options

| 問い | 候補 | 利点 | 欠点・リスク |
| --- | --- | --- | --- |
| 初回の入力 | 任意の一日付 | 不定期・延期も同じ操作で扱い、単純に検証できる | 次の予定を手動で入力する必要がある |
| 初回の入力 | 毎週などの繰り返しも実装 | 定期作品の入力負担を減らせる | 繰越・休載・月末・読了後の規則まで必要になる |
| 過去予定 | 明示変更まで保持 | 未確認の予定を残せる | 過去予定が残るため利用者による更新が必要 |
| 過去予定 | URL起動や日付経過で解除 | 過去の表示を自動で減らせる | 更新・読了を確認できないまま予定を失う |
| 保存の意味 | 日付だけを保持 | 入力した日本の日付をそのまま扱える | 既存の時刻とは別の検証が必要 |
| 保存の意味 | 便宜的な午前0時の時刻 | 既存時刻の処理を利用しやすい | 不要な時刻と時差変換を持ち込み、日付ずれを招く |
| 未来OFF | 予定順だけに適用 | 他の順序で作品を探すときに隠さない | 並び順によって表示対象が異なる |
| 未来OFF | すべての順序へ適用 | 絞り込み条件が共通になる | 意図せず登録・タイトル順でも作品を隠す |

## Decision

初回は一作品につき任意の一日付とする。Asia/Tokyoの暦日を扱い、時刻・繰り返し・複数予定は持たない。保存・APIは日付文字列`YYYY-MM-DD`と未設定を基準とし、UTCの午前0時へ変換しない。既存の発生時刻は引き続きUTCとする。実在しない日付や時刻付き入力は拒否し、勝手な繰り上げ・補正をしない。

予定日は日付経過・URL起動・最終アクセス保存で変更・解除しない。既存の作品編集に任意の日付欄を追加し、空欄を明示して保存した場合に解除する。登録フォームへの追加は初回対象外とする。テキストと予定日は一つの編集操作として扱い、値を指定しない既存呼び出しで予定日を意図せず消さない。

今日をAsia/Tokyoで判断し、今日→昨日、一昨日…→未来ONなら明日、明後日…→未設定の順に並べる。同じ日付と未設定同士は登録古い順とする。予定順は逆順を追加せず、3形式の選択と行の予定日見出しから同じ順序を使う。

未来ON/OFFは予定順だけに適用し、初回ONで保存復元する。他の並び順では未来の作品を隠さない。未設定は未来ON/OFFにかかわらず末尾に残す。未来ON/OFF切替は1ページ目へ戻し、検索を維持する。日付変更・スリープ復帰では今日と表示対象を自動で見直し、現在ページと検索を維持する。ページがなくなったときだけ最後へ補正する。

行一覧に「更新予定日」列を追加する。カードは最終アクセスの下へ予定日を1行追加し、未設定も同じ領域を確保する。画像サイズとタイトル2行を維持し、日付1行分だけ縦に広げる。小型は現在の密度を維持する。

採用理由は、不定期作品を含めて一日付で扱い、予定の消失や読了の誤認を避け、既存の操作と表示を段階的に拡張できるためである。現在有効な詳細は[一覧設計](../library-design.md#手入力の更新予定日の合意issue-312026-10-25)を正本とする。

## Consequences

### 保存設定の具体化（2026-10-26、Issue #282）

grillingで、並び順の許可値はアプリ側の完全一致検証へ集約し、DBはNOT NULLの文字列として保持する方針を承認された。予定順追加のたびにDBの列挙CHECKを変更する負担を避け、未知値も補正せず残せるためである。DBの許可値制約も維持する案は不正値を二重に防げるが、順序追加ごとに制約移行が必要になる。直接SQLでの未知値書き込みは防がなくなるため、読取時の検証と非修復を維持する。他列の制約は変更しない。

予定順は`scheduled_date`、未来表示は独立した0/1列とし、初期値ON・項目単位保存とする。#282はStoreと移行までを扱う。未来表示のAPI追加と、画面の整列・絞り込み・日付見直しは未接続であり、Validation StatusはPendingを維持する。保存の詳細は[データ仕様](../データ仕様.md#表示設定)を参照する。

- 次の予定日は利用者が更新する。繰り返し・休載・自動取得・アラートは別の判断とする。
- 既存作品は未設定へ移行し、作品・画像・最終アクセス・他設定を保持する必要がある。
- 編集の無変更・取消・保存失敗、結果不明・確定後警告、削除確認の対象変更検出へ新項目を整合させる必要がある。
- 予定条件によって表示対象が変わるため、条件適用→全件整列→ページ分割とし、開始済み処理・結果通知を表示から分離し続ける。
- 保存/APIは#263、編集UIは#264、表示・予定順・未来設定・日付見直しは#265へ分ける。大きい場合はさらに独立検証できる単位へ分ける。
- 日付の保存は将来の繰り返し規則を予約した実装ではない。必要になった時点で移行と操作規則を検討する。

## Validation

このPRは設計記録だけであり、予定日は未実装・未検証である。Validation StatusはPendingとする。次を後続Issueで確認する。

- 実在日・うるう日・無効日付、未設定・明示解除と入力省略の区別
- 旧DB移行・再接続・他項目保持、編集と削除確認、受付・停止・終了、失敗と部分成功
- 今日・過去・未来・未設定・同日順、未来OFFと他の順序、検索とページ境界
- UTCと日本の日付境界、月末・年末・うるう日、日付変更・スリープ復帰と遅い応答
- 設定保存復元・未知値非修復・失敗時表示、編集入力保持・フォーカス・通知保持
- 合成保存先の実WebView2で入力・解除・取消・日付表示・操作・再起動復元

具体的な値の型・範囲、APIの省略/解除表現と互換性、列幅・カード高さ、設定の追加方法、時計の注入・見直し間隔と復帰イベントは各実装の着手前に確認する。承認済みの表示規則から技術検証の成功を推定しない。

### 保存基盤の具体化（Issue #267）

親#263を分割し、暦日型とNULL許可列、登録/ID取得/一覧/内部編集/削除確認へ予定日を接続する。内部の空文字は未設定、編集のnilは保持、明示空文字は解除とする。0001〜9999年の実在日を検証し、時刻へ変換しない。旧6移行からの追加・他項目保持、無変更、失敗とCommit結果不明を一時DBで検証する。Wails公開・画面入力・表示・予定順は未接続のため、Validation StatusはPendingを維持する。

### API公開の検証（Issue #263）

WorkDTOは日付文字列/null、編集入力は省略・nullで保持、空文字で解除として公開する。JSONからの変換、再起動保持、不正入力と保存済みデータのエラー分類、予定日だけが変わる削除確認をAPIテストで確認する。画面は編集結果の予定日を古い一覧応答で戻さず、削除スナップショットへ引き継ぐことをDOMテストで確認する。日付入力の実画面確認（#264）と表示・予定順・設定・日付見直し（#265）は未実施のため、Validation StatusはPendingを維持する。

### 編集入力の接続（Issue #264）

標準の日付欄を既存編集のサイト名とメモの間に置き、日付範囲は保存/APIと同じ0001〜9999年とする。空文字による明示解除と、妥当性確認での不完全入力の拒否を区別する。初期値・取消・失敗・遅延応答の自動検証と、実WebView2の確認範囲は[予定日入力の検証](../verification/scheduled-date-input.md)へ記録する。常時表示・予定順・未来設定・日付見直し（#265）が残るため、Validation StatusはPendingを維持する。

### 行・カード表示の接続（Issue #278）

親#265から表示だけを分割する。行一覧へ予定日列、カードへ最終アクセス下の1行を追加し、小型は維持する。暦日を時刻変換せず整形し、未設定も領域を確保する。表示と保存成功反映の自動検証、寸法と実画面の確認範囲は[表示検証](../verification/scheduled-date-display.md)へ記録する。予定順・未来設定・日付見直しは未接続のため、Validation StatusはPendingを維持する。
