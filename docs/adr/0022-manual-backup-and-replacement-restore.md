# ADR-0022: 手動バックアップと退避付き一式復元から始める

- Status: Accepted
- Validation Status: Pending
- Date: 2026-11-03
- Related: #378、#379

## Context

作品・画像・予定日・タグを保存できる一方、アプリのバックアップ・復元機能は未実装である。利用者は手動方式を先行し、合意記録後に技術Spikeで整合性と復旧方法を確認する順序を承認した。

## Decision Drivers

- 関連する作品・タグ・画像をまとめて戻す
- 現在データを失わず、失敗時に戻せる設計を優先する
- 初回実装と操作を小さく保つ
- 合意と技術的な実現性の検証を区別する

## Considered Options

| 候補 | 利点 | 負担・リスク |
| --- | --- | --- |
| 現在データへ統合復元 | バックアップ後の追加を残しやすい | ID・重複・タグ・画像・更新競合の判断が増える |
| 退避後の一式復元 | 関連を保ちやすく復元対象が明確 | バックアップ後の変更は復元先へ引き継がれない。安全な切替と回復の検証が必要 |
| 操作を続けながら退避 | 利用者の待ち時間を減らせる | DBと画像の一貫した取得と操作寿命の管理が複雑になる |

## Decision

[初回設計](../backup-restore.md)の範囲で、通常操作を止めた手動バックアップ・退避付き一式復元を採用する。DBの保存内容と管理画像を1ファイルにまとめ、元画像を含めない。欠損/破損画像は警告して除外し、作品情報と正常画像の退避を続ける。復元後は終了・再起動する。初回は暗号化せず、個人データを含む保管上の注意を案内する。

統合復元、暗号化、自動定期処理、クラウド同期は初回対象外。1ファイルの具体形式、整合性・除外参照の表現、安全な切替と復旧の実装方式は採用していない。

2026-11-03、#380の調査後にZIP＋版付きJSON目録＋VACUUM INTOによるDBコピーを利用者が承認した。目録にはサイズ・ハッシュ・除外画像を記録する。上の具体形式未採用は初回合意時点の履歴であり、この追加合意で更新する。この時点では形式の詳細・安全な公開・復旧・具体的な入力制限は未確定だった。現在の形式契約は次の追記を参照する。

2026-11-03、#389で[形式v1・目録・上限・検証順](../backup-format.md)を具体化し、#390で目録検証、#391でZIPの限定読込を実装した。利用者は#391で検証だけを先行することを承認し、本文を破棄して全件成功時だけ目録を返す。準備領域への保存・意味的検証・製品への接続は後続である。上限は展開後合計2GiB・DB256MiB・管理画像1万枚で、形式パーサーの保護上限と対応条件は形式契約を正本とする。これらの検証だけで復元可能とは判断せず、ValidationはPendingを維持する。

2026-11-03、#399で[一時保存と完成名への切替の方針](../backup-restore.md#一時保存と完成ファイルへの切替3992026-11-03)を利用者と確認した。同じ保存先内の専用一時ファイルへ書込み・同期・読戻し検証を行い、既存ファイルを上書きせず完成名へ切り替える。通常失敗・取消時の削除は今回作成したと安全に確認できる一時ファイルだけに限定し、異常終了後の残置を初回は自動整理しない。初回はローカル保存先を先行し、必要な安全機能を確認できない先は中止する。取消は切替開始前までとし、保存済み完成ファイルを遅れた取消で削除しない。結果不明では保全原則に従い保持して案内する。具体方式の採用と保証は#400の限定Spike後に判断し、実装済みとは扱わない。

## Consequences

2026-11-03、#406で利用者は[初回の保存先条件](../backup-restore.md#初回の保存先条件4062026-11-03)を承認した。初回はローカルNTFSに限定し、内蔵・USBとも必要な能力を確認できなければ中止する。exFAT・FAT32・ネットワーク共有は対象外とする。保存先と途中のフォルダーの再解析ポイントを拒否し、通常フォルダーの選び直しを案内する。処理終了まで保存先と途中のフォルダーを保持する方式を採用し、保持できなければ開始しない。これは対応範囲と制御方針の採用であり、具体APIや製品実装の検証完了ではない。

NTFS以外やリンク経由の便利な保存先を初回から扱えなくなる一方、検証範囲を絞り、確認後の保存先変更を抑える。保持中は他アプリからのフォルダー移動・改名・削除が失敗する場合がある。NTFSという形式名だけで安全性を認めず、能力確認・保持失敗と結果不明の扱い、解放順を実装で検証する。既存の非上書き・所有確認後の一時片付け・不明時の保持を緩めず、全競合や電源断耐久性を保証しない。

2026-11-03の#387で利用者は、対応範囲の旧DBを準備用コピーで移行・検証し、新しすぎる形式や未対応構造は現データを変更せず拒否する方針を承認した。目録に作成時の除外を記録した画像以外の欠落/ハッシュ不一致は復元中止とし、部分救出は初回対象外。バックアップは日時付き初期名の新規ファイルへ保存し、既存ファイルを上書きしない。当時未確定だった形式仕様・入力上限は上記形式契約で具体化したが、対応DBの許可リスト・公開時競合の実装は残っている。元バックアップと通常データを変更して検証したものではない。

2026-11-03の#381調査後、利用者は[復元と退避保持の追加合意](../backup-restore.md#復元と退避保持の追加合意3852026-11-03)を承認した。段階切替と通常起動前の復旧確認を採用し、完了未確定の中断は安全に特定できる旧一式へ戻す。特定や復旧ができなければ双方と記録を保持して停止し、確定済みなら新一式を維持する。正常復元の退避は直近3回を残し成功確定後に古いものを整理するが、失敗/中断/状態不明と利用者バックアップは対象外。準備中だけ取消可能とし、退避/切替前の確認と処理段階・経過時間の案内を行う。上記の切替/保持方式未採用の記述は初回合意時点の履歴であり、この追加合意で更新する。

これにより保存先構成の変更を抑えられるが、一括原子的切替ではなく、永続化と安全な識別を伴う回復手順が必要となる。直近3回の整理が失敗した場合は退避が多く残り容量を使う。具体実装・故障検証は未完了であり、回復保証や通常データの削除許可へ拡張しない。

利用者が扱う保存物をまとめ、初回の復元規則を単純にできる。一方、処理中に通常操作を待ってもらい、復元後の再起動が必要となる。暗号化なしの保存物が第三者へ渡ると内容を秘匿できない。除外画像の警告と、完全な退避との区別が必要になる。

保存先内の一時作成は別ドライブへの完成物コピーを避けられる一方、異常終了や片付け失敗で未完成ファイルが保存先に残り、容量を使う。ローカル先行によりネットワーク切断時の検証を後続へ分けるが、ローカル保存先すべての対応や耐久性を保証する判断ではない。専用名だけに依存する自動削除を認めず、結果確認と保存済みファイルの保全を取消要求より優先する境界が必要になる。

現在データの退避と復旧は設計目標であり、未検証の回復保証ではない。保存と復元のSpike後に、失敗・取消・終了・退避保持を具体化してから実装する。

## Validation

方針は利用者承認済み。以下の限定試験と純粋な入力検証は完了しているが、製品のバックアップ生成・復元・切替・故障注入は未完了のためPending。

#406は保存先条件の合意記録のみである。ローカルNTFSの判定と必要能力の確認、保存先・祖先の再解析ポイント拒否と保持、失敗時の解放・保全は製品コードへ未接続。後続で合成データの異常系・競合試験と独立レビューを行うまで、設計承認を検証成功へ読み替えない。

| 範囲 | 確認済み | 限界と根拠 |
| --- | --- | --- |
| #380 保存Spike | 合成DBのVACUUM INTO、最小ZIPの読戻し・最終化失敗 | [記録](../verification/backup-snapshot-spike.md)。製品のDB/画像を一体で取得する処理には未接続 |
| #381 復元Spike | 一時領域の文字列ファイルによる段階切替・旧一式への戻し・復旧先衝突 | [記録](../verification/restore-switch-spike.md)。実DB/画像ハンドル・強制終了・電源断等は未実測 |
| #390 目録検証 | 厳密なJSON、型・日時・履歴・対応・上限 | [記録](../verification/backup-manifest.md)。目録の妥当性だけで実DBの互換性を認めない |
| #391 ZIP検証 | 上限付きの構造検証、本文の実量・SHA-256・CRC照合 | [記録](../verification/backup-archive.md)。本文は破棄し、ファイル出力・意味的検証・復元は行わない |
| #397 ZIP書込み | Writerへのストリーム書込み、内容照合、最終化・失敗・協調キャンセル、限定読込との往復 | [記録](../verification/backup-writer.md)。実ファイルの保存/公開や通常データ取得は未接続 |
| #400 公開Spike | ローカルNTFS・専用一時領域の非上書きハンドル名前変更、ID維持、所有片付け、合成ZIPの再読込。取消/不明は模型で確認 | [記録](../verification/backup-publication-spike.md)。相対名と保存先ハンドルの経路は引数エラー。USB/NAS・電源断・製品境界は未検証 |

残る製品検証条件は次のとおり。通常操作の停止と整合した取得、安全な非上書き公開、準備保存、意味的検証と旧版移行、管理画像の識別再確立、切替・起動前復旧と保持整理、API/UI・実機検証を後続で扱う。

#399は一時配置・片付け・対応先・取消境界の合意記録であり、#400の限定Spikeを上表に追記した。#400は上限30分に対し約8分19秒で公開仕様と専用一時領域を調査した。通常保存先、実USB/NAS、OS設定は変更していない。安全な保存先境界と結果型の具体契約、未測定の障害条件は残るため、未検証の方式を製品へ接続せず、Pendingを維持する。

- 同じ時点のDBと画像を扱い、除外画像を識別できる
- 合成データで一式復元し、作品・タグ・予定日・アクセス・設定・正常画像を保持できる
- 現在データの退避、途中失敗・中断・容量不足と再起動時の復旧境界を検証できる
- 完了・警告・失敗・結果不明を区別し、旧状態へ通常操作を再開しない
- 入力形式・サイズ・パス・版互換の安全性、退避と通常データの境界を確認できる

具体的な試験条件は#380/#381の限定結果と後続実装から具体化し、この記録だけでVerifiedへ変更しない。
