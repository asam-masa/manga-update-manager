# ADR-0022: 手動バックアップと退避付き一式復元から始める

- Status: Accepted
- Validation Status: Pending
- Date: 2026-11-03
- Related: #378、#379

## Context

作品・画像・予定日・タグを保存できる一方、アプリのバックアップ・復元機能は未実装である。利用者は手動方式を先行し、合意記録後に技術Spikeで整合性と復旧方法を確認する順序を承認した。

## Decision Drivers

- 関連する作品・タグ・画像をまとめて戻す
- 現在データを失わず、失敗時に戻せる設計を優先する
- 初回実装と操作を小さく保つ
- 合意と技術的な実現性の検証を区別する

## Considered Options

| 候補 | 利点 | 負担・リスク |
| --- | --- | --- |
| 現在データへ統合復元 | バックアップ後の追加を残しやすい | ID・重複・タグ・画像・更新競合の判断が増える |
| 退避後の一式復元 | 関連を保ちやすく復元対象が明確 | バックアップ後の変更は復元先へ引き継がれない。安全な切替と回復の検証が必要 |
| 操作を続けながら退避 | 利用者の待ち時間を減らせる | DBと画像の一貫した取得と操作寿命の管理が複雑になる |

## Decision

[初回設計](../backup-restore.md)の範囲で、通常操作を止めた手動バックアップ・退避付き一式復元を採用する。DBの保存内容と管理画像を1ファイルにまとめ、元画像を含めない。欠損/破損画像は警告して除外し、作品情報と正常画像の退避を続ける。復元後は終了・再起動する。初回は暗号化せず、個人データを含む保管上の注意を案内する。

統合復元、暗号化、自動定期処理、クラウド同期は初回対象外。1ファイルの具体形式、整合性・除外参照の表現、安全な切替と復旧の実装方式は採用していない。

## Consequences

利用者が扱う保存物をまとめ、初回の復元規則を単純にできる。一方、処理中に通常操作を待ってもらい、復元後の再起動が必要となる。暗号化なしの保存物が第三者へ渡ると内容を秘匿できない。除外画像の警告と、完全な退避との区別が必要になる。

現在データの退避と復旧は設計目標であり、未検証の回復保証ではない。保存と復元のSpike後に、失敗・取消・終了・退避保持を具体化してから実装する。

## Validation

方針は利用者承認済み。設計記録のみで、バックアップ生成・復元・切替・故障注入は未実施のためPending。

- 同じ時点のDBと画像を扱い、除外画像を識別できる
- 合成データで一式復元し、作品・タグ・予定日・アクセス・設定・正常画像を保持できる
- 現在データの退避、途中失敗・中断・容量不足と再起動時の復旧境界を検証できる
- 完了・警告・失敗・結果不明を区別し、旧状態へ通常操作を再開しない
- 入力形式・サイズ・パス・版互換の安全性、退避と通常データの境界を確認できる

具体的な試験条件は#380/#381と後続実装で確定し、この記録だけでVerifiedへ変更しない。
