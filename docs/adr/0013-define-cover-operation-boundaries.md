# ADR-0013: 画像操作と不要ファイル削除の成功境界を分ける

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-11
- Related: [#42](https://github.com/asam-masa/manga-update-manager/issues/42)、[#43](https://github.com/asam-masa/manga-update-manager/issues/43)、[#56](https://github.com/asam-masa/manga-update-manager/issues/56)

## Context

画像生成はIssue #41で実装した。次の保存・変更・解除では、ファイルとSQLiteを一つの原子的操作にできない。旧ファイル削除まで操作の成功条件へ含めると、DB更新後の失敗で何を戻すか曖昧になる。起動時の整理は、別プロセスが準備中の未参照画像を消す危険もある。

ユーザーは以下の成功境界、再試行、競合、キャンセル、解除、欠損時の振る舞いと、配信の事前検証を承認した。このADRはADR-0008で未決定だった後処理を具体化する。実装済みとは扱わない。

## Decision Drivers

- 元画像と現在の参照を失敗から守る
- 利用者が操作結果と後処理の警告を区別できる
- 途中終了で残る不要画像を安全に整理する
- 小規模なアプリに複数プロセス間の複雑な操作調停を持ち込まない

## Considered Options

### 旧ファイル削除まで操作成功に含める

容量を整理できたことまで成功で示せるが、DB確定後の削除失敗で参照を戻す処理が増える。ファイルとDBの完全なロールバックは保証できない。

### DB確定で成功とし、削除失敗は警告する

表示上の状態と成功境界が明確になる。一方、削除失敗・途中終了で不要ファイルが残り、再試行が必要になる。

### 同じ保存先の複数起動を許可する

複数の画面を使えるが、画像操作と起動時整理のプロセス間排他が必要になる。同じ保存先を一つの起動に限定すると、使い方は制限されるが調停を単純化できる。

## Decision

2026-10-17、Issue #107で画像管理の保護範囲を具体化した。操作ミス・不正パス・通常の同時操作から利用者データを守ることを目標とし、同じWindowsユーザー権限の悪意ある別プロセスによるドライブ割当・フォルダー特殊属性の意図的変更への完全防御は保証しない。リンク拒否、処理中のフォルダー保持、上書き禁止、削除前の管理記録・未参照・実ファイル照合は緩和しない。確認失敗時に操作を進めない条件と、DB確定後の後処理失敗を警告とする成功境界も維持する。

- 新画像の生成・保存、またはDB更新に失敗した場合は操作失敗とし、旧画像と旧参照を維持する。
- 新画像を保存してからDBの参照を確定する。解除ではDBの参照を外す。DB確定を操作の成功とし、その後の旧管理画像削除失敗は警告として区別する。成功した変更・解除を戻さない。
- 不要ファイルは次回起動時に整理を再試行する。対象は管理領域内のアプリ生成画像で、DBから未参照と安全に確認できたものだけとする。確認できない場合は削除しない。再試行失敗でも起動を継続して警告する。元画像は変更・削除しない。
- 同じ保存先での二重起動を禁止し、二つ目には既に起動していることを案内する。別保存先の確認用アプリは区別する。保存先の排他を確保する前に整理を開始しない。
- 同じ作品の画像操作が進行中の場合、追加の設定・変更・解除は受け付けず、完了後の再操作を案内する。別作品は受け付け、画像生成は既存方式で一件ずつ処理する。
- ファイル選択のキャンセルは変更なしとし、画像を維持して成功・エラー通知を出さない。
- 解除は確認ダイアログなしとし、初回は取り消し機能を設けない。元画像からの再設定は可能である。
- 保存済み画像の欠損・破損時は画面を仮表示とし、DB参照を自動解除しない。利用者の明示的な変更・解除で扱う。

2026-10-11、配信Spike完了後のgrillingで次を追加合意した。

- 配信はWails Middlewareで専用経路を扱い、作品IDからDBの現在の管理画像を解決する。画面から任意パスを受け取らない。初回はno-storeとし、変更後は画面から再取得する。
- 変更・解除の成功結果は更新後の作品情報と警告を返す。DB確定後の削除失敗を通常の操作エラーとして返さない。
- 起動時の整理失敗はまとめて、画面上部に閉じられる警告を出す。作品一覧は利用できる状態を保つ。具体的な画面実装はIssue #43で扱う。
- 画像選択APIは作品IDだけを受け取り、Go側がファイル選択から取り込みまで行う。解除は別APIとする。キャンセルは変更なしを返し通知しない。
- ファイル選択画面はアプリ全体で一つだけにする。開いている間の別の選択要求も拒否し、選択中と案内する。選択完了後の取り込みは同じ作品の追加操作を拒否し、別作品の操作は受け付ける。
- 保存先の排他を確保できない場合は、DB・画像に触れず、起動中または安全な起動失敗を案内して終了する。先行するIssue #58の実装方式は[ADR-0014](./0014-lock-storage-before-startup.md)へ記録する。

配信・画像API・選択・警告UIは合意済みだが、本番未実装である。具体的な識別子・結果型・安全な保存削除の実装は後続Issueで記録・検証する。試作コードを本番へそのままコピーしない。

2026-10-13、保存した新画像のファイル識別情報を取得できない場合は画像設定を失敗とし、現在の画像と参照を維持する方針を承認した。識別情報を持たない画像を作品へ結び付けて設定成功とは扱わない。安全性を確認できない残存ファイルは保持し、警告する。本番実装と検証は引き続きPendingである。

2026-10-17、Issue #113でClose失敗時と通常終了操作の方針を追加承認した。

- 画像ファイル・保持中フォルダーのClose失敗で解放を確認できない場合、その起動中は画像機能を停止して再起動を案内する。新たな保存・解除・整理・配信は進めず、既存DB機能は継続する。DB確定前は操作失敗、確定後は成功と警告に分け、確定済み変更を戻さない。
- 画像処理中の「×」などによる通常終了は処理中の案内を表示して拒否する。終了要求を理由にキャンセルせず、自動終了を予約しない。処理と後始末の完了後に利用者が再度閉じる。時間切れによる強制終了や処理中のDB終了は行わない。

完了を待って自動終了する案も検討したが、利用者が処理結果を確認してから再度閉じる方式を選んだ。どちらもOS処理が必ず終わる保証にはならない。長時間停止時の案内、処理中の具体的な範囲、画像機能停止時の進行中操作の収束と排他方式は未決定であり、接続前に具体化する。OSによる強制終了を防止する保証ではない。

2026-10-17、Issue #115で、#113時点の未決定事項のうち次の利用者向け方針を追加承認した。

- 選択画面、選択後の待機・生成・保存・DB更新・後始末、解除、起動時整理を通常終了拒否の対象とする。表示用読み取りは別扱いとし、終了時に新規受付を止め、開始済み処理と解放を待つ。変更・整理中の終了要求を自動終了予約へ変えない。
- 画像機能停止時は、進行中の別処理も安全な区切りで止めて解放を試みる。待機・生成から新たな保存・DB更新へ進めず、実行中OS処理は強制中断しない。DB更新の確定結果を確認し、確定済み変更は戻さない。停止検知後に新たな削除を始めず、残存ファイルを保持する。
- 長時間処理では案内を表示するが、時間だけで故障や画像機能停止と判定したり強制中断したりしない。案内までの時間は実装時に調整する。

進行中処理を無条件に完了まで続ける案より、解放が不確かな状態で変更を重ねないことを優先した。通常終了は処理をキャンセルしない一方、安全上の停止では段階的に収束させる。具体的な排他、進行中配信・選択画面の扱い、DB確定結果が確認できない場合の結果契約は接続前に定める。[設計正本](../cover-persistence.md#close失敗と通常終了)を参照する。

2026-10-18、Issue #125でDB更新の結果不明時の扱いを追加承認した。確定・未確定を判別できない場合は成功・失敗を断定せず、新旧画像を削除しない。変更の自動再試行・旧参照への書き戻しをせず、その起動中の画像機能を停止して再起動後の状態確認を案内する。既存DB機能は利用可能な範囲で継続し、DB故障時まで継続可能とは保証しない。結果不明の場合は、前述の「旧参照を維持する失敗」と区別する。停止中の既存処理は安全な区切りで収束させる。

Commitエラーを一律に未確定と扱う案や自動再試行する案では、確定済み変更を上書きする恐れがあるため、判別不能時には保全を優先する。具体的な判別・接続回復方式は未採用である。[結果不明の契約](../cover-persistence.md#db更新の結果不明)を正本とする。

2026-10-18、Issue #127で初回の結果分類を具体化した。Commitエラーは結果不明とし、再読取などによる自動回復を行わない。DB変更前と確認できる入力拒否まで不明にしない。判別範囲を広げて利用継続性を高める案は、接続状態とRollbackの追加検証を必要とするため初回には含めない。Storageの印がないことだけでRollback成功や接続健全性を判断しない。

2026-10-18、Issue #131で、DB接続の安全性を確認できない場合は画像機能に加えて新たなDB操作も停止する方針を承認した。表示済み一覧を残し、再起動後の状態確認を案内する。画像ファイル・フォルダーだけの解放失敗でDBに問題がない場合は、既存DB機能を継続する。正常な入力拒否をDB停止へ広げず、Commitの確定結果と接続安全性を別に扱う。

不確かな接続で利用を継続する案より、登録・更新などを重ねないことを優先した。その代わり、一時的に新しい一覧取得や設定保存も利用できなくなる。接続安全性の判別・隔離、進行中処理の扱い、受付との排他、終了時の解放とUIは未設計・未検証である。処理中のDB終了・強制中断を許可せず、再起動の成功や表示済み一覧の最新性を保証しない。[設計正本](../cover-persistence.md#db接続の安全性を確認できない場合)を参照する。

2026-10-18、Issue #133でDB停止時の収束方針を承認した。DB実行待ちの処理は開始せず停止エラーを返し、すでに実行中の処理は強制中断せず結果と後始末を確認する。その後の別DB操作は開始しない。受け付けた利用者操作全体を無条件に完了まで進める案より、不確かな接続へ後続操作を重ねないことを優先する。

すでに行ったブラウザー起動などは取り消せないため、続くDB保存を開始できなかった場合は部分成功として区別して案内する。自動再試行・確定済み変更の書戻し・処理中のDB終了は行わない。具体的な境界・排他・結果確認・後始末・接続隔離とUIの検証は残る。[設計正本](../cover-persistence.md#db停止時の待機中実行中処理)を参照する。

2026-10-18、Issue #139で、Store内の共通実行制御と保守的な停止条件の本番導入を承認した。接続取得後の実行権確定と停止を同じmutexで順序付け、結果消費・Tx後始末・返却まで実行権を保持する。初回は画像参照Commit失敗後の接続再利用の安全性を確認できないためDBも停止する。Rollback/返却確認不能も停止し、通常入力拒否・重複だけでは止めない。詳細なエラー別回復より安全側を優先し、一時的な競合でも再起動を要し得る。確定済み結果と後始末失敗は区別する。[本番Store契約](../verification/store-db-admission.md)を正本とし、物理隔離・本番画像API・専用UIの完成とは扱わない。

2026-10-18、Issue #141で、初回は既存Store停止を使い、物理接続隔離を画像API接続の前提にしない方針を承認した。新規SQL拒否・自動再接続なし・開始済み処理の後始末・再起動後の状態確認を条件とする。物理切断や復旧を保証せず、追加の隔離は必要性を別途評価する。DB停止案内とURL起動後の部分成功の保持を先行し、[APIと画面の契約](../verification/store-db-admission.md#db停止のapi案内issue-141)へ接続する。

2026-10-18、Issue #145で管理記録確定・参照変更・削除の区間を、アプリ内の共通排他で1件ずつ進める方式を承認した。画像ごとの複数ロックより単純さと検証可能性を優先する。別作品の選択・生成・reserved状態での新規保存は区間外とし、ready確定前に排他を取得する。未参照確認から削除までに別操作が参照を追加しないことが目的であり、画像パスを受け取る作品登録も同じ排他へ参加させる。

排他は最後のフォルダー解放の結果を通知してから返却する。画像停止だけでは通常の作品登録を停止せず、画像段階とStoreの実行許可は別に確認する。後続の解除・削除・整理・配信も必要な区間を同じ排他へ接続する。待機・長時間I/Oによる遅延は生じ得るが、時間切れで強制中断する方式にはしない。

2026-10-18、起動時整理はウィンドウ表示後に実行し、整理中は画像操作を拒否する方針を承認した。表示前の無表示待ちを避け、処理中の通常終了は案内して拒否し、完了後の再操作を求める。整理失敗は警告として保持し、既存のDB機能を利用可能にする方針を維持する。起動・終了との結合と実WebView2での確認は後続で行う。

## Consequences

2026-10-19、配信前に画像全体を上限付きでメモリへ読み込み、安全性を確認してファイル・フォルダーと参照排他を解放してから応答する方式を承認した。通信完了まで資源を保持する案より、変更・削除の待ち時間を短くする。その代わり、一応答では読み取り時点の旧画像を返す場合があり、変更完了後には画面から再取得する。初回の読み取りは生成PNGの600px上限に対して2 MiBまでとする。Issue #159はWindows読み取り部品だけを実装し、現在参照解決・PNG検査・受付と排他・HTTP・画面への接続は後続で検証する。これらの未接続を理由にPendingを維持する。

上記の境界により、外部の悪意ある別プロセスとの完全な攻防を本番化の達成条件には含めない。一方、通常の共有違反・途中終了・保存失敗・アプリ内の競合を無視する理由にはしない。#105の通常読取・読み書き共有・削除共有なしは、ドライブルートからの確認候補として本番化の条件を整理する段階であり、まだ採用済みではない。[保護範囲と本番化の条件](../cover-persistence.md#保護範囲と本番化の条件)に、採用前の検証と未決定事項を記録する。既存の起動排他・DB機能は変更しない。

2026-10-17、初回の画像管理はローカル保存先だけを対象とし、ネットワークまたは保存先までの途中にリンクがある場合は画像機能を停止して案内する方針を承認した。既存のDB機能・保存場所・リンクは変更しない。必要なフォルダーは画像処理中だけ保持し、保存・DB確定・後処理後に解放する。ドライブルートから一階層ずつ確認する方式は検証候補として承認し、Issue #105で調査する。具体的な共有設定・取得方式の本番採用や検証完了を意味しない。

2026-10-12、作品の画像参照とは別に、アプリ生成画像の管理記録をSQLiteへ持つ方式を承認した。管理記録あり、全作品から未参照、ファイル安全確認済みを満たすものだけを削除候補にする。記録のないファイルは名前が似ていても削除しない。記録だけで安全性を保証せず、リンク拒否や実ファイルとの照合を併用する。詳細は[画像保存契約](../cover-persistence.md)に記録する。本番未実装でPendingを維持する。

2026-10-12、画像の設定・変更・解除を作品情報の変更として扱い、DB確定時に`updatedAt`も更新する方針を承認した。キャンセル・操作失敗・未設定状態での解除では更新しない。漫画の更新予定と最終アクセス日時は変更しない。

2026-10-12、Issue #42再開時に、既存画像を上書きせず毎回別名のPNGを保存する方式を追加承認した。新画像の保存完了、DB参照の切り替え、旧管理画像の削除の順に処理する。一時的に新旧両方の容量を必要とする。途中終了で残る未参照ファイルは、安全な起動時整理で扱う。この追記は実装・検証済みを意味しない。具体化と残る問いは[画像保存・配信契約](../cover-persistence.md)へ記録する。

DBの操作結果と削除の警告を区別する結果契約が必要になる。DB更新失敗や途中終了で残る新画像も整理対象の候補になるが、現在の参照と準備中のファイルを削除しない検証が必要である。

本番の二重起動制御はIssue #58で先行し、ファイル保存・削除、DB変更はIssue #42、設定UIはIssue #43で実装する。Issue #43は解除確認・欠損時の契約と警告の配置を引き継ぐ。ボタンや通知の具体的なレイアウトはそこで決める。

## Validation

Issue #107は保護範囲と採用条件の文書化であり、実装や実行検証を追加しない。通常読取候補の本番用境界、未作成領域、失敗時の解放、保存・削除・配信の保持区間とアプリ内排他の検証が残るためPendingを維持する。

本番の検証はPendingである。一時ファイル・SQLiteで生成失敗、容量不足、DB失敗、削除失敗、途中終了、参照確認失敗、競合を確認する。同じ保存先の二重起動と別保存先の起動を検証し、排他の解放も確認する。実WebView2でキャンセル・解除・欠損・破損・警告を確認する。
