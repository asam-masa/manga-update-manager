# ADR-0013: 画像操作と不要ファイル削除の成功境界を分ける

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-11
- Related: [#42](https://github.com/asam-masa/manga-update-manager/issues/42)、[#43](https://github.com/asam-masa/manga-update-manager/issues/43)、[#56](https://github.com/asam-masa/manga-update-manager/issues/56)

## Context

画像生成はIssue #41で実装した。次の保存・変更・解除では、ファイルとSQLiteを一つの原子的操作にできない。旧ファイル削除まで操作の成功条件へ含めると、DB更新後の失敗で何を戻すか曖昧になる。起動時の整理は、別プロセスが準備中の未参照画像を消す危険もある。

ユーザーは以下の成功境界、再試行、競合、キャンセル、解除、欠損時の振る舞いと、配信の事前検証を承認した。このADRはADR-0008で未決定だった後処理を具体化する。実装済みとは扱わない。

## Decision Drivers

- 元画像と現在の参照を失敗から守る
- 利用者が操作結果と後処理の警告を区別できる
- 途中終了で残る不要画像を安全に整理する
- 小規模なアプリに複数プロセス間の複雑な操作調停を持ち込まない

## Considered Options

### 旧ファイル削除まで操作成功に含める

容量を整理できたことまで成功で示せるが、DB確定後の削除失敗で参照を戻す処理が増える。ファイルとDBの完全なロールバックは保証できない。

### DB確定で成功とし、削除失敗は警告する

表示上の状態と成功境界が明確になる。一方、削除失敗・途中終了で不要ファイルが残り、再試行が必要になる。

### 同じ保存先の複数起動を許可する

複数の画面を使えるが、画像操作と起動時整理のプロセス間排他が必要になる。同じ保存先を一つの起動に限定すると、使い方は制限されるが調停を単純化できる。

## Decision

- 新画像の生成・保存、またはDB更新に失敗した場合は操作失敗とし、旧画像と旧参照を維持する。
- 新画像を保存してからDBの参照を確定する。解除ではDBの参照を外す。DB確定を操作の成功とし、その後の旧管理画像削除失敗は警告として区別する。成功した変更・解除を戻さない。
- 不要ファイルは次回起動時に整理を再試行する。対象は管理領域内のアプリ生成画像で、DBから未参照と安全に確認できたものだけとする。確認できない場合は削除しない。再試行失敗でも起動を継続して警告する。元画像は変更・削除しない。
- 同じ保存先での二重起動を禁止し、二つ目には既に起動していることを案内する。別保存先の確認用アプリは区別する。保存先の排他を確保する前に整理を開始しない。
- 同じ作品の画像操作が進行中の場合、追加の設定・変更・解除は受け付けず、完了後の再操作を案内する。別作品は受け付け、画像生成は既存方式で一件ずつ処理する。
- ファイル選択のキャンセルは変更なしとし、画像を維持して成功・エラー通知を出さない。
- 解除は確認ダイアログなしとし、初回は取り消し機能を設けない。元画像からの再設定は可能である。
- 保存済み画像の欠損・破損時は画面を仮表示とし、DB参照を自動解除しない。利用者の明示的な変更・解除で扱う。

2026-10-11、配信Spike完了後のgrillingで次を追加合意した。

- 配信はWails Middlewareで専用経路を扱い、作品IDからDBの現在の管理画像を解決する。画面から任意パスを受け取らない。初回はno-storeとし、変更後は画面から再取得する。
- 変更・解除の成功結果は更新後の作品情報と警告を返す。DB確定後の削除失敗を通常の操作エラーとして返さない。
- 起動時の整理失敗はまとめて、画面上部に閉じられる警告を出す。作品一覧は利用できる状態を保つ。具体的な画面実装はIssue #43で扱う。
- 画像選択APIは作品IDだけを受け取り、Go側がファイル選択から取り込みまで行う。解除は別APIとする。キャンセルは変更なしを返し通知しない。
- ファイル選択画面はアプリ全体で一つだけにする。開いている間の別の選択要求も拒否し、選択中と案内する。選択完了後の取り込みは同じ作品の追加操作を拒否し、別作品の操作は受け付ける。
- 保存先の排他を確保できない場合は、DB・画像に触れず、起動中または安全な起動失敗を案内して終了する。先行するIssue #58の実装方式は[ADR-0014](./0014-lock-storage-before-startup.md)へ記録する。

配信・画像API・選択・警告UIは合意済みだが、本番未実装である。具体的な識別子・結果型・安全な保存削除の実装は後続Issueで記録・検証する。試作コードを本番へそのままコピーしない。

2026-10-13、保存した新画像のファイル識別情報を取得できない場合は画像設定を失敗とし、現在の画像と参照を維持する方針を承認した。識別情報を持たない画像を作品へ結び付けて設定成功とは扱わない。安全性を確認できない残存ファイルは保持し、警告する。本番実装と検証は引き続きPendingである。

## Consequences

2026-10-12、作品の画像参照とは別に、アプリ生成画像の管理記録をSQLiteへ持つ方式を承認した。管理記録あり、全作品から未参照、ファイル安全確認済みを満たすものだけを削除候補にする。記録のないファイルは名前が似ていても削除しない。記録だけで安全性を保証せず、リンク拒否や実ファイルとの照合を併用する。詳細は[画像保存契約](../cover-persistence.md)に記録する。本番未実装でPendingを維持する。

2026-10-12、画像の設定・変更・解除を作品情報の変更として扱い、DB確定時に`updatedAt`も更新する方針を承認した。キャンセル・操作失敗・未設定状態での解除では更新しない。漫画の更新予定と最終アクセス日時は変更しない。

2026-10-12、Issue #42再開時に、既存画像を上書きせず毎回別名のPNGを保存する方式を追加承認した。新画像の保存完了、DB参照の切り替え、旧管理画像の削除の順に処理する。一時的に新旧両方の容量を必要とする。途中終了で残る未参照ファイルは、安全な起動時整理で扱う。この追記は実装・検証済みを意味しない。具体化と残る問いは[画像保存・配信契約](../cover-persistence.md)へ記録する。

DBの操作結果と削除の警告を区別する結果契約が必要になる。DB更新失敗や途中終了で残る新画像も整理対象の候補になるが、現在の参照と準備中のファイルを削除しない検証が必要である。

本番の二重起動制御はIssue #58で先行し、ファイル保存・削除、DB変更はIssue #42、設定UIはIssue #43で実装する。Issue #43は解除確認・欠損時の契約と警告の配置を引き継ぐ。ボタンや通知の具体的なレイアウトはそこで決める。

## Validation

本番の検証はPendingである。一時ファイル・SQLiteで生成失敗、容量不足、DB失敗、削除失敗、途中終了、参照確認失敗、競合を確認する。同じ保存先の二重起動と別保存先の起動を検証し、排他の解放も確認する。実WebView2でキャンセル・解除・欠損・破損・警告を確認する。

Issue #56の配信試作は、合成画像だけを使い、開発モードとexeで配信経路・表示・差し替えを確認する。本ADRの保存・削除・DB・二重起動・画面操作の検証の代替にはしない。

2026-10-12、Issue #58で保存先単位の起動排他を実装・検証した。確認範囲は[ADR-0014](./0014-lock-storage-before-startup.md)を参照する。画像保存・削除・復旧・画面操作の検証が残るため、本ADR全体のPendingは維持する。

2026-10-13、Issue #95で生成画像管理テーブルを本番マイグレーションへ追加した。一時SQLiteで、既存作品・最終アクセス・表示設定の保持、既存パスの自動登録なし、状態・128bit識別情報の制約、再接続時の記録保持、適用記録失敗時のテーブル追加のロールバックを検証する。管理記録の操作API、ファイル保存・照合・削除、参照変更、整理・配信はまだ本番へ接続していない。画像管理全体のPendingは維持する。列の正本は[データ仕様](../データ仕様.md#生成画像の管理記録)とする。

2026-10-13、Issue #97でStorageの予約・確定・ID取得を追加した。一時SQLiteで再接続・上位bitの保持、重複・二重確定・確定失敗・キャンセル・破損した記録の拒否を確認した。実ファイル確認、作品参照変更、整理・配信との接続は残るためPendingを維持する。内部の操作契約は[画像保存契約](../cover-persistence.md#実装済みのstorage操作)を参照する。

2026-10-13、Issue #101で作品の画像参照と`updatedAt`を同じトランザクションで設定・解除するStorage操作を追加した。正常なready記録の検証、再接続、時計の巻き戻り、変更なし、DB失敗・キャンセル時の旧状態保持を一時SQLiteで検証する。ファイル保存・削除・配信、操作排他、Applicationとの接続が残るためPendingを維持する。
