# ADR-0018: 作品の編集範囲と確認後の完全削除を決める

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-21
- Related: [#204](https://github.com/asam-masa/manga-update-manager/issues/204)

## Context

最新話や話数一覧へ移動しやすい入口が、作品固定URLでないサイトがある。登録済みURLを変えるために別作品として再登録すると、画像・メモ・最終アクセスを分断する。通常利用でも入力修正と誤登録の削除が必要になり、利用者は表示切替・タグなどより編集・削除を優先すると判断した。

基準main `699382b35c3c366a9fb81d9a8c96e38ef97d549e`に編集・作品削除はない。URL起動はWorkOpener、画像変更はCoverOperationsが別々に同作品の受付を制御している。DBと画像ファイルの削除は一つの原子的操作にできない。既存の画像機能を拡張済みとは扱わない。

## Decision Drivers

- 入口URLを変更しても同じ作品の情報を引き継ぐ
- 誤削除の対象を利用者が確認できる
- 元画像と他作品の参照を守る
- 初回にゴミ箱・Undo・履歴保存を持ち込まない
- 同作品の競合を防ぎ、別作品を不要に止めない

## Considered Options

### URLだけを編集する

変更は小さいが、タイトルなどの入力修正を別機能へ分けることになる。

### 登録時のテキスト4項目をまとめて編集する

URL・タイトル・サイト名・メモを一つの操作で修正できる。入力検証と既存データ保持、一覧への反映を検証する必要がある。画像と日時の手動編集は含めない。

### ゴミ箱へ移して復元できるようにする

誤削除に対応できるが、復元とURL重複、画像保持期間、通常一覧との区別が必要になる。

### 確認後に完全削除する

状態を単純にできる一方、確認後の誤削除は取り消せない。確認画面と元画像保持、管理画像整理の安全確認が必要になる。

## Decision

利用者が会話で承認した初回の範囲を次のとおり記録する。

- 編集はURL・タイトル・サイト名・メモ。同じ作品IDの情報修正として、画像・登録日時・最終アクセス日時を保持する。画像は既存の専用操作で扱う。
- 各作品の編集ボタンでダイアログを開き、保存/キャンセルで閉じる。保存を実行しなければ変更しない。
- 削除は作品名とURLを表示した確認画面を通す。確認後の完全削除とし、ゴミ箱・Undoを初回に設けない。
- 元画像は変更・削除しない。アプリ管理画像は、他の作品が参照していないことと実ファイルの安全性を確認できたものだけ整理する。確認不能なものを推測で削除しない。
- 同作品の画像操作・URL起動・編集・削除は処理を重ねず、先行操作の完了まで追加操作を拒否する。別作品は利用可能な範囲で継続する。全体の画像選択枠、起動時整理、共通参照排他、DB/画像停止など既存の制約は撤廃しない。

## Consequences

作品URLを手動で最新側の入口へ差し替えられるが、最新話の自動取得や読了管理にはならない。削除後の復元手段はない。管理画像の即時回収を保証せず、削除のために元画像や共有画像を消さない。

これは利用者向け方針の決定であり、API・SQL・受付部品・画面の非同期反映は未実装である。編集を先行し、削除は別Issueで実装する。[実装前の具体化事項](../work-edit-delete.md#実装前に具体化する契約)を満たすまで、実装IssueをDoR達成として扱わない。既存のADR-0013のVerifiedを、新しい作品削除の検証済み根拠として流用しない。

## Validation

### 編集保存の追加合意（Issue #209、2026-10-21）

利用者は、前後空白除去・URL/タイトル必須・他作品との重複URL拒否を登録時と同じ規則にし、変更なしでは更新日時も変えない方針を承認した。変更時だけ更新日時を記録し、既存値より戻さない。登録日時・最終アクセスは保持する。

保存のCommit結果が不明なら自動再試行せず、新たなDB操作を停止して再起動後の状態確認を案内する。入力拒否・URL重複ではDBを停止しない。画面は入力と案内を残し、結果不明を通常の成功/失敗と同一視しない。

検索文字を維持し、保存後に条件から外れた作品は一覧から外すが、成功通知は残す。保存中は連打とキャンセル・Esc・背景クリックで閉じることを防ぐ。編集を開いている間の入力は自動で差し替えず、保存時に4項目だけを更新し、キャンセルで破棄する。これらの画面動作はまだ未実装である。

Issue #209は[入力とSQLite更新の基盤](../verification/work-edit-storage.md)だけを先行実装する。Application・共通排他・API・UIは未接続であり、親#205の完了や本ADR全体のVerified化ではない。

### 共通受付と通常終了（Issue #211）

編集保存中のアプリ本体の通常終了も案内して拒否し、結果後に再度閉じる方針を追加承認した。結果不明でも処理終了後は通常終了できる。ダイアログに入力しているだけの時間は保存中としない。

#211ではApplicationの`WorkOperations`を同Appの正規API入口へ1個接続し、URL起動・画像設定/変更/解除の同作品の重なりを拒否する。AppのDB寿命ロック内で取得し、既存処理の完了・後処理・解放後に返却する。画像段階・参照排他・DBの実行権は別の責務として維持する。これは既存利用側に合わせた局所的な接続方式であり、直接生成したApplication部品の全インスタンスを跨ぐ排他ではない。

後続編集の`BeginEdit`と終了確定を同mutexで順序付け、編集が残る場合は既存の画像終了受付を変更せず拒否する。画像側が終了を拒否した場合も共通受付を閉じない。URL実行中のDB寿命保持は既存のAppロックで継続する。新しい編集API・UIと削除はまだ接続せず、[検証範囲](../verification/work-operation-admission.md)と区別してPendingを維持する。

Pending。設計文書と承認内容の通常・独立レビューを行う。実装後は入力拒否・重複・保持項目・再接続、同作品の相互排他・別作品継続、削除のDB/後処理失敗・共有/不明画像保持、古い一覧応答とダイアログ・実WebView2操作を一時DB/合成画像で確認する。今回、利用者データの編集・削除やGUI試験は行わない。

### 編集APIの接続（Issue #213）

#213でApplicationのWorkEditorとWailsのEditWorkを共通受付へ接続する。4項目だけを保存し、通常成功と確定後解放失敗の警告、Commit結果不明の拒否を区別する。[API契約](../work-api.md#編集apiissue-213)と[検証範囲](../verification/work-edit-api.md)を参照する。前節の未接続は#211時点の範囲であり、現在の未接続は編集UIと削除である。実WebView2の保存・終了案内も後続へ残し、Pendingを維持する。

### 編集画面の追加合意と接続（Issue #215）

利用者は背景の一覧・検索・別作品操作を止めるモーダルで進める方針を承認した。開始済み処理は継続し、保存/キャンセル後に背景操作へ戻る。#215で4項目入力・保存・入力保持・検索と通知・フォーカス復帰を接続する。#209/#211/#213時点の未接続記録と区別し、現在の検証範囲は[編集ダイアログ](../verification/work-edit-dialog.md)を参照する。実画面の保存/キャンセル・検索条件外の通知を確認し、利用者もTab/Shift+Tab・Escとフォーカス復帰・キャンセルを手動確認した。保存中の終了案内の実画面確認と削除などの残条件は完了扱いにせず、Pendingを維持する。

### 編集保存中の終了案内（Issue #219）

待機点付き計測用exeの実WebView2で、保存中の終了拒否・既存案内・解除後の実SQLite保存・自動終了されないこと・結果後の再要求終了をUIA確認した。待機点のない通常ビルドで同じ専用データを再起動し保存保持も確認した。[方法・版・限界](../verification/work-edit-close.md)を参照する。これは先行の未確認条件を補う記録であり、物理Commit/Close故障や無改変productionでの実遅延の検証ではない。削除などの残条件は完了扱いにせずPendingを維持する。

### 削除結果と確認画面の追加合意（Issue #221）

2026-10-22、利用者は次の方針を承認した。設計の追加合意であり、削除の実装・検証が完了したとは扱わない。

- DBで削除が確定したら作品を一覧から外す。管理画像整理に失敗しても作品を復元せず、削除済みと整理未完了の警告を分ける。安全に整理できる残存管理画像は次回起動時の整理対象とするが、回収を保証しない。
- DBの削除結果が不明なら自動再試行・画像整理を行わず、DB操作を停止して再起動後の確認を案内する。
- 削除直前に、確認時の編集4項目と画像を現在値と照合する。変化した場合は削除せず、最新の作品名・URLで再確認する。最終アクセス日時だけの変化では再確認しない。
- 対象が既に存在しなければ、その旨を案内して確認画面を閉じ、一覧から外す。今回の削除成功とは扱わず、この要求による画像整理をしない。
- 確認は背景操作を止めるモーダルとし、開始済み処理は継続する。最初はキャンセルへフォーカスし、処理開始前はEscでも取り消せる。処理中は連打・キャンセル・Escによる閉鎖とアプリの通常終了を防ぎ、終了要求には案内する。結果後は結果不明でも閉じられる。

DBとファイルを一括成功/失敗にすると、作品は消えたのに再削除を促す恐れがあるため、確定と後処理の結果を分ける。確認時から変わった作品を無条件に削除する方式は、利用者が確認した内容との不一致を生むため採用しない。ダイアログを開いている時間全体をバックエンドの操作予約にする代わりに、削除時の照合と既存の処理受付を組み合わせる。照合と削除の不可分性、画像の照合情報、API・SQL、停止・解放の詳細は各実装Issueで具体化する。

DB基盤、APIと画像後処理、確認UIの順に分けて検証する。不存在・変更・結果不明・確定後失敗、元画像・共有/未知ファイル保持、次回整理、同作品競合・終了、古い応答・検索・キー操作を対象とし、ADR-0013の検証を新しい削除の検証結果に流用しない。Pendingを維持する。

### 削除SQLite基盤の具体化（Issue #222、2026-10-23）

利用者は、確認対象の画像は参照先で比較し、ファイル自体の安全確認は整理時に分ける方針を承認した。確認後にA→B→Aと変わっても削除直前の値が同じなら削除を許可し、変更履歴のためのrevisionは追加しない。

#222で5項目の完全一致をTx内で照合して作品行だけ削除する。不存在・対象変更・Commit結果不明・確定後返却失敗を区別し、結果不明は成功データなしでDB停止する。画像ファイル・管理画像レコードは保持する。[契約と検証の限界](../verification/work-delete-storage.md)を参照する。App共通受付と参照排他・API・画像後処理は#223、確認UIは#224へ残す。保存基盤だけを利用者向け削除全体の検証済み根拠とせず、Pendingを維持する。

### 画像停止時の削除とApplication手順（Issue #227、親#223）

2026-10-23、利用者は画像機能だけの停止ならDBが正常な限り作品削除を許可し、画像整理を警告付きで見送る方針を承認した。画像の問題によって不要な作品まで削除不能にしないためであり、DB停止を迂回する方式ではない。元画像や安全性不明のファイルは保持し、残存管理画像の次回整理も安全確認を省略しない。

削除確定後の画像後処理・資源解放まで通常終了を案内して拒否し、結果後は整理失敗でも閉じられる方針も承認した。#227はApplicationと画像整理だけを先行し、既存参照排他と画像段階・管理ディレクトリ保護・確認済みファイル削除を再利用する。Appの共通作品予約・通常終了判断とWails APIへの接続は親#223へ残す。[契約と検証の限界](../verification/work-delete-application.md)を参照し、未接続の終了案内や画面まで検証済みとは扱わない。Pendingを維持する。

### 削除API・共通予約と通常終了の接続（Issue #223）

#223で`DeleteWork`をWailsへ公開し、DB寿命と共通作品予約を画像後処理・資源解放・結果変換まで保持する。削除と終了確定を同mutexで順序付け、未開始の起動時整理を取消す前に終了拒否する。確定後の警告、不存在、対象変更、結果不明を区別し、安全なエラー復元へ接続する。[API契約と検証範囲](../verification/work-delete-api.md)を参照する。先行#227時点の未接続記録と区別し、確認UIと実WebView2での削除/終了案内は#224へ残す。Pendingを維持する。

### 削除確認UIの具体化（Issue #224）

利用者は、対象変更時にダイアログを閉じず最新情報へ更新して再確認し、もう一度の削除操作を待つ方針を承認した。取得失敗時は削除を無効にし、再読込か取消を選べる。#224で確認・結果分類・一覧反映へ接続する。[画面契約と検証範囲](../verification/work-delete-dialog.md)を参照する。専用データの実WebView2で取消・削除・検索とフォーカス・再起動保持・通常終了を確認し、利用者もTab/Shift+Tab・Escとフォーカス復帰を確認した。処理中の終了案内の実画面確認は#230へ残し、Pendingを維持する。

### 削除処理中の終了案内（Issue #230）

2026-10-23、待機点付き計測用exeの実WebView2で削除受付後の通常終了拒否・専用案内をUIA確認した。解除後に実SQLite削除と画像後処理を完了し、自動終了せず、結果後の再要求で通常終了した。待機点なし通常版で同じ専用データを再起動し、削除結果保持と通常終了も確認した。[方法・版・限界](../verification/work-delete-close.md)を参照する。待機はStore処理前であり、物理障害や後処理段階の実遅延の再現とは扱わない。親#206の全条件の照合・完了判断は別に行い、本追記だけでVerifiedへ変更せずPendingを維持する。
