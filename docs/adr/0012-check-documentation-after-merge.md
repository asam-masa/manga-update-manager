# ADR-0012: 文書確認を差分レビューとマージ後の照合に分ける

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-11
- Related: [#52](https://github.com/asam-masa/manga-update-manager/issues/52)

## Context

実装やCI、外部設定が完了すると、以前の文書にある未実装・未検証の記述が古くなる。今回の変更に必要な記録と、既存文書の状態確認を毎コミットでまとめて行うと負担が増える。ユーザーは以下の二段階の確認を承認した。

## Decision Drivers

- 重要な仕様・判断の記録をマージ前に残す
- 実装後の状態変化も見落とさない
- 小さな開発単位を維持し、確認を全体監査へ広げない
- 未実装・未検証と反映漏れを区別する

## Considered Options

### 毎コミットで関連文書を一括照合する

- 利点: 早い段階で漏れを見つけられる
- 欠点: 同じ文書を繰り返し確認する負担が増える
- リスク: 外部設定の完了後に変わる状態を捉えられない

### マージ後だけ確認する

- 利点: 完了した実装を根拠にまとめて確認できる
- 欠点: 必要な仕様・判断の記録がないままマージされる
- リスク: レビューと後続実装が不完全な記録に依存する

### 差分の軽い確認とマージ後・外部設定後の照合を分ける

- 利点: 必要な記録を先に残し、状態変化は確定した根拠で確認できる
- 欠点: 再開時の追加手順が必要になる
- リスク: マージ後の確認を忘れると古い状態が残る

## Decision

三つ目の方式を採用する。既存の差分レビューは今回の変更に必要な文書を確認する。マージ後の開発再開時と外部設定完了後に、読み取り専用の`check-documentation-consistency`で関連文書を照合する。

漏れは別の小さなIssue・PRで修正する。自動編集、mainへの直接修正、Pendingの自動解除、Git hookは導入しない。ADR-0007のレビュー要件と既存のマージ条件は維持する。

## Consequences

全体監査を毎コミットで行わず、実装状況と検証状況を分けて記録できる。親の開発工程が確認の起動と修正Issueの作成を担う。スキル自身に書き込み権限は与えない。既存アプリ文書の漏れの修正は本Issueに含めない。

## Validation

スキルの形式検証と固定差分の通常・独立レビューを行う。関連文書を使う読み取り専用の試行で、根拠付きの報告とPendingの区別を確認する。マージ後・外部設定後の継続運用は未検証のためPendingを維持する。
