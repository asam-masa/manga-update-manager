# ADR-0002: 内部アーキテクチャを選定する

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-04
- Related: [#7](https://github.com/asam-masa/manga-update-manager/issues/7)

## Context

本プロジェクトは、漫画作品の登録、一覧、URL起動、最終アクセス記録、更新予定、要確認判定、バックアップ、将来の自動更新確認を一つのWindows向けデスクトップアプリで提供する。

すべての機能は漫画作品を中心データとして共有する。一方、バックアップ形式と自動更新確認は、データ互換性、外部サイト、公開API、RSS、利用規約など、作品管理とは異なる理由で変更される。

アプリの初期規模は小さい。学習目的でGoのパッケージ設計、エラー処理、`context.Context`、小さなinterface、Unit Test、SQLiteトランザクションを扱う。ただし、将来の可能性だけを理由に抽象化や階層を増やさない。

このADRでは、Goバックエンドの責務、依存方向、外部境界、規模拡大時の分割方針を決定する。フロントエンドフレームワーク、SQLiteライブラリ、具体的な型とinterfaceは対象外とする。

## Decision Drivers

- 一つの作品モデルを複数の機能で一貫して扱えること
- 状態判定と日時計算をWails、SQLite、OSから分離してテストできること
- SQLite、ブラウザー、ファイル、時刻、HTTPの境界を制御できること
- 自動更新確認が失敗しても手動管理を継続できること
- Goのパッケージ設計とテストを学べること
- 小規模な初期版に対して過度な抽象化を持ち込まないこと
- 機能が増えた場合に段階的に分割できること

## Considered Options

### 実用重視のレイヤード・モジュラーモノリス

責務の種類でWails境界、Application、ドメイン、外部境界を分ける。漫画作品を中心ドメインとし、`backup`と`updatecheck`は独立したモジュールとして扱う。

- 利点:
  - 状態判定と日時計算を純粋なGoコードとしてテストできる
  - 漫画作品のモデルと規則を一か所に保てる
  - Wails、SQLite、OS、HTTPの詳細が中心ロジックへ入りにくい
  - Applicationで複数処理の順序と失敗時の整合性を管理できる
  - 外部事情で変化しやすいバックアップと自動更新確認を分離できる
  - 将来、実際に独立した機能だけを垂直分割できる
- 欠点:
  - 一つの機能追加で複数パッケージを変更する場合がある
  - `application`や`storage`が雑多な置き場になる可能性がある
  - interfaceとDTOを機械的に増やすと過剰設計になる
- リスク:
  - フォルダーだけを分け、責務と依存方向が守られない可能性がある
  - `service.go`や`manager.go`へ処理が集中する可能性がある

### 機能単位の垂直分割

登録、一覧、スケジュール、ブラウザー起動、バックアップ、更新確認など、利用者機能ごとにモデル、処理、保存をまとめる。

- 利点:
  - 一つの機能に関するコードを近い場所で確認できる
  - IssueとPRの変更範囲を機能に対応させやすい
  - 独立性が高い機能を追加、テスト、削除しやすい
  - サイト別更新確認を増やす場合に拡張しやすい
- 欠点:
  - 漫画作品の型、検証、保存処理が機能間で重複しやすい
  - 機能をまたぐ操作とSQLiteトランザクションの責任が曖昧になりやすい
  - 初期段階では機能境界が安定しておらず、分割を誤る可能性がある
- リスク:
  - 共通層を後から追加し、垂直分割とレイヤーが不規則に混在する可能性がある
  - 変更のたびに機能間の依存調整が必要になる可能性がある

### Wails境界へ直接実装する

Wailsの`app.go`からSQLite、時刻、ブラウザー、ファイルを直接操作する。

- 利点:
  - 初期ファイル数が少なく、試作品を早く作れる
  - 呼び出し経路が短い
- 欠点:
  - Wailsを起動せずに重要な処理をテストしにくい
  - UI境界、状態判定、外部処理が混在する
- リスク:
  - 機能追加に伴って`app.go`が巨大化し、後から責務を分離する費用が高くなる

### 厳密なClean Architecture

各層に個別のDTO、変換処理、ユースケース型、ポート、アダプターを設ける。

- 利点:
  - 依存方向と外部境界を厳密に管理できる
  - 大規模な変更や複数実装へ対応しやすい
- 欠点:
  - 初期版に対して型、変換、interface、ファイルが多くなる
  - Goそのものより設計パターンの実装負担が大きくなる
- リスク:
  - 利用者価値より構造の維持へ時間を使う可能性がある

## Decision

実用重視のレイヤード・モジュラーモノリスを採用する。

中心となる漫画作品と状態判定を`manga`ドメインへ集める。利用者操作の順序はApplicationで管理する。WailsはTypeScriptとの薄い境界とし、SQLite、時刻、ブラウザー、ファイル、HTTPの詳細を中心ロジックから分離する。

バックアップは形式のバージョン、互換性、復元時の安全性を持つため、`backup`モジュールとして分離する。自動更新確認は外部仕様と利用規約によって変更され、失敗時も手動管理を継続する必要があるため、`updatecheck`モジュールとして分離する。両モジュールは作品を直接保存せず、Applicationが検証と保存の順序を管理する。

初期構成は次を基準とする。

```text
internal/
├─ manga/
├─ application/
├─ storage/
├─ platform/
├─ backup/
└─ updatecheck/
```

依存方向は次とする。

```text
UI -> Wails -> Application -> Domain
                         -> external boundary interfaces
Infrastructure ---------> interface implementations
```

ドメインからWailsとSQLiteを参照しない。UIからSQLiteを直接操作しない。サイト別Providerは作品を直接保存しない。StorageからApplicationを呼び出さない。

## Consequences

- 状態判定、更新予定、入力検証をWailsとSQLiteなしでUnit Testできる
- Applicationのテストでは、時刻、ブラウザー、ストレージを偽実装へ置き換えられる
- SQLiteは一時データベースを使うIntegration Testで確認する
- Wails APIを安定した外部契約として扱い、内部パッケージの変更を画面へ直接伝播させない
- interfaceは利用側で定義し、テストまたは外部境界で差し替える必要がある場合だけ導入する
- Go内部ではドメイン型を共有し、外部契約が異なる場所だけDTOを作る
- Applicationは操作単位のファイルへ分け、曖昧な`service.go`と`manager.go`への集中を避ける
- SQLiteマイグレーションを初期版から順番付きで管理する
- バックアップ形式は初期版からバージョンを持つ

規模拡大時は、行数だけを理由に分割しない。次の兆候が複数現れた場合に、まとまりのある機能を垂直分割する。

- 同じ概念に関するファイルが増え、同時に変更される
- 一つのパッケージに異なる変更理由が混在する
- 同じ条件分岐が複数箇所へ現れる
- サイト追加のたびに中心コードを変更する
- SQLiteトランザクションの責任が不明確になる
- パッケージの責務を一文で説明できなくなる

将来は、必要に応じて`catalog`、`access`、`schedule`などの機能モジュールへ分割する。単一の実行ファイルとSQLiteを維持し、ローカルデスクトップアプリである限りマイクロサービス化を原則として行わない。

## Validation

雛形生成と最初の機能実装で次を確認する。

- Wails境界がApplicationの呼び出しと入出力変換だけを担当している
- 状態判定と日時計算をWailsとSQLiteなしでUnit Testできる
- ブラウザー起動失敗時に最終アクセス日時を更新しない振る舞いをテストできる
- SQLiteを一時データベースでIntegration Testできる
- バックアップ形式にバージョンが含まれる
- パッケージ間に禁止した依存がない

Issue #21で、Wailsの入出力変換、Applicationの登録・一覧操作、利用側interface、StorageのSQL、platformのOS保存先を分離した。一時SQLiteと固定時刻のテストで各境界を確認した。ブラウザー起動とバックアップの検証は後続Issueに残るため、Validation Statusは`Pending`を維持する。
