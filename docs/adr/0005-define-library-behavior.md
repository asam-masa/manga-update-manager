# ADR-0005: 作品一覧の操作と表示状態の扱いを決める

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-09
- Related: [#25](https://github.com/asam-masa/manga-update-manager/issues/25), [#26](https://github.com/asam-masa/manga-update-manager/issues/26), [#27](https://github.com/asam-masa/manga-update-manager/issues/27), [#28](https://github.com/asam-masa/manga-update-manager/issues/28), [#29](https://github.com/asam-masa/manga-update-manager/issues/29), [#30](https://github.com/asam-masa/manga-update-manager/issues/30), [#31](https://github.com/asam-masa/manga-update-manager/issues/31)

## Context

#23で作品登録と一覧を実装した。続くgrillingで、最終アクセス、表示形式、検索、並び順、タグ、設定保持の振る舞いを利用者と検討し、文書化・Issue分割を承認された。

これらは同じ作品データと表示条件を共有する。後から各機能で異なる意味を持たせないため、合意済みの横断的契約を一つのADRへ記録する。具体的なDB/API、画像保存、設定保存、更新予定計算は対象外であり未決定である。

## Decision Drivers

- アクセス記録が何を保証するか明確であること
- 作品名をコピーでき、開く操作を重複させないこと
- 情報量が違っても検索・絞り込みの意味が変わらないこと
- 再起動後に便利な配置を維持し、作品を見失う絞り込みを避けること
- タグの表記揺れを減らし、意図しない分類変更を避けること
- 小さなIssue・PRで段階的に検証できること

## Considered Options

| 問い | 候補 | 利点 | 欠点・リスク |
| --- | --- | --- | --- |
| 最終アクセス | ブラウザー起動要求の成功時刻 | サイトを問わずアプリの操作として扱える | ページ表示・読了は保証しない |
| 最終アクセス | 読んだボタンによる記録 | 利用者が読書を申告できる | 毎回の追加操作が必要 |
| 最終アクセス | ページ表示完了の検知 | 実際の表示に近づけられる | ブラウザー連携と検証が増える |
| 開く操作 | タイトルまたはタイトルとURLの両方 | 見つけやすい | タイトルのコピーと操作が競合し、入口が重複する |
| 開く操作 | URLだけ。小型表示は画像だけ | タイトルをコピーでき、入口を一つにできる | 表示形式ごとに入口を示す必要がある |
| URL全文 | 標準title属性 | 実装負担が小さい | 表示の位置・待ち時間・キーボード対応を制御できない |
| URL全文 | 独自ツールチップ | 表示とフォーカス対応を制御できる | 画面端・閉じ方・重なりなどの確認が増える |
| 設定保持 | 検索と選択タグも復元 | 継続して同じ条件で使える | 絞り込みを忘れ作品を見失う可能性がある |
| 設定保持 | 配置・並び方だけ復元 | 便利な配置を保ち、絞り込みを解除できる | 検索条件を再入力する必要がある |
| タグ絞り込み | AND | 対象を絞り込みやすい | 条件が増えると0件になりやすい |
| タグ絞り込み | OR | 関連作品を広く拾える | 絞り込みが広くなる |
| タグ重複 | 最初から統合を実装 | 表記揺れをまとめられる | 全作品の関連変更と選択状態の判断・テストが増える |
| タグ重複 | 候補を再利用し、統合は別機能 | 誤作成を減らし、初回範囲を小さくできる | 作成済みの別表記をまとめる機能は残る |

## Decision

最終アクセスは、アプリから登録URLを開く要求が既定ブラウザーへ正常に渡った時刻とする。起動失敗では記録せず、起動成功後の保存失敗はページを開いたまま警告し、保存済み日時を維持する。未アクセスを登録日時から補完しない。

開く入口はURLだけとし、画像・タイトルだけの小型表示では画像だけとする。作品名はコピーできる通常の文字列とする。URLは1行で省略し、標準title属性で全文を確認する。

三つの表示形式で検索・絞り込み条件を維持する。配置と並び方は再起動後も復元するが、検索文字と選択タグは起動時に解除する。初回はメモなしカード・登録フォーム表示とする。

更新予定の表示順は今日、過去の近い順、未来ONなら未来の近い順、未設定の順とする。未来は同じ表の列に含め、別領域へ分けない。

タグは複数・階層なし、選択タグのAND絞り込みとする。既存候補を再利用し、明示操作で新規作成する。前後の空白を除いた同名重複を禁止する。名前変更は関連作品へ反映し、削除は関連だけを外す。統合は後続とする。

採用理由は、コピー操作と一覧の密度を両立し、操作結果と表示条件を機能間で一貫させ、初回実装の負担を抑えるためである。詳細な現在有効の合意仕様は[拡張設計](../library-design.md)を参照する。

## Consequences

Issue #25の追加合意として、一作品につき最新の日時だけを保存し、履歴は保存しない。未設定はDBのNULLとAPIのnullで表す。

- 既存作品へ最終アクセスの未設定値を扱う保存・API変更が必要になる
- 画像を持たない作品、削除済みタグ、破損した設定の扱いを各実装前に決める
- ブラウザー起動とDB保存は一つの原子的操作にはできず、部分成功を利用者へ示す
- タイトル検索はタグ条件と組み合わせ、表示形式と保存対象を分ける
- 検索・選択タグの再起動後の復元は将来追加できるが、先行実装しない
- 画像保存、更新予定計算、設定保存方式、タグDB構造は別の判断として残す
- 大きいFeatureは設計後に独立して検証できる子Issueへ分ける

## Validation

### 表示切替の具体化（Issue #44、2026-10-24）

利用者は、全形式の常時表示「⋯」へ作品操作をまとめ、小型の仮画像も起動入口にする方針を承認した。省スペースと操作場所の一貫性を優先する一方、編集等はメニューを開く1操作が増える。画像に重ねる案や右横の細いボタン案は、重なり・押しにくさ・余白が理由で採用しなかった。小型は通常幅横5件・中央画像140×187px・タイトル17px最大3行とし、タイトル下に高さ28pxの横長ボタンを置く。行・カードは40×40pxの操作ボタンを基準とする。小型は狭い幅で列数を減らし、行一覧は表内の横スクロールで列の整合を保つ。[合意内容と検証時に確認する寸法](../library-design.md#issue-44の追加合意2026-10-24)を参照する。

設定は切替を先に画面へ反映し、保存失敗では戻さず警告する。既存SQLiteで項目単位に保存し、フォーム設定を古い設定全体で上書きしない。処理中の切替を許可するため、表示要素の寿命と開始済み操作の寿命を分け、作品名付き共通通知へ結果・警告を引き継ぐ。形式切替時は検索を維持して先頭へ戻る。作品メニューは1つだけ開き、Esc・外クリック・形式切替で閉じ、Escでは元のボタンへ戻す。ページ切替は直後の別Issueへ分け、形式切替後は1ページ目とする。件数24/20/12はまだ仮案である。

上記は追加合意とサンプル比較時点の記録である。その後#235/#236/#250/#252で保存・共通操作・描画・接続を実装し、#237で[実WebView2確認](../verification/library-layouts.md)を補った。利用者はWindows文字サイズ110%の環境で、幅1200pxの5列・1024pxの4列を含む、画像と文字の大きさを保って列数を減らす現在の挙動を承認した。100%との比較は未実施。ADR-0006のVerifiedは既存フォーム設定の範囲であり、新しい形式へ流用しない。

Issue #25では、起動・保存の失敗、未アクセス、同一作品の並行起動、既存スキーマからの移行、再起動後の保持、日本時間DTO、キーボード操作、一覧応答との競合を自動テストで確認した。2026-10-10にユーザーが実ブラウザー起動、アクセス表示、コピー、標準title、Enter・Space、連打、再起動後の保持を確認した。長いURLのはみ出しは手動確認で発見して修正し、ユーザーが再確認した。

Issue #26ではフォーム開閉・入力保持・フォーカス・検索・IMEイベント・検索中の登録を自動テストで確認した。2026-10-11の反映確認で、[PR #34](https://github.com/asam-masa/manga-update-manager/pull/34)に記録された実WebView2のユーザー確認を照合した。2026-10-10に、IME変換中の一覧維持と確定後の検索、半角カナの一致、Tab・Enterの開閉、IME確定用Enterによる誤登録防止を確認済みである。

フォーム開閉の再起動後の復元は[ADR-0006](./0006-persist-display-settings.md)で検証済みである。三形式の切替・復元・保存失敗と画像処理中切替は#237の範囲で確認した。タグ、並び順、更新予定などの後続検証は残るため、Validation Statusは`Pending`を維持する。以下は全体の検証項目であり、タグ等の未実装部分まで完了したとは扱わない。

- 起動要求失敗・保存失敗・未アクセスを制御したテスト
- 長いURL・タイトル・未入力でも均一な表示、コピー・キーボードの手動確認
- 三形式の切り替えでも検索と選択タグが維持されるテスト
- 再起動で保存対象だけを復元し、検索と選択タグを解除するテスト
- タグ重複・変更・削除で作品が欠落しない保存テスト
- Asia/Tokyoの日付境界と予定優先順のテスト

### ページ切替の具体化（Issue #238、2026-10-25）

利用者は小型20件・行20件・カード12件、検索/形式変更で1ページ目、登録作品が一致すればそのページへの移動を承認した。編集・削除後は現在位置を保ち、ページがなくなった場合だけ最後へ補正する。ページ番号は保存しない。明示ページ移動では上側の現在番号へフォーカスし、全件取得を維持して描画だけを分割する。全件取得の通信量・メモリは減らせないが、既存の全件検索・状態保持を維持し、DB/APIの変更を避けられるため採用した。[一覧設計](../library-design.md#ページ切替の合意issue-2382026-10-25)を正本とする。

これは既存の表示・操作契約の具体化で、新しいデータ保存方式の採用ではない。サンプルの24/20/12は今回の確定値へ置き換える。タグ・予定等の残条件によりValidation StatusはPendingを維持する。

### 基本並び順の具体化（Issue #29、2026-10-25）

利用者は登録順・タイトル順・最終アクセス順の各昇降順を承認した。初回は既存と同じ登録古い順とし、選択は再起動後に復元する。未アクセスは両方向とも末尾、同順位は登録古い順とする。タイトルは検索と同じ表記差を吸収し、数字はゼロ埋め不要の自然順とする。読み仮名は追加せず、漢字の正確な五十音順は保証しない。具体的な契約は[一覧設計](../library-design.md#基本並び順の合意issue-292026-10-25)を正本とする。

単純な文字列順は実装が容易だが「作品10」が「作品2」より前になるため採用しなかった。未アクセスを昇順の先頭へ置く案より、両方向で日時のある作品を先に確認する扱いを選んだ。最終アクセス保存後は再読み込みまで順番を固定する案より、保存済み日時と整列を一致させる扱いを選んだ。その結果、作品が別ページへ移る場合があるため、現在ページと通知を維持する。

全件取得を維持し、検索→整列→ページ分割とする。並び順変更は1ページ目、登録成功は該当作品のページ、編集・アクセス後は現在ページを保つ。設定保存は既存方式を拡張し、種類と方向の組だけを更新する。新しい保存方式ではなく本ADRの具体化として記録し、新ADRは追加しない。

設計記録#256、保存API#257、画面接続・実機確認#258へ分割する。自然順・同順位・未アクセス・ページ境界、初期復元と遅延応答、保存失敗と他設定の保持を後続で検証する。現時点では未実装・未検証であり、タグ・予定の残条件もあるためValidation StatusはPendingを維持する。
