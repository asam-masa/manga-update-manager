# ADR-0005: 作品一覧の操作と表示状態の扱いを決める

- Status: Accepted
- Validation Status: Pending
- Date: 2026-10-09
- Related: [#25](https://github.com/asam-masa/manga-update-manager/issues/25), [#26](https://github.com/asam-masa/manga-update-manager/issues/26), [#27](https://github.com/asam-masa/manga-update-manager/issues/27), [#28](https://github.com/asam-masa/manga-update-manager/issues/28), [#29](https://github.com/asam-masa/manga-update-manager/issues/29), [#30](https://github.com/asam-masa/manga-update-manager/issues/30), [#31](https://github.com/asam-masa/manga-update-manager/issues/31)

## Context

#23で作品登録と一覧を実装した。続くgrillingで、最終アクセス、表示形式、検索、並び順、タグ、設定保持の振る舞いを利用者と検討し、文書化・Issue分割を承認された。

これらは同じ作品データと表示条件を共有する。後から各機能で異なる意味を持たせないため、合意済みの横断的契約を一つのADRへ記録する。具体的なDB/API、画像保存、設定保存、更新予定計算は対象外であり未決定である。

## Decision Drivers

- アクセス記録が何を保証するか明確であること
- 作品名をコピーでき、開く操作を重複させないこと
- 情報量が違っても検索・絞り込みの意味が変わらないこと
- 再起動後に便利な配置を維持し、作品を見失う絞り込みを避けること
- タグの表記揺れを減らし、意図しない分類変更を避けること
- 小さなIssue・PRで段階的に検証できること

## Considered Options

| 問い | 候補 | 利点 | 欠点・リスク |
| --- | --- | --- | --- |
| 最終アクセス | ブラウザー起動要求の成功時刻 | サイトを問わずアプリの操作として扱える | ページ表示・読了は保証しない |
| 最終アクセス | 読んだボタンによる記録 | 利用者が読書を申告できる | 毎回の追加操作が必要 |
| 最終アクセス | ページ表示完了の検知 | 実際の表示に近づけられる | ブラウザー連携と検証が増える |
| 開く操作 | タイトルまたはタイトルとURLの両方 | 見つけやすい | タイトルのコピーと操作が競合し、入口が重複する |
| 開く操作 | URLだけ。小型表示は画像だけ | タイトルをコピーでき、入口を一つにできる | 表示形式ごとに入口を示す必要がある |
| URL全文 | 標準title属性 | 実装負担が小さい | 表示の位置・待ち時間・キーボード対応を制御できない |
| URL全文 | 独自ツールチップ | 表示とフォーカス対応を制御できる | 画面端・閉じ方・重なりなどの確認が増える |
| 設定保持 | 検索と選択タグも復元 | 継続して同じ条件で使える | 絞り込みを忘れ作品を見失う可能性がある |
| 設定保持 | 配置・並び方だけ復元 | 便利な配置を保ち、絞り込みを解除できる | 検索条件を再入力する必要がある |
| タグ絞り込み | AND | 対象を絞り込みやすい | 条件が増えると0件になりやすい |
| タグ絞り込み | OR | 関連作品を広く拾える | 絞り込みが広くなる |
| タグ重複 | 最初から統合を実装 | 表記揺れをまとめられる | 全作品の関連変更と選択状態の判断・テストが増える |
| タグ重複 | 候補を再利用し、統合は別機能 | 誤作成を減らし、初回範囲を小さくできる | 作成済みの別表記をまとめる機能は残る |

## Decision

最終アクセスは、アプリから登録URLを開く要求が既定ブラウザーへ正常に渡った時刻とする。起動失敗では記録せず、起動成功後の保存失敗はページを開いたまま警告し、保存済み日時を維持する。未アクセスを登録日時から補完しない。

開く入口はURLだけとし、画像・タイトルだけの小型表示では画像だけとする。作品名はコピーできる通常の文字列とする。URLは1行で省略し、標準title属性で全文を確認する。

三つの表示形式で検索・絞り込み条件を維持する。配置と並び方は再起動後も復元するが、検索文字と選択タグは起動時に解除する。初回はメモなしカード・登録フォーム表示とする。

更新予定の表示順は今日、過去の近い順、未来ONなら未来の近い順、未設定の順とする。未来は同じ表の列に含め、別領域へ分けない。

タグは複数・階層なし、選択タグのAND絞り込みとする。既存候補を再利用し、明示操作で新規作成する。前後の空白を除いた同名重複を禁止する。名前変更は関連作品へ反映し、削除は関連だけを外す。統合は後続とする。

採用理由は、コピー操作と一覧の密度を両立し、操作結果と表示条件を機能間で一貫させ、初回実装の負担を抑えるためである。詳細な現在有効の合意仕様は[拡張設計](../library-design.md)を参照する。

## Consequences

Issue #25の追加合意として、一作品につき最新の日時だけを保存し、履歴は保存しない。未設定はDBのNULLとAPIのnullで表す。

- 既存作品へ最終アクセスの未設定値を扱う保存・API変更が必要になる
- 画像を持たない作品、削除済みタグ、破損した設定の扱いを各実装前に決める
- ブラウザー起動とDB保存は一つの原子的操作にはできず、部分成功を利用者へ示す
- タイトル検索はタグ条件と組み合わせ、表示形式と保存対象を分ける
- 検索・選択タグの再起動後の復元は将来追加できるが、先行実装しない
- 画像保存、更新予定計算、設定保存方式、タグDB構造は別の判断として残す
- 大きいFeatureは設計後に独立して検証できる子Issueへ分ける

## Validation

Issue #25では、起動・保存の失敗、未アクセス、同一作品の並行起動、既存スキーマからの移行、再起動後の保持、日本時間DTO、キーボード操作、一覧応答との競合を自動テストで確認する。実ブラウザー・WebView2の手動確認と、後続機能の検証は残るためPendingを維持する。

今回確認したのはユーザーの合意と文書の整合性であり、機能の実装検証は未実施である。Validation StatusはPendingとする。

- 起動要求失敗・保存失敗・未アクセスを制御したテスト
- 長いURL・タイトル・未入力でも均一な表示、コピー・キーボードの手動確認
- 三形式の切り替えでも検索と選択タグが維持されるテスト
- 再起動で保存対象だけを復元し、検索と選択タグを解除するテスト
- タグ重複・変更・削除で作品が欠落しない保存テスト
- Asia/Tokyoの日付境界と予定優先順のテスト
