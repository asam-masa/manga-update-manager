# 復元前の準備領域と片付け方針

Issue #616、親 #378。2026-11-20に承認した準備場所と、現在データの退避・切替を始める前の失敗・取消時の扱いを記録する。製品の復元処理は未実装である。

既存の[初回設計](./backup-restore.md)、[形式v1](./backup-format.md)、[ADR-0022](./adr/0022-manual-backup-and-replacement-restore.md)を前提とする。現在データを退避してから段階切替し、成功後は終了・再起動する既存方針は変えない。

## 承認した方針

### 準備場所

- アプリのデータ保存先に、復元の実行ごとに新しい専用フォルダーを作る。
- バックアップ作成時と同じローカルNTFS・リンク経由の拒否・親フォルダー保持の安全条件を適用する。条件を満たせない場合に、別ドライブや緩い方式へ自動で切り替えない。
- 現在のDB・画像を退避または置換する前に、専用領域で展開と必要な検証を行う。準備物を通常データとして起動・画像整理へ渡さない。
- 同じドライブに展開したDB・画像等の容量が必要になる。退避・切替開始時点までの必要容量は後続で具体化する。容量の事前確認だけで書込み成功を保証しない。

別ドライブを利用者が選ぶ方式は初回に採用しない。既存の保存領域と安全条件を再利用し、ドライブ間コピーとその失敗処理を初回から増やさないためである。

### 退避・切替前の失敗と取消

- 今回の復元準備で作成したと安全に確認できる準備用DB・画像だけを削除対象にする。フォルダー名やパスが一致するだけで所有確認済みとは扱わない。
- 所有確認ができない物、削除できない物、異常終了後の残置物は自動削除せず、残置場所と警告を案内する。
- 実行ごとの新規領域を使い、残置物を次の準備へ再利用しない。異常終了後に残置を検出・案内する具体的な方法は未確定であり、起動時の自動削除を導入する合意ではない。
- 選んだ元のバックアップZIP、現在データ、退避済みデータは、この準備物の削除対象に含めない。
- 削除を許可する今回の合意は、現在データの退避・切替を始める前に限る。退避・切替開始後は既存の中断記録・旧一式への復旧・保全方針へ従い、未確定の切替や復旧に必要な物を準備物として削除しない。

準備物を毎回すべて残す方式より、作品情報を含むコピーと使用容量の増加を抑えられる。一方、安全な識別や削除が成立しない場合には残置物が残る。

### 子出力方式の採用と取消後処理（#620、2026-11-20）

#617で確認した、親フォルダーの保持を維持し、その中の準備ファイルだけを新規作成する方式を採用する。既存部品の入れ子による共有違反を避けるために親保持を解放する方式は採用しない。子出力の作成・識別・解放を扱う部品を追加し、失敗時の契約と故障試験を先に行う。採用は方式の決定であり、製品実装の完了ではない。

親保持の所有は呼出元に残し、子部品はこれを借りる。子の作成失敗やCloseで親を勝手に解放しない。呼出元は子の後処理結果を集約してから、最後に親の解放を試みる。解放未確認を残したまま次の復元工程へ進まない。

| 観測 | 契約 |
| --- | --- |
| 作成前の失敗・取消 | 子出力の所有を返さない。ネイティブ作成の成否を確認できない場合もあり、作成成功を観測していないことだけで不在と断定しない |
| 作成後の識別・名前・属性確認失敗 | 作成事実と残置候補の場所を返し、取得済み資源の解放を試みて結果を残す。パスや作成事実だけでは削除を許可しない |
| 作成・識別・保持の成功 | 子保持の所有を呼出元へ渡す。書込みやCloseと、削除前の再確認・削除許可は別に扱う |
| 子のClose・解放失敗 | 子の解放結果を保持し、元の処理結果と分けて返す。Closeを削除・親解放・通常操作再開の許可と同一視しない |

退避・切替前の準備をキャンセルした後も、安全確認・所有確認できる準備物の片付け・ハンドル解放が終わるまで待つ。元の取消要求でこれらの後処理を途中終了させず、「取消後の片付け中」と経過時間を表示する方針とする。進捗の観測であり、終了時刻や正常動作を保証する表示にはしない。

確認できない物は保全して警告し、失敗・取消を片付け成功へ読み替えない。片付けや解放が終わっても、取消された復元の退避・切替には進まない。詳細UIと、解放未確認時の終了案内・通常操作の再開条件は引き続き実装前に具体化する。

最初の部品実装は[Issue #621](https://github.com/asam-masa/manga-update-manager/issues/621)で作成・識別・解放と故障試験に限定する。削除部品、入力保持と上限付き展開、DB/画像の意味的検証、復元経路への接続は後続とし、今回の採用でまとめて実装しない。

## 実装前に具体化する事項

#621でWindowsの`CreateRestorePreparationFile`と子保持型を追加する。呼出元が所有する`BackupWorkDirectory`の保持を取り直さず、親の識別・名前を確認して、部品側が生成したランダムな名前をCREATE_NEW・共有なしで作成する。既存のハンドル観測でディスクファイル・属性・リンク数・名前・初期サイズ0を確認し、成功時だけ子保持の所有を渡す。作成・確認・失敗後の解放が親のClose/DiscardEmptyと重ならないよう直列化する。

`RestorePreparationFileError`は作成事実・残置候補の場所・子の解放観測と原因を返す。失敗や取消では取得済みの子だけを解放し、削除や親解放は行わない。`Close`と`ReleaseResult`は子ハンドルだけを対象にし、Close結果は一度だけ確定して再試行しない。呼出元は成功後の子の寿命が終わるまで親保持を維持する。返るパス・IDは観測であり、閉じた後の再取得・削除権限ではない。

合成NTFSで複数作成・共有拒否・Close後の内容保持・既存名衝突・親ID/名前不一致・nil/閉じた親を確認し、故障模型で作成失敗・取得とエラーの併発・観測/名前/サイズ不一致・前後の取消・Close失敗を確認する。並行Closeは1回だけ実行し、解放未確認を維持する。Close失敗の模型は実OS故障の再現ではない。今回は作成・識別・解放だけで、I/O・削除の公開API、ZIP展開、製品App/UIへの接続は追加しない。

#624で保持中の子へ`Write`・`ReadAt`・`Sync`・`Size`を追加する。作成時の同じハンドルだけを使い、パス再取得・親の取得/解放は行わない。各I/OはCloseと同じ子mutexで直列化し、Close開始後は解放成否にかかわらず拒否する。未作成の子も拒否する。ReadAtは逐次書込位置を変えず、件数・EOF・OSエラーをそのまま返す。

このI/Oは低水準の部品であり、呼出元が上限・操作間の取消・内容検証を所有する。入力や容量の上限は変更せず、無制限入力のZIP展開を許可しない。Sync成功だけで一式の永続化・復元可能性を保証せず、削除・切替の許可にも使わない。合成試験で読書き・位置・同期・サイズ・Close後の拒否とネイティブエラー保持を確認する。#621時点で対象外だったI/Oをこの段階で追加し、削除・ZIP展開・製品App/UIは未接続のままとする。

#626で保持中の子1件に`Discard`を追加する。作成時に借りた親保持と、同じ子のID・ハンドル名・属性・リンク数を再確認してから、保持ハンドルへ削除指定する。親→子の順にロックし、子Close後の不在確認まで親保持を維持する。パス削除・再帰削除・閉じた物の再取得・親の削除/解放は行わない。

削除指定を試みた後は再試行とI/Oを拒否し、指定成功・不在確認・子の解放結果を別々に残す。確認拒否や削除指定失敗で子保持が残る場合は呼出元がCloseし、親を最後に解放する。元の取消contextは受け取らず、取消後の片付けにも同じ条件を使う。削除指定後のClose失敗・不在確認失敗で、成功や不在を推測したりパス削除へ切り替えたりしない。

合成NTFSで削除・親保持・同名後発ファイルの保全を確認し、模型で親子ID/名前/確認の失敗、削除指定失敗、Close失敗、不在確認失敗と二重試行拒否を確認する。実OS故障や電源断は再現していない。既存の退避・切替前という適用範囲を広げず、App接続時にその段階を守る制御は後続とする。

以下は作成部品以外も含む後続の具体化事項であり、#621だけで復元準備全体が実装済みとは扱わない。

今回の合意を、保存側の作業領域部品が復元でもそのまま安全に使えることの証明とは扱わない。

- 準備フォルダー・展開ファイルの作成、識別、保持、解放と、削除前の所有照合。
- 入力ZIPは#634の同じ読取ハンドルで保持する方針と、#637の[受入・識別・解放契約](./restore-source-input.md)に従う。元ZIPのパスだけで同じ入力と判断しない。
- 件数・個別サイズ・合計展開量の既存上限を守る展開順序と、途中失敗・取消・想定外のファイルの扱い。
- 準備物の片付け結果と、元の失敗・取消結果の分離。解放未確認時の停止・終了案内、通常操作の再開条件。
- 入力DBの構造・意味的検証、対応版の許可リスト、旧版の準備領域での移行と検証、管理画像の識別情報の再確立。
- 準備完了から退避・切替へ移る境界と所有の引継ぎ、中断記録の永続化、再起動時の復旧。

これらの未確定事項を推奨案だけで実装へ固定しない。互換性の合意済み方針（対応範囲の旧DBは準備用コピーで移行・検証し、未対応・新しすぎる形式は拒否する）は維持する。

## 複数ファイルの片付け継続（#628、2026-11-21）

現在データの退避・切替前に限り、1件の片付けに失敗しても、親の保持・識別が有効で、所有を個別に確認できる残りの子は片付ける。失敗・確認不能な物は保全し、残置候補の場所と原因を警告する。親自体を確認できなくなった場合は、以後の削除を止める。

削除の継続可否とは別に、各子のハンドル解放を試み、親を最後に解放する。元の処理の失敗・取消、各子の削除指定・不在確認・解放、親の解放を別々に記録する。一部の片付け成功で元の失敗や解放未確認を成功へ丸めない。

対象は今回の準備で所有を受け渡した子だけとする。パス一覧やフォルダー走査から削除権限を推測せず、既存の再試行禁止・同名後発ファイルの保全を維持する。パス削除・再帰削除へ切り替えず、元の取消要求でも必要な安全確認と解放を途中終了しない。入力ZIP・現在データ・退避済みデータは対象外のままとする。

#628時点では、[後続 #629](https://github.com/asam-masa/manga-update-manager/issues/629)で所有の集約と故障試験を実装し、所有受渡しAPIと二重所有・不正入力の拒否を具体化する計画とした。空になった親の扱いは以下の#631で確定した。#629で追加した部品の範囲は後述する。通常操作の再開条件や画面接続は、この承認には含めない。

## 空の準備フォルダーの片付け（#631、2026-11-21）

退避・切替前の片付けでは、今回作成した準備フォルダーの所有を再確認し、全子の不在と解放を確認できた場合だけ、その空フォルダーも削除対象にする。空でも毎回残す方式より、実行ごとの残置物を減らすためである。

保持中の同じフォルダーハンドルで所有を再確認する既存の`DiscardEmpty`を使い、非空なら削除しない。フォルダー走査で見つけた中身を削除したり、パス削除・再帰削除へ切り替えたりしない。子の不在・解放、親の所有を確認できない場合や、非空・削除失敗の場合は保全し、残置候補と警告を残す。#628で親確認不能により停止した削除を、後の再確認で再開しない。

親の削除指定・不在確認・解放結果も分離して記録する。削除できない場合も解放を試み、子の後に親を解放する。既存の再試行禁止と同名後発物の保全、取消後も必要な後処理を待つ方針は維持する。元ZIP・現在データ・退避済みデータは対象外であり、通常操作の再開条件は別途具体化する。

この採用は契約の記録である。既存の空フォルダー削除部品だけで復元準備全体の安全性を実証したとは扱わず、#629で複数件の片付けへの接続と、子の失敗・解放未確認・親確認不能・非空・親削除失敗の故障試験を行う。ADR-0022はPendingを維持する。

## 複数件の所有と片付け部品（#629）

`CreateRestorePreparation`は実行ごとの親フォルダーを新規作成し、`RestorePreparation`が親と子の記録を所有する。`CreateFile`で自ら作成した子だけを登録し、外部のパス一覧・既存の親子を受け入れるAPIは設けない。別実行の所有物の取込みや二重登録の入口を設けず、nil・未初期化の所有者と片付け開始後の作成を拒否する。呼出元は子のI/Oを借り、全消費処理を終えてから片付ける。作成と片付けは同じmutexで順序付ける。

作成失敗時も、パスや解放の未確認が残る場合はエラーと残置候補を登録する。保持中の子を取得できなかった物は、パスから再取得・削除しない。子のパス・保持を得る前に失敗して解放確認済みの場合は、削除候補を作らない。

`Cleanup(originalErr)`は、元の失敗・取消を`OriginalErr`に保持し、返すエラーは片付け側だけとする。各子の削除前と親の削除前に親を確認し、子の内部再確認も含めて親確認不能を検出したら以後の削除を止める。個別の子の確認・削除・Close・不在確認の失敗は、親を確認できる残りの片付けを妨げない。全子の解放を試み、全子の不在・解放と親の所有を確認できた場合だけ`DiscardEmpty`を呼び、最後に親とその親階層を解放する。

子ごとのパス・削除指定・不在・解放・原因と、親の削除指定・不在・解放・原因を返す。親が残る場合も警告となるエラーを残す。再度の`Cleanup`は元の結果と再実行拒否を返し、ネイティブ処理を再試行しない。結果の子一覧は複製して返し、受取側の編集で保持結果を変えない。結果だけで通常操作の再開を許可しない。

合成NTFSで複数子と空の親の片付け、同名後発物・別実行・元ZIP/現在/退避データ役のファイルの保全、作成と片付けの並行受付を確認する。故障模型で先頭・中間・末尾の子の確認/削除/Close/不在確認の失敗、親確認不能による停止、作成途中の識別失敗、非空・親の削除/Close/不在確認/親階層解放の失敗と複数解放未確認を確認する。実OS故障・電源断は再現しておらず、ZIP展開・復元経路・画面には接続しない。

## 復元元ZIPの読取保持（#634、2026-11-21）

ZIPの検証から展開完了まで、選んだ元ZIPを同じ読取専用ハンドルで保持する。保持中の書換え・改名・削除を拒否できる方式を採用条件とし、必要な保持を確認できなければ検証・展開を開始しない。途中で閉じて同じパスを開き直すことで、同じ入力だと判断しない。

専用領域へZIP一式をコピーしてから処理する方式は、初回に採用しない。ZIP1個分の追加容量・コピー時間・コピー後の片付けを増やさないためである。一方、処理中は他アプリからの元ZIPの変更を制限し、既存のアクセスと両立しない場合は開始できない。保持に失敗しても、コピーや弱い共有条件へ自動で切り替えない。

元ZIPは読取対象だけとし、書換え・修復・削除の対象にしない。準備物の失敗・取消時にも元ZIPを片付け対象へ含めない。保持できたこととZIPの形式・実量・ハッシュ/CRC検証、DB/画像の意味的検証は別であり、既存の検証や上限を省略しない。

採用方針と技術的な成立確認を区別する。[Spike #635](https://github.com/asam-masa/manga-update-manager/issues/635)で、同じハンドルからの読取、保持中の別アクセス拒否、先行する書込/削除用ハンドルとの競合、取得前後の取消・失敗・解放を合成ファイルで確認する。既存の共有条件、親階層・別名経由、取得済みハンドルやマッピング等の限界も調べ、未確認の環境へ成功を一般化しない。成立しない条件は阻害要因として記録し、未確認の方式を製品へ接続しない。

入力ZIPの受入保存場所・パス/リンクの扱い、必要な識別と解放結果の具体契約は、Spikeの結果を踏まえて製品実装前に確定する。準備先に適用するローカルNTFS・リンク拒否等の条件を、入力ZIP側の確定済み対応範囲と扱わない。この記録では製品コード・ZIP展開・退避/切替/復旧・App/UIを変更せず、ADR-0022はPendingを維持する。

2026-11-22、#635の[合成Spike](./verification/restore-source-hold-spike.md)で、選択した名前への書込・改名・削除の拒否と、同じハンドルでの読取を確認した。一方、別ハードリンク名は改名・削除でき、全別名の固定までは成立していない。先行する書込/削除用ハンドルや今回の書込マッピングでは取得を拒否したが、全環境への保証ではない。入力の対応範囲と識別/解放の契約は#637で具体化し、未確認の方式を製品へ接続しない。

#637で[初回の入力契約](./restore-source-input.md)を記録した。ローカルNTFS上の通常の絶対パスに限定し、親/対象のリンク経由と複数ハードリンクを拒否する。同じハンドルの照合、取消/失敗/解放の観測を分離し、元ZIPの変更・削除を許可しない。#639で取得、#640で読取・再確認を部品として追加し、ZIP展開・製品経路は未接続のままとする。

## 後続の確認
