# GitHub Issue運用

## 方針

作業管理にはGitHub Issuesだけを使用します。別の課題管理サービスと進行状態を重複管理しません。

Issueには、実装方法ではなく、目的と外部から確認できる完了条件を記載します。調査が必要な場合は、機能Issueへ調査を混在させず、必要に応じてSpike Issueを先行させます。

## Issueの種類

| 種類 | 用途 |
| --- | --- |
| Feature | 利用者価値を追加または変更する |
| Bug | 期待結果と実際の結果が異なる問題を修正する |
| Spike | 技術的な問いを期限付きで調査し、後続の判断材料を作る |

## Definition of Ready

次の条件を満たしたIssueへ着手します。

- 目的と解決する問題が明確である
- 外部から確認できる受け入れ条件がある
- 対象外が明確である
- 依存する作業と未決定事項が確認されている
- 一つのPRで扱えるか、独立して検証できる単位へ分割されている
- 設計判断が必要な場合、ADRまたはSpikeの要否が判断されている

## Definition of Done

次の条件を満たしたときにIssueを完了します。

- 受け入れ条件を満たしている
- 必要なテストが追加・更新されている
- 必須の静的解析とビルドが成功している
- 必要な手動確認を実施している
- 関連する文書とADRが更新されている
- 個人データ、秘密情報、不要な生成物が含まれていない
- 既知の制約と後続作業がIssueまたはPRへ記録されている
- PRのレビューが完了し、`main`へマージされている

## Spikeの終了条件

Spikeは実装の完成ではなく、問いに答えて後続の判断が可能になった時点で完了します。調査結果、確認できなかった事項、検証コードの扱い、推奨案をIssueへ記録します。
