# PR・レビュー運用

## PRの原則

- 一つのPRでは一つの目的を扱う
- 背景、変更内容、確認結果、対象外、既知の制約を記載する
- 大きな変更は、独立して検証できる単位へ分割する
- PRが大きくなった場合は、分割しない理由を記載する
- 設計上の重要な判断はADRへリンクする
- 自動生成物や個人データを含めない
- データ形式と外部アクセスへの影響を明示する

## レビューコメント

PR作成・更新前に`review-code-changes`でベースとheadを固定した差分を確認します。[重要変更](../quality/code-review.md#レビュー方式)では独立した敵対的レビューも実施します。コミット前と同じ対象を確認済みなら、版と範囲が一致する部分の結果を利用できますが、ブランチ全体の整合性は別途確認します。

PRのReview欄には、ベース・head・merge-baseのコミットID、確認範囲、通常・独立レビューの実施状況、指摘と対応、実施・未実施の検証を記載します。独立レビューが不要な場合は理由を記載します。本文だけの更新では、コード差分が同じことを確認して結果を流用できます。レビュー後に差分が変わった場合は変更部分と関連する前提を再確認します。

指摘には重要度と根拠を含めます。

| Prefix | 意味 |
| --- | --- |
| `[must]` | マージ前に対応が必要 |
| `[should]` | 原則として対応する。見送る場合は理由を残す |
| `[question]` | 意図や前提の確認 |
| `[suggestion]` | 任意の改善提案 |
| `[praise]` | 良い判断や実装の共有 |

## マージ条件

- 受け入れ条件を満たしている
- `[must]`がすべて解決されている
- 必須のテスト、静的解析、ビルドが成功している
- 必要な文書とADRが更新されている
- 個人データと秘密情報が含まれていない
- 未対応事項がIssueまたはPRへ記録されている

## PRの分割例

一つの機能が複数の境界へまたがる場合は、動作を独立して検証できる単位へ分割します。例えば作品登録は、モデルと入力検証、永続化、アプリケーション境界、画面、統合確認に分けられます。

行数だけを機械的な上限にはしません。変更目的が一つであり、レビュー担当者が正しさと影響を理解できることを基準にします。
