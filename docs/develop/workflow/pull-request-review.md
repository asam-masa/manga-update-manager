# PR・レビュー運用

## PRの原則

- 一つのPRでは一つの目的を扱う
- 背景、変更内容、確認結果、対象外、既知の制約を記載する
- 大きな変更は、独立して検証できる単位へ分割する
- PRが大きくなった場合は、分割しない理由を記載する
- 設計上の重要な判断はADRへリンクする
- 自動生成物や個人データを含めない
- データ形式と外部アクセスへの影響を明示する

## PR本文の構成

PR本文は`## Overview`から始め、`# Pull Request`の見出しは付けません。

PR作成・本文更新には[PRテンプレート](../../../.github/pull_request_template.md)を使用します。次の5項目を残し、該当内容がない場合は「なし」または対象外・未実施の理由を記載します。

| 項目 | 内容 |
| --- | --- |
| `Overview` | 背景、目的、概要、重要な設計判断と採用理由 |
| `Related` | GitHub Issue、PR、ADR、設計資料。作業管理はGitHub Issuesのみ |
| `AI Review` | 使用ツール、固定した対象の版、通常・独立レビュー、指摘と対応 |
| `Result` | テスト・静的解析・ビルド・手動確認のコマンド、環境、結果、未実施理由 |
| `Remarks` | 重点確認点、対象外、制約、後続作業、データ・外部アクセスへの影響、学習資料への参照 |

画面変更では必要なスクリーンショット等を、再現しにくい不具合では再現手順と修正後の結果を添えます。個人データや秘密情報を含めません。対象外の検証は理由を添え、失敗・未実施を成功としてチェックしません。

AIによるコード・文書生成だけをレビュー実施と扱いません。指摘なしは「指摘なし」、未実施は「未実施」と理由を記載します。指摘がある場合は次の表で対応を整理します。

| Prefix | Finding | Status | Response |
| --- | --- | --- | --- |
| `must` | 具体的な問題と影響 | 修正済み・未対応など | 修正と検証結果、または対応しない理由 |

この構成と以下のレビュー運用は[browser-launcherのPR運用](https://github.com/asam-masa/browser-launcher/blob/main/docs/develop/workflow/pull-request-review.md)を参考にしています。Jira・APM固有の項目は移植しません。Botの英語本文は提案として扱い、人が作成・整理する本文にはこの構成を使用します。

## レビューコメント

PR作成・更新前に`review-code-changes`でベースとheadを固定した差分を確認します。[重要変更](../quality/code-review.md#レビュー方式)では独立した敵対的レビューも実施します。コミット前と同じ対象を確認済みなら、版と範囲が一致する部分の結果を利用できますが、ブランチ全体の整合性は別途確認します。

PRの`AI Review`欄には、ベース・head・merge-baseのコミットID、確認範囲、通常・独立レビューの実施状況、指摘と対応、実施・未実施の検証を記載します。独立レビューが不要な場合は理由を記載します。本文だけの更新では、コード差分が同じことを確認して結果を流用できます。レビュー後に差分が変わった場合は変更部分と関連する前提を再確認します。

指摘には重要度と根拠を含めます。

| Prefix | 対応 | 意味 |
| --- | --- | --- |
| `must:` | 必須 | 正しさ・安全性・要件などの重大な問題。マージ前に解決する |
| `want:` | 原則必須 | このPRでの改善を求める。見送りには理由と合意が必要 |
| `ask:` | 回答 | 意図・仕様の確認。回答により修正が必要になる場合がある |
| `imo:` | 任意 | レビュアーの意見としての改善案 |
| `nits:` | 任意 | 表記などの軽微な指摘 |
| `info:` | 不要 | 補足や知識共有 |

新規コメントはこの形式を使い、問題・影響・可能なら改善案を添えます。`imho`は使いません。過去のレビューは書き換えません。旧`[must]`は`must:`と同じ必須指摘であり、既存スキルのコミット停止条件にも適用します。旧`[should]`・`[question]`・`[suggestion]`は新規報告ではそれぞれ`want`・`ask`・`imo`へ整理し、旧`[praise]`の知識共有は`info`で扱います。

作成者は`must`・`want`へ対応または返信し、`ask`へ回答します。修正内容・検証結果、見送りの理由と合意を残します。レビュアーは好みを必須にせず、対応後の差分を確認してから会話を解決し、未確認の内容を推測で承認しません。

## Draft PR

設計・実装途中の共有はDraftを使用します。未回答の`ask`、見送り方針が未合意の`want`が残る場合もDraftとします。必要な検証が完了し、これらが解決してから通常PRとしてレビューを依頼します。

未解決`must`または必要な独立レビューの実行不能時は、従来どおりコミットを止めて相談します。Draftはこの停止条件を解除しません。既にコミット済みの対象を共有するDraftでも、未解決指摘を隠さずマージしません。

## マージ条件

- 受け入れ条件を満たしている
- `must`がすべて解決され、`want`の対応・見送りが合意済みで、`ask`が回答済みである
- 必須のテスト、静的解析、ビルドが成功している
- 必要な文書とADRが更新されている
- 個人データと秘密情報が含まれていない
- 未対応事項がIssueまたはPRへ記録されている

## マージ後・外部設定後の文書確認

マージ後の開発再開時と、Renovate Appの導入など外部設定の完了後に、[check-documentation-consistency](../../../.agents/skills/check-documentation-consistency/SKILL.md)で関連文書をまとめて照合します。実装状況だけでなく、CI・実機確認・外部設定により以前の「未検証」「未導入」の記述が古くなっていないか確認します。

対象の版と確認範囲、根拠、未確認を記録します。ADRのPendingを一律にVerifiedへ変更せず、残る検証条件を確認します。履歴としてのContextと現在の状態を区別します。

反映漏れは別の小さなIssue・PRで修正し、mainへ直接書き込みません。この確認は、上記のマージ条件やIssueのDefinition of Doneを緩めません。今回の変更に必要な仕様・判断の記録は、コミット前・PR前に確認します。Git hookや自動修正は導入しません。

理由と検証方法は[ADR-0012](../../adr/0012-check-documentation-after-merge.md)を参照してください。

## PRの分割例

一つの機能が複数の境界へまたがる場合は、動作を独立して検証できる単位へ分割します。例えば作品登録は、モデルと入力検証、永続化、アプリケーション境界、画面、統合確認に分けられます。

原則として、各PRを単独で安全にmainへ入れられる単位へ分けます。テスト、基盤、振る舞い、呼び出し元、不要な旧実装の削除の順を検討します。単独で成立しない場合だけ短命な統合作業ブランチを使い、最終PRに関連PR、追加差分、統合後検証を記載します。マージは引き続き利用者の明示依頼時だけ行います。

| 指標 | 推奨 | 分割を強く検討 |
| --- | ---: | ---: |
| 追加＋削除行数 | 200行以内 | 400行超 |
| 変更ファイル数 | 10ファイル以内 | 20ファイル超 |

生成物・lockfile・スナップショットを除いた実質的な対象で数えます。機械的な上限ではありません。分割するとかえって理解しにくい変更は、その理由とレビュー方法を`Remarks`に記載します。

## レビュー依頼前のセルフチェック

- [ ] 一つの関心事とIssueの受け入れ条件に閉じている
- [ ] 差分全体を確認し、必要なテスト・静的解析・ビルド・手動確認が成功している
- [ ] 不要なデバッグコード・整形・生成物・個人データ・秘密情報が含まれない
- [ ] 安全性・データ・外部アクセスへの影響を確認した
- [ ] 文書・設定・ADRを必要に応じて更新した
- [ ] 必要な独立レビューと、指摘への対応・回答・合意を記録した
- [ ] PR本文が5項目テンプレートに沿っている
