# ブランチ戦略

## 方針

GitHub Flowを採用し、`main`と短命な作業ブランチで運用します。

作業の状態と受け入れ条件はGitHub Issuesで管理します。別の課題管理サービスへ同じ情報を重複登録しません。

- `main`は常にビルド・テスト可能な状態を保つ
- 作業ブランチは最新の`main`から作る
- 一つのブランチでは一つの関心事を扱う
- `main`への変更は原則としてPRを経由する
- レビューと必要な検証が完了してからマージする
- 原則としてSquash and mergeを使用する

## マージ方式

一つのPRでは、一つの論理的な変更を完了させます。この単位を`main`の一つのコミットとして残すため、Squash and mergeを原則とします。途中の試行錯誤やレビュー対応を`main`へ残さず、Issue、PR、ADRから変更の目的と判断を確認できる状態にします。

変更が大きい場合は、マージ方式を変える前に、独立して検証できるPRへ分割します。AIが生成した変更も同じ基準で扱います。複数の機能、無関係なリファクタリング、基盤変更を一つのPRへまとめたままSquashしません。

個別コミットを`main`へ残したい場合も、最初にPRを分割できないか検討します。次の条件をすべて満たし、分割が適切でない場合に限り、Rebase and mergeを検討します。

- 各コミットが一つの論理的な変更になっている
- 各コミットが単独でビルドとテストに成功する
- 調査、`revert`、`cherry-pick`などで個別コミットを残す具体的な価値がある
- PRに例外とする理由を記載している

Merge Commitは使用しません。`main`の線形履歴を維持する方針と両立せず、短命な作業ブランチを使う現在の規模では、追加のマージコミットを残す利点が小さいためです。

次の状況が生じた場合は、この方針を見直します。

- 複数人が一つのPRを共同で開発することが増えた
- 長期間維持する作業ブランチが必要になった
- 個別コミットを使った原因調査や部分的な取り消しが継続的に必要になった
- 一つのPRへ複数の論理的変更を含めることを避けられなくなった

## ブランチ名

```text
<type>/<issue-number>-<short-description>
```

| type | 用途 | 例 |
| --- | --- | --- |
| `feature` | 機能追加 | `feature/12-manga-registration` |
| `fix` | 不具合修正 | `fix/18-schedule-calculation` |
| `refactor` | 外部仕様を変えない改善 | `refactor/21-storage-boundary` |
| `docs` | 文書のみ | `docs/5-adr-policy` |
| `chore` | 開発環境や保守 | `chore/7-ci-setup` |

Issueがない軽微な作業では番号を省略できます。説明部分には小文字の英数字とハイフンを使用します。
