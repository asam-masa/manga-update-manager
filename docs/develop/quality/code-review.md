# コードレビュー観点

次の順序で確認します。

1. Issueの目的と受け入れ条件を満たすか
2. 責務と依存関係が妥当か
3. 正しく安全に動作するか
4. 重要な振る舞いがテストされているか
5. 読みやすく保守できるか

## 確認事項

- 正常系、主要な異常系、境界値が考慮されている
- UI、ドメイン、永続化、外部通信の責務が混在していない
- 将来の可能性だけを理由に抽象化を増やしていない
- エラーを握りつぶさず、利用者が次の行動を判断できる
- 時刻、ファイル、データベース、外部通信をテストで制御できる
- URL、パス、外部入力を検証している
- Cookie、認証情報、閲覧履歴をログやリポジトリへ出していない
- 自動取得が利用規約と安全設計に従っている
- 新しい依存関係の必要性、保守状況、ライセンスが説明されている
- 変更に伴う文書とADRが更新されている

## レビュー方式

通常の差分レビューは[review-code-changes](../../../.agents/skills/review-code-changes/SKILL.md)を使用します。コミット前はステージ済み差分、PR前は固定したmerge-baseからheadまでを確認します。対象の版、指摘と対応、実施・未実施の検証を記録します。

次の重要変更では、通常レビューに加えて[run-adversarial-review](../../../.agents/skills/run-adversarial-review/SKILL.md)による独立レビューを実施します。

- SQLiteの構造変更・マイグレーション、データ削除・復旧・バックアップ
- ファイル操作、ブラウザー起動、外部通信など、安全性に関わる境界の変更
- 非同期処理、競合、保存順序など、順序や状態によって結果が変わる変更
- 複数の層にまたがる仕様変更で、前提や影響に大きな不確実性がある変更

ファイル数だけで判断しません。文書だけの変更や、既存方式に沿った小さな変更は、上記の影響がなければ通常レビューで扱います。ただし、重要変更の制御手順や安全性・権限の規則を変更する文書は、その影響で判断します。今回のレビュー方針の導入も独立レビューの対象です。

独立担当には実装担当の結論を渡さず、固定した対象と仕様から確認させます。親は指摘の根拠と反証を検討し、指摘なしも有効な結果として扱います。実行できない場合や上限内で重大な判断が解決しない場合は、省略や自己レビューによる代用をせず相談します。

この方針の理由と制約は[ADR-0007](../../adr/0007-require-change-reviews.md)へ記録します。
