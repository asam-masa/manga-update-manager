# 画像保存・配信契約

Issue #42の段階実装の設計メモ。Issue #143で`SelectWorkCover`を接続し、#148で変更確定後の旧管理画像削除、#150で`RemoveWorkCover`を追加した。配信・起動時整理・画面操作は未実装である。以下のIssue別の「未接続」は各段階時点の履歴であり、現在の接続範囲は次節と[取り込み](./verification/cover-import-api.md)・[解除API](./verification/cover-remove-api.md)・[旧画像削除の結合検証](./verification/verified-cover-cleanup.md)を参照する。成功境界は[ADR-0013](./adr/0013-define-cover-operation-boundaries.md)、起動排他は[ADR-0014](./adr/0014-lock-storage-before-startup.md)を正本とする。

## 現在の段階実装

2026-10-18、Issue #143で選択からDB参照変更までを先に接続し、削除と配信を後続へ分ける方針を承認した。初回の`SelectWorkCover`は、作品確認、OSの選択画面、読み取り専用の元画像からのPNG生成、祖先保持、ランダムIDの予約、新規保存・照合、管理記録確定、作品参照変更の順に実行する。元画像パスはDBや結果へ保存しない。

Issue #143時点では旧画像を保持し、`cover_cleanup_deferred`を返した。#148では変更確定後に旧管理画像の未参照と実ファイルを確認して削除する。確認不能・後処理失敗は成功と`cover_cleanup_failed`に分け、確定済み参照と日時を戻さない。共有参照があれば保持し、それ自体は警告にしない。未知パス・管理記録なし・reservedは削除せず警告する。失敗した新規出力・予約を走査で削除せず、起動時整理も未実装のため、残置で容量が増える場合がある。

操作票は最終解放まで保持し、各段階終了前に停止対象エラーを通知する。保存先が安全でない場合も画像機能を停止する。画像操作中の通常終了は案内して拒否し、完了後に再度閉じる。DB停止は既存APIのエラー経路からも画像受付へ通知するが、別々のStoreと画像受付のmutexを単一の原子的な停止判定とは扱わない。Store自身が停止後のDB実行を拒否する。

DB参照Commit結果不明では`cover_outcome_unknown`で再起動後の確認を案内し、成功や旧状態保持を断定しない。確定済み後のDB返却失敗は成功と`database_stopped_after_commit`、最後のフォルダー解放失敗は成功と`cover_release_unconfirmed`に分ける。生のエラー・絶対パスを利用者へ返さない。画像UI・警告表示は#43、削除・配信・整理は#42の後続で扱う。

### 参照と後処理の共通排他

Issue #145で、Applicationの`CoverOperations.LockReferences(ctx)`を同じAppの画像取り込みと作品登録へ接続する。取り込みは新規PNGの保存・照合後、管理記録をreadyへ確定する前に取得し、参照変更と最後のフォルダー解放の結果通知まで保持する。ready確定と作品参照更新の間へ整理が割り込むことを防ぐ。生成やreserved状態の新規保存は区間外であり、別作品の選択を一律に拒否しない。

作品登録も画像パスを入力として受け付けるため、同じ排他を取得してから登録処理を呼ぶ。URL起動・最終アクセス保存・一覧・表示設定は画像参照を変更せず、この排他の対象にしない。Store内のDB実行直列化は引き続き別の責務である。

排他待機はcontextキャンセルで終了できる。画像停止中に待機が解けても、次の段階開始で停止を再確認してDB確定へ進まない。画像ファイルの解放失敗だけで通常の作品登録まで止めず、DB停止はStoreが判断する。排他取得自体はSQL・削除・画像段階の開始許可を意味しない。

Issue #148の旧画像削除は同じ排他と操作票を使い、候補取得から削除・不存在確認・記録整理までを保護する。#150の解除も同じ区間を保護する。起動整理・配信は未接続であり、後続も必要な区間をこの排他へ参加させる。[参照排他の検証](./verification/cover-reference-exclusion.md)と[旧画像削除](./verification/verified-cover-cleanup.md)を参照する。

### 画像の解除

Issue #150の`RemoveWorkCover`は同作品の操作票を取り、存在確認、ローカル保存先の準備・祖先保持、共通参照排他、DB参照解除、旧画像の後処理、最終解放の順に処理する。画像選択・元画像読取・生成・新規予約保存は行わない。未設定の解除も同じ安全確認を行い、必要なら空のcoversを作成するが、作品の日時は変更しない。安全でない保存先ではDB解除へ進まず画像機能を停止する。

結果は更新後作品と警告配列であり、`cancelled`は含めない。確定前の通常失敗は`cover_remove_failed`、結果不明は`cover_outcome_unknown`、確定後の後処理・解放失敗は成功と既存の警告コードを返す。確認ダイアログ・Undoはなく、元画像から再設定する。画面操作は#43で実装する。

### 旧管理画像の削除と記録整理

旧パスは削除許可ではない。固定形式`covers/<小文字16進32文字>.png`に限り、`UnusedManagedCover`が正常なready記録と全作品から未参照であることを確認する。`DeleteVerifiedCover`はローカルの祖先とcoversを保持し、共有なし・リンクを追わない読取/DELETEハンドルで開く。通常ファイル・単一リンク・volume serial・128bit ID・サイズ・SHA-256が記録と一致した同じハンドルへ削除を要求する。属性や共有条件を緩めて再試行しない。

参照はWindowsの別表記を考慮し、大小文字・区切り違いの直接の管理パスを共有参照として検出する。共有参照を確認できた場合は、他の表記の有無によらず正常に保持する。それ以外で認識できない非空パスが他作品に残る場合は、別名で同じファイルを指す可能性を排除できないため、その回の旧画像削除と記録整理を見送って警告する。短い名前・末尾ドット・ストリームなどを推測で解決せず、既存値を書き換えない。無関係に見えるlegacyパスでも削除が保留される保守的な制約がある。

Close後に固定パスの不存在を確認してから、`ForgetUnusedManagedCover`が同じ識別情報のready記録と未参照条件を再確認して1件だけ削除する。最初からファイル不存在の場合も、祖先保持下で固定ファイルの不存在を再確認する。パス不存在・アクセス拒否・削除待ちなどを成功に読み替えない。記録整理失敗では記録を保持する。別のファイルが現れた場合は削除せず、確認失敗とする。

各段階前の停止確認と終了前のエラー通知を維持する。結果不明・確定後DB停止では旧画像の後処理を始めない。削除後に停止した場合も新たなDB段階へ進まず記録を残す。後処理の解放確認不能では`cover_release_unconfirmed`、DB停止では`database_stopped_after_commit`、画像受付停止での拒否では`cover_unavailable_after_commit`を追加する。警告はコードと固定文言だけで、パスや元エラーを公開しない。

## 保存順序

1. 同じ作品の操作権を確保し、作品の存在を確認する。
2. 元画像を読み取り、既存の`thumbnail.Generate`でPNGを生成する。
3. アプリ専用領域の`covers`へ別名で保存する。既存画像を上書きしない。
4. 書き込み・同期・ファイル確定の失敗を確認してからDB参照を変更する。
5. DB確定後、旧管理画像が未参照と確認できた場合だけ削除する。失敗は成功結果の警告とする。

DB確定前の失敗では旧画像と旧参照を保持する。新規未参照ファイルの後処理にも失敗した場合は残置し、次回の安全な起動時整理で再試行する。解除はDB参照を外してから同じ削除条件を確認する。元画像は変更・削除しない。電源断やストレージ自体の故障に対する完全な耐久性は保証しない。

2026-10-13、保存した新画像のファイル識別情報を取得できない場合は画像設定を失敗とし、現在の画像と参照を維持する方針を承認した。識別情報なしの画像を成功結果として作品へ結び付けない。安全性を確認できない残存ファイルは保持し、警告する。

画像の設定・変更・解除がDBへ確定した時点で、作品内容の`updatedAt`を同じDBトランザクションで更新する。キャンセル・DB確定前の失敗・すでに未設定の解除では更新しない。DB確定後の削除警告では更新済み日時を戻さない。`createdAt`、`lastAccessedAt`、漫画の更新予定は変更しない。時計が戻った場合も日時の既存規則を壊さず、保存済み`updatedAt`より前へ戻さない。

## APIの実装状況と予定

| API | 入力 | 成功結果 |
| --- | --- | --- |
| `SelectWorkCover`（#143で実装） | 作品ID | `cancelled`、`work`、`warnings` |
| `RemoveWorkCover`（#150で実装） | 作品ID | 更新後の`work`、`warnings` |
| `LoadCoverWarnings` | なし | 起動時整理の警告配列 |

`work`は既存作品DTO、`warnings`は安全な`code`と`message`の配列。選択キャンセルでは`cancelled: true`、`work: null`、空の警告配列を返し、変更と通知を行わない。成功結果に元画像のパスや内部診断を含めない。DB確定前の失敗は既存の`{code, message}`によるrejectへ変換する。

選択画面はアプリ全体で一つ。同作品の選択・取り込み・解除は完了まで拒否し、失敗・キャンセルでも処理中状態を解放する。別作品は選択画面が閉じた後なら受け付け、生成は既存処理で直列化する。画像操作UIと警告表示はIssue #43で扱う。

### Close失敗と通常終了

2026-10-17、Issue #113で次の方針を承認した。Application・UIへの接続と検証は未実施である。

- 画像ファイルや保持中フォルダーのCloseが失敗し、解放を確認できない場合は、その起動中の画像機能を停止して再起動を案内する。新たな保存・解除・整理・配信は進めない。作品一覧・登録・URLを開く既存DB機能は継続する。
- DB確定前の操作は失敗、確定後は成功と警告に分ける。確定済みの参照や更新日時を戻さない。解放失敗を、処理をキャンセルして旧状態へ戻せたことと同一視しない。
- 画像処理中に「×」などで通常の終了操作をした場合は、処理中の案内を表示して閉じない。終了要求を理由に画像処理をキャンセルせず、自動終了も予約しない。処理と後始末の完了後、利用者が再度閉じる。
- 時間切れによる強制終了や、画像処理中にDBを先に閉じることはしない。OSによる強制終了まで防止できるという保証ではない。

2026-10-17、Issue #115で処理中の範囲・停止時の収束・長時間処理の案内を次のように具体化した。排他・終了受付・エラー識別の具体実装は未決定であり、ハンドルの解放・復旧や終了制御の実装が完了したとは扱わない。

#### 終了を拒否する範囲

画像選択画面を開いている間、選択後の待機・生成・保存・DB更新・後始末が完了するまで、画像解除と起動時整理の実行中は通常終了を拒否する。DB更新だけが終わった時点で終了可能とは扱わない。

一覧表示用の画像読み取りは別扱いとする。終了時に新しい読み取りの受付を止め、開始済みの読み取りと解放を待って終了する。表示用読み取りだけを理由に毎回「処理中」として終了を拒否する方式にはしない。これは表示用読み取りだけが残る場合の終了処理であり、変更・整理などの処理中に自動終了を予約する方針ではない。

#### 画像機能停止時の進行中処理

解放確認不能のClose失敗で画像機能を停止する場合は、新規受付を止めるだけでなく、進行中の処理も安全に止められる区切りで止めて解放を試みる。通常の「×」操作を理由とするキャンセルとは区別する。

- 待機中・生成中の処理は、以降の保存・DB更新へ進めない。
- 書き込みなど実行中のOS処理は強制中断せず、戻ったところで停止する。
- DB更新中の場合は確定結果を確認する。確定済み変更を戻さず、成功と警告を分ける。結果不明時は下記の契約に従う。確定結果の具体的な確認方法は接続前に検証する。
- 停止を検知した後は新たな削除を始めず、残存ファイルを保持する。開始済み処理を巻き戻せたとは扱わず、所有・安全性が不明なファイルも削除しない。

停止判定と各処理段階の開始を競合させない具体的な排他方式、進行中の配信や選択画面の収束、解放結果の管理は、接続前に設計・検証する。

#### DB更新の結果不明

2026-10-18、Issue #125で、確定・未確定を判別できない場合の扱いを承認した。成功とも、旧参照を維持できた失敗とも断定しない。新旧画像を削除せず、変更の自動再試行や旧参照への書き戻しを行わない。その起動中の画像機能を停止し、「変更結果を確認できませんでした。再起動して状態を確認してください」と案内する。文言の具体的なUI接続は後続で行う。

既存DB機能は利用可能な範囲で継続する。DB自体の読み書きに失敗する場合まで正常動作を保証しない。停止は既存処理の強制中断や票の自動完了ではなく、安全な区切りで止め、資源解放を試みる既存方針に従う。次回起動でも、結果不明だったという理由だけで画像を削除せず、通常の管理記録・未参照・実ファイルの安全確認を必要とする。

[Commit結果の調査](./verification/cover-commit-outcome.md)は、合成DBの限定ケースと採用版ソースの確認である。再読取による自動回復方式を採用したものではない。結果不明時の保全・停止・案内の一連の処理は未接続であり、ADR-0013はPendingを維持する。

#### DB接続の安全性を確認できない場合

2026-10-18、Issue #131で停止範囲を追加承認した。DB接続の安全性を確認できない場合は、画像機能に加えて新たなDB操作も停止する。登録・最終アクセスの記録・設定保存などの書込だけでなく、一覧再取得などの新しい読取も対象とする。表示済みの一覧は残し、再起動後の状態確認を案内する。表示がDBの最新状態と一致する保証や、再起動すれば必ず復旧する保証にはしない。

画像ファイルや保持フォルダーの解放失敗だけでDBに問題がない場合は、従来どおり既存DB機能を継続する。正常な入力拒否までDB停止に広げない。Commit結果が不明であることと接続の安全性は別の判定であり、結果不明の印の有無だけでDB利用の可否を決めない。

これは停止範囲の方針であり、接続の安全性の判別・隔離・再利用の具体方式は未採用である。実行中DB処理の扱い、停止判定と次の受付の排他、終了時の解放、表示・案内は実装前に設計・検証する。既存の処理中のDB終了や強制中断を許可する変更ではない。Storage・Application・Wails/UIは未実装・未検証で、ADR-0013はPendingを維持する。

#### DB停止時の待機中・実行中処理

2026-10-18、Issue #133でDB停止時の収束方針を承認した。受付済みでもDB実行待ちの処理は開始せず、停止エラーを返す。すでにDBで実行中の処理は強制中断せず、結果と後始末を確認する。その後の別のDB操作は開始しない。確定済みの変更を戻さず、確定結果が不明なら既存の保全・停止・再起動後の確認の契約に従う。

利用者操作全体を受け付けたことは、その操作が後から行うすべてのDB処理の開始許可ではない。例えばブラウザー起動後にDB停止となった場合、ページを開いた事実を取り消したとは扱わず、最終アクセス日時を保存できなかったことを案内する。保存の自動再試行や、未保存なのに保存成功とすることはしない。

停止判定と各DB実行開始の順序を競合させないこと、待機中処理が接続取得後に検査なしで実行へ進まないこと、実行中処理の結果確認・Rollbackなど必要な後始末を新規操作と同じ停止判定で妨げないことを、実装時に検証する。後始末の成功や接続の再利用可能性は別に確認する。停止を理由とする処理中のDB終了・強制中断は行わない。

[管理記録の状態と候補取得のSpike](./verification/managed-cover-state.md)で、同じ表現を予約・保存確認済みの制約へ組み合わせ、合成の共有参照と照合する。本番の作品テーブル、競合排他、安全な領域確認、削除への統合は残る。

| 情報 | 用途 |
| --- | --- |
| アプリ生成の識別子・相対パス | 一意の管理名。作品IDや元ファイル名を使わない |
| 作成予定・保存確認済みの状態 | 名前を予約しただけの記録を削除許可に使わない |
| ファイルの識別情報 | 開いたハンドルの情報と照合し、同名の別ファイルを拒否する |
| 保存確認済みPNGのサイズ・SHA-256 | 内容が変更されたファイルを削除しない |

生成後、保存予定の新規名を記録し、衝突時は既存ファイルを触らない。新規作成・書き込み・同期・Closeと実ファイルの安全な再確認に成功した後、識別情報と内容を保存確認済みとして記録する。作品参照と`updatedAt`は、その後の同じトランザクションで確定する。参照更新に失敗しても生成画像の管理記録を残すことで、次回の未参照確認に使える。

作成予定だけ、部分書き込み、識別情報や内容の不一致、記録確定前の途中終了は削除可能と扱わない。安全に所有を確認できない残存ファイルは保持して警告する。この場合、自動整理で容量を必ず回収できるとは保証しない。実行中の後処理も、開いた実体の所有を確認できた場合だけ行う。

起動時整理は保存確認済み記録から候補を得て、全作品の参照と照合し、同じハンドルで通常ファイル・リンク数・識別情報・内容を確認して削除する。確認失敗時はファイルと記録を残す。削除成功後の記録処理に失敗した場合も警告し、次回はファイルの不存在を安全に確認して記録を再処理する。参照中の欠損ファイルは、参照も管理記録も自動解除しない。

記録がないファイルを走査で削除対象へ加えない。DBの記録取得や参照確認に失敗したら削除しない。管理記録の取得・更新、参照変更、削除候補の確認を取り込み処理と競合させない。別作品を受け付ける契約を維持しつつ、記録の整合性確認と削除の区間を保護する。具体的な排他方式は実装テストで確認する。

排他とDB初期化の後、画像操作を受け付ける前に行う。全参照の取得に失敗したら何も削除しない。管理領域内のアプリ生成ファイルで、通常ファイル・安全なリンク状態・DB未参照を確認できたものだけを処理する。名前だけで所有や安全性を証明しない。未知名・サブディレクトリ・判定不能なファイルは削除しない。整理失敗でも一覧を利用可能にし、まとめた警告を保持する。保存先全体の再帰削除は行わない。

#101の参照操作は、成功時に更新後作品と旧相対パスを返す。旧パスは削除許可ではなく、管理記録・全作品の未参照・実ファイル・排他の確認が別途必要である。既存の任意パスも自動登録せず変更・解除できる。Commit前失敗・Commit結果不明時はゼロ値作品と空パスを返す。#139のCommit成功後の返却失敗は例外で、確定した作品・旧パスと`ErrWorkCoverCommitted`を返し、成功を未確定へ戻さない。不存在作品は`ErrWorkNotFound`、不存在管理記録は`ErrManagedCoverNotFound`、reserved・破損・不正IDは`ErrInvalidManagedCover`とする。

操作時刻0と保存済み作成・更新日時の不整合は`manga.ErrTimestampInvalid`で拒否する。変更時刻はUTCへ変換し、保存済み更新日時より戻さない。未設定の解除と同一参照の再設定は日時も変更しない。`createdAt`・`lastAccessedAt`・その他の作品項目は保持する。このStorage操作は実ファイルの検証や操作排他を代替せず、まだApplicationから呼び出していない。

Storageの`ManagedCoverInfo`はuint64のvolume serial、APIの順序を保つ16 byte file ID、正のint64サイズ、32 byteのSHA-256を持つ。DBでは既存の小文字16進・INTEGER・BLOBへ変換する。`ManagedCover.Info`は予約時だけnil、保存確認済みでは確認情報を返す。これらは内部の保存契約であり、Wailsへ公開するDTOではない。キャンセル・DBエラーは失敗として返し、呼び出し側は内部診断をUIへ直接出さない。

一時SQLiteで再接続と上位bitの保持、重複・二重確定・確定失敗・キャンセル・DB終了・破損情報の拒否を検証する。#101では参照変更の再接続、時計の巻き戻り、変更なし、DB失敗時の旧状態保持を検証する。未参照候補の取得、整理・ファイル操作との排他は後続に残る。
