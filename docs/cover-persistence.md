# 画像保存・配信契約

Issue #42の段階実装の設計メモ。Issue #95で管理記録テーブル、#97でStorageの予約・確定・取得処理、#101で作品参照変更を追加した。ファイル保存・削除・配信・画像APIは本番未実装であり、具体API名・型は実装予定である。成功境界は[ADR-0013](./adr/0013-define-cover-operation-boundaries.md)、起動排他は[ADR-0014](./adr/0014-lock-storage-before-startup.md)を正本とする。

## 保存順序

1. 同じ作品の操作権を確保し、作品の存在を確認する。
2. 元画像を読み取り、既存の`thumbnail.Generate`でPNGを生成する。
3. アプリ専用領域の`covers`へ別名で保存する。既存画像を上書きしない。
4. 書き込み・同期・ファイル確定の失敗を確認してからDB参照を変更する。
5. DB確定後、旧管理画像が未参照と確認できた場合だけ削除する。失敗は成功結果の警告とする。

DB確定前の失敗では旧画像と旧参照を保持する。新規未参照ファイルの後処理にも失敗した場合は残置し、次回の安全な起動時整理で再試行する。解除はDB参照を外してから同じ削除条件を確認する。元画像は変更・削除しない。電源断やストレージ自体の故障に対する完全な耐久性は保証しない。

2026-10-13、保存した新画像のファイル識別情報を取得できない場合は画像設定を失敗とし、現在の画像と参照を維持する方針を承認した。識別情報なしの画像を成功結果として作品へ結び付けない。安全性を確認できない残存ファイルは保持し、警告する。

画像の設定・変更・解除がDBへ確定した時点で、作品内容の`updatedAt`を同じDBトランザクションで更新する。キャンセル・DB確定前の失敗・すでに未設定の解除では更新しない。DB確定後の削除警告では更新済み日時を戻さない。`createdAt`、`lastAccessedAt`、漫画の更新予定は変更しない。時計が戻った場合も日時の既存規則を壊さず、保存済み`updatedAt`より前へ戻さない。

## APIの実装予定

| API | 入力 | 成功結果 |
| --- | --- | --- |
| `SelectWorkCover` | 作品ID | `cancelled`、`work`、`warnings` |
| `RemoveWorkCover` | 作品ID | 更新後の`work`、`warnings` |
| `LoadCoverWarnings` | なし | 起動時整理の警告配列 |

`work`は既存作品DTO、`warnings`は安全な`code`と`message`の配列。選択キャンセルでは`cancelled: true`、`work: null`、空の警告配列を返し、変更と通知を行わない。成功結果に元画像のパスや内部診断を含めない。DB確定前の失敗は既存の`{code, message}`によるrejectへ変換する。

選択画面はアプリ全体で一つ。同作品の選択・取り込み・解除は完了まで拒否し、失敗・キャンセルでも処理中状態を解放する。別作品は選択画面が閉じた後なら受け付け、生成は既存処理で直列化する。終了処理は開始済み操作の終了を待ち、DBを先に閉じない。画像操作UIと警告表示はIssue #43で扱う。

## ファイルと配信の安全条件

DBには管理領域内の相対パスだけを保存する。元ファイル名や画面指定のパスを管理名へ使わない。新規名の衝突時は上書きしない。既存の任意の相対パスを削除してよいアプリ生成画像と同一視しない。

管理ディレクトリと対象のreparse point・複数hard link・ディレクトリを拒否し、チェックと操作の間の付け替えも検証する。`os.Root`による領域制限だけで領域内リンクも拒否できたとは扱わない。Windowsの開いたハンドルの属性・種類・共有制御を使う具体方式は、実装テストが成立してから確定する。保存・削除・配信で同じ安全条件を守る。

Middlewareは固定接頭辞と正の作品IDからDBの現在画像を解決する。任意パスを受け取らず、GET以外、余分なパス・クエリ、エンコードされた区切り・二重エンコードを拒否する。正常な管理PNGを`image/png`、`no-store`、`nosniff`で返す。未設定・不存在・欠損・破損は画像を返さず、DB参照を自動解除しない。内部パスをHTTP応答へ含めない。

## 起動時整理

### 生成画像の管理記録

2026-10-12に、作品参照とは独立したSQLiteの管理記録を削除候補の根拠とする方式を承認した。作品が画像を外しても記録を先に消さず、削除成功またはファイル不存在を安全に確認した後に記録を処理する。未知の既存`thumbnail_path`を自動で管理記録へ登録しない。

Issue #95の`004_managed_covers.sql`で`managed_covers`を追加した。用途を画像ファイル管理に限定し、閲覧履歴や元画像パスは保存しない。列・制約は[データ仕様](./データ仕様.md#生成画像の管理記録)を参照する。#97のStorage処理はまだApplicationや実ファイルの照合から呼び出していない。

2026-10-12、従来の64bitファイルIDではなく、128bitのファイルIDとvolume serial・サイズ・SHA-256の照合を検証する方針を承認した。識別情報を取得できない場合は削除せず保持・警告する。[Windows照合Spike](./verification/cover-file-identity.md)は合成ファイルでの確認に限定する。[SQLite候補の検証](./verification/managed-cover-schema.md)は従来API用の保存表現を扱った履歴であり、本番採用前に保存表現を合わせて再検証する。

[SQLiteとWindows照合の接続Spike](./verification/cover-sqlite-identity.md)では、16文字volume serial・32文字file IDを保存表現の候補として検証する。管理記録の状態制約・作品参照・削除処理との統合や、本番方式の採用は含まない。

[管理記録の状態と候補取得のSpike](./verification/managed-cover-state.md)で、同じ表現を予約・保存確認済みの制約へ組み合わせ、合成の共有参照と照合する。本番の作品テーブル、競合排他、安全な領域確認、削除への統合は残る。

| 情報 | 用途 |
| --- | --- |
| アプリ生成の識別子・相対パス | 一意の管理名。作品IDや元ファイル名を使わない |
| 作成予定・保存確認済みの状態 | 名前を予約しただけの記録を削除許可に使わない |
| ファイルの識別情報 | 開いたハンドルの情報と照合し、同名の別ファイルを拒否する |
| 保存確認済みPNGのサイズ・SHA-256 | 内容が変更されたファイルを削除しない |

生成後、保存予定の新規名を記録し、衝突時は既存ファイルを触らない。新規作成・書き込み・同期・Closeと実ファイルの安全な再確認に成功した後、識別情報と内容を保存確認済みとして記録する。作品参照と`updatedAt`は、その後の同じトランザクションで確定する。参照更新に失敗しても生成画像の管理記録を残すことで、次回の未参照確認に使える。

作成予定だけ、部分書き込み、識別情報や内容の不一致、記録確定前の途中終了は削除可能と扱わない。安全に所有を確認できない残存ファイルは保持して警告する。この場合、自動整理で容量を必ず回収できるとは保証しない。実行中の後処理も、開いた実体の所有を確認できた場合だけ行う。

起動時整理は保存確認済み記録から候補を得て、全作品の参照と照合し、同じハンドルで通常ファイル・リンク数・識別情報・内容を確認して削除する。確認失敗時はファイルと記録を残す。削除成功後の記録処理に失敗した場合も警告し、次回はファイルの不存在を安全に確認して記録を再処理する。参照中の欠損ファイルは、参照も管理記録も自動解除しない。

記録がないファイルを走査で削除対象へ加えない。DBの記録取得や参照確認に失敗したら削除しない。管理記録の取得・更新、参照変更、削除候補の確認を取り込み処理と競合させない。別作品を受け付ける契約を維持しつつ、記録の整合性確認と削除の区間を保護する。具体的な排他方式は実装テストで確認する。

排他とDB初期化の後、画像操作を受け付ける前に行う。全参照の取得に失敗したら何も削除しない。管理領域内のアプリ生成ファイルで、通常ファイル・安全なリンク状態・DB未参照を確認できたものだけを処理する。名前だけで所有や安全性を証明しない。未知名・サブディレクトリ・判定不能なファイルは削除しない。整理失敗でも一覧を利用可能にし、まとめた警告を保持する。保存先全体の再帰削除は行わない。

## 検証計画と未決定事項

### 実装済みのStorage操作

`internal/storage/managed_covers.go`はDB記録だけを扱う。ファイルがアプリ生成画像であることや、保存・確認が完了したことをこの処理自身では証明しない。後続の呼び出し側がファイル確認を終えてから確定する。

| 操作 | 入力と結果 |
| --- | --- |
| `ReserveManagedCover` | 小文字16進32文字のIDをそのまま検証し予約する。重複は`ErrManagedCoverExists`で既存記録を保持 |
| `ConfirmManagedCover` | IDと確認情報を受け、予約かつ確認情報が全NULLの場合だけ一つのUPDATEで確定。更新件数1が必須。不存在・確定済み・破損した予約は`ErrManagedCoverNotReserved` |
| `ManagedCoverByID` | IDで取得し、状態・生成パス・NULL・確認情報を検証。不存在は`ErrManagedCoverNotFound`、不正情報は`ErrInvalidManagedCover`。失敗時はゼロ値を返し自動修復しない |
| `SetWorkCover` | 作品ID・管理ID・操作時刻を受け、正常なready記録だけを設定。作品取得・管理記録検証・参照と日時の更新を同じトランザクションで確定 |
| `RemoveWorkCover` | 作品ID・操作時刻を受け、参照と日時を同じトランザクションで更新。ファイルと管理記録は変更しない |

#101の参照操作は、成功時に更新後作品と旧相対パスを返す。旧パスは削除許可ではなく、管理記録・全作品の未参照・実ファイル・排他の確認が別途必要である。既存の任意パスも自動登録せず変更・解除できる。失敗時はゼロ値作品と空パスを返す。不存在作品は`ErrWorkNotFound`、不存在管理記録は`ErrManagedCoverNotFound`、reserved・破損・不正IDは`ErrInvalidManagedCover`とする。

操作時刻0と保存済み作成・更新日時の不整合は`manga.ErrTimestampInvalid`で拒否する。変更時刻はUTCへ変換し、保存済み更新日時より戻さない。未設定の解除と同一参照の再設定は日時も変更しない。`createdAt`・`lastAccessedAt`・その他の作品項目は保持する。このStorage操作は実ファイルの検証や操作排他を代替せず、まだApplicationから呼び出していない。

Storageの`ManagedCoverInfo`はuint64のvolume serial、APIの順序を保つ16 byte file ID、正のint64サイズ、32 byteのSHA-256を持つ。DBでは既存の小文字16進・INTEGER・BLOBへ変換する。`ManagedCover.Info`は予約時だけnil、保存確認済みでは確認情報を返す。これらは内部の保存契約であり、Wailsへ公開するDTOではない。キャンセル・DBエラーは失敗として返し、呼び出し側は内部診断をUIへ直接出さない。

一時SQLiteで再接続と上位bitの保持、重複・二重確定・確定失敗・キャンセル・DB終了・破損情報の拒否を検証する。#101では参照変更の再接続、時計の巻き戻り、変更なし、DB失敗時の旧状態保持を検証する。未参照候補の取得、整理・ファイル操作との排他は後続に残る。
