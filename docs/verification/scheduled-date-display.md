# 更新予定日の行・カード表示

Issue #278、親#265/#31。判断は[ADR-0019](../adr/0019-use-manual-japan-schedule-dates.md)、日付保存と入力は[API](../work-api.md#更新予定日のapiissue-263)と[入力検証](./scheduled-date-input.md)を参照する。

## 表示と対象外

行一覧は最終アクセスと操作の間に「更新予定日」列を追加する。カードは最終アクセスの下へ「更新予定 YYYY/MM/DD」または「更新予定 未設定」を1行追加する。小型には日付を追加しない。日付はAPIのYYYY-MM-DDを文字列整形し、時刻やUTCへ変換しない。年の先頭ゼロも維持する。

カードの画像100×134pxとタイトル2行を保ち、最小高さを164pxから191pxへ広げる。行は最小幅820px、タイトル220px・最終アクセス200px・更新予定日128px・操作72pxを確保し、URLに残り幅を使う。狭い幅では既存の横スクロールを使う。長い文字列は省略して標準titleで全文を確認できる。

表示は既存のWorkViewを読むだけで、検索・整列・ページ・共通通知・保存APIを変えない。予定順、行見出しの並べ替え、未来ON/OFFと日付見直しは親#265へ残す。予定日は過ぎても自動で消さない。

## 自動検証

work-display.test.tsでうるう日・0001/9999年を時刻変換せず整形し、null/省略/空文字を未設定と表示する。予期しない非文字列の応答は「日付を確認できません」とし、描画を壊さない。これは表示の防御であり、DBの値を補正する処理ではない。

WorkList.layouts.test.tsxで3形式の表示範囲、日付/解除・time要素の暦日・未設定の領域を確認する。App.edit.test.tsxで保存成功の日付と解除がカードへ反映されることを確認する。既存の遅い一覧応答・削除再確認・ページ保持の試験も含め、全219テストが成功した。

初回は4件失敗し、うち不正型の削除再確認応答で表示が例外になった。型を確認する表示へ修正した。他はtime要素で分かれた日付を文字列全体で検索していたため、表示の標準titleを取得する形へ直した。失敗を最終成功へ混同しない。

## 実画面

2026-10-26、Wails v2.17.0のproductionビルドを専用APPDATA/TEMPと合成4作品で起動した。うるう日、予定未設定、長いタイトル、0001/9999年を使用し、UI Automationとキャプチャでカード・行・小型を照合した。初期案の行最小幅900pxでは標準幅で操作列が外へ出たため、820pxと上記の固定列幅へ調整した。

最終版を通常終了・再起動し、文字サイズ110%の環境で幅1024pxでは行の操作列まで表示されること、600pxでは横スクロール領域があり、カードが同じ高さで日付を表示することを目視確認した。利用者の手操作でも3形式の表示範囲、予定日の変更保存と一覧反映、全空欄保存で未設定となることを確認した。確認後は合成アプリを通常終了した。普段の保存先・元画像は使用していない。
