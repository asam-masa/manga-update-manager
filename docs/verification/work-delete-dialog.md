# 作品削除の確認ダイアログと一覧反映

Issue #224、親#206。既存の削除APIをカードの削除ボタンへ接続する。標準`dialog.showModal()`で背景操作を止め、開始済み処理は継続する。新しい依存関係は追加しない。

## 契約

- 作品名とURL、完全削除で元に戻せないこと、元画像を削除しないことを表示する。初期フォーカスはキャンセル。未処理時は取消/Escで閉じ、背景クリックでは閉じない。処理中はrefでも連打・取消・Escを防ぐ。
- 開いた確認値を保持し、背景の一覧応答で自動差替えしない。対象変更をAPIが返した場合だけ一覧を再取得し、最新の確認値に更新して再度の削除操作を待つ。取得失敗は削除無効、再読込か取消を選べる。自動再送はしない。
- 不存在なら今回の削除成功とは扱わず、不存在の通知と一覧除外を行う。削除確定は一覧から外し、整理警告と成功通知をカード外に残す。検索文字は保持する。
- 結果不明・DB停止・伝達不能・不正な成功応答では追加の編集/削除を止め、再起動確認を案内する。結果後は閉じられる。確定後のDB停止警告でも削除は維持する。画像停止だけの警告をDB停止へ広げない。
- 取消では元の削除ボタン、削除等で消えた場合は検索へ戻す。次の操作へ利用者が既にフォーカスを移した場合は、遅延したフォーカス復帰で奪わない。

一覧の遅延応答は削除済み登録の識別子（IDと登録日時）で除外する。SQLiteは数値IDを再利用し得るため、同じIDの新規登録まで永久に隠さない。画像・編集・アクセスの過去の応答も登録日時が違う作品へ混ぜない。これは画面内の応答整合用であり、永続的な世代IDの導入やDB削除条件の変更ではない。

## 検証

`App.delete.test.tsx`はStrictModeと合成DTO、遅延Promiseで取消、初期フォーカス、確認5項目、処理中操作拒否、検索・警告保持、遅延一覧除外、ID再利用、対象変更と再読込失敗、不存在、結果不明・伝達不能・不正応答を確認する。jsdomのshowModal/closeは最小代替であり、背景inert・Tab移動は実WebView2で別に確認する。

全体実行中のテストで、削除後の遅延フォーカス復帰が直後の登録入力を検索欄へ奪う状態を検出した。利用者が別要素へ移動済みなら復帰しないガードを追加し、全体テストを再確認する。テスト用の不正応答の型指定も修正した。

## 実画面の確認

専用APPDATA/TEMPと合成3作品・画像のproductionアプリで、UI Automationによる確認を実施した。確認画面のスクリーンショットを読み、作品名・URL・完全削除の説明を確認した。初期フォーカスがキャンセルであること、取消で作品が残ること、再度開いて削除するとカードが消え成功通知が残ること、検索文字の保持と検索欄へのフォーカス復帰を確認した。利用者も別の合成作品でTab/Shift+Tabが確認画面内を移動し、Escで閉じて元の削除ボタンへ戻ることを手動確認し、問題なしと回答した。

同じ専用保存先の通常版を再起動し、削除済み作品が復活せず残る作品を表示できることと、通常終了を確認した。最初の再起動確認ではサンドボックス内から元のプロセスを観測できず終了済みと誤認し、二重起動の案内が出た。通常権限で元プロセスの起動継続を確認し、二重起動案内を閉じてから元アプリを通常終了し、再起動確認をやり直した。強制終了・ACL変更・普段の保存先操作はしていない。UIAの検索欄取得でもラベルを誤選択したため、編集コントロールに絞って再実行した。

削除処理中のネイティブ終了案内はAPIの自動テストとは分け、#230の[待機点付き実WebView2検証](./work-delete-close.md)で補った。対象変更・警告・結果不明は合成DTOでの自動試験であり、実画面の故障再現ではない。実OS故障・全競合順序・利用者データの試験は対象外。対象版と実行結果、通常・独立レビューはPRへ記録し、親#206の全条件の照合まではADR-0018のPendingを維持する。
