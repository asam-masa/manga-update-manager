# 作品編集のタグ欄の検証（Issue #306）

親#295、判断は[ADR-0020](../adr/0020-confirm-tags-with-work-edits.md)、契約は[画面設計](../work-screen.md#タグ編集の画面接続issue-306)。管理・AND絞り込み・削除確認画面のタグ接続は対象外。

## 自動テスト

合成API応答のDOMテストで、候補/現在タグの読込待ちと失敗、不正返却値、再取得、改名採用/削除済み解除、本文・付け外し・複数仮追加の保持を確認する。検索の幅/大小差と保存名の完全一致、Go互換の前後空白・50/51コードポイント・制御文字、文字列IDの精度、明示空選択、保存中の二重送信/取消拒否、通常失敗、IME/通常EnterとチェックのSpace操作、StrictModeの古い応答とアンマウント後の応答破棄、二つの読取の失敗順序とDB停止を扱う。

初回の全frontendテストは既存3件が失敗した。タグAPIのmock不足と、読込中に保存を押す旧テストが原因だった。候補/現在タグのmockを追加し、保存可能になるのを待つように変更した。期待結果や既存のページ補正・予定・並び順の条件は維持する。最終実行結果はPRへ記録する。

## 実WebView2（2026-10-28）

Windowsの専用AppData/TEMPと合成2作品・5候補を使用する。通常データと#292の日付またぎ確認用アプリは操作しない。ビルドはGo/Wailsの通常production版で、検証用の保存分岐を本体へ追加しない。

最初の実画面で入力部と下部ボタンが重なった。fieldset自体の高さ指定だけでは解消せず、外側のdivをスクロール領域とし、min-height: 0を指定して入力部の下へボタンを分離した。showModal後はURLへ明示フォーカスし、スクロール領域が初期フォーカスを取る挙動を避ける。DOMテスト成功だけではCSSの重なりを検出できなかった事例である。

利用者が、入力部を下へスクロールしても保存/取消が見えて重ならないこと、「ﾏﾝｶﾞ」で「マンガ」が候補に出ること、Tab/Spaceでの選択、「週末」「確認用」の複数仮追加・保存と開き直し時の保持を確認した。最後は編集をキャンセルして一覧へ戻った。

親担当が通常終了後に同じ専用保存先で再起動し、既存3タグと新規2タグの選択表示を確認した。読み取り専用のSQLite照合では候補は5件から7件となり、作品1に「連載中」「ファンタジー」「マンガ」「週末」「確認用」が関連していた。候補「マンガ」は既存IDを維持し、作品2との関連も保持した。続けて「取消確認」を仮追加してキャンセルし、候補7件・関連とも変化しないことを読み取り専用で確認した。幅640pxではサイト名と予定日の縦並び、下部ボタンの表示を画面と要素位置で確認し、1024pxへ戻した。

対象はreview tree `30ab5eb3f56050cddbfde8950a91c2882c1f1c9c` の実装部分。通常production exeのSHA-256は`B2324A18F12F2F091C5AF53466E0F2914F99F66D54D41953F79F55A2BCB6A0ED`。画像・専用セッション・fixtureはGit対象外のbuild/bin内に保持する。CIはローカルexeとは別にPRの対象SHAと結果を確認する。

改名/削除・読込故障・DB停止のUI分岐は合成APIのDOM試験であり、実OS故障の検証ではない。標準IMEの入力状態、全倍率・全解像度や管理/絞り込みを検証したものでもない。ADR-0020はPendingを維持する。
