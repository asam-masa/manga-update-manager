# 作品削除のApplicationと確定後の画像整理

Issue #227、親#223/#206。SQLite基盤#222を`WorkDeleter`へ接続する。Wails API・Appの共通作品予約と通常終了・確認UIは未接続である。スキーマ・依存関係・保存形式の変更なし。

## 手順と境界

`WorkDeleteRepository`は利用側に必要な`DeleteWork`だけを定義する。`NewWorkDeleter`へ渡すStoreと既存`CoverImporter`のリポジトリは同じDBを参照し、画像参照を書き込む他の経路と同じ`CoverOperations`を共有する。呼出側は同作品の共通操作予約とDB寿命を、削除・画像後処理・資源解放の完了まで保持する必要がある。この子IssueではAppへ接続しない。

1. 既存の`LockReferences`を取得する。画像だけのStopでもこの排他は取得できるが、画像操作段階の許可にはならない。
2. 確認情報を正規化せずStoreへ渡す。不一致・不存在・通常失敗・結果不明では画像整理へ進まない。エラーを画像受付へ通知し、DB停止は画像側にも伝える。
3. Commit成功後の解放失敗なら、削除確定作品と`database_stopped_after_commit`を返す。画像参照があれば`cover_cleanup_failed`も返し、整理を開始しない。
4. 通常の削除確定で画像参照がある場合だけ、既存の画像変更ticket・段階受付・管理ディレクトリ保護・`cleanupPrevious`へ接続する。他作品の参照、管理記録、ファイル同一性と安全性を確認し、許可できた未参照管理画像だけ整理する。画像参照がなければ整理も整理警告も不要である。
5. 画像機能が停止・終了受付済み、または起動時整理などでticketを取れなければ、確定済み削除を維持し整理未完了を警告する。停止済み画像機能を再開せず、直接ファイルを消さない。
6. ディレクトリ保護の解放結果を画像受付へ通知してからticketを返し、最後に共通参照排他を解放する。確定後の失敗を削除エラーへ戻さず、再送・復元しない。

結果は`WorkDeleteResult{Work, Warnings}`。`Work`は削除確定時だけ非nilで、警告配列は空でも非nil。確定前は原因エラーとnilの作品を返す。安全な警告コードは既存画像処理と同じ`cover_cleanup_failed`、`database_stopped_after_commit`、`cover_release_unconfirmed`、`cover_unavailable_after_commit`を用いる。利用者向け文言・APIエラーへの変換は後続Wails境界で行う。

画像整理が失敗して残った管理画像は、再起動時に既存の管理記録一覧と安全確認を通して整理する。共有・所有不明・改変済みファイルの回収は保証しない。元画像を消す処理は追加しない。

## 確認範囲と限界

- 一時SQLiteと合成PNGで、正常な管理画像整理、共有画像・管理記録の保持、所有不明・改変済みファイルの保持、元画像に見立てた未知ファイルの保持を確認する。
- 画像だけの停止でも作品は削除し整理を見送る。管理記録削除のトリガー失敗では作品を復元せず警告し、ファイルや記録の残存を分ける。これらの残存物を、再接続したDBと新しい画像受付で既存起動時整理へ渡して確認する。
- ファイル削除段階の解放エラー、ディレクトリ保護の解放エラー、未参照確認後の画像停止を合成し、警告・停止・ファイル保持を確認する。解放コールバック内で参照排他と同画像の予約が保持され、画像側の終了受付が拒否されることも確認する。
- 実Storeの不一致・不存在・取消・停止と、画像なしの削除を確認する。合成リポジトリで確定後失敗・結果不明等を返し、画像準備なし・Store呼出し1回・確認情報の維持・結果分類を確認する。実Commit障害の再現ではない。

Appの共通受付・通常終了案内、Wailsの型とエラー変換、古い一覧への反映、実WebView2は後続#223/#224の確認対象である。合成故障を実OSのClose障害・電源断・全競合順序の検証済み根拠に広げない。利用者データは使用しない。実行コマンド・固定版・通常/独立レビューはPRへ記録し、ADR-0018はPendingを維持する。
