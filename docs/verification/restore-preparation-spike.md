# 復元準備領域と片付けのSpike

#620で[親保持を借りる子出力方式と取消後処理](../restore-preparation.md#子出力方式の採用と取消後処理6202026-11-20)を採用した。以下の未採用記述はSpike時点の履歴であり、方式採用後も部品実装・故障試験・復元接続の検証完了を意味しない。

Issue #617。2026-11-20、PR #618マージコミット`a9a2df2c8851be86afee54fbae77eabffe21e025`を基準に、30分を目安として合成試験を行った。製品の復元処理や採用方式の確定ではない。

## 結果

既存部品をそのまま入れ子にする方式は共有違反になった。一方、作成済み親フォルダーの保持を続け、子ファイルだけを直接新規作成する候補では、2ファイルの展開・照合・所有確認後の削除と親の解放が成立した。

| 条件 | 観測 |
| --- | --- |
| 保持中の準備フォルダー内で既存CreateBackupTempを使う | ERROR_SHARING_VIOLATION。親フォルダーを取り直すHoldBackupDirectoryが、作成時からDELETEアクセスで保持しているハンドルと共有条件で両立しない。製品の既存バックアップ経路の不具合という意味ではない |
| 親の保持を維持し、子をCREATE_NEW・共有なしで作る候補 | 合成DB相当と画像相当の2エントリーを別ファイルへ書き込み、保持ハンドルから読んだSHA-256が目録と一致した。親フォルダーの移動は共有違反で拒否された |
| 入力ZIPを読取ハンドル・FILE_SHARE_READで保持 | 同じハンドルでValidateArchiveと展開を行った。保持中の通常の書込み・改名は共有違反で拒否され、最後の入力バイト列も不変だった |
| 正常な片付け | 子ごとに親の識別、ファイルID・ハンドルの名前・属性・リンク数を照合し、同じハンドルで削除指定→Close→不在確認した。その後の親のDiscardEmptyと全解放確認が成功した |
| 取消後・生成側失敗後の部分ファイル | 接頭辞だけを書いた状態を模型化し、元の取消contextを片付けへ渡さず削除できた。生成側失敗は失敗後の状態模型であり、ディスク故障を注入した試験ではない |
| 所有ID不一致・保持済みハンドルの終了 | 削除を拒否し、部分ファイルの内容が残った。ID不一致は比較対象のIDを変更した模型であり、実ファイルを別実体へ差し替えた試験ではない |
| 想定外の子ファイル | 所有する子だけを片付けた後、親の非空削除がERROR_DIR_NOT_EMPTYで拒否された。想定外の内容を残して保持を解放できた |
| 残置物と次の準備 | 所有確認不能の残置領域を残したまま、新しい準備領域が別名で作成された。古い領域は再利用しなかった |

各試験で、通常データと退避データを模した別のsentinelファイルが不変であることも確認した。これは実SQLite・実退避データを使った検証ではない。

## 再現と境界

```powershell
go test ./tools/spikes/restore-preparation -v -count=1
go vet ./tools/spikes/restore-preparation
```

Windows 10.0.26300、Go 1.26.5、ローカルNTFSで、3トップレベル試験（部分準備の5条件を含む）がskipなしで成功した。Go全体の試験も成功した。CreateDirectory2Wが見つからない環境は能力未確認としてskipし、成功の根拠に含めない。

コードは[合成試験](../../tools/spikes/restore-preparation/preparation_windows_test.go)だけで、製品から呼ばれない。t.TempDirの中にだけ入力と出力を作る。テスト終了後はGoの一時領域片付けにより領域全体が消えるため、「残す」は候補処理の終了時点での観測であり、アプリ異常終了後の保全を再現した意味ではない。

ZIPの目録とエントリー名は形式v1に従うが、DB/PNGの本文はsentinel bytesである。展開先はテスト内の固定leaf名を生成し、ZIP内のパスを連結しない。64 bytesという小さな試験用の読取上限を置いた。実SQLiteで開くための名前や画像フォルダー構成、移行後の管理記録、製品の上限付き展開器は未実装である。

## 未成立・未検証と後続案

- 既存CreateBackupTempの親保持を取り直さない部品が必要になる。ただし今回の直接作成候補を製品へ採用する判断はしていない。作成後の属性/名前確認失敗時の所有と候補場所、部分取得/解放失敗を返せる契約を先に具体化する。
- 入力ZIPの通常I/Oによる変更拒否は限定実測した。入力パスのリンク/特殊表記の検証、既存の書込み可能なメモリーマップ等、デバイス故障や全変更経路は未確認である。目録のハッシュは真正性を保証しない。
- ファイル数1万枚・合計2GiB・DB256MiB等の既存上限は変更していない。最大量や圧縮による展開増大、全入力形式を新しい出力経路で検証したわけではない。既存ZIP検証の成功だけで復元可能と判断しない。
- Close失敗・解放未確認、ファイルの削除指定失敗、実OSの容量不足、再解析ポイント/ハードリンクの競合、プロセス異常終了・電源断、警告UIは今回未実測である。非空フォルダーの拒否をこれらの故障の再現とは扱わない。
- 次は親保持を借りる子出力の作成・識別・解放を部品単位で検討し、出力所有の失敗契約と故障試験を先行する。その後に入力保持/上限付き展開、DB・画像の意味的検証、所有確認後の片付け、最後に切替への引継ぎへ分ける。

今回の候補は調査結果であり、[準備方針](../restore-preparation.md)以外の新たな採用Decisionではない。通常データの退避・切替・起動前復旧へ接続しておらず、ADR-0022のPendingを維持する。
