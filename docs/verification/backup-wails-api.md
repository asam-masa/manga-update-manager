## 選択中の終了要求で判明した問題

検証補助が保存ダイアログ中の親へ`PostMessage(WM_CLOSE)`を送ると、既存の終了案内が表示された。その案内を閉じると利用者の確認でアプリも終了した。終了判定の前後だけを記録する計測版でも再現し、`beforeClose`へ入った記録はあるが戻り値と`OnShutdown`の記録はなく、終了コードは1だった。

スタックは`MessageDialog / windows.MessageBox → Wails onFocus → Chromium.Focus → errorCallback → os.Exit(1)`。採用ソースでも`onFocus`は`Focus`を呼び、go-webview2の`errorCallback`は`os.Exit(1)`する。数値HRESULTやWebView2内部の理由は採取していない。同じ終了経路を持つ[#176の記録](./webview-focus-exit.md)とは、今回の入力が親の前面化ではなく外部終了メッセージである点が異なる。

保存ダイアログ中の親は無効で、普通の本体×クリックとこの外部メッセージは同じ条件ではない。初回に両者を同じと説明したのは不正確だった。今回、通常操作だけで終了したと判定したものではない。一方、この追加試験で失敗した事実は残し、終了防止成功や#176解決へ読み替えない。

## 承認した対策と再検証

利用者は2026-11-15に、バックアップの保存先選択中は追加案内なしで終了を拒否し、選択終了後の保存処理中は従来の終了案内を維持する方針を承認した。

#591では、バックアップの終了案内もファイル選択と同じ排他を使う。選択が先なら案内を呼ばず終了だけを拒否し、案内が先ならその表示中に後から選択を開かせない。mutexを保持したままネイティブ処理を呼ばず、終了要求で選択・保存・取消・受付停止を新たに進めない。

- 合成試験で選択中の終了要求3回に案内を出さないこと、取消後の排他解放、保存処理中の案内、案内中の選択拒否、処理完了後の通常終了判定を確認した。
- 実Wailsの修正版では、保存ダイアログ表示と親の無効状態を確認後、同じ外部終了メッセージを3回送った。3回とも終了判定はtrueを返し、プロセスと選択画面が継続した。案内ダイアログは呼ばれていない。
- 利用者が選択をキャンセルして追加案内や終了なしで確認画面へ戻り、本体×で通常終了できることを確認した。計測記録でも選択取消、終了判定false、OnShutdownの完了、終了コード0を確認した。

## 残る範囲

今回の実保存は画像なし・短時間の小規模データである。長時間処理の取消/公開競合、画像除外詳細のページ送り、資源解放未確認や実OS故障、電源断、全WebView2/OS版の振る舞いを実Wailsで網羅していない。これらは既存の合成試験と区別する。アプリ終了後の結果保持は仕様に含まれない。

製品のバックアップ画面は未接続で、復元も未実装である。#176の全フォーカス問題や画像選択中の経路は修正対象に広げていない。ADR-0022はPendingを維持する。
