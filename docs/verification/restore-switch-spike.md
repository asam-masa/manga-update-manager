# 復元時の退避・切替・復旧のSpike

Issue #381、2026-11-03。#380の保存候補調査と、その後に承認されたZIP＋版付き目録＋VACUUM INTOを前提に、30分上限で公開仕様と専用一時フォルダーの最小試験を確認した。製品の復元処理は未実装である。

その後、段階切替・起動前復旧確認・退避保持・取消境界は[追加合意](../backup-restore.md#復元と退避保持の追加合意3852026-11-03)で承認された。形式・入力上限は[形式v1](../backup-format.md)、#390/#391までの検証結果と残作業は[ADR-0022のValidation](../adr/0022-manual-backup-and-replacement-restore.md#validation)を参照する。以下の推奨・未決定は調査時点の記録であり、合意済み方針を未採用へ戻すものではない。切替・復旧の製品実装や耐障害性は未検証のままである。

## 比較と推奨案

| 切替案 | 利点 | 制約 |
| --- | --- | --- |
| DB・画像をその場で上書き | 保存先構成を変えずに済む | 途中失敗で新旧が混在し、戻す根拠が失われる。推奨しない |
| 作業領域で検証後、旧一式を退避し段階切替 | 現在のDB/画像パスを維持し、旧データを保持できる | 複数の移動は一括原子的ではない。起動前の中断検出と復旧が必要 |
| 世代フォルダーと選択ポインター | データ一式と世代を対応付けやすい | 通常保存先・パス解決・排他を含む設計変更が大きい。未採用 |

段階切替を今後の設計候補として推奨するが、採用済みではない。保存先ルートには起動排他の.instance.lockがあり、ルート全体を単純に移動してよいとは判断しない。DBとcoversの切替だけでなく、WAL等の関連物とハンドルを閉じる境界、画像配信・整理・設定要求も含む停止を先に定義する。既存のStore.Closeは接続終了と停止を行うが、そのまま通常操作へ戻す再開APIではない。

## 合成試験

`go test ./tools/spikes/restore-switch -v`で、[合成試験](../../tools/spikes/restore-switch/restore_switch_test.go)の5チェックポイントと復旧先衝突が成功した。旧/新DB相当の文字列ファイルと画像相当の文字列だけをt.TempDir内で作成し、実DBや画像デコーダーは使っていない。

- 準備済み、旧DBのみ退避、旧DB/画像退避、新DBのみ設置、新DB/画像設置という段階を作った。
- 中間段階からファイル移動で旧一式へ戻し、新出力も保持できることを確認した。最終段階では新一式と退避旧一式の双方を確認した。
- 復旧先に想定外の非空フォルダーがある場合の移動は失敗し、旧画像と想定外の内容が残った。これを消して強行する処理は追加していない。

これは同一プロセス内で明示した段階から戻す試験である。プロセス強制終了・電源断・ディスク容量不足・実SQLite/画像ハンドル・実起動排他・別ボリューム・再解析ポイントは未実測。失敗Writerや段階の打切りを実ディスク故障の再現とは扱わない。

## 実装前に必要な契約

1. ZIPを専用作業領域で検証する。絶対/親参照/リンク/重複/未知エントリーを拒否し、件数・個別/合計展開量・目録量に上限を設ける。ハッシュは真正性の保証ではない。DBのschema・版・関連、画像内容と除外記録も検証する。具体的な制限値と不正DBへの防御は未決定。
2. 通常データを置換する前に入力検証と必要領域の確保を行う。容量の事前確認だけで書込成功を保証しない。現在データの退避が失敗した場合に切替を続ける案は推奨しない。
3. 中断を識別する記録と旧/新/退避の識別子を保存し、通常のDB接続・移行・起動画像整理より前に確認する。通常操作や二重起動と競合しない排他が必要。記録とファイルの一致が不明なら自動削除・推測による成功表示をせず停止する。
4. 切替失敗後の旧データへの復旧にも失敗したら、成功や通常再開とはせず、旧/新/記録を保持して回復待ちにする。各移動と記録更新の間で中断した状態を列挙し、復旧操作自体の再中断も検証する必要がある。
5. 成功後も旧一式を直ちに消さず、退避の保持・一覧/整理・復旧導線を別途合意する。成功時は承認済みどおり終了・再起動する。切替後に旧接続や画面状態を再利用しない。

以上は後続判断のための要件候補であり、実現済みの回復保証や新たな採用Decisionではない。DBと画像の混在を通常起動で開かせないことが、移動方法だけより重要である。記録の永続化順序とファイル/ディレクトリの耐障害性は今回検証していない。

## 公開仕様と限界

[Go os.Rename](https://pkg.go.dev/os#Rename)は非Unix環境で原子的な操作を保証しない。[Windows MoveFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)も移動元/先や既存ディレクトリー等の条件がある。単一の移動やWrite-through指定から、DBと画像と復旧記録の一括コミットを保証できるとは判断しない。

試験コードだけを再現用に保存し、一時データはt.TempDirで管理する。通常保存先・OS設定・依存は変更していない。全体の安全切替と復旧が未検証なので[ADR-0022](../adr/0022-manual-backup-and-replacement-restore.md)はPendingを維持する。
