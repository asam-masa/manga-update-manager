# 復元時の退避・切替・復旧のSpike

Issue #381、2026-11-03。#380の保存候補調査と、その後に承認されたZIP＋版付き目録＋VACUUM INTOを前提に、30分上限で公開仕様と専用一時フォルダーの最小試験を確認した。製品の復元処理は未実装である。

その後、段階切替・起動前復旧確認・退避保持・取消境界は[追加合意](../backup-restore.md#復元と退避保持の追加合意3852026-11-03)で承認された。形式・入力上限は[形式v1](../backup-format.md)、#390/#391までの検証結果と残作業は[ADR-0022のValidation](../adr/0022-manual-backup-and-replacement-restore.md#validation)を参照する。以下の推奨・未決定は調査時点の記録であり、合意済み方針を未採用へ戻すものではない。切替・復旧の製品実装や耐障害性は未検証のままである。

## 比較と推奨案

| 切替案 | 利点 | 制約 |
| --- | --- | --- |
| DB・画像をその場で上書き | 保存先構成を変えずに済む | 途中失敗で新旧が混在し、戻す根拠が失われる。推奨しない |
| 作業領域で検証後、旧一式を退避し段階切替 | 現在のDB/画像パスを維持し、旧データを保持できる | 複数の移動は一括原子的ではない。起動前の中断検出と復旧が必要 |
| 世代フォルダーと選択ポインター | データ一式と世代を対応付けやすい | 通常保存先・パス解決・排他を含む設計変更が大きい。未採用 |

段階切替を今後の設計候補として推奨するが、採用済みではない。保存先ルートには起動排他の.instance.lockがあり、ルート全体を単純に移動してよいとは判断しない。DBとcoversの切替だけでなく、WAL等の関連物とハンドルを閉じる境界、画像配信・整理・設定要求も含む停止を先に定義する。既存のStore.Closeは接続終了と停止を行うが、そのまま通常操作へ戻す再開APIではない。

## 合成試験

`go test ./tools/spikes/restore-switch -v`で、[合成試験](../../tools/spikes/restore-switch/restore_switch_test.go)の5チェックポイントと復旧先衝突が成功した。旧/新DB相当の文字列ファイルと画像相当の文字列だけをt.TempDir内で作成し、実DBや画像デコーダーは使っていない。

- 準備済み、旧DBのみ退避、旧DB/画像退避、新DBのみ設置、新DB/画像設置という段階を作った。
- 中間段階からファイル移動で旧一式へ戻し、新出力も保持できることを確認した。最終段階では新一式と退避旧一式の双方を確認した。
- 復旧先に想定外の非空フォルダーがある場合の移動は失敗し、旧画像と想定外の内容が残った。これを消して強行する処理は追加していない。

これは同一プロセス内で明示した段階から戻す試験である。プロセス強制終了・電源断・ディスク容量不足・実SQLite/画像ハンドル・実起動排他・別ボリューム・再解析ポイントは未実測。失敗Writerや段階の打切りを実ディスク故障の再現とは扱わない。

## 実装前に必要な契約

1. ZIPを専用作業領域で検証する。絶対/親参照/リンク/重複/未知エントリーを拒否し、件数・個別/合計展開量・目録量に上限を設ける。ハッシュは真正性の保証ではない。DBのschema・版・関連、画像内容と除外記録も検証する。具体的な制限値と不正DBへの防御は未決定。
2. 通常データを置換する前に入力検証と必要領域の確保を行う。容量の事前確認だけで書込成功を保証しない。現在データの退避が失敗した場合に切替を続ける案は推奨しない。
3. 中断を識別する記録と旧/新/退避の識別子を保存し、通常のDB接続・移行・起動画像整理より前に確認する。通常操作や二重起動と競合しない排他が必要。記録とファイルの一致が不明なら自動削除・推測による成功表示をせず停止する。
4. 切替失敗後の旧データへの復旧にも失敗したら、成功や通常再開とはせず、旧/新/記録を保持して回復待ちにする。各移動と記録更新の間で中断した状態を列挙し、復旧操作自体の再中断も検証する必要がある。
5. 成功後も旧一式を直ちに消さず、退避の保持・一覧/整理・復旧導線を別途合意する。成功時は承認済みどおり終了・再起動する。切替後に旧接続や画面状態を再利用しない。

以上は後続判断のための要件候補であり、実現済みの回復保証や新たな採用Decisionではない。DBと画像の混在を通常起動で開かせないことが、移動方法だけより重要である。記録の永続化順序とファイル/ディレクトリの耐障害性は今回検証していない。

## 公開仕様と限界

### 画像先行の切替と復旧記録（#672）

承認済みの順序を `tools/spikes/restore-switch/recovery_records_test.go` の合成模型で確認した。事前記録の公開前後、旧DBと旧画像の退避、新画像の配置、作業DBの更新、新DB配置、完了記録の公開を順に再現する。復旧側は中断点を受け取らず、事前記録・完了記録・ファイル配置を観測する。

完了記録と実物が一致する場合は新一式を維持した。完了記録がなく旧一式を特定できる場合は、復旧操作を1回進めるたびに判断をやり直しても旧一式へ戻り、新一式は作業領域に残った。途中の記録ファイル、破損した完了記録、別の復元ID、対象の不一致、配置先の衝突では移動指示を出さなかった。

模型の識別は合成バイト列のダイジェストで表現し、作業DBの更新前後は既知の2値で表した。製品が更新後のDBハッシュを事前に知ることは前提としない。

#### Windowsの記録公開部品の組合せ

隔離したWindows一時領域で `BackupTemp` を使い、事前記録と完了記録を個別に書込み・同期・読戻しして非上書き公開した。公開後に保持ファイルの同一性を確認し、同期・解放を終えた記録を模型で読み直した。両記録とも同名での公開は衝突となり、公開済み本文と未公開の本文が残った。公開前に閉じた一時ファイルも模型では停止の根拠とした。

この試験はWindowsで記録公開部品を組み合わせた確認である。記録公開操作の途中での中断、製品の復旧経路、電源断後の耐久性の確認は残る。

#### 保持した準備ファイルの物理識別

合成の準備ファイルを保持したまま、既存のWindows非上書き移動を試験コードから呼んだ。同一ボリュームの別ディレクトリーに配置し、保持ハンドルの正規名とvolume serial・128ビットfile IDを確認した。解放後の再取得でも同じIDを観測した。元ファイルを保持したまま同じ内容の別ファイルを配置するとIDは異なった。配置先が既にある場合は移動が失敗し、双方の識別と配置先の内容を確認できた。

この試験の再取得は隔離した合成パスで行った。製品で必要な親・配置先の保護、所有権の引継ぎ、別ボリューム、複数画像やディレクトリー一式の移動、プロセス中断後の再取得は検証範囲外である。ADR-0022はPendingを維持する。

#### 作業DBの画像管理記録の更新と再読取

現行の移行SQLで合成作業DBを作り、含有画像2件の識別情報をひとつのトランザクションで更新した。書込み接続の終了後に読取専用で開き直し、更新した識別、更新対象外の除外画像の記録、作品の参照、サイズとハッシュを照合した。2件目の更新条件を不一致にした試験では、1件目を含めて更新前の状態であることを再読取で確認した。

識別値は合成値を使った。この試験は更新結果の再読取と条件不一致時のロールバックを確認したもので、実ファイルから取得した識別との接続、DBの安全な書込み取得、コミット結果不明、プロセス中断後の復旧と耐久性は未検証である。

#### 子プロセスの強制終了と別プロセスでの復旧

Windowsの隔離した一時領域で、子プロセスが事前記録を非上書き公開し、旧一式を退避して新画像だけを配置した。配置の合図を受けて親がその子プロセスを強制終了し、別のテストプロセスを起動した。復旧側は中断点を受け取らず、記録と合成ファイルの配置を照合して旧一式を通常パスへ戻した。新一式が作業領域に残ることも確認した。

合図の時点では事前記録の同期と解放、各移動が完了している。この試験ではOS操作の途中、製品の起動時排他、物理識別を用いた復旧、電源断を扱わない。

#### SQLiteコミット前後の子プロセス中断

現行移行SQLで作成したWindowsの合成作業DBで、子プロセスを二つの境界で停止した。1件目の更新後でコミット前に停止すると、独立した読取専用接続で2件とも旧識別を確認できた。2件を更新してコミットが成功を返した直後に、DB接続を閉じる前に停止すると、2件とも新識別を確認できた。

この条件ではSQLiteのコミット前後を比較できた。コミット呼出しの途中、書込み途中のOS障害、読取専用で開けない状態からの復旧手順、製品の排他、電源断は未検証である。

#### 配置したファイルの識別と作業DBの接続

Windowsの合成領域で同じ本文のファイル2件をそれぞれ非上書き公開し、配置後に照合した保持ファイルのvolume serialとfile IDを作業DBへ反映した。閉じたDBから既存の管理記録読取で識別を取り出し、その値で最終配置の2件を照合して本文を読めた。除外画像に相当する3件目の管理記録・参照は変更されなかった。配置名に同じ本文の別ファイルを置くと、DBからの識別との照合で拒否された。

同一ディレクトリー内で試験用ファイルを公開し、SQLiteは隔離された作業パスを使用した。実PNGの検証、製品の保持・所有移管、複数ディレクトリーの切替、異常終了をまたぐ物理識別の引継ぎはこの結合試験の範囲外である。

#### 物理識別を使った別プロセスでの復旧判断

Windowsの合成試験用ファイル4件のvolume serialとfile IDを事前記録へ保存し、新画像だけを配置した時点で切替子プロセスを強制終了した。別の復旧子プロセスが物理識別を照合し、旧DBと旧画像を通常パスへ戻した。新DBと新画像は作業領域に残った。同じ中断状態で、元の新画像を別名で残したまま同一内容の別ファイルを配置すると、復旧側は移動を指示せず既存ファイルを保全した。

この試験のファイル観測と移動は競合のない隔離領域に限る。製品の保持、パスの安全な再取得、複数画像を含むディレクトリー、SQLite更新結果、電源断はこの試験の範囲外である。物理識別は更新後のDB内容やコミットの成否を証明しない。

#### 完了記録・物理識別・作業DBの管理記録の照合

Windowsの合成模型で、完了記録と通常・退避パスの物理識別が一致する状態を作った。既存の読取専用DB検査で画像管理記録を読み、配置済み画像の物理識別と合成データの期待サイズ・ハッシュに照合した。管理記録が更新済みのときだけ新一式を維持する判断になった。旧識別のままの場合と、DBを同一ファイルIDのまま読取不能にした場合は、どちらも移動指示を返さず、通常パスのDBと画像および旧一式・完了記録を保全した。画像本文を読み直すのは判断後の保全確認である。

この模型は完了記録が存在する場合の追加照合であり、製品の保持・起動時の安全な再取得、コミット呼出しの途中の障害、読取不能なDBの修復は未検証である。

#### 排他下での復旧候補の再取得

Windowsの隔離領域で、既存のストレージ排他、親ディレクトリー保持、書込み・削除を共有しない読取ハンドルを組み合わせた。排他が競合している場合と、記録した物理識別と異なる同一内容のファイルに差し替えた場合は、候補を利用する処理に進まなかった。識別が一致した場合は同じハンドルで本文を読み、利用中の別ロック取得、書込み、ファイルと親ディレクトリーの改名が拒否されることを確認した。親自身へのDELETEアクセスも保持中は拒否され、解放後は取得できた。候補ファイルは解放後に改名できた。

この試験は単一候補の読取中の保持を確認する。解放から移動に至る境界の保護、複数候補を同時に保持する手順、製品の復旧やSQLiteの書込み取得は後続で扱う。

ZIP専用の内容検査と、記録本文の検査はそれぞれの呼出側に属する。公開結果不明を記録不在に読み替えず、模型では途中ファイルを観測したら停止する。記録が見つからないという模型の結果は、通常起動の許可を表さない。記録公開経路の障害試験は後続とする。

[Go os.Rename](https://pkg.go.dev/os#Rename)は非Unix環境で原子的な操作を保証しない。[Windows MoveFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)も移動元/先や既存ディレクトリー等の条件がある。単一の移動やWrite-through指定から、DBと画像と復旧記録の一括コミットを保証できるとは判断しない。

試験コードだけを再現用に保存し、一時データはt.TempDirで管理する。通常保存先・OS設定・依存は変更していない。全体の安全切替と復旧が未検証なので[ADR-0022](../adr/0022-manual-backup-and-replacement-restore.md)はPendingを維持する。
