# 更新予定順と未来表示の画面接続

Issue #290、親#265。判断は[ADR-0019](../adr/0019-use-manual-japan-schedule-dates.md)、現在の[画面契約](../work-screen.md#予定順未来条件日付見直しissue-290)、整列・時計の先行検証は#288を参照する。

## 接続と自動検証

3形式共通の選択欄へ予定順を追加し、予定順中だけ未来チェック欄を出す。検索から予定条件・全件整列を経てページを切り出す。未来切替は1ページ目、日付変更・編集は現在ページを維持し、範囲外だけ補正する。設定復元・保存は他設定と共有した要求列と項目別の世代・操作番号を使い、初期値の自動保存をしない。

追加ケースは3形式、未来OFFと他順序、見出しのフォーカス、未知値・読取失敗のONと警告、StrictModeの古い復元、共有保存列と警告、日付変化と編集中の内容・検索・現在ページ、未来へ移る編集と遅い一覧、未来だけの空表示と補正、遅い初期設定と登録ページ、隠れたURL処理の成功通知、アンマウント後の未送信要求を扱う。既存テストの新APIの初回値も補った。独立レビュー前の全241テストは成功した。

独立レビューで、行見出しから予定順へ変えた際に未来OFFで0件となると、表ごと消えてフォーカスを失うwantを受けた。回帰テストを追加して見出しがDOMから外れることを再現し、0件でも行一覧の見出しを維持する描画へ修正した。未登録時の案内は維持する。修正後は追加15ケースを含む全242テストとTypeScriptビルドが成功した。

初回の新規11ケースは5件失敗した。共有列で送信される前に保存呼出しを確認していた3件は待機を追加した。入力ラベルの「任意」を含む照合と、0件時にページ部品が存在しない前提も直した。次の対象29ケースでは1件が通知見出しを作品名と数えたため失敗し、作品見出しを区別して最終全件成功を確認した。これらの失敗を成功として扱わない。

Appの統合テストは観測した日本の日付を注入している。時計の実装自体は#288の偽時計テストで午前0時・遅延・復帰相当・巻戻し・解除を検証した。DOM試験を実スリープの確認とは扱わない。

## 実WebView2

2026-10-26、Wails v2.17.0のproductionビルドを専用APPDATA/TEMPで起動し、今日2作品・昨日・0001年・明日・9999年・未設定の合成30作品を使用した。通常保存先、実在サイト、OS時計へは触れていない。UI Automationとキャプチャで行・カード・小型、未来OFFで30件から28件への変化を確認した。標準幅1024pxでは検索・選択欄・チェック欄が同じ段に収まり、600pxではチェック欄が折り返す。

確認用プロセスだけへWebViewのデバッグ環境変数を渡したが、Go WebView2ローダーが引数を消去するため、検証用の時計差替えには使えなかった。子プロセスの引数から専用APPDATA内のWebViewデータ保存先を確認し、OS時計やレジストリを変更する代案は採らなかった。起動直後にサンドボックス内からPIDが見えなかったが、外側では同じプロセスが起動しており、終了・再起動とは判定していない。

標準selectの項目をUI AutomationのSelectionItemとして取得する操作は失敗した。画面の選択そのものの失敗とは扱わず、手操作とキー操作の確認へ分けた。利用者は3形式の未来ON/OFF・他順序での再表示、チェック欄のTab/Space、別順序から見出しへTabで移りEnterで今日優先順へ切り替える操作とフォーカス保持を確認した。同じ予定順の見出しを押して表示が変わらない点は、逆順を作らない仕様である。

未来OFFをUI Automationで明示し、画面のOffと読み取り専用SQLの0を照合してから通常終了・再起動した。再起動後も行一覧・scheduled_date・未来OFFが画面とDBで一致した。最初の再起動は終了前のチェック状態を採取していなかったため、OFFの復元試験として採用しない。比較条件を揃えた後の結果を使う。確認後は合成アプリを通常終了した。

独立レビュー修正後のproductionビルドも同じ合成保存先で開いた。登録順で「明日」を検索し、予定日見出しへフォーカスして今日優先順を選ぶと0件となるが、見出しとキーボードフォーカスが残ることをUI Automationとキャプチャで確認した。操作は実際のコントロールのValuePatternと見出しのTogglePatternを使い、固定InvokePatternの初回試行は未対応パターンで失敗したため実行結果を分けた。最後に通常終了した。
