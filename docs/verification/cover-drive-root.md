# ドライブルートからの確認と共有設定の検証

Issue #105のWindows専用Spike。[試作](../../tools/spikes/cover-file-boundaries/drive_root_windows_test.go)は本番から呼び出さない。実ドライブのルートからテスト保存先までを短時間・読取で保持し、作成・移動・リンク作成は`t.TempDir()`内に限定する。利用者画像・DB・ACL・システム設定は変更しない。

## 問いと観測

2026-10-17、Windows・Go 1.26.9・CGO無効で追加5テストと失敗条件3サブテストがskipなしで成功した。

- ドライブ文字付き絶対パスを一階層ずつ開き、ディスク上の通常ディレクトリか同じハンドルで確認した。UNC・デバイス形式・相対・親参照・末尾の区切り等は字句判定で拒否する。任意のWindows名前空間の完全なパーサーではない。
- `GENERIC_READ`、`FILE_SHARE_READ | FILE_SHARE_WRITE`（削除共有なし）の候補では、テスト用の各階層の移動を拒否した。解放後には同じ移動・復元が成功した。
- 保持中でも二つ目の同方式の取得、ディレクトリ列挙、合成の子ファイルの読み書きが成功した。共有なしの祖先保持は行わない。テスト外の全アプリとの互換性を保証しない。
- symlinkと通常ファイルを途中階層として指定した場合、属性検証で拒否した。不在も失敗し、いずれも部分ハンドルを返さず、一時領域の移動が成功した。リンク先の合成内容と件数は不変だった。
- 既にDELETE権限のハンドルがある場合は共有違反で取得に失敗し、共有設定を緩めて続行しなかった。
- ドライブ種別は固定・リムーバブル・RAMを候補とし、それ以外を拒否する述語を検証した。実測は今回の一時保存先だけであり、実ネットワークや各種ドライブでの動作検証ではない。

## 失敗から分かったこと

最初は`FILE_READ_ATTRIBUTES`だけで削除共有を外したが、移動拒否の期待が成立せず、既存DELETEハンドルとの競合も拒否しなかった。通常の読取権限を要求する候補へ変更すると必須条件が成立した。

属性専用候補を独立した観測テストへ分離すると、後の実行では親の移動が拒否された。両観測の差の原因は未確定である。そのため属性専用候補のPASSは保護の保証に使わず、移動成功・所定の拒否のいずれも記録する。公式仕様も属性アクセスが共有フラグの影響を受けないことを示しており、属性取得と共有による移動防止を同一視しない。

```powershell
$env:GOTOOLCHAIN='go1.26.9'
$env:CGO_ENABLED='0'
go test ./tools/spikes/cover-file-boundaries -run TestDrive -v
go test ./...
go vet ./...
go build ./...
```

## 限界と後続

これは本番方式の採用Decisionではない。ドライブ文字の再割当・SUBST等の別名、確認途中のreparse属性変更、別プロセスの攻撃、junction・全reparse tag、別ファイルシステム、実ネットワーク、アクセス不足、Close失敗・途中終了は未検証。ドライブ種別だけで実体の全条件を証明しない。通常読取を要求すると、属性だけ取得できる保存先も非対応になり得る。

実際の保存先フォルダーの作成、PNG保存、管理記録と削除、DB・配信との競合、終了待ちは接続していない。既存の起動排他は変更しない。画像処理中だけ保持するという承認済みの寿命も、本番ではまだ実装していない。ADR-0013と親Issue #42はPendingを維持する。
