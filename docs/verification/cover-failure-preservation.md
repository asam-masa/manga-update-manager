# 生成・保存失敗時の取り込み全体の保全

Issue #192、親#42。[最終照合](./cover-validation-audit.md)で不足した、部品の生成/書込失敗からApplicationの保全までの接続を検証する。[保存契約](../cover-persistence.md)は変更しない。

## 検証方法

`TestCoverFailurePreservesExistingDataAndUnverifiedOutput`は、一時SQLiteと実PNGを使って最初に管理画像を設定する。その後、実ファイルの元画像を選択する取り込みへ、次の4条件をそれぞれ通常と解放失敗併発に分けて与える（計8ケース）。

| 条件 | 注入する境界と残置 |
| --- | --- |
| 生成失敗 | 合成元ファイルを非画像にし、本番のOpenCoverSourceとthumbnail.Generateへ渡す。保存準備・予約・書込へ進まない |
| 通常の書込失敗 | 本番の管理ID予約後、Applicationのwrite境界が合成エラーを返す。予約だけが残る |
| 容量不足相当 | 同境界でCREATE_NEWした出力へ生成PNGの半分を書き、ハンドルを閉じてsyscall.ENOSPCを返す。reserved記録と部分出力が残る |
| 同期失敗 | 同境界で生成PNG全体を書き、ハンドルを閉じて合成の同期失敗を返す。確認情報を持たないreserved記録と全出力が残る |

保存失敗の注入はApplicationの既存write関数だけをテスト内で差し替える。WriteNewCover内部の実OS書込/Sync故障を発生させたものではない。実際の部品の伝播は、`internal/platform/cover_file_windows_test.go`の`TestCoverWriteFailures`で短い書込、書込失敗、ENOSPC、同期失敗をwriteAndSyncCoverに注入して確認する。WriteNewCoverが部品のエラーで成功確認情報を返さないことは、実装の早期returnと既存保存/再取得テストも合わせて確認する。部品試験と上位境界注入を、一回の実OS障害試験として扱わない。

併発条件では、生成失敗時の元画像Close、保存失敗時の保持フォルダーCloseで、実際のCloseを試した後に合成の解放失敗を返す。元の生成/保存原因とErrCoverReleaseの両方が残り、画像受付だけが停止する。通常の生成/保存エラーだけなら受付は停止しないことを、新しい操作票の受付と完了で確認する。失敗操作を自動再試行する試験ではない。

## 確認する結果

- 失敗で作品DTO相当の成功結果を返さず、取消や確定後警告にも変換しない。元原因と併発した解放失敗を保持する。
- RepositoryのConfirmManagedCover・SetWorkCoverと、旧画像のdelete呼出しが0件である。生成失敗ではprepare・writeも0件、保存失敗では各1件である。
- 作品全項目、旧画像バイト列、元ファイルバイト列、旧ready管理記録を保持する。保存失敗で新しくできる記録はreserved・確認情報なしに限る。
- 同じDBを閉じて再接続し、新しい受付で本番Cleanupを実行する。参照中旧画像・作品全項目・元ファイル・管理記録を保持し、reservedがあればcover_cleanup_unverifiedを返す。
- 予約のみのケースでは出力を勝手に生成せず、部分出力と未確認の全出力ではバイト列を保持する。ファイルの見た目や今回の名前だけで安全に削除できると推測しない。

独立レビューの任意改善に対応し、サイト名・メモ・最終アクセス日時を非空にしてから旧画像を設定する。空値同士の比較だけでこれらの情報保持を確認したとは扱わない。

## 実行結果（2026-10-21）

Windows、Go 1.26.5、CGO_ENABLED=0、Node 24.18.0、Wails CLI v2.16.0。対象8ケースと書込部品テストの10回反復、Go全体テスト・vet・ビルド、画面89テスト、TypeScript/Viteビルド、Wails productionビルドを確認する。反復検証は全競合順序や実故障の証明ではない。最終の対象版・実行結果・CIはPRへ記録する。

## 範囲と残る検証

テストは実SQLite・実ファイルと合成のエラーを組み合わせる。同期失敗は保存境界から返るエラーを合成したもので、実OSのSync故障や本物のディスク満杯、電源断の再現ではない。Closeも合成失敗を加えており、実ハンドルが解放されなかったことの実証ではない。

今回は同じテストプロセス内でStoreを閉じて再接続する。画像処理途中で子プロセスを終了する#193、破損画像の実WebView2確認#194は別である。API/UIは変更せず、故障の実画面試験も追加しない。ADR-0013はPendingを維持する。
