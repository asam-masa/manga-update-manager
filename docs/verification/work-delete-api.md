# 作品削除APIと共通受付・通常終了

Issue #223。先行#227のApplicationをWailsの`DeleteWork`へ接続する。確認画面・検索・古い一覧応答への反映は#224であり、利用者向け削除UIは未実装である。スキーマ・依存関係変更なし。

## API契約

入力はIDと`DeleteWorkInput`（URL・タイトル・サイト名・メモ・画像参照先）の確認時の文字列で、正規化しない。成功は`DeleteWorkResult{workID,warnings}`。`warnings`は通常成功なら`[]`、日時や削除前の作品全体は返さない。内部診断・元画像の絶対パス・ファイル識別情報も返さない。警告があっても削除確定を取り消さない。

| 状態 | APIの結果 |
| --- | --- |
| 対象変更 | `work_changed`。削除せず、最新情報での再確認を案内 |
| 不存在 | 既存`work_not_found`。今回の削除成功ではない |
| Commit結果不明 | `work_delete_outcome_unknown`。自動再試行しない。DB停止と再起動後の確認を案内 |
| その他のDB停止 | `database_stopped`。対象変更や不存在を併せ持っても停止を優先 |
| 同作品で処理中 | `work_busy`。先行操作の完了を案内 |
| 終了受付済み・DB初期化前/終了後 | `database_unavailable` |
| 通常失敗 | 既存の安全な`workAPIError`で変換 |
| 確定後の画像整理/解放失敗 | `workID`付き成功と警告。`cover_cleanup_failed`、`database_stopped_after_commit`、`cover_release_unconfirmed`、`cover_unavailable_after_commit`ごとに、削除済みと次の行動を案内 |

フロントエンドの安全なエラー復元へ新規コードを追加し、結果不明をDB停止として判定する。Wails v2.16.0から入力・結果モデルとAPIバインディングを生成する。確認UIによる結果反映や再確認はまだ接続しない。

## 受付と終了

Appは同じStoreと画像受付を共有する`WorkDeleter`を起動時に生成し、終了時に解除する。DB寿命のRLock内で`BeginDelete`を取得し、Applicationの後処理・資源解放と結果変換が終わるまで保持する。同作品のURL起動・画像・編集・削除を拒否し、別作品は既存DB/画像/参照排他の範囲で利用できる。

`BeginDelete`と通常終了確定は共通mutexで順序付ける。削除が残る場合、既存画像終了判断や未開始の起動時整理取消より前に拒否する。Appのロックを外してから「作品を削除中です」と案内する。削除確定後も後処理が終わるまでは拒否し、結果後は整理失敗や結果不明でも再度閉じられる。拒否を後で自動終了する予約にはしない。待機にAppや受付のmutexを保持しない。

## 検証範囲と限界

- 一時SQLiteでAPI経由の削除・完全一致拒否・不存在・再接続後の保持、画像だけ停止時の警告付き削除、初期化前/終了後の利用不能を確認する。
- 合成リポジトリで対象変更・DB停止・結果不明・確定後解放失敗・通常失敗を返し、安全なコードと警告、内部診断非表示、呼出し1回、予約解放を確認する。実Commit障害はStore層の試験と区別する。
- 実Store削除の後、画像未参照確認の境界に待機を置き、作品が消えた後も同作品の5種の操作と通常終了を拒否し、別作品の編集は継続することを確認する。解除後の警告付き完了・再要求終了・終了受付後拒否も確認する。実ファイル削除待機の再現ではない。
- 開始済み削除がある場合、終了拒否が未開始の起動時整理を取消さないことを確認する。共通受付の削除と終了の競合を100回順序付けし、両方を受け付けないことを確認する。
- TypeScriptでWailsのError包装後も対象変更と結果不明を復元し、結果不明だけをDB停止にすることを確認する。

実WebView2の削除/終了案内、確認ダイアログ・フォーカス、全競合順序、物理障害・電源断、実利用者データは未検証。削除UIの接続と実画面確認は#224へ残し、ADR-0018はPendingを維持する。
