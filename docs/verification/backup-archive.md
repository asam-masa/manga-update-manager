# バックアップZIPの限定読込

Issue #391。`internal/backup.ValidateArchive(io.ReaderAt, size)`は[形式v1](../backup-format.md)に従いZIPの構造と本文を検証する。ファイルは作成せず、SQLite接続や画像のデコードも行わない。ADR-0022はPendingを維持する。

## 入出力と失敗

呼び出し側が入力の所有・Close・正しいサイズの取得を担当し、関数実行中は入力を変更しない。指定範囲をSectionReaderで限定する。全件が成功した場合だけ目録を返す。失敗時はゼロ値を返し、`errors.Is(err, ErrArchive)`で識別できる。目録不正は`ErrManifest`、下位の読込・CRCエラーも原因として保持する。API/UI向けの文言は未実装である。

## 確認した条件

- 本文の展開前にZIP32/ZIP64の終端記録・中央ディレクトリーの宣言量と実件数を確認する。過大な件数による標準ライブラリの先行割当てを防ぎ、メタ情報は64MiBまでとする。
- 単一ボリュームだけを扱い、未知名・親参照・絶対パス・バックスラッシュ・ディレクトリー・リンク等の非通常ファイル・暗号化・未知圧縮・重複・欠落を拒否する。
- ローカルヘッダーと中央ディレクトリーの名前・圧縮方式・フラグの一致を確認する。
- 目録と含有ファイルの対応、宣言サイズの個別上限と合計を確認する。除外画像の本文を含めることは許可しない。
- 本文は32KiBのバッファーで読み、目録のサイズ+1で制限する。実サイズとSHA-256を照合し、EOFまでの読込失敗も成功扱いしない。目録も上限付きで読み、標準ライブラリが実サイズを照合する。CRCは目録・本文とも独立して計算し、格納値が0の場合も照合を省略しない。

`go test ./internal/backup`でStore/Deflate、画像なし・除外記録、ZIP64、切断・改変・未知パス・非通常ファイル・重複・欠落・目録不正・ハッシュ不一致・サイズ不一致・偽の件数・巨大なZIP64値を検証する。サイズ宣言より大きく展開される入力の拒否と、2MiBの本文を一括で読まないことも合成データで確認する。

独立レビューの指摘2件は修正前に回帰試験で再現した。data descriptorなし・格納CRCが0の目録/DB/画像を誤って受け入れる問題は独立CRC照合で拒否し、中央ディレクトリーが65535バイトのZIP32を誤って拒否する問題はZIP64 locator不在時のZIP32継続で解消した。

2GiBの実データや1万枚の画像のZIPを生成した運用試験ではない。目録の合計・個別上限の等値/1超過は#390の試験を利用し、ZIP側ではヘッダーと目録のサイズ一致、実読込量の一致を検証する。中央ディレクトリー64MiBの実生成試験は未実施で、超過する宣言の拒否を確認する。

正しいハッシュは真正性の証明ではない。DBの実構造・データ規則・参照整合、画像内容、除外理由の真偽、旧版移行、準備領域への保存、安全な切替・復旧・実機確認は後続であり、この関数の成功から復元可能とは判断しない。
