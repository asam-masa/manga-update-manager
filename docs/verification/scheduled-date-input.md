# 更新予定日の編集入力

Issue #264。保存/APIは#267/#263、判断は[ADR-0019](../adr/0019-use-manual-japan-schedule-dates.md)を正本とする。

## 入力の契約

既存編集のサイト名とメモの間に任意の標準日付欄を置く。日本の暦日として0001〜9999年を入力し、時刻やUTCへ変換しない。表示書式はWebView2の言語設定によるが、APIへはYYYY-MM-DD文字列を送る。空欄で保存した場合は空文字を送って解除する。

開いた時点の日付を固定し、背景の一覧応答で差し替えない。日付欄はuncontrolled inputとし、入力途中の年・月・日をReactの再描画で消さない。保存直前にフォームのreportValidityを確認し、不完全な入力の空valueを解除として送らない。APIでも実在日を検証する。取消・保存失敗では入力と保存済み値を区別し、保存成功だけを一覧状態へ反映する。

4テキストと日付を一度のEditWorkへ渡す。二重保存、IME確定Enter、保存中の閉鎖、停止・結果不明、フォーカスと通知の扱いは既存編集を維持する。日付の常時表示・予定順・未来設定は#265の範囲である。

利用者の手操作で2028/02/29の保存と再表示、変更取消、不完全な月/日の入力では保存されないこと、カレンダーでの選択、Tab/Shift+Tabで前後の項目へ移動できることを確認した。年・月・日をすべて消して保存し、編集を開き直した場合の未入力表示も確認した。`yyyy/mm/dd`は未入力の案内表示であり、保存する日付文字列ではない。

親が通常終了・同じ合成保存先で再起動し、編集画面のキャプチャで2028/02/29の保持を確認した。解除後も通常終了・再起動して未入力表示を確認した。合成DBを読み取り専用で照合し、設定時は`2028-02-29`、解除後はNULLだった。最後に確認用アプリを通常終了した。普段の保存先や元画像は使用していない。

画面キャプチャは文字サイズ110%の確認用環境で目視確認した。保存中の遅延・結果不明・DB停止はDOM/APIの自動検証と区別し、今回の実画面で故障注入したとは扱わない。実OS故障や全言語設定でのカレンダー操作は未確認である。
