# DBコピーの保持解放・再取得の限定Spike（#456）

## 結果と範囲

2026-11-06、#454に続き、データ用ハンドルを閉じて削除用に取り直す案を合成DBで検証した。属性参照用ハンドルを残したまま、削除用のREAD/DELETE・共有なしのハンドルを取得できた。属性・ID・名前・内容の再確認後の削除が成立し、入替え・元名消失・同じ長さの内容変更・他の書込ハンドル・ハードリンクでは削除しない結果を得た。製品方式への採用は行っていない。

利用者承認済みの方向で上限30分とした。初期実測は約3分34秒（01:07:25〜01:10:59 UTC）で完了し、以後は記録・レビュー・通常検証を行う。[再現コード](../../tools/spikes/backup-db-handle/reacquire_windows_test.go)はt.TempDir内の合成DBだけを扱う。既存の作業フォルダー基盤を使うが、製品Store/Application・通常データへ接続せず、ACLや権限設定も変更しない。

## 候補の順序

1. 確認・保持した専用フォルダー内にCREATE_NEWで出力を作り、READ/WRITE・同共有のハンドルを保持してVACUUM INTOを実行する。作成時のボリューム/128bit IDを維持することを確認し、完了後のバイト数・SHA-256を合成試験の基準値とする。
2. データ用ハンドルを閉じる前に、同じ名前をFILE_READ_ATTRIBUTES・READ/WRITE/DELETE共有で開き、同じIDを確認する。この属性参照は元オブジェクトの参照を維持するが、改名・削除・書込を抑止する保持ではない。
3. データ用ハンドルをCloseし、OPEN_EXISTING・GENERIC_READ | DELETE・共有なし・OPEN_REPARSE_POINTで取り直す。属性参照用ハンドルは残す。パスの同じ綴りだけを所有確認に使わない。
4. ディスク上の通常ファイル・再解析ポイントなし・リンク数1と、作成時ID・属性参照用ハンドルのID・正規化DOS名・バイト数・SHA-256を照合する。再取得や照合が成立しなければ削除指定しない。
5. 一致した場合だけ、その削除用ハンドルへFileDispositionInfoを指定する。削除用ハンドルと属性参照用ハンドルを両方Closeしてから、親を保持したまま元名の不在を確認する。最後に空の作業フォルダーを既存のDiscardEmptyで片付ける。

公開仕様は[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)のアクセス・共有条件・OPEN_EXISTINGと、[FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)の同じオブジェクトの比較を参照した。属性アクセスはデータの読取・書込・削除アクセスと共有条件が異なるため、#454で失敗したDELETE権限付き保持をそのまま残す方式とは区別する。

## 実測

`go test ./tools/spikes/backup-db-handle -run TestReacquireDBCopyForCleanup -v -count=1`が、6条件で成功した。試験の成功は下表の成立・拒否を観測したことを示す。

| 再取得前の状態 | 結果 |
| --- | --- |
| 無変更 | 同じID・名前・内容を確認。削除指定・両ハンドルClose・元名不在・空フォルダーの片付けが成功 |
| 元コピーを改名して同名の別ファイルを配置 | ID不一致で拒否。別物の内容と、改名先の元コピーのID・内容を保持 |
| 元コピーを改名し、元名を空ける | 再取得のFILE_NOT_FOUNDで拒否。改名先の元コピーのID・内容を保持 |
| 同じID・同じ長さのまま先頭1バイトを変更 | SHA-256不一致で拒否。長さだけでは成功判定しない |
| 他の書込ハンドルを開いたままにする | 共有なしの再取得がSHARING_VIOLATIONで拒否。削除指定しない |
| ハードリンクを追加 | リンク数が1ではないため拒否。子ファイルの削除や再帰削除へ切り替えない |

使用環境で作業フォルダーAPIが利用できない場合は理由付きSKIPとなる。今回は上記6条件が実行され、SKIPはなかった。試験用の残置物はt.TempDirの掃除で管理し、この掃除を製品の削除許可へ流用しない。

## 限界と後続

推奨候補は、属性参照用ハンドルを残し、削除用に取り直した後の照合を必須にする案である。ただし、実行中ずっと名前や内容が不変となる方式ではない。属性参照が外部による削除・改名・書込まで防ぐ保証にせず、確認不能な場合は自分では削除せず案内する設計が必要である。

今回の合成試験は出力を小さく制限しており、製品のDB256MiB上限の実装ではない。基準ハッシュの確定方法・完了/失敗/取消時の扱い、再解析ポイント・別名・ID再利用等の全条件、外部同時書込、Closeや削除指定の失敗・結果不明、電源断、実USB・全OSは未検証。#454のコピー後片付け未成立を更新する限定結果であり、無条件の再open・パス削除を採用した記録ではない。

採用可否と資源・結果の契約を利用者と決め、異常系を含む小さな実装へ分割する。[初回設計](../backup-restore.md)と[ADR-0022](../adr/0022-manual-backup-and-replacement-restore.md)はPendingを維持する。

2026-11-06、#458で利用者は[再取得による片付け方式](../backup-restore.md#dbコピーの再取得による片付け方式4582026-11-06)の採用と設計記録を承認した。上記の採用前判断はこの合意で更新するが、Spike時点の観測・未検証は変更しない。成功・失敗・取消の契約と故障試験をそろえるまで通常経路へ接続せず、Pendingを維持する。
