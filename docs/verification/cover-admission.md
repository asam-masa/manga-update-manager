# 画像操作の受付状態管理

Issue #117。`application.CoverOperations`は未接続の受付部品であり、ゼロ値から使える。インスタンスは使用後にコピーしない。DB・ファイル・選択画面・Wails・配信にはまだ接続していない。上位方針は[画像保存契約](../cover-persistence.md#close失敗と通常終了)と[ADR-0013](../adr/0013-define-cover-operation-boundaries.md)を参照する。

## 契約

- `BeginChange(workID, selecting)`は正の作品IDを受け、同作品の追加操作を拒否する。選択を伴う場合はアプリ内で一つの選択枠も取得する。別作品の選択を伴わない操作は妨げない。
- 成功した受付票の`SelectionDone`は自身の選択枠だけを解放する。作品枠は保存・DB更新・後始末まで保持する。別作品の次の選択は受付可能になる。
- `BeginRead`は表示読取の受付。`BeginCleanup`は起動整理用で、他の画像受付がない場合だけ成功し、完了まで新規受付を拒否する。読取・変更相互の安全なファイル操作排他を実装した意味ではない。
- 成功した元の受付票の`End`を、呼び出し側が後始末・資源解放の試行を終えてから呼ぶ。二重完了、古い票、コピーした票で別の操作権を解放しない。#119以降は段階実行中なら`ErrCoverBusy`を返し、操作権を維持する。段階を完了してから操作の`End`を再度呼ぶ。その他の完了はnilを返す。`End`はOSハンドルを閉じず、解放成功も証明しない。票のnil・ゼロ値は使用しない。
- `Stop`は新規受付と新しい段階開始を永久に拒否する。進行中の票を削除・自動完了・キャンセルしない。既存の段階完了・資源解放は引き続き行う。#123の`ObserveError`が`platform.ErrCoverRelease`の検知をこの停止へ接続する。実際の画像操作からの通知は後続で行う。
- `RequestClose`は変更・選択・起動整理が残る場合、`ErrCoverBusy`とnilを返し、終了予約や受付停止をしない。呼び出し側は案内して再操作を待つ。
- 読取だけ、または受付なしでの`RequestClose`は、全画像受付を閉じて完了通知channelを返す。開始済み読取の最後の`End`で通知し、受付なしなら即時通知する。再要求は同じ通知を返す。待機中に呼び出し側のApplication・DBロックを保持しない。実際の終了やDB Closeは行わない。

受付・停止・選択枠解放・完了・終了判定は同じmutexで更新する。mutex内でI/Oやchannel待機を行わない。停止が先なら新規受付を拒否し、受付が先なら既存票として残す。終了受付が先なら追加受付を拒否し、読取受付が先なら終了通知に含める。

## 段階開始と停止の境界

Issue #119で、変更・整理の元の受付票に`BeginStage`を追加した。同じmutexでactive所属・票の種類・停止状態・段階の重複を検査し、成功時に`CoverStage`を返す。完了済み・コピー票・表示読取は段階を開始できない。停止が先なら開始を拒否し、段階登録が先なら実行中として残す。成功は物理I/Oが既に始まった・完了したことを意味しない。

呼び出し側は開始に成功した段階だけをmutex外で実行し、結果を確認して段階票の`End`を呼ぶ。停止後も開始済み段階を強制中断・ロールバックしない。次の保存・DB更新・削除などは、別の`BeginStage`を通す。段階票の二重・古い・コピー完了は現在の段階を解放しない。nil・ゼロ値の段階票は使用しない。

同じ操作内の段階は一つだが、別作品の段階や読取を直列化する仕組みではない。生成の直列化、共有参照と削除の排他、段階名・順序の強制は行わない。解放の試行は停止後も必要であり、新規変更の段階受付とは区別する。DB確定結果の確認・成功警告の分類も呼び出し側に残る。

## 解放失敗の通知

Issue #123で`ObserveError(err)`を追加した。Applicationはplatformの公開エラー契約だけを参照し、OS操作は行わない。`errors.Is(err, platform.ErrCoverRelease)`なら`Stop`を呼ぶ。nil・通常失敗・キャンセルだけ・同じ文字列の別エラーでは停止しない。ラップ・Join・キャンセルとの併発では解放失敗を見逃さない。成功の通知で停止状態を解除しない。

通知は操作結果や元エラーを変更・消費しない。DB確定前後の成功・失敗・警告の分類、票の完了、解放試行、利用者案内は別の責務である。呼び出し側は処理と解放のエラーを集め、次段階開始や票の完了より先に通知する。停止と段階開始の順序は既存mutexで確定し、通知より先に開始済みの段階は取り消さない。この呼び出し順序が実I/Oの全経路で守られることは未検証である。

## 検証と限界

Windows・Go 1.26.9・CGO無効で、同一作品と選択枠の重複、選択解放後の別作品、古い票・二重完了・コピー票、起動整理、停止後の拒否、読取の終了待ちを検証する。goroutineを同時に解放し、読取/変更/整理と終了要求、同一作品の多重要求、停止と完了を競合させる。sleepを成立条件にしない。反復テストは全スケジュールの証明ではない。

#119では段階開始と停止・操作完了の競合、段階実行中の終了拒否、古い段階票、段階中も読取受付可能であることを反復検証する。race検出はCコンパイラーがPATHにないため未実施であり、反復成功で代替したとは扱わない。

#123では分類7ケース、停止後の全新規受付と次段階拒否、既存段階・操作・読取の保持、繰り返し通知、段階開始との競合を検証する。実OSのClose故障を起こす試験ではない。

通常終了と安全上の停止のUI接続、実処理が必ず段階受付とエラー通知を通ることの検証、共有参照と削除の排他、DB確定結果不明時の扱い、進行中の選択・配信の収束、長時間案内は未実装。画像機能全体とADR-0013はPendingである。
