# 開発モードでの本番画像操作・配信の検証

Issue #170、親 #42。2026-10-19に本番コード`9d5606424d93334e20603f47ee6ce750ab5f3131`を検証した。配信Spikeやproduction exeの結果を流用せず、Wails開発モードの本番UI・API・Middlewareを使用した。結果は部分確認であり、画像表示全体の合格判定ではない。

## 環境と手順

- Windows、Go 1.26.9、CGO_ENABLED=0、Wails CLI v2.16.0、Node.js v24.18.0、Vite v8.3.4。
- `go run github.com/wailsapp/wails/v2/cmd/wails@v2.16.0 dev -m -nosyncgomod -nogorebuild -noreload -nocolour`で起動した。自動バックエンド再ビルドとアセット変更時の再読み込みは無効にし、手動の画像操作を検証した。HMR・自動再ビルドの検証ではない。
- 子プロセスだけのAPPDATA/TEMP/TMPを分離した。確認専用領域は`D:\appdata_local_tmp\mum-dev-cover-242e37bf88c54bac8cdbbdf61c9903d2`。利用者のDB・画像は使っていない。
- 確認専用3作品に正常なグラデーションPNG、欠損参照、未設定を用意した。選択元はグラデーション120×60と青色48×48の合成PNGだけである。
- UI Automationで対象PIDのUI・OS選択ダイアログを操作し、所有ウィンドウだけをPrintWindowで撮影した。外部ブラウザーで作品URLは開いていない。
- ログはVite `localhost:5173`、Wails開発サーバー `localhost:34115`への接続を示した。固定経路`/__covers/works/3`のHTTP応答も確認した。

## 確認結果

| 対象 | 観測した結果 | 限界 |
| --- | --- | --- |
| 起動・初期表示 | 正常画像と画像操作ボタン、欠損の仮表示・案内、未設定の設定ボタンを確認 | 全配置・狭幅は未確認 |
| 設定 | OS選択で設定成功、画像配信200を確認 | 異常な元画像は未検証 |
| 別画像への変更 | HTTP画像のSHA-256が変化し、no-store/nosniffを維持 | 画面撮影は旧画像を示すケースがあり、表示切替は未解決 |
| キャンセル | 成功通知なし、現在のHTTP画像ハッシュは不変 | 全競合順序は未確認 |
| 解除 | 解除成功表示、配信404を確認 | 実削除失敗・容量不足は未検証 |
| 欠損からの回復 | 合成ファイルを同じ固定名へ戻して一覧を再読み込みし、案内の消去と画像表示を確認 | 破損・権限障害は未検証 |
| 保存状態・終了 | 通常終了と次の開発起動後の解除状態保持を確認。合成元画像のSHA-256は不変 | 別の再確認ではWebView2エラー終了も発生した |

## 未解決1: フォーカス処理での終了

同じ確認用保存先で再起動し、`SetForegroundWindow`を含む自動前面化で描画を再確認していた際、`[WebView2 Error] The parameter is incorrect.`を記録して開発アプリが終了した。

専用ログのスタックは`Frontend.onFocus → Chromium.Focus → errorCallback`を示した。採用版go-webview2 v1.0.22では`Focus`の`MoveFocus`失敗が`errorCallback`へ渡り、`os.Exit(1)`することをソースで確認した。エラーログは`focus-error-stderr.log`として確認専用領域へ保全した。

自動前面化が原因とは断定していない。通常の手動切替、起動タイミング、開発モード限定かは未確認であり、画像保存処理の失敗とも確認していない。強制前面化を外した別の再確認では画像操作と通常終了が成功したが、これだけで原因の特定や解決とは扱わない。[Issue #171](https://github.com/asam-masa/manga-update-manager/issues/171)で切り分ける。

## 未解決2: 保存・配信と撮影の不一致

変更直後の撮影には旧画像が残った。強制前面化を使わない再確認でも、青色PNGからグラデーションPNGへ変更し、合計約3秒待ってから撮影したが、撮影画像は青色を示した。

その後の通常終了後、確認専用SQLiteを`mode=ro`で開いて現在参照を読み取った。参照先の実PNGは120×60、中央RGB=120,180,120のグラデーションであった。保存が変更されなかったとは確認していない。初回のHTTP変更確認と、この再確認の終了後DB・実ファイル確認も別の観測である。

実画面を利用者が直接見た確認はまだなく、PrintWindowの古いフレームなのか、WebView2の取得・表示が古いのかは未確定である。配信内容の変更から表示の切り替わりまでを成功と断定せず、[Issue #172](https://github.com/asam-masa/manga-update-manager/issues/172)で対応させて確認する。根拠なくキャッシュ方式や保存処理を変更しない。

## 検証補助と残件

UI Automationの要素やInvokePatternを取得できない補助スクリプト失敗もあり、対象要素とInvokePatternの準備を待って再実行した。これらを本番APIの失敗と同一視しない。上記WebView2エラー終了後に残った今回のGo/Wails/Vite補助プロセスは、親子関係と名前を確認して停止した。ファイルは削除していない。通常終了した起動と、エラー終了・補助プロセス停止を混同しない。

強制前面化なしの最終起動は通常終了した。終了時の専用stderrにはNode側のEPIPEも観測したため、開発ツールの終了ログ全体が無警告だったとは扱わない。実行補助、合成DB/画像、ログ、撮影画像はGitへ追加しない。

本番コード・依存・システム設定・ACLは変更していない。停止/結果不明の実WebView2案内、長時間処理の案内、実I/O故障、全競合と自動再ビルドは未確認である。#171・#172の未解決も残るため、ADR-0013はPendingを維持する。
