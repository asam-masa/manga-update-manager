# 生成画像管理の状態遷移と整理候補の検証

Issue #89。[状態制約](./managed-cover-schema.md)と[128bit識別情報の保存・照合](./cover-sqlite-identity.md)を、[Windows専用の試作](../../tools/spikes/cover-file-boundaries/managed_state_windows_test.go)で接続する。本番マイグレーションは追加しない。

## 検証する条件

候補の`managed_covers`は生成ID・相対パス、`reserved`／`ready`、16文字volume serial・32文字file ID、サイズ、SHA-256を持つ。予約時の確認情報はすべてNULL、保存確認済みではすべて必須とする。旧桁数・埋め込みNUL・識別情報不足を拒否する。

合成ファイルの確認後、状態と確認情報を一つのUPDATEで確定する。UPDATEは予約状態だけを対象とし、更新件数が1でなければ成功と扱わない。ファイル確認失敗と、トリガーで注入したDB更新失敗では、予約状態とNULLの確認情報を維持する。

候補取得は保存確認済みの記録に限定し、合成の`work_refs`に同じ相対パスの参照が一件もないことを確認する。2作品の共有参照は両方を外すまで候補にしない。記録不存在と予約状態も候補から除外する。DB再接続後の候補は、既存の同一ハンドルによる実ファイル照合へ渡す。

## 結論の境界と次の実装

この候補取得は削除の許可ではない。実ファイルの削除要求は実装していない。`work_refs`は共有参照のモデルであり、本番の作品テーブル・トランザクション・競合排他との統合は未検証。合成ファイルはPNGではなく、生成・書込・同期・Closeの成功順序も今回の保証に含めない。

本番へ進める際は、今回の候補表現と状態制約を保存基盤の実装に用い、全作品の参照確認とファイル操作の間を排他する必要がある。安全な管理領域の確保、未確認ファイルの保持・警告、段階ごとの失敗、終了待ちを残る検証条件として扱う。Issue #42は未完了、ADR-0013はPendingを維持する。旧64bit候補の検証履歴は変更しない。
