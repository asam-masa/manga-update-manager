# タグによる作品一覧の絞り込み

Issue [#323](https://github.com/asam-masa/manga-update-manager/issues/323)、実装の親は[#297](https://github.com/asam-masa/manga-update-manager/issues/297)。2026-10-31の相談と合成サンプルで承認された設計を記録する。製品への接続は未実装であり、[ADR-0020](./adr/0020-confirm-tags-with-work-edits.md)のValidation StatusはPendingを維持する。

## 条件と候補件数

- 選択タグをすべて持つ作品を表示するAND条件とする。未選択ならタグで制限しない。選択操作で作品のタグ自体は変更しない。
- 漫画名検索・予定条件・タグ条件を全作品へ適用し、既存の並べ替え後にページ分割する。表示中のページだけを検索・集計しない。
- 候補の件数は「現在の漫画名検索・予定条件・選択済みタグに、その候補も加えた場合の作品数」。選択済み候補を重ねても条件を増やさず、現在の一致件数になる。
- 管理画面の使用作品数は全作品に対する数であり、この候補件数と混同しない。候補検索の文字は候補名だけに適用し、作品の条件や件数を変えない。
- 未使用タグや追加すると0件になるタグも表示・選択できる。0件は取得失敗とは区別し、条件を減らす案内とタグ全解除を表示する。タグ全解除では漫画名検索や予定条件を解除しない。
- 候補はタグ名の自然な昇順、同順位はタグID昇順に揃える。検索とタイトル順の既存比較を再利用し、件数の変化で候補を移動させない。
- 候補検索は既存の全半角・英字大小の違いを吸収した部分一致とする。保存名の同一性やタグ統合は変更しない。

## 配置と操作

通常幅では漫画名検索・並び順・「タグで絞り込み」を横並びにする。ボタン近くに候補のポップアップを開き、内部に候補検索とスクロール可能なチェック欄を置く。狭い幅では操作を折り返し、ポップアップを画面幅に収める。一覧を押し下げずに候補を開ける反面、開いている間は一覧の一部が隠れる。

選択済みタグは検索操作の下に解除ボタン付きで並べ、「すべて解除」を置く。多数・長い名前は折り返し、横にはみ出させない。閉じている間は候補欄の高さを取らない。候補の選択・解除は即時反映し、複数選択中も開いたままにできる。

- 開くと候補検索へフォーカスを移す。Tab／Shift+Tabで操作し、標準チェックボックスのSpaceで選択する。モーダルとしてフォーカスを閉じ込めない。
- Esc・閉じるボタンでは候補だけを閉じ、開いたボタンへ戻す。外側クリックでも閉じるが、クリック先の操作・フォーカスを奪わない。いずれも選択を保持する。
- 条件変更による再描画で、操作中のチェック欄のフォーカスを失わない。候補名検索中のIME入力を壊さない。
- 管理・作品編集等の既存ダイアログを開く場合は候補を閉じ、既存のモーダルと処理受付を維持する。

## 条件変更とページ

| 操作・変化 | 条件とページ |
| --- | --- |
| 選択・個別解除・全解除 | 即時反映し1ページ目へ戻す。検索と予定条件は維持 |
| 表示形式の切替 | タグ条件を維持し、ページは既存の形式切替方針に従う |
| 再起動 | 選択タグ・候補検索を解除。新しい永続設定は追加しない |
| 選択タグの改名 | 固定IDの条件を維持し、新しい表示名へ更新。現在ページを維持 |
| 選択タグの削除 | 削除された条件だけ外し、通知して1ページ目へ戻す。残る条件で作品が増える場合がある |
| 作品編集で一致対象が変化 | 現在ページを維持し、範囲外なら最後の有効ページへ補正 |

改名・削除は、管理APIの確定した結果または取得に成功した完全な最新情報から判断する。読込失敗・部分応答・古い遅延応答で選択条件を削除しない。削除による条件解除通知は候補を閉じても残す。既存の操作結果やDB停止警告を上書きして消さない。

登録後の対象ページへの移動、予定日の見直し等は[一覧設計](./library-design.md)の既存契約を維持する。絞り込みから外れた作品でも、開始済みの編集・画像処理・ページ起動等を取り消さず、結果通知を保持する。

## 同じ時点の情報をまとめて取得する

作品一覧・未使用を含む全タグ候補・作品とタグの対応を、一つの読取スナップショットとして取得するAPIを追加する。既存のListWorks・LoadTags・LoadWorkTagsや管理APIは互換性のため残す。既存APIを作品数分呼ぶ方式は採用しない。

Storeは一式を同じ時点の状態として読み、Applicationが利用する読取interfaceを経由してWailsへ公開する。複数SQLを使う場合も同じ読取トランザクション等で整合性を保証する。具体的な公開名・型と実現方法は取得APIの実装Issueで固定し、既存WorkDTOや識別子精度の互換性を確認する。異なる取得結果を画面で寄せ集めて一式と扱わない。

- 空の成功配列と未取得を区別し、全作品・全候補・全対応が成功・検証済みの場合だけ一式を採用する。不正ID・重複・不存在への関連等は修復や黙示除外をせず、失敗として返す。
- 作品の同一性は既存のIDと登録日時の扱いを維持する。削除後に同じ数値IDで登録された別作品へ古い関連や応答を適用しない。新しいDTOのID表現と照合は既存の[タグAPI](./tag-api.md)の精度を損なわない。
- 読取から検証・DTO変換までDBの寿命を保ち、内部診断やパスを利用者へ返さない。DB停止を通常の読込失敗へ戻さない。
- 画面は要求の世代と操作結果の反映順を管理する。新しい取得や編集・削除の確定後に、古い応答で作品・候補・条件を巻き戻さない。必要な再取得で失敗しても、確定済みの操作を未確定や通常失敗へ変えず、自動再送しない。

## 取得中・失敗時

再取得中・再取得失敗時は選択条件と前回の一覧を残し、「最新情報は未確認」と明示する。成功するまでタグの追加・個別解除・全解除を止め、再読み込みを用意する。再取得中に一部だけ新しい作品や件数へ切り替えない。前回情報を使う場合も候補件数を最新と表示しない。

初回失敗はタグなし・作品0件の正常状態として扱わず、エラーと再読み込みを表示する。選択中のタグが見つからなくても、完全な取得に成功するまでは削除と判断しない。DB停止・結果不明を観測した場合は既存の停止と警告保持を優先し、再読み込みで書込可能へ戻さない。

## 操作確定後の一覧更新（Issue #345）

2026-11-01の相談で、編集・削除等が確定した後も、一式の再取得に成功するまでは前回の一覧と操作の成功通知を残す方針を承認された。これは今後の画面接続に適用する契約であり、現在のAppの直接更新を変更したという記録ではない。

現在のAppは編集・削除・画像変更・最終アクセスを作品配列へ直接反映する。一括取得へ接続した後は、操作の返却値を以前の一覧へ継ぎ足して、作品・タグ・関連が同一時点の一式であるかのように表示しない。成功通知は確定した操作を表し、一覧は最後に取得できた情報を表す。

| 結果と読取状態 | 一覧と通知 |
| --- | --- |
| 変更が確定し、再取得中 | 古い読取を失効して一式を再取得する。前回の一覧を残し「最新情報は未確認」と示す。成功通知と登録後の入力クリアは維持する |
| 再取得が通常失敗、部分応答、変換不能ID | 前回の一覧と条件、成功通知を残す。操作を保存失敗へ戻さず再送しない。再読み込みを案内する |
| 一式の取得・検証が成功 | 作品・候補・関連を同時に採用し、その一式から検索・整列・件数・ページを計算する |
| DB停止・結果不明、確定後の停止警告 | 既存の停止と結果通知を優先する。再取得の成功や再読み込みで停止を解除せず、停止後の追加取得を始めない |

例えばタイトル「旧名」を「新名」へ保存した後に再取得が失敗すると、一覧には「旧名」が残り、保存成功の通知と未確認の案内を併記する。削除成功後も、再取得成功までは削除済み作品の古い表示が残り得る。これはDBの削除失敗や作品の復活を意味しない。前回が0件の一覧だった場合も、登録成功通知を失わず、未確認の空表示を最新の登録件数と扱わない。

作品だけを先に反映してタグ・件数を隠す案は、変更をすぐ見せられる一方、表示用の部分更新と一式取得の状態を別々に管理する必要がある。今回は同一時点の表示を優先し、採用しない。作品の同一性はIDと登録日時で判断し、削除済みの旧登録に対する確定結果を、同じ数値IDで再登録された別作品へ適用しない。

対象は登録・作品編集・削除・画像変更・最終アクセス保存・タグの改名/削除による一覧更新とする。読取の失効・再取得を通知するのは確定した変更であり、取消や確定前失敗を変更成功として扱わない。開始済みの操作とダイアログ、親が保持する結果通知の寿命を一覧取得と分離する。タグ管理ダイアログ内の確定表示や競合再確認の契約は維持する。

登録作品のページへ移動するのは一式取得成功後とし、その間の利用者の検索・ページ・表示形式変更やモーダル操作を巻き戻さない。編集・最終アクセスの更新後は、検索条件と現在ページを保って一式を並べ直し、範囲外のページだけ補正する。選択タグ削除後の条件解除・通知・1ページ目への移動は、既存の[条件変更とページ](#条件変更とページ)の契約に従う。

後続は①既存一覧読取と確定済み操作の再取得への接続、②タグ条件・候補UIへの接続、③合成保存先の実WebView2検証に分ける。①では、各操作の確定後に読取が遅延・失敗する場合、古い応答と停止の順序逆転、確定後警告、登録と後発ナビゲーション、削除済みの古い表示からの再操作、ID再利用、開始済み操作と通知保持を検証する。②ではAND件数・改名/削除後の条件・ページと未確認時の条件変更停止を確認する。設計の承認だけでこれらの製品接続や検証を完了とはしない。

## サンプル確認と検証の限界

[HTMLサンプル](../tools/mockups/tag-filter/index.html)は30作品・8タグの合成データだけを使う。通常・多数選択・0件・再取得失敗・初回失敗・選択タグ削除後の表示例を切り替えられる。DB・Wails・ネットワーク・外部ページ起動・永続化は接続しない。

2026-10-31にChromeの1200×900、520×960で描画を確認し、利用者は通常幅のポップアップと狭い幅の選択タグの折り返し配置を承認した。ブラウザー内の簡易チェック7項目でAND件数・未使用候補・半角カナ比較・開いた後のフォーカス・閉じた後の選択とフォーカス・0件案内・取得失敗時の条件変更停止を確認した。人による全操作の試験、実APIの原子性、遅延応答や競合、実WebView2のIME・キー操作・3形式は未検証である。

サンプルの6件ページ、行へのタグ補助表示、2種類だけの並び順、静的な予定表示と状態切替は確認用の仮動作。製品の小型20件・行20件・カード12件や既存の並び順・予定条件を変更しない。サンプルのIntl.Collatorは概略比較であり、製品の正確な自然順比較の試験を代替しない。

## 後続の分割と着手条件

### 内部一括取得（Issue #335）

Storeの`LoadLibrarySnapshot(ctx)`は`LibrarySnapshot{Works, Tags, Links}`を返す。作品は既存の`manga.Work`を全フィールドと登録日時を含めて保持し、関連は`WorkTagLink{WorkID, TagID}`のint64とする。作品/タグはID昇順、関連は作品ID・タグID昇順。成功時の空は非nilの空配列、失敗時は構造体全体をゼロ値にして部分結果を返さない。

既存の受付と接続寿命内で単一トランザクションを開始し、作品・タグ・関連を同じ読取時点から取得する。書込みやCommitは行わず、Rollbackで読取を解放する。作品のドメイン規則・UTF-8・ID順、タグ名とID/名前の重複、関連の重複・不存在参照を検証する。Rows走査/解放・Rollback・接続解放の失敗では結果を破棄し、既存のDB停止へ接続する。取消がトランザクションの自動Rollbackと競合し、解放結果を確認できない場合も保守的に停止する。

一時DBで空・共有・未使用・タグなし、全作品フィールド・ナノ秒精度・int64上限ID・再接続、読取前後のtotal_changes不変を確認する。合成故障で不正保存値・孤立参照・重複・途中SQL失敗、開始前取消・終了後拒否、Rows/読取Rollback解放失敗での全体破棄と停止を試験する。WALの別接続が最初のSELECTの途中で作品・タグ・関連を変更しても、後のSELECTが古い一式を読み、次回は新しい一式になることを確認する。

解放故障は実SQLiteで解放後にエラーを返す合成試験であり、実OSのI/O故障や本当のRollback不成立は再現していない。接続解放の停止判定は既存の共通受付を再利用し、この変更で実接続のClose故障を新たに注入したものではない。Application・Wails API/DTO・フロントエンドへの接続は次段に残し、既存のListWorks等とDB構造は変更しない。ADR-0020はPendingのままとする。

### 公開API・計算・画面への接続

#337でApplicationのLibraryReaderを経由した`LoadLibrarySnapshot()`を公開する。新規DTOの作品・タグ・関連IDは10進文字列、作品日時は日本時間RFC 3339 Nanoとし、一式の検証と変換完了までDB寿命を保持する。既存のWorkDTOと変更APIは維持する。[公開API契約と試験限界](./tag-api.md#一括取得apiissue-337親297)を参照する。画面の読取はまだ既存APIであり、新APIを追加しただけで条件計算・候補件数や遅延応答の統合を完了とはしない。

### AND条件と候補件数の計算（Issue #339）

`frontend/src/tag-filter.ts`の`filterLibrary`は、同一時点で取得・検証済みの全作品・全タグ・関連と表示条件を受け取り、一致作品と候補`{tag, workCount}`を返す純粋関数とする。作品ID・タグIDは文字列で保持する。最小限の作品情報だけを制約にし、渡された作品型・全フィールド・入力順を維持する。作品の整列とページ分割、API呼出し・応答検証・状態管理はここでは行わない。

既存のタイトル部分一致を作品名と候補名にそれぞれ使う。予定の未来条件は既存処理と共有する`scheduledDateVisible`へ渡し、予定順のときだけ適用する。タイトル・予定・全選択タグのANDを通過した全作品から各タグを持つ作品数を数えると、その候補を追加した件数になる。選択済みタグも同じ集計で現在件数となる。未使用/0件候補を除外せず、候補名検索後も既存の自然順・同順位の文字列ID順に揃える。

重複した選択は集合として扱うが、未知の選択IDは例外として拒否し、勝手に条件を解除しない。削除確定や完全な取得に成功した後の条件更新・通知・ページ1への移動は後続の状態管理が行う。APIの未取得/不正応答や孤立/重複データの検証をこの計算関数で代替しない。呼出し側は検証済みの完全なスナップショットと有効な日本の今日の日付を渡す。

合成データで未選択/タグなし/複数/重複選択/未使用/0件、漫画名・予定・候補名検索の独立性、全半角/大小と記号の区別、自然順とint64上限ID、41件の全件集計、凍結入力の非変更性を試験する。画面・APIとの結合、遅延応答・条件削除の状態更新・ページ移動、実WebView2は未接続/未検証。ADR-0020はPendingを維持する。

### 画面側の取得応答検証（Issue #341）

`readLibrarySnapshot(value: unknown)`は一括取得応答を全件検証してから、文字列IDの`LibrarySnapshot`を返す。works/tags/linksの必須配列、作品の全フィールド・文字列型/サロゲート・HTTP(S) URL/相対サムネイル参照、IDの正規表現と昇順・URL重複、タグ名とID/名前の重複、関連のID順/重複/存在参照を確認する。未取得の配列・null・疎な作品/関連配列も成功へ置換しない。例外なら一部だけ採用せず、呼出し側が取得失敗として扱う。

登録・更新・最終アクセスには既存の`validCreatedAt`を変更せず再利用する。正規RFC 3339 Nanoの暦日・時刻・オフセット・非ゼロを確認し、登録と更新の前後は秒と9桁に揃えた小数部を別々に比較する。Dateへ全時刻を変換してナノ秒を丸めたり、比較後に保存文字列を再生成したりしない。予定日はnullまたは年1〜9999の正確なYYYY-MM-DD、最終アクセスの未設定は明示nullとし、項目の欠落をnullへ補完しない。

独立レビューで、Goが保存を許可する大文字のHTTP(S)スキームとU+FEFFだけのタイトルを、JS側が拒否する問題を検出した。回帰試験2件が修正前に失敗することを確認し、スキーム判定は大小文字を区別せず、タイトルはGoの保存済み値の検証と同じ非空判定へ揃えた。元のURL・タイトルは小文字化やtrimをせず保持する。

続く通常確認で、ブラウザーのURL解析にはGoが許可する数値ポートを拒否し、逆に欠落したホストを補完して受理する差も確認した。読み取り側はブラウザーのURL解析を使わず、HTTP(S)・ユーザー情報を除いたホスト部分の非空・制御文字の有無を確認する。URL構文の正本はGo側の検証とし、読み取り時に別の正規化規則を追加しない。数値ポート・ホスト欠落・ユーザー情報だけのURLを回帰試験へ追加する。

`libraryWorkView`は検証済みの作品を既存の数値IDの画面・操作へ渡すための明示変換とする。IDは正規int64文字列かつNumberの安全な正整数で、文字列の往復が一致する場合だけ変換する。読取結果自体はint64上限も文字列で保持するが、安全整数の範囲外を既存操作へ丸めて渡さない。範囲外があったときの実際の表示・操作の扱いは後続の画面接続で具体化する。

合成応答で全フィールド/未使用/空、未取得/部分値/不正型/ID・重複/孤立/順序/疎配列、日時の1ナノ秒差と東京の歴史的夏時間、予定日の暦日、安全整数境界/最大int64・凍結入力を試験する。API呼出し、Reactの取得世代・選択更新・通知/停止・ページ/フォーカス、実WebView2はこの段階では接続しない。ADR-0020はPendingを維持する。

### 一括取得の状態管理（Issue #343）

`useLibrarySnapshot`は初回と`reload()`で一括取得APIを呼び、応答検証と全作品の安全なWorkView変換に成功した場合だけ`data={snapshot, works}`を同時に採用する。snapshotのIDは文字列のまま保持する。loading/fresh/stopped/errorを別に持ち、取得中や通常失敗では前回dataを残してfresh=falseとする。初回失敗はdata=nullであり、全配列が空の正常成功とは区別する。安全整数範囲外の作品を含む場合も、丸めたり一部を除外せず取得失敗として扱う。

新しい取得が始まると古い成功・通常失敗は採用しない。古い要求からDB停止が返った場合は例外として観測し、stoppedを保持して進行中の成功応答も失効させる。外部の`stop()`でも同じ停止へ接続する。停止後のreload/変更通知やloaderの切替で停止を解除しない。エラーの表示には既存の安全な包装を使い、生の診断は表示しない。

呼出し側が変更の確定後に`changed()`を通知すると、古い取得を同期で失効し、未確認にして自動再取得を予約する。同一ターンの通知をまとめ、明示reloadもその予約を取り込む。これは読取だけであり、登録・編集・削除等の変更操作を再送しない。確定結果と通知は元の所有箇所で維持し、再取得失敗を保存失敗へ戻さない。unmountやloader切替後の古い予約は実行せず、応答も新しい状態へ反映しない。

合成PromiseとReactのhook試験で、初回/空/失敗/部分値/変換不能ID、前回データ保持、新旧応答の逆転、変更通知の集約と明示取得、古いDB停止と遅い成功、外部停止・loader切替、StrictMode・unmount後の予約を確認する。Appの既存ListWorks呼出しは未変更で、このhookの追加をタグUI・選択条件・ページ・操作通知との統合や実WebView2確認済みとは扱わない。ADR-0020はPendingを維持する。

設計PRのマージ後、#297を親として次の単位を具体化する。API層の変更が大きい場合は内部取得と公開APIをさらに分ける。

1. 同一時点の一括取得と公開API：型・識別子・空/不正/部分結果・寿命・停止・別接続での途中変更・既存API互換を確認する。
2. AND条件と候補件数の計算：全件で検索・予定・タグを合わせ、自然順、0件、未使用、候補検索との独立性、ページ分割前の集計を試験する。
3. 画面接続と実機検証：承認配置、初回/再取得失敗、遅延応答、改名/削除後の条件、作品編集・ページ補正・通知保持、3形式、再起動解除、Tab／Space／Esc・IME・狭い幅を合成保存先の実WebView2で確認する。

設計サンプルの承認だけで#297の実装・機能全体の検証完了とはしない。OR、タグ統合・階層、検索/選択タグの再起動保持、新しい並び順、通常の利用者データでの検証は対象外とする。
