# 手動バックアップ・復元の初回設計

2026-11-03に合意。親#378、設計#379、判断は[ADR-0022](./adr/0022-manual-backup-and-replacement-restore.md)。目録検証とZIPの読込・Writerへの書込みは実装済みだが、利用者が実行するバックアップ・復元機能は未接続である。

## 合意した範囲

- 利用者が明示操作する手動方式から始める。作品情報・予定日・タグ・最終アクセス・保存済み設定とアプリ管理画像を1ファイルへまとめる。利用者が選んだ元画像は含めない。
- 初回はパスワード暗号化なし。作品情報や最終アクセスを含むため、共有せず安全な場所へ保管するよう保存時に案内する。
- 開始済みの操作が完了してから実行し、登録・編集・削除・URL起動・画像操作等の通常操作を処理中は止める。DBと画像を整合した状態で扱う方法はSpikeで確認する。
- 既知の欠損・破損画像は除外内容を記録・警告し、作品情報と正常な画像の退避を続ける。作品自体は復元後も残り、除外画像は仮表示となる。対象ファイルの安全性を確認できない場合や、一般の読込/書込失敗まで無条件に無視する方針ではない。具体的な分類・参照の扱いは未決定。
- 保存物を完成できない書込失敗等は成功と扱わない。
- 復元は現在データへの追加・統合ではなく、バックアップ時点への一式復元とする。バックアップ後の変更は復元先へ引き継がれない。
- 復元前の現在データを退避し、復元失敗時に戻せる設計とする。退避や復旧の実現性を検証するまで安全を保証したと案内しない。
- 復元成功後は完了画面から終了し、利用者が再起動する。旧画面状態・接続を持ったまま通常操作へ戻さない。

自動定期バックアップ、クラウド同期、データ統合、暗号化は初回対象外。DBや画像を今すぐ手動コピーする手順の承認ではない。

## 保存方式の追加合意（2026-11-03）

#380の調査後、ZIPにDBコピー・管理画像・版付きJSON目録を格納し、DBコピーをVACUUM INTOで生成する方針を利用者が承認した。目録にはサイズ・ハッシュ・除外画像を記録する。この合意時点では個別の形式仕様、入力制限値、版互換、整合性を保つ受付停止、安全な公開・復旧は未確定だった。その後の形式契約と検証状況は次節を参照する。

## 未決定と導入順序

具体的な構成・目録・入力上限・検証順・実装分割は[バックアップ形式v1](./backup-format.md)を参照する。展開後合計2GiB・DB256MiB・管理画像1万枚を利用者が承認した。対応DBの実際の許可リストと復旧記録等は後続で確定する。

2026-11-03、#390で[目録モデルと厳密な検証](./verification/backup-manifest.md)、#391で[ZIPの限定読込と本文照合](./verification/backup-archive.md)を実装した。ZIP検証では利用者承認どおり本文を破棄し、全件成功時だけ目録を返す。ファイル出力・SQLite解析・画像デコード・通常保存先への接続は行わず、形式検証の成功を復元可能と判断しない。

#397では[WriterへのZIP書込み](./verification/backup-writer.md)を先行した。目録と読み取り元を照合し、読込・書込・最終化・協調キャンセルを扱う。返り値の成功はZIP最終化だけを表し、実ファイルのSync/Close・失敗出力の破棄・非上書き公開、通常データの取得と受付停止は後続に残す。

### 互換性と保存の追加合意（#387、2026-11-03）

- アプリ版だけで可否を決めず、バックアップ形式とDB構造の対応範囲で判断する。対応する旧DBは準備用コピーで移行・検証してから使う。新しすぎる形式・未対応構造は現在データを変更せず拒否する。元のバックアップも書き換えない。
- 復元で許容する画像欠損は、作成時に目録へ除外を記録したものに限る。それ以外の画像/DBの欠落やハッシュ不一致は、現在データを変更せず復元を中止する。破損バックアップからの部分救出は初回対象外。
- 目録に除外記録があるだけで入力全体を信頼しない。DB参照との対応や、正規形式・サイズ・パス等の検証も必要であり、ハッシュ一致は真正性の保証ではない。
- 保存ダイアログでは日時付きの名前を初期表示し、新規ファイルへ保存する。既存ファイルは上書きせず、同名が存在する場合は別名を選んでもらう。利用者が保存したバックアップの整理は利用者が行い、復元用退避の自動整理と混同しない。

この追加合意時点では、対応可能な旧DBの具体的な範囲・形式版・移行経路、入力検証の順序と上限、目録の厳密な項目と参照整合性、同名競合を防ぐ完成物の公開方法は未決定だった。現在は形式v1・目録項目・検証順・上限を形式契約に記録済みである。旧DBの対応許可リスト・移行経路、DB/画像の意味的検証と参照整合性、完成物の安全な非上書き公開は残っている。全旧版からの復元や非上書きの実装成立性を保証した記録ではない。

### 一時保存と完成ファイルへの切替（#399、2026-11-03）

利用者は次の方針を承認した。完成名への切替を、ここでは公開と呼ぶ。具体的なWindows APIや耐障害性の確認は後続であり、実ファイル保存はまだ製品へ接続しない。

- 選んだ保存先と同じフォルダーに、完成物と区別できる専用名の一時ファイルを新規作成する。書込み・同期・読み戻し検証が終わってから完成名へ切り替える。既存ファイルは上書きせず、公開直前に同名が現れた場合も内容を変更しない。
- 通常の失敗・取消では、今回作成した一時ファイルだと安全に確認できる場合だけ削除する。確認できない場合は保持する。削除失敗時は場所と未完成であることを案内し、保存成功とは扱わない。
- 異常終了後に残った一時ファイルは、初回は自動整理しない。名前や接頭辞が一致するだけでは削除対象にしない。これらは復元前の退避とは別で、下記の直近3回の整理規則も適用しない。
- 初回は内蔵ドライブ・USB等のローカル保存先を先行し、NAS等のネットワーク共有は後続に分ける。ローカルでも必要な安全な作成・識別・非上書き公開の機能を確認できない保存先では、理由を案内して中止する。すべてのUSBやファイルシステムに対応済みという保証ではない。
- 取消は完成名への切替開始前まで受け付ける。開始後は結果確認を優先する。保存済みと確認できた完成ファイルを、遅れて届いた取消で削除しない。

結果を安全に特定できない場合は既存のデータ保全原則を適用し、関連ファイルを保持して結果不明を案内する。推測した成功・失敗や自動削除・自動再実行へ置き換えない。名前の存在確認だけを非上書きの競合対策とせず、同期・読戻し・切替・Closeの確認可能な保証と失敗の分類を#400のSpikeで調べる。単一操作の成功だけから、電源断後の耐久性や復元可能性を保証しない。

#400の[限定Spike結果](./verification/backup-publication-spike.md)では、ローカルNTFSでの同じ元ハンドルによる絶対パスへの非上書き名前変更とID維持、合成ZIPの公開後再読込を確認した。一方、保存先ハンドルと相対名の経路はローカルで引数エラーだった。安全な保存先境界と結果型の具体化は残っており、この結果だけで方式を製品へ採用しない。

### 初回の保存先条件（#406、2026-11-03）

#400の限定Spike後、利用者は次の対応範囲と制御方針を承認した。上記#399のローカル先行を具体化するものであり、製品のファイル操作は未実装である。

- 初回はローカルNTFSに限定する。内蔵ドライブ・USBとも、必要な新規作成・識別・保持・非上書き公開の能力を確認できた場合だけ使う。NTFSであることだけを成功条件にせず、確認できなければ理由を案内して中止する。exFAT・FAT32・ネットワーク共有は初回対象外とする。
- 保存先と途中のフォルダーにシンボリックリンク・ジャンクション等の再解析ポイントがある場合は拒否し、通常のフォルダーを選び直してもらう。リンク先へ自動で置き換えて続行しない。
- 保存先と途中のフォルダーは、確認後に移動・改名・削除されることを抑えるため、処理終了まで保持する。保持中はエクスプローラー等からの移動・改名・削除が一時的に失敗する場合がある。必要な保持を確立できない場合は保存を開始せず、途中で前提を確認できなくなった場合は推測して続行しない。

同じ保存先内での新規一時作成・非上書き公開、今回作成したと確認できる一時ファイルだけの片付け、結果不明時の保持は変更しない。フォルダー保持はドライブ割当て変更や保持中の悪意ある再解析情報変更を含む全競合への保証ではない。

具体的なパスの許可・拒否判定、ローカル/NTFSの確認、祖先の取得・識別・保持と再確認、ハンドルの取得失敗・解放順・解放失敗は後続の実装契約と試験で具体化する。#400で動いたAPIをそのまま製品へ採用した記録ではない。合成データによる正常系・異常系・競合試験と独立レビューを行い、実USB等の未検証条件を区別する。ADR-0022はPendingを維持する。

### 保存先パスの先行検証（#408）

利用者は初回を通常のドライブ文字付き絶対パスに限定し、相対パス・ドット要素・特殊なデバイス指定等を自動補正せず拒否する方針を承認した。日本語や空白を含む通常の名前は対象とする。

`platform.ParseBackupDestination`はこの文字列検証だけを行い、ディレクトリーとファイル名を返す。UNC、混在・重複区切り、末尾区切り、予約名、末尾の空白/ピリオド、制御文字・不正UTF-8・代替ストリーム等を拒否する。Clean等で補正した文字列を受理せず、拡張子の制限もここでは加えない。

成功は存在・ローカルNTFS・再解析ポイント不在・能力・所有の確認ではない。後続は元パスの各フォルダーを開いて確認・保持し、検証成功の構造体だけで書込みを許可しない。現時点では通常保存経路へ未接続で、パスの長さや別名を含むOS上の成立性は保証しない。フォルダー保持・新規一時作成・公開・片付けは後続であり、ADR-0022はPendingを維持する。

### 既存フォルダーの確認と保持（#410）

`platform.HoldBackupDirectory`は保存ファイルの通常絶対パスを再検証し、ローカル固定/リムーバブルのドライブ直下から保存先まで、既存フォルダーを順に開く。削除共有なしのハンドルで保持し、各ハンドルのディスク種別・ディレクトリー属性・再解析ポイント不在と、ハンドルに対応するファイルシステムがNTFSであることを確認する。RAMディスク・ネットワーク・不明な種別や確認失敗は受け付けない。フォルダーや完成先ファイルは作らず、完成先の存在も調べない。

取得途中の失敗・取消は部分的な保持結果を返さず、取得済み全ハンドルの解放を逆順に試みる。返却した保持のCloseも各ハンドル1回だけ試み、解放失敗は専用エラーと元の原因を保持する。Close失敗後に同じOSハンドルを再Closeしない。呼出し側は解放失敗を成功として扱わず、後続の保存処理でも結果へ伝える必要がある。

合成一時領域で、保存先と親の改名が保持中は失敗し、解放後は可能なこと、欠損/非ディレクトリー/リンクの拒否を確認する。非NTFSの名前判定、非ローカル種別、取得途中・確認・取消・解放失敗は模型で試験し、実USB・実exFAT・ネットワーク・悪意ある属性変更やドライブ再割当ての試験とは区別する。OS APIは[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)と[GetVolumeInformationByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew)を根拠とする。

これは保存に必要な確認の一部であり、書込権限・新規作成・ファイルID・非上書き公開の能力を保証しない。通常保存経路には未接続であり、保持の寿命を新規一時ファイルと結果確認へつなぐ処理は後続である。ADR-0022はPendingを維持する。

### 一時ファイルの新規作成と識別（#412、2026-11-04）

`platform.CreateBackupTemp`は#410の保存先確認・保持を取得し、同じフォルダーへ128bitの暗号学的乱数から作った専用名`.manga-update-backup-<32桁hex>.partial`をCREATE_NEW・共有なしで作成する。完成名と一時名が同じ場合は拒否し、同名競合では既存物を変更せず失敗する。衝突時の自動再試行は行わない。完成先ファイルは開かない。

作成した同じハンドルでディスク上の通常ファイル・再解析ポイント不在・リンク数1を確認し、ボリューム識別と128bitファイルIDを取得する。返却する`BackupTemp`はファイルと親の保持をまとめて所有し、Closeでファイル→フォルダーの順に各1回だけ解放を試みる。解放失敗は元原因とともに保持し、再Closeしない。PathとIdentityは観測情報であり、Close後の同じ名前を開く権限や削除許可にはならない。

作成後の識別失敗・取消では、部分的な成功オブジェクトを返さず解放を試みる。`BackupTempError`のPath・Createdと元原因から、新規作成が成功したかと残置候補の場所を確認できる。Createdは識別の成功や所有の再確認を表さない。この先行段階では成功Close・失敗・取消とも削除せず、空の未完成ファイルを残す。#399の所有確認後の片付けは後続で実装し、名前やCreatedだけで削除しない。通常保存経路へ接続する前に片付けと利用者への残置案内を含めて完成させる。

合成一時領域で、完成先/同名一時の非上書き、書込再open拒否、同じIDの確認、親保持とClose後解放、識別失敗・作成後取消の保全、Close失敗の模型を検証する。根拠は[CREATE_NEWと共有モード](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)、[FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)。ZIP書込み・Sync・読戻し・公開・所有確認後削除・異常終了残置整理は未実装で、製品保存操作へは未接続。実USB・電源断・Close失敗の実測や全競合への保証ではなく、ADR-0022はPendingを維持する。

### 復元と退避保持の追加合意（#385、2026-11-03）

- 旧DB・画像を退避してから新一式へ段階切替する。通常のDB接続・移行・画像整理より前に中断記録を確認し、復旧が必要なら通常起動を始めない。
- 完了確定前の中断は、安全に旧一式を特定できる場合だけ元へ戻し、「復元は完了しなかった」と案内する。新一式への切替は自動続行しない。完了確定済みと安全に判断できる場合は新一式を維持する。
- 旧一式を特定できない、または戻す処理も失敗した場合は、旧/新データと復旧記録を保持し、通常起動を停止する。推測や想定外の内容の削除によって復旧を強行しない。
- 正常に復元を完了した際の退避は直近3回分を保持し、新しい復元の成功確定後に古いものを自動整理する。失敗・中断・状態不明に関わる退避は件数にかかわらず対象外とし、利用者が保存したバックアップファイルも対象外とする。
- 復元完了画面で退避先を案内する。復元成功と、その後の整理失敗は区別して警告する。整理失敗を理由に復元を再実行しない。
- キャンセル可能なのは、入力検証・展開など現在データを変更しない準備段階までとする。退避・切替を始める前に確認し、開始後は完了または旧一式への復旧まで待つ。処理段階と経過時間を表示する。表示は進捗の観測であり、残り時間や正常動作の保証ではない。

これらは制御方針の合意であり、現物の識別・状態記録の永続化・再中断からの回復・整理対象の安全な判定が実装済みという意味ではない。整理対象の誤判定や記録不整合があれば自動削除しない。中断に関わる退避を後から整理対象へ戻す条件は未決定であり、正常な復元の退避へ自動分類しない。
