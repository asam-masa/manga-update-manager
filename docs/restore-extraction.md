# 復元元ZIPの全体検証と準備領域への展開

Issue #643、親 #378。2026-11-22に承認した検証・展開の順序と、展開先の同期・読戻しを記録する。[形式v1](./backup-format.md)、[入力の保持契約](./restore-source-input.md)、[準備物の所有と片付け](./restore-preparation.md)を前提とする。#645の展開と#646のSync・読戻しを、#647で同じ入力の保持から実準備物までの内部処理へ接続した。意味的検証・App/UI・退避/切替を含む製品復元経路は未接続である。

## 採用する順序と理由

1. 同じ読取専用ハンドルで元ZIPを取得し、サイズ・識別を再確認する。
2. 既存の`ValidateArchive`でZIP全体を検証する。本文は保存せず、全件成功時だけ目録を受け取る。
3. 入力を再確認し、今回専用の準備領域を作る。同じ入力ハンドルから再検証しながらDB・画像を展開する。
4. 各準備ファイルをSyncし、同じ出力ハンドルからサイズ・SHA-256を読み戻して照合する。
5. 元ZIPの最終読取後の再確認と解放を終え、すべて成功した場合だけ、準備成果物の所有を次の検証工程へ渡す。

全体検証と展開を同時に行う案より、既存の検証だけのAPIを維持し、不正なZIPで準備ファイルを書き始めることを避ける案を採用する。元ZIPの本文の読取・解凍が2回分になる。前半の成功だけを根拠に後半の検証を省略せず、途中で入力を閉じて同じパスを開き直さない。

展開中の検証・書込結果・Syncだけで終える案より、書かれた準備ファイルも照合する案を採用する。DB・画像の読戻し時間が追加される。Sync・読戻しの成功も、任意の電源断への永続性、SQLiteやPNGの意味的な正しさ、復元可能性の保証とは扱わない。

## 再検証と出力の対応

全体検証・展開とも[形式v1の上限と検証順](./backup-format.md#上限と検証順)を維持する。展開後合計2GiB・DB256MiB・画像1万枚と、目録・画像1個・ZIP全体・ディレクトリーの保護上限を緩めない。宣言値だけでなく実量を有界バッファと上限付き読取で確認し、入力や展開結果の全体をメモリーへ保持しない。

展開時にも構造・名前・型・圧縮方式・重複・件数・目録との対応・実量・CRC・SHA-256を確認する。全体検証で受け取った目録との一致も確認し、別の目録へ黙って差し替えない。検証ロジックの共有は後続実装で照合し、検証だけのAPIの振る舞いを変更しない。最終読取後の入力再確認は、最後の本文読取だけでなくZIPメタ情報の読取も終えてから行う。

| 入力 | 出力への対応 |
| --- | --- |
| `manifest.json` | 検証済みの有界な目録として扱い、任意の名前でファイルへ保存しない |
| `database.sqlite` | `RestorePreparation.CreateFile`が作る子1件とDBの役割を対応付ける |
| `images`にある画像 | 同じ部品が作る子と画像IDを対応付ける。共有画像はIDごとに1件とする |
| `omittedImages` | 本文を要求・生成しない。除外記録を次の意味的検証へ渡す |
| 未知名・重複名・リンク・不正な構造 | 形式契約に従って拒否する。救出や汎用展開へ切り替えない |

ZIPの名前を出力パスへ連結せず、既存部品のランダム名による新規作成と所有登録を使う。固定の展開名で既存物を探す方式、外部パス一覧の所有への取込み、パスからの再取得は採用しない。DBの役割・画像IDと保持した子の対応を次の工程へ渡し、物理名を論理IDとして扱わない。

出力は今回作成した子の保持ハンドルへ書く。短い書込・下位エラー・取消で部分成功へ変換しない。Sync後にサイズを照合し、読戻しにも期待サイズに基づく上限を設けて余分・不足・SHA-256不一致を拒否する。借用I/Oの部品が親や子を勝手にClose・削除しない。

## 所有と失敗・取消

入力所有者と準備物所有者は別に保持する。読取・書込などの消費処理をすべて終えてから解放や片付けへ進み、使用中の借用reader・writerとCloseを競合させない。取消は各操作の前後・操作間で確認し、開始済みOS I/Oの強制中断や厳密な終了時刻を保証しない。

| 状態 | 契約 |
| --- | --- |
| 全体検証前・全体検証中の失敗/取消 | 準備領域を作らず、取得済みの入力を解放する。取得時の部分所有・解放未確認も既存の観測に残す |
| 準備領域の作成・展開・Sync・読戻しの失敗/取消 | 成功成果物を返さず、入力解放と、今回の準備物だけの既存Cleanupを実行する |
| 最終入力再確認・入力解放の失敗/未確認 | 準備完了とは扱わず、準備物の片付けも行う。入力解放未確認を片付け成功で消さない |
| 準備物の片付け・解放の失敗/未確認 | 元の失敗/取消と分離し、子・親・入力の観測と残置候補を保持する。再取得や再帰削除で補わない |
| 全体成功 | 入力の解放確認後、準備物の親と子の所有・DB/画像の対応・目録を次の工程へ渡す。出力はその工程の消費が終わるまで保持する |

元の原因、入力の解放原因と観測、準備物の片付け原因と観測を区別する。失敗結果に残るパスや観測を、再利用可能な成果物や削除許可へ変換しない。片付けは親の確認不能による削除停止、確認できる残りの子の片付け、子の後に親を解放する既存契約を維持する。取消後も必要な安全確認・片付け・解放を待つ。

この契約の片付けは、現在データの退避・切替を始める前に限る。元ZIP・現在データ・退避済みデータを削除・変更しない。成功した準備物も本番へ公開せず、意味的検証で失敗・取消された場合には、引き継いだ所有者が同じ準備物の契約で片付ける。通常操作の受付/再開・終了案内、切替開始後の保全・復旧は別契約とする。

## 実装と検証の分割

### 再検証付き展開部品（#645）

`backup.ExtractArchive(ctx, reader, size, expected, open)`は、呼出元が全体検証で得た目録を受け取り、既存の`ValidateArchive`と同じ構造・目録・本文検証を使う。目録の全フィールドが一致してから、DB、目録順の含有画像の順に`open(File)`で借用Writerを得る。`File.Path`はコンテナー名であり、ファイルシステムの保存先ではない。呼出元が自ら作る準備物へ対応付ける。目録や除外画像は出力しない。

各出力は宣言サイズを超えて書かず、実量・CRC・SHA-256を照合する。本文の転送バッファは32KiBとし、全本文を一括保持しない。入力の非EOFエラーは、ZIP読込側が返却バイトを利用しても見落とさないよう保持し、以後の読取・新しい出力・全体の成功を拒否する。取消もI/Oとcallbackの前後で確認し、下位原因と併記する。

APIはエラーだけを返し、書込み途中でも成功成果物を返さない。`open`がWriterとエラーを同時に返した場合も、そのWriterは呼出元の所有に残る。入力・出力のClose、Sync、削除、公開、所有の引継ぎは行わない。呼出元は全体エラー時に今回の全出力を準備物の契約で片付ける。期待目録は呼出中に変更せず、同じ入力の保持・前半の全体検証・節目の再確認は#647で接続する。

合成Store/Deflate ZIPで正常なDB/画像、除外画像の非出力、目録不一致、後半のCRC/ハッシュ不一致、短い書込、出力取得/読取の失敗と取消、借用Writerを閉じないことを確認する。既存の不正ZIPコーパスを検証・展開の両APIへ通す。各読取境界でバイト列とエラーが併発する模型、2MiBの転送で入力/出力の最大呼出サイズ、出力上限境界も確認する。巨大入力全体・実OS故障・実保持ファイルへの展開はこの部品試験の対象外とする。

### 同期・読戻し照合部品（#646）

`application.VerifyRestorePreparationFile(ctx, file, expectedSize, expectedSHA256)`は、作成済みの準備ファイルから`Sync・Size・ReadAt`だけを借りる。呼出元は形式検証済みの目録から期待サイズと32バイトのSHA-256を渡し、画像1個/DBなどの種別ごとの上限も検証済みとする。部品側も、期待サイズが正で、最大の構成要素であるDBの256MiB上限以下であることを確認する。パスを受け取らず、画像の上限を256MiBへ変更する許可ではない。

Syncの成功後、サイズを照合してから32KiBバッファで期待サイズ+1バイトまで読み、実量とSHA-256を確認する。最後にサイズを再確認する。不足・余分な内容・ハッシュ不一致、前後のサイズ変化、Sync/Size/ReadAtの失敗では成功を返さない。エラーなしの短いReadAtも`io.ErrUnexpectedEOF`で止め、読取が進まない状態で繰り返さない。各操作の前後・間の取消と下位原因を保持し、`ErrRestoreReadback`を付けて返す。

呼出元は処理中、子と親の保持を維持し、書込み・Close・片付けを並行実行しない。部品はファイルを保持し直さず、Close・削除・所有の移譲・通常受付の変更を行わない。識別・意味的検証・退避/切替の許可や電源断への保証も追加しない。

合成の実保持ファイルで、同期と全本文の読戻し、非Close・非削除・逐次書込位置の維持を確認する。故障模型では同期→サイズ→読取→サイズの順序、余分/不足/ハッシュ不一致、読取バイトとエラーの併発、進まない読取、各段階の取消と下位原因の併発を確認する。2MiBの本文で有界転送を確認し、256MiB境界の受入判定はメタ情報の模型で行う。上限全量の転送や実OSのSync故障・電源断を再現した試験ではない。

### 入力保持から準備成果物までの接続（#647）

`application.PrepareRestore(ctx, sourcePath, directory)`は、呼出元が受付状態とデータ保存先を管理する内部処理である。入力の取得・サイズ/識別再確認→全体検証→展開前再確認→実行専用の準備領域作成→再検証付き展開→全出力のSync/読戻し→最終入力再確認→入力解放の順に接続する。全体検証に失敗したら準備領域を作らない。

検証済み目録からDB/画像IDと出力メタ情報の対応を作り、`CreateFile`で今回作った子だけへ書く。未知・重複・メタ情報不一致の出力要求と不足を拒否し、ZIP名を任意の保存先へ連結しない。除外画像の本文は作らない。

成功時は、準備物の親と子を所有する`PreparedRestore`を返す。目録とファイル一覧は複製した観測を返し、借用ReaderはReadAtだけを公開する。生ハンドルや子のWrite/Closeは渡さない。入力は既に解放確認済みであり、この所有者の片付け対象ではない。呼出元は全借用処理を終えてから`Cleanup`し、準備物を本番へ公開・切替しない。

失敗/取消時は所有者を返さず、消費処理の終了後、入力解放と既存の準備物Cleanupを行う。`RestorePrepareError`で元の失敗/取消、入力の解放原因/観測、準備物の片付け原因/観測を分けて保持する。取得途中のエラーの解放観測も引き継ぎ、入力解放や片付けの未確認を成功へ丸めない。入力Close中に届いた取消でも成果物を返さず片付ける。観測や残置候補を再利用・削除・通常再開の許可に変換しない。

合成NTFSで全経路、DB/画像対応、目録/一覧の複製、入力の解放、成功後の全準備物の片付け、元ZIP・現在/退避データ役の保全を確認する。実際の破損ZIPは前半で拒否する。故障模型では後半のCRC不一致、短い書込、Sync/読戻し・前/後の入力確認・入力Closeの失敗、入力解放未確認、展開/読戻し/Close中の取消、片付け原因/解放未確認を確認する。後半の入力破損は読取の差替え、Close/片付けの故障は実解放後に原因/観測を加える模型であり、保持を破る実外部変更や実OS解放故障の再現ではない。

### 各工程の対応

1. [#645](https://github.com/asam-masa/manga-update-manager/issues/645)：再検証付きストリーム展開。借用Writerを使う形式部品として、既存の検証だけのAPI・上限・エラー保持を維持する。
2. [#646](https://github.com/asam-masa/manga-update-manager/issues/646)：準備ファイルのSync・読戻し照合。保持ハンドルを借用し、親子の所有や片付けを変更しない。
3. [#647](https://github.com/asam-masa/manga-update-manager/issues/647)：両部品と入力保持・準備物の所有を内部制御へ接続し、成功時の所有受渡しと失敗時の片付けを確認する。

通常レビューと独立レビューを行う。合成ZIPで構造不正、宣言と実量の不一致、CRC/ハッシュ不一致、上限境界・1単位超過、目録の不一致、後半の画像破損を試験する。故障模型で読取・短い書込・Sync・読戻し・入力再確認・入力/準備物解放の失敗と取消、残置候補を確認する。正常系ではDB/画像の対応・全内容・所有の寿命と、元ZIPや現在データ役のファイルの保全を合成NTFSで確認する。

APIの具体形と共通化範囲は各Issueで照合する。SQLiteの構造・移行/意味的検証、PNG内容・寸法とDB参照の照合、管理画像の識別再確立、通常操作の制御、App/UI、退避・切替・復旧への接続は対象外である。[#651](https://github.com/asam-masa/manga-update-manager/issues/651)で意味的検証の契約を具体化する。#653の[合成VFS Spike](./verification/restore-vfs-spike.md)を踏まえ、#655で[読取専用VFSの採用・原因保持・解放契約](./restore-sql-session.md)を確定した。SQL使用中/解放未確認のCleanup防止とVFS/SQL接続は#656/#657の後続であり、現行の準備物へ検査を接続済みとは扱わない。各部品単独の試験と#647の内部接続試験を区別し、実OS故障・電源断も未検証とする。ADR-0022のValidation StatusはPendingを維持する。
