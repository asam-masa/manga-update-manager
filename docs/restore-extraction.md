# 復元元ZIPの全体検証と準備領域への展開

Issue #643、親 #378。2026-11-22に承認した検証・展開の順序と、展開先の同期・読戻しを記録する。[形式v1](./backup-format.md)、[入力の保持契約](./restore-source-input.md)、[準備物の所有と片付け](./restore-preparation.md)を前提とする。今回は契約の記録であり、製品の展開処理は未実装である。

## 採用する順序と理由

1. 同じ読取専用ハンドルで元ZIPを取得し、サイズ・識別を再確認する。
2. 既存の`ValidateArchive`でZIP全体を検証する。本文は保存せず、全件成功時だけ目録を受け取る。
3. 入力を再確認し、今回専用の準備領域を作る。同じ入力ハンドルから再検証しながらDB・画像を展開する。
4. 各準備ファイルをSyncし、同じ出力ハンドルからサイズ・SHA-256を読み戻して照合する。
5. 元ZIPの最終読取後の再確認と解放を終え、すべて成功した場合だけ、準備成果物の所有を次の検証工程へ渡す。

全体検証と展開を同時に行う案より、既存の検証だけのAPIを維持し、不正なZIPで準備ファイルを書き始めることを避ける案を採用する。元ZIPの本文の読取・解凍が2回分になる。前半の成功だけを根拠に後半の検証を省略せず、途中で入力を閉じて同じパスを開き直さない。

展開中の検証・書込結果・Syncだけで終える案より、書かれた準備ファイルも照合する案を採用する。DB・画像の読戻し時間が追加される。Sync・読戻しの成功も、任意の電源断への永続性、SQLiteやPNGの意味的な正しさ、復元可能性の保証とは扱わない。

## 再検証と出力の対応

全体検証・展開とも[形式v1の上限と検証順](./backup-format.md#上限と検証順)を維持する。展開後合計2GiB・DB256MiB・画像1万枚と、目録・画像1個・ZIP全体・ディレクトリーの保護上限を緩めない。宣言値だけでなく実量を有界バッファと上限付き読取で確認し、入力や展開結果の全体をメモリーへ保持しない。

展開時にも構造・名前・型・圧縮方式・重複・件数・目録との対応・実量・CRC・SHA-256を確認する。全体検証で受け取った目録との一致も確認し、別の目録へ黙って差し替えない。検証ロジックの共有は後続実装で照合し、検証だけのAPIの振る舞いを変更しない。最終読取後の入力再確認は、最後の本文読取だけでなくZIPメタ情報の読取も終えてから行う。

| 入力 | 出力への対応 |
| --- | --- |
| `manifest.json` | 検証済みの有界な目録として扱い、任意の名前でファイルへ保存しない |
| `database.sqlite` | `RestorePreparation.CreateFile`が作る子1件とDBの役割を対応付ける |
| `images`にある画像 | 同じ部品が作る子と画像IDを対応付ける。共有画像はIDごとに1件とする |
| `omittedImages` | 本文を要求・生成しない。除外記録を次の意味的検証へ渡す |
| 未知名・重複名・リンク・不正な構造 | 形式契約に従って拒否する。救出や汎用展開へ切り替えない |

ZIPの名前を出力パスへ連結せず、既存部品のランダム名による新規作成と所有登録を使う。固定の展開名で既存物を探す方式、外部パス一覧の所有への取込み、パスからの再取得は採用しない。DBの役割・画像IDと保持した子の対応を次の工程へ渡し、物理名を論理IDとして扱わない。

出力は今回作成した子の保持ハンドルへ書く。短い書込・下位エラー・取消で部分成功へ変換しない。Sync後にサイズを照合し、読戻しにも期待サイズに基づく上限を設けて余分・不足・SHA-256不一致を拒否する。借用I/Oの部品が親や子を勝手にClose・削除しない。

## 所有と失敗・取消

入力所有者と準備物所有者は別に保持する。読取・書込などの消費処理をすべて終えてから解放や片付けへ進み、使用中の借用reader・writerとCloseを競合させない。取消は各操作の前後・操作間で確認し、開始済みOS I/Oの強制中断や厳密な終了時刻を保証しない。

| 状態 | 契約 |
| --- | --- |
| 全体検証前・全体検証中の失敗/取消 | 準備領域を作らず、取得済みの入力を解放する。取得時の部分所有・解放未確認も既存の観測に残す |
| 準備領域の作成・展開・Sync・読戻しの失敗/取消 | 成功成果物を返さず、入力解放と、今回の準備物だけの既存Cleanupを実行する |
| 最終入力再確認・入力解放の失敗/未確認 | 準備完了とは扱わず、準備物の片付けも行う。入力解放未確認を片付け成功で消さない |
| 準備物の片付け・解放の失敗/未確認 | 元の失敗/取消と分離し、子・親・入力の観測と残置候補を保持する。再取得や再帰削除で補わない |
| 全体成功 | 入力の解放確認後、準備物の親と子の所有・DB/画像の対応・目録を次の工程へ渡す。出力はその工程の消費が終わるまで保持する |

元の原因、入力の解放原因と観測、準備物の片付け原因と観測を区別する。失敗結果に残るパスや観測を、再利用可能な成果物や削除許可へ変換しない。片付けは親の確認不能による削除停止、確認できる残りの子の片付け、子の後に親を解放する既存契約を維持する。取消後も必要な安全確認・片付け・解放を待つ。

この契約の片付けは、現在データの退避・切替を始める前に限る。元ZIP・現在データ・退避済みデータを削除・変更しない。成功した準備物も本番へ公開せず、意味的検証で失敗・取消された場合には、引き継いだ所有者が同じ準備物の契約で片付ける。通常操作の受付/再開・終了案内、切替開始後の保全・復旧は別契約とする。

## 実装と検証の分割

1. [#645](https://github.com/asam-masa/manga-update-manager/issues/645)：再検証付きストリーム展開。借用Writerを使う形式部品として、既存の検証だけのAPI・上限・エラー保持を維持する。
2. [#646](https://github.com/asam-masa/manga-update-manager/issues/646)：準備ファイルのSync・読戻し照合。保持ハンドルを借用し、親子の所有や片付けを変更しない。
3. [#647](https://github.com/asam-masa/manga-update-manager/issues/647)：両部品と入力保持・準備物の所有を内部制御へ接続し、成功時の所有受渡しと失敗時の片付けを確認する。

通常レビューと独立レビューを行う。合成ZIPで構造不正、宣言と実量の不一致、CRC/ハッシュ不一致、上限境界・1単位超過、目録の不一致、後半の画像破損を試験する。故障模型で読取・短い書込・Sync・読戻し・入力再確認・入力/準備物解放の失敗と取消、残置候補を確認する。正常系ではDB/画像の対応・全内容・所有の寿命と、元ZIPや現在データ役のファイルの保全を合成NTFSで確認する。

APIの具体形と共通化範囲は各Issueで照合する。SQLiteの構造・移行/意味的検証、PNG内容・寸法とDB参照の照合、管理画像の識別再確立、通常操作の制御、App/UI、退避・切替・復旧への接続は対象外である。既存の部品試験は展開全体の試験成功を意味せず、実OS故障・電源断も未検証である。ADR-0022のValidation StatusはPendingを維持する。
