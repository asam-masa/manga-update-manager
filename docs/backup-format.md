# バックアップ形式v1の契約

Issue #389、親#378。[初回設計](./backup-restore.md)を具体化する。#390で[目録検証](./verification/backup-manifest.md)、#391で[ZIPの限定読込](./verification/backup-archive.md)、#397で[WriterへのZIP書込み](./verification/backup-writer.md)を実装した。実DB・画像の意味的検証、実ファイルへの保存・公開、製品の作成・復元への接続は未実装であり、以下は後続実装と試験の基準も含む。

## 構成と目録

ZIP内は`manifest.json`、`database.sqlite`、`covers/<画像ID>.png`だけとする。画像IDは現行管理画像と同じ小文字16進32桁。ディレクトリーエントリーや任意の元ファイル名を保存しない。絶対パス、親参照、バックスラッシュ、リンク、重複名、未知エントリー、暗号化エントリーは拒否する。圧縮方式はStore/Deflateのみとする。

目録はUTF-8のJSONオブジェクトで、次の情報を持つ。未知キー・同一キーの重複・欠落・不正型・後続JSON値を拒否する。整数値を浮動小数から丸めて採用しない。

| キー | 意味 |
| --- | --- |
| formatVersion | 整数1。未知版は拒否する |
| createdAt | UTCのRFC 3339文字列。日時妥当性を検証する |
| appVersion | 作成元の表示情報。これだけでDB互換性を判断しない |
| migrations | DBに適用済みの移行ファイル名を順序付きで記録。実DBとの一致を後段で検証する |
| database | path=`database.sqlite`、正のsize、sha256（小文字16進64桁） |
| images | id、path、正のsize、sha256を持つ配列。pathはcovers/<id>.pngと一致する |
| omittedImages | id、path、reasonを持つ配列。reasonはmissing/corruptだけ。imagesとIDが重複しない |

images/omittedImagesは空配列も明示する。idやpathの重複を拒否し、目録にない画像の追加や、含めると宣言したファイルの欠落を拒否する。除外記録はDB参照との整合を後段で検証し、ユーザー入力の目録を真正な作成履歴と断定しない。

2026-11-07の#496で、作成時の対象を登録作品が現在使う管理画像に限定した。事前検証で形式上限内の安全な読取と同じ管理対象ファイルであることを確認できても、保存時のサイズ・ハッシュと異なる画像は変更/破損としてcorruptへ記録し、警告して除外する。目録確定後のZIP書込時に変化や不一致を検出した場合は中止する。再検証方式・安全確認不能時の中止と未実装範囲は[画像取得の合意](./backup-restore.md#画像対象再検証と変更画像の除外4962026-11-07)を参照する。形式版・上限値・理由の列挙値は変更しない。

2026-11-07の#500で、`covers`フォルダー自体の欠損はバックアップを中止し、全画像のmissing除外へ変換しない方針を追加した。画像単体の既知の欠損の除外は維持し、フォルダーを自動作成・修復しない。[保存領域と画像単体の欠損の区別](./backup-restore.md#管理画像フォルダー自体の欠損5002026-11-07)を参照する。これは作成側の方針記録であり、ZIP形式・omittedImagesの理由・上限値や既存パーサーは変更しない。

## 上限と検証順

2026-11-08、#520で`application.BuildBackupManifest`を追加した。呼出元が通常受付停止・コピー所有/同一性・親保持を維持するReaderAtと、先行処理で検証した有界のメタ情報を借りる。注入日時をUTCのRFC 3339へ変換し、アプリ版・実履歴・正常/除外画像を目録へまとめる。DBは32KiBのバッファと宣言サイズ+1の範囲で読み、実量が一致した場合だけSHA-256を採用する。readerを閉じず、本文を一括保持しない。

固定64桁の仮ハッシュで符号化した目録を既存DecodeManifestへ渡し、JSON自体を含む総量・形式・重複/件数を確認してからDBを読む。確定ハッシュも64桁の小文字16進で、最終JSONのサイズは変わらない。取消・読取/形式不一致では目録を返さず原因を保持する。これは目録の部品実装であり、App/ZIPへの接続・書込時の再検証・完成ファイル公開は後続。メタ情報と実DB/画像の対応・所有や復元可否を、この部品の形式検証だけで証明しない。

利用者合意の上限は、展開後合計2GiB、DB256MiB、管理画像1万枚とする。画像数はimagesとomittedImagesの合計で数え、共有画像はID単位とする。合計には目録・DB・実際に含める画像をすべて含む。境界値は許可し、1単位超過から拒否する。作成も同じ上限を守り、上限超過を画像除外へ変換しない。

形式パーサーの保護上限として、目録8MiB、画像1個20MiB、ZIP全体2GiB＋64MiBを設ける。ZIPヘッダーや目録の宣言値だけを信じず、実読込量を上限+1で制限し、サイズ・SHA-256・読込/CRCエラーも確認する。入力全体や展開結果を一括でメモリーへ載せない。

#391の読込処理では、中央ディレクトリーを本文の解析前に検査し、宣言・実際の件数を最大10002に制限する。メタ情報の割当ても抑えるため、中央ディレクトリーはZIPの保護用余裕と同じ64MiBを上限とする。単一ボリュームのZIP32/ZIP64を扱い、ヘッダー間の名前・圧縮方式・フラグの不一致も拒否する。汎用ZIPとの互換性より、アプリのバックアップ形式に限定した読込を優先する。

2026-11-03、利用者は#391で検証だけを先行する方針を承認した。本文はストリームで検証して破棄し、全件成功時だけ目録を返す。準備領域への保存は後続に分け、下記3の準備保存まで実装したとは扱わない。

1. ZIPファイルサイズ・エントリー件数（最大10002）・名前・型・圧縮方式・宣言サイズを検証する。
2. 上限付きで目録を読み、形式・配列・対応関係・総量を検証する。
3. DBと各画像を専用準備領域へ、入力名を任意の保存先へ連結せず読み出す。実量とハッシュが一致しなければ中止する。
4. DBの構造・移行履歴・データ規則・外部キー/画像参照、画像の内容と寸法、除外記録を検証する。
5. 対応する旧DBなら準備コピーだけを移行し、移行後も意味的検証を行う。元バックアップと現在データは変更しない。

形式検証だけの成功を、復元可能・安全なDB・正しい画像と扱わない。すべてが成功した後に初めて、別契約の退避・切替前確認へ進む。任意ZIPの汎用展開機能は実装しない。

## DB互換と管理画像

2026-11-08、#518で作成側の`storage.DatabaseCopyMigrations`を追加した。呼出元が所有と親保持を維持する検証済みコピーから、読み取り専用・同一トランザクションで履歴を名前順に取得し、埋込みの現行移行一覧との完全一致だけを返す。空・欠落・重複・未知/未来・過去版は拒否し、現在のアプリに合わせて履歴を補完しない。SQL側で返却件数と名前のバイト長を制限し、Go側で無制限に履歴を保持しない。SQL後処理失敗・取消では部分結果を返さず、解放未確認は既存のErrDatabaseCopyReleaseを残す。履歴名の一致は実構造の一致や復元可能性の証明ではなく、下記の復元互換許可リストを追加する処理でもない。目録組立・App経路への接続は後続。

現行は001_create_works.sql〜009_tags.sql。対応範囲は、既知の移行履歴と実構造が一致し、移行・意味的検証のfixture試験が揃った版だけを許可リストへ登録する。未知・飛び番・未来の移行、目録とDBの不一致は拒否する。現行の通常起動migrateは未知履歴の拒否を保証する関数ではなく、入力の事前検証なしに復元DBへ適用しない。全旧版への対応は未保証である。

画像の管理記録には元ファイルのvolume/file ID等がある。復元先で元の物理識別をそのまま所有確認に使えないため、準備領域から最終配置までの安全な識別とDB管理情報の再確立、除外画像の参照を保持して仮表示にする方法を後続契約で確定する。これが未解決のまま通常起動の画像整理を実行しない。

## 実装の分割

1. 形式モデル・目録/エントリー検証と境界/異常入力試験。SQLite・通常保存先へ接続しない。
2. 専用出力のストリーム書込みと検証。ZIP最終化・容量/取消・非上書き公開の試験。
3. 全操作の停止とDBコピー・管理画像の安全な取得を接続。
4. DB/画像の意味的検証・旧版準備移行・配置後の管理記録再確立。
5. 中断記録・退避・切替・起動前復旧と再中断、最後に画面と実機確認。

具体的な復旧記録の形式・永続化順序・退避整理の識別、対応DB版のfixture一覧は後続Issueで固定する。ADR-0022のPendingは維持し、本契約追加だけで安全な復元を保証しない。
