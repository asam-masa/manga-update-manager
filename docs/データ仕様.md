## タグ保存の構造（Issue #299）

親#294、判断は[ADR-0020](./adr/0020-confirm-tags-with-work-edits.md)。#299は名前検証と追加構造を先行した。#301で[内部のタグ保存取得と作品編集](./tag-storage.md)を接続する。公開API・UIは未接続である。

| テーブル・列 | 制約と役割 |
| --- | --- |
| `tags.id` | 正のINTEGER PRIMARY KEY AUTOINCREMENT。名前から独立し、自動採番で削除済みIDを再利用しない。明示ID指定やDBの直接編集に対する保証ではない |
| `tags.name` | TEXT、BINARY、NOT NULL、UNIQUE。SQLは長さ1〜50とNUL不在を検証する |
| `work_tags.work_id` / `tag_id` | 両方NOT NULLのINTEGER、複合主キーで同一関連を一つにする。作品/タグを参照し、どちらの削除でも関連だけCASCADEする。タグ側から探す索引も持つ |

名前の正規化は`manga.NormalizeTagName`が前後空白を除去する。先頭末尾の改行・タブも空白として除去し、正規化後を1〜50 Unicodeコードポイント、不正UTF-8・Unicode Cc制御文字・U+2028/U+2029不可として検証する。途中の空白と大文字小文字・全半角・結合文字の表記は保持する。`TagName.Validate`は保存済み値の前後空白も拒否し、読み取った不正値を自動修復しない。SQLだけでこの全規則を検証したとは扱わない。

`009_tags.sql`は既存列を改変せず空の2テーブルと索引を追加し、適用台帳と同じトランザクションで確定する。旧作品はタグなしのまま移行し、作品・予定日・アクセス・管理画像記録・表示設定を保持する。

[外部キーの有効化](https://www.sqlite.org/foreignkeys.html#fk_enable)は接続単位で必要である。#299ではテスト専用接続で有効化したが、#301からStore.Open専用ドライバーのフックで、プール再接続を含む各物理接続の有効化と確認を行う。標準名sqliteの別用途へ設定を広げない。公開APIからタグを作成する操作はまだない。

一括編集・複数新規タグと完全同名の既存タグの自動再利用、改名/削除検出、未指定入力の保持、結果不明と内部削除確認の整合は[タグ保存の契約](./tag-storage.md)に従う。公開DTOへの接続とUIは後続で扱う。

## 保存境界

利用者データと画像キャッシュはOSが提供するアプリデータ領域へ保存し、Gitリポジトリ内には作成しない。

WindowsのDB保存先は`%AppData%\MangaUpdateManager\manga.sqlite`とする。起動・終了処理とAPI契約は[作品API設計](./work-api.md)を参照する。

Issue #58で同じ保存先の排他用に`.instance.lock`を作る。内容やファイルの存在を起動状態として扱わず、Windowsの共有なしハンドルをDB終了まで保持する。既存内容を変更せず、終了時にも削除しない。DBのデータ形式とマイグレーションは変更しない。[ADR-0014](./adr/0014-lock-storage-before-startup.md)を参照する。

サムネイルの保存方針は[ADR-0008](./adr/0008-manage-imported-cover-images.md)、PNG生成と方向補正は[ADR-0011](./adr/0011-generate-png-cover-thumbnails.md)を参照する。取り込み・旧画像削除・解除・起動時整理に加え、HTTP配信と画像設定・変更・解除のUIも接続済みである。[ADR-0013の最終判定](./verification/cover-validation-final.md)に検証範囲と限界を記録している。元画像の絶対パスや外部画像URLを作品参照として保存しない。[新規保存](./verification/new-cover-file.md)・[解除API](./verification/cover-remove-api.md)・[旧画像削除](./verification/verified-cover-cleanup.md)・[起動時整理](./verification/startup-cover-cleanup.md)を参照する。整理では未参照かつ照合できた実体の削除・不存在確認後に管理記録を処理し、作品の参照や日時は変更しない。

## 日時の境界

Issue #25の`002_last_access.sql`で`last_accessed_at TEXT`を追加する。未アクセスはNULLとし、既存作品も登録日時で補完しない。起動要求成功後の日時をUTC・小数秒固定9桁で上書きする。アクセス履歴は持たず、作品内容の`updated_at`は変更しない。

タグの保存構造は上記の「タグ保存の構造」、内部保存取得は[内部契約](./tag-storage.md)を参照する。公開API・画面は未接続である。更新予定日は[ADR-0019](./adr/0019-use-manual-japan-schedule-dates.md)に従う。保存形式、API・画面への接続状況、残る作業は以下の「手入力の更新予定日」にまとめる。

- 保存する時刻はUTCへ統一する
- 画面表示、利用者入力、更新予定、アラート判定は`Asia/Tokyo`を基準にする
- 日付だけを表す値は、日本時間のカレンダー日付として`YYYY-MM-DD`で保存する
- Windowsのタイムゾーン設定が変わっても、利用者向けの基準時間は日本時間を維持する

## 手入力の更新予定日（Issue #267）

`007_scheduled_date.sql`でworksへNULL許可の`scheduled_date TEXT`を追加する。既存作品はNULLで、作品・管理画像・最終アクセス・他設定は変えない。内部の`manga.ScheduledDate`は空文字で未設定を表し、DBへはNULLとして書く。0001〜9999年の実在する`YYYY-MM-DD`だけを許可し、空白・桁違い・時刻付き・無効なうるう日を補正しない。日付をUTC時刻へ変換しない。

SQLのCHECKはNULLまたは10文字の日付形式と年の範囲を保証する。完全な暦日の検証はドメインが行い、SQLiteの日付変換に任せない。登録・内部編集で検証し、ID取得・一覧でも保存値を検証する。SQLで直接不正な暦日が入った場合も読み取りでエラーとし、自動修復しない。

内部のEditWorkInputは日付ポインターのnilを保持、空文字へのポインターを明示解除として区別する。4テキストと日付を一つのトランザクションで更新し、変更がなければupdated_atも維持する。画像や最終アクセスの更新は日付を保持する。削除確認は予定日も厳密比較し、NULL条件を含めて確定した内容だけを削除する。結果不明・確定後警告・DB停止と後処理の順序は既存処理を維持する。

#263でWorkDTOのscheduledDateを日付文字列またはJSON nullとして公開する。編集入力の省略・nullは保持、空文字は解除とし、不正な入力日はinvalid_inputで拒否する。削除確認には日付文字列（未設定は空文字）を含め、保存済み日付と異なればwork_changedで拒否する。画面も編集結果と削除確認へ日付を引き継ぐ。#264の編集フォームは開いた日付を初期表示し、保存時にその文字列または解除の空文字を明示して送る。

一時DBでNULL・変更・解除・省略・無変更・再接続、画像/アクセス/設定保持、旧6移行からの追加、不正保存値の非修復、書込拒否と取消、Commit結果不明、削除確認の差異を検証する。旧移行の試験データは旧列のSQLで作り、新しい列を要求する現行Storeを旧DBへ直接呼び出さない。

#278で行一覧とカードへ保存済み日付を表示する。これは#265の段階分割のうち表示だけの接続であり、予定順・未来設定・日付見直しの画面接続は#290で扱う。保存形式と検証規則は変更しない。[現在の表示と検証範囲](./verification/scheduled-date-display.md)を参照する。

## 表示設定

`003_display_settings.sql`で同じDBに`display_settings`のSTRICTテーブルを追加する。作品データは変更しない。

| 列 | SQLite型 | 規則 |
| --- | --- | --- |
| `id` | INTEGER | PRIMARY KEY。CHECKで1だけを許可する単一行 |
| `registration_form_visible` | INTEGER | NOT NULL。CHECKで0（非表示）と1（表示）だけを許可する |
| `work_list_mode` | TEXT | #235の`005_work_list_mode.sql`で追加。NOT NULL、DEFAULTは`cards`。CHECKで`compact`/`rows`/`cards`だけを許可する |
| `work_sort` | TEXT | #257で追加、#282の`008_schedule_settings.sql`で許可値のCHECKを撤去。NOT NULL、DEFAULTは`registration_asc`。許可値はアプリ側で検証する |
| `show_future_schedules` | INTEGER | #282で追加。NOT NULL、DEFAULTは1（ON）。CHECKで0/1だけを許可する。予定順に限って適用する設定 |

移行と読み取りでは設定行を作らない。未登録は表示の初期値で扱い、利用者が開閉したときにUPSERTで指定項目だけを保存する。読み取り時も0/1を検証し、未知値はエラーとして扱う。初期値を自動上書きしない。新しい設定は各機能実装時に追加し、任意キー・検索文字・途中入力は保存しない。理由は[ADR-0006](./adr/0006-persist-display-settings.md)を参照する。

#235では表示形式を専用の読取・保存操作へ分ける。列追加で既存行の形式は`cards`となるが、フォーム開閉・作品・管理画像は変更しない。未登録の読取は`cards`で正常、未知値や読取不能はエラーとし修復しない。保存は許可された文字列の完全一致だけを受け付け、前後空白や大文字を自動補正しない。表示形式のUPSERTは競合時に形式列だけ、フォームのUPSERTはフォーム列だけを更新する。表示形式を先に初回保存した場合のフォーム値はtrue。明示保存で未知の形式を変更することはできるが、読取だけでは保存しない。

並び順の許可値は`registration_asc`/`registration_desc`/`title_asc`/`title_desc`/`last_access_asc`/`last_access_desc`で、種類と方向を一つの値として保存する。#257では列追加だけを行い、既存作品・管理画像・フォーム・表示形式を維持する。未登録は登録古い順で正常、未知値・読み取り不能はエラーとし、修復しない。並び順のUPSERTはこの列だけを更新し、初回挿入時はフォーム表示true・表示形式cardsとなる。他の2設定の更新も並び順を維持する。不正入力は大文字・前後空白を含め完全一致で拒否する。画面からの操作順保存・整列は#258で接続する。

#282では許可値へ`scheduled_date`（今日優先の予定順、逆順なし）を追加する。`008_schedule_settings.sql`は新しい設定テーブルを作成し、既存行を補正せずコピーして旧テーブルと置き換える。全体と移行記録を一つのトランザクションで確定する。未知の並び順文字列も保持するため、当該CHECKだけを撤去する。STRICT・NOT NULL・他列の制約は維持し、他列の制約違反などで移行できない場合はロールバックする。アプリが作る索引・トリガー・ビュー・外部キー参照はこの設定テーブルにはない。独自に改造したスキーマの移行や旧版への逆移行は保証しない。方法は[SQLite公式のテーブル再構築手順](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes)を参照する。

未来表示のStore読取は未登録ならtrueで正常とし、行を挿入しない。不正な保存値・読取不能はtrueとエラーを返し、補正しない。明示保存は未来列だけを更新し、既存3設定の保存も未来列を保持する。初回保存の他設定はフォーム表示true・cards・登録古い順とする。#286で未来表示の[Application/Wails API](./work-api.md#未来表示設定の専用apiissue-286)を追加する。#290で画面の予定順選択・整列・未来条件・日付見直しへ接続する。既存の並び順APIは共有型の許可値拡張により`scheduled_date`も受け付けるが、#290以降の画面も予定順を含む7種類である。

## 生成画像の管理記録

Issue #95の`004_managed_covers.sql`で、空の`managed_covers` STRICTテーブルを追加する。既存作品・最終アクセス・表示設定を変更せず、既存の`thumbnail_path`を自動登録しない。元画像パスや閲覧履歴は保存しない。

| 列 | SQLite型 | 規則 |
| --- | --- | --- |
| `id` | TEXT | PRIMARY KEY、NOT NULL。小文字16進32文字、埋め込みNUL不可。取り込み時に暗号学的乱数16 byteから生成 |
| `relative_path` | TEXT | `covers/<id>.png`のSTORED生成列。NOT NULL、UNIQUE。任意パスを直接書き込めない |
| `state` | TEXT | NOT NULL。`reserved`（名前予約）か`ready`（保存確認済み） |
| `volume_serial` | TEXT | `ready`では小文字16進16文字、NUL不可。64bitの全bitを保持する |
| `file_id` | TEXT | `ready`では小文字16進32文字、NUL不可。128bitファイルIDの16 byteをAPIの順序のまま表す |
| `byte_size` | INTEGER | `ready`では正のファイルサイズ |
| `sha256` | BLOB | `ready`では32 byteのSHA-256 |

`reserved`では確認情報の4列をすべてNULLにする。`ready`ではすべて必須とし、旧桁数・不正表記・不足・サイズ0以下・不正ハッシュ長を拒否する。状態と確認情報はCHECKで整合させる。予約からの一度だけの確定や、保存・参照変更・削除順序は操作APIで扱うため、列制約だけで保証したとは扱わない。

このテーブルは作品参照から独立して残す。作品の画像解除時に記録を自動削除する外部キーやトリガーは設けない。記録だけでファイルの所有や削除許可を証明しない。#148の旧画像削除は[画像保存契約](./cover-persistence.md)に従い、実ファイルの照合と削除・不存在確認を先に行う。記録整理は同じready・識別情報・未参照を条件とする。Windowsの大小文字・区切り違いも共有参照として扱い、他の別表記を排除できなければ記録も残す。既存のパスを自動で書き換えない。

マイグレーションは既存の同一トランザクション方式で適用記録とともに確定する。適用済みの再接続では管理記録を維持する。#97で予約・保存確認済みへの確定・ID取得のStorage操作を追加した。取得時にも状態・生成パス・確認情報を検証する。#101ではready記録の設定と参照解除を追加した。`thumbnail_path`と`updated_at`を同じトランザクションで更新し、他項目と管理記録は保持する。日時は既存値より戻さず、未設定解除と同一参照再設定は変更なしとする。具体契約は[画像保存契約](./cover-persistence.md#実装済みのstorage操作)を参照する。ADR-0013は#199／PR #200の[最終判定](./verification/cover-validation-final.md)でVerifiedとなった。過去の各段階の検証範囲や、実OS故障などの未検証範囲を今回広げるものではない。
