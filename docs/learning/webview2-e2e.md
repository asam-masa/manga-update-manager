# E2Eツールより先に接続の前提を確かめる

## この調査で分かったこと

PlaywrightがWebView2を操作できることと、このアプリのWebView2へ接続できることは別の問題です。Issue [#35](https://github.com/asam-masa/manga-update-manager/issues/35)では、ツールを導入する前にCDP接続口を確認し、現在のloaderでは公式の環境変数方式が利用できないと分かりました。

結果の正本と再現手順は[調査報告](../verification/webview2-playwright-spike.md)です。この資料から新しい採用判断は確定しません。

## 問題を分ける

自動操作には、アプリを起動する、WebView2の接続口を開く、画面へ接続する、操作と保存結果を確かめる、終了する、という段階があります。最初の接続口がないまま操作テストを書いても、登録処理の正しさは検証できません。

今回、DBとWebView2データが作られ、アプリプロセスも動いていました。それでも接続口は開きませんでした。単なるアプリ起動失敗と、デバッグ設定が届かない問題を区別できた点が調査の成果です。

環境変数は、渡せば必ず最後まで保たれるとは限りません。loaderが初期化時だけでなく環境作成時にも消去するため、アプリの`main`で設定し直す案も、そのままでは解決しません。設定の入口から消費する場所まで追うことが重要です。

## データ分離も同じように追う

WebView2のデータ分離用環境変数も消去されます。そこで既存のWailsとGoが使う`APPDATA`を子プロセスだけ変更しました。このアプリのDBとWebView2の既定パスが同じ専用領域へ向くことを、作成されたファイルと依存ソースの両方で確認しました。

テストで実データを使わないためには、テスト側の設定だけでなく、保存側が実際に参照する設定を確かめる必要があります。調査用データはGitへ入れず、通常の利用者データも削除しません。

## 未実施を成功と呼ばない

DOMテストは画面の操作を、Go・SQLiteテストは保存やドメイン処理を確かめます。実WebView2へ接続するE2Eは、その間の実行経路も確かめる役割です。ブラウザー上でAPIを差し替えたテストが成功しても、実Wails APIを通った証拠にはなりません。

今回の接続不可は、Playwrightの不要さや、ほかの接続方式の不可能さを証明しません。現在のバージョンと調査範囲で分かったことを残し、追加調査の費用と機能開発の優先順位を比較するための材料です。

## 接続調査と画面回帰を別々に進める

2026-11-02には、実Wails接続を待たず、ブラウザーで実React画面の回帰を保護する方針を合意しました。正本は[ADR-0021](../adr/0021-verify-react-ui-with-playwright.md)と[画面検証の設計](../browser-ui-testing.md)です。これは導入前の判断であり、試験成功の報告ではありません。

画像が同じでも、ボタンを押した直後に編集画面が消えることはあります。画像比較と操作の期待結果は別々に確認します。反対にDOM上でボタンが動いても、実ブラウザーで文字や画像がはみ出す場合があります。既存DOM試験を残して実ブラウザー検証を加えるのは、異なる失敗を見つけるためです。

APIを差し替えれば時刻やデータを揃えやすくなりますが、実保存の結合は見えなくなります。自動化の量ではなく、どの境界を通った証拠かを確認し、保護できた範囲から手動確認を減らします。

## テスト専用コードを製品へ入れない

#359の基盤では、製品をビルドした後、ブラウザーのページスクリプトが動く前に合成APIを注入します。製品へ「テスト中なら保存を省略する」という条件を足す必要はありません。テスト用フォルダーを作るだけでは誤importを防げないため、依存グラフへ入った時点でビルドを失敗させます。

未対応APIへ常に成功を返す代替は、製品が新しいAPIを呼び始めても試験が緑のままになる危険があります。代替する操作を明示し、足りない操作は失敗として見えるようにします。具体的な手順と未検証の境界は[設計正本](../browser-ui-testing.md)へ記録します。
