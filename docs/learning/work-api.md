# 保存基盤を作品APIへつなぐ

## 処理の順序をどこへ置くか

今回の題材は、入力を受けて時刻を取得し、作品を検証して保存する流れである。Wailsにすべてを書くと、画面との変換と操作の順序が混在する。Applicationへ順序を移すと、Wailsを起動せずに「不正入力では保存を呼ばない」をテストできる。

`WorkRepository`は利用側のApplicationが必要とする二つの操作だけを持つ。Storageの全メソッドをinterfaceへ複製しない。時刻取得には一つの関数を渡す。単純な差し替えに独立したinterface階層は必要ない。

## 重複を先に検索しない理由

登録前にURLを検索しても、検索と登録の間に別の登録が入る可能性がある。最終的な保証はDBのUNIQUE制約で行う。Storageはドライバーの数値コードを共通エラーへ変換し、Wailsはその共通エラーを`duplicate_url`へ変換する。これでApplicationにSQLiteの型が漏れない。

## 接続を持つ期間とテスト

DBはAPIごとに開かず、起動時に開いて終了時に閉じる。終了とAPIが重なった場合も、実行中の操作が終わるまで接続を閉じない。テストでは保存先を一時フォルダーへ差し替え、登録後に終了・再オープンして同じ作品が残ることを確認する。

初期化失敗のテストには、DBファイルと同名のディレクトリを作る方法を使う。OSのACLや実利用者の保存先を変更せずに失敗を再現できる。利用者向けエラーに内部診断をそのまま渡さず、次に取れる行動を示す。

## Goのerrorと画面の契約

Go内部では`errors.Is`で共通エラーを判別する。画面へ届く時点ではGoの型は残らないため、Wailsの`ErrorFormatter`でコードとメッセージへ変換する。メッセージだけを比較すると、文言修正で画面の分岐が壊れる。

日時も境界で変換する。DBとGo内部はUTCを使い、画面へは日本時間の文字列を返す。同じ瞬間を別の表示へ変換するだけなので、保存値の時刻を加算して変更しない。
