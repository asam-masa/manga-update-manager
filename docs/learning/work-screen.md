# 非同期の登録と一覧を分けて考える

## 登録成功と一覧成功は別の出来事

登録APIが成功した後でも、一覧の取得は失敗する可能性がある。一つのtry/catchで両方を登録失敗として扱うと、保存済みの作品を利用者が再登録してしまう。

今回の画面では、登録成功時点で入力をクリアして成功を表示する。一覧取得の失敗は一覧のエラーとして表示する。テストでは、登録成功と次の一覧失敗を順に返し、成功表示・入力クリア・再読み込みでの復旧を確認する。

## 状態を増やす理由

空の配列だけでは、未登録と取得失敗を区別できない。初回の一覧はnullとし、取得できた後だけ配列を持つ。読み込み中、取得エラー、登録中、登録エラーは別々に管理する。各状態に画面上の意味があるので、共通の一つのエラーへまとめない。

## ボタンの無効化だけでは不十分な場面

Reactのstate変更は次の描画へ反映される。描画前に同じ送信処理が呼ばれる場合を防ぐため、refで送信中を即座に記録する。利用者にはfieldsetの無効化と「登録中…」を表示する。テストでは保留中のPromiseを使い、送信を重ねてもAPIが一度しか呼ばれないことを確認する。

## 古い応答を捨てる

ReactのStrictModeでは開発中のEffectが再実行される。また、初回取得と登録後の取得が重なる場合もある。先に開始したリクエストが後から完了しても、古い結果を新しい一覧へ反映しない。リクエスト番号を比較し、最後の取得だけを反映する。

## テストが確認できる範囲

APIを差し替えるDOMテストでは、入力、クリック、ラベル、エラー表示を確認できる。Go側の保存テストと合わせると、画面と保存の責務を個別に検証できる。ただし、それだけでWebView2と実DBの結合動作を確認したとは言えない。日本語IMEの確定と再起動後の表示は、実機確認の対象として残す。
