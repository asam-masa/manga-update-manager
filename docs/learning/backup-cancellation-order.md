# 取消要求と処理完了を分ける

## 読む入口

#549の`internal/application/backup_execution.go`と対応する試験を読む。仕様の正本は[バックアップ設計](../backup-restore.md#実行制御部品549)と[ADR-0022](../adr/0022-manual-backup-and-replacement-restore.md)である。部品は既存保存経路へ未接続であり、ここでの合成試験を実ファイルの安全性保証と扱わない。

## 読む順番と観点

1. `Cancel`と`BeginPublication`を比較する。「先にcontextを取り消し、後で公開可否を確認する」だけでは、確認直後に別のgoroutineが公開する隙間ができる。同じロック内で状態を変えると、どちらが先だったかを1か所で決められる。
2. `Cancel`のロック解放後を見る。状態を取消受付済みにしてから、その実行の取消関数を呼ぶ。取消関数の実行前でも公開は拒否され、次回実行へ古い取消が届くことも防ぐ。
3. `Finish`と`Begin`を見る。取消受付はI/Oや片付けの完了ではない。所有者が解放の試行を終えるまでは次の開始を止める。完了状態も、解放成功や通常操作の再開許可を意味しない。
4. `TestBackupExecutionCancelPublicationRace`を見る。どちらが勝つかは固定せず、「取消を受け付けたのに公開を開始した」という組合せを禁止している。Sleepで順序を推測せず、チャネルで同時要求を始めて両方の終了を待つ。

## 自分で考える問い

- 取消時にすぐ完了状態へ変えると、片付け中に次のバックアップが始まらないか。
- 古いIDの`Finish`を許可すると、次回の実行表示に何が起こるか。
- 状態確認のロックを保持したままファイル書込をすると、状況取得や取消は応答できるか。
- 部品の試験が成功しても、実際の公開呼出しがこの制御を通らなければ何を保証できないか。

## 結果を保持するときの観点（#551）

`app_backup_run_windows.go`の`start`→`finish`→`snapshot`も読む。完了状態だけが先に見えると「完了なのに結果がない」という矛盾が生じるため、同じロックで結果を対応付ける。一方、処理の実行と大きな目録のコピーはロック外へ置き、観測や取消をI/O待ちに巻き込まない。

Goの構造体をコピーしても、スライスの元配列やポインターの指す先は共有される。`cloneBackupSaveRunResult`と`TestBackupRunRetainsOutcomes`で、保持時・取得時の両方で分離する理由を確かめる。エラーの診断チェーンは内部で読み取り専用とし、任意のオブジェクトを複製できる仕組みに広げない。公開APIのDTO変換と実保存への接続は別の検証である。

## 予約と停止を分ける観点（#553）

`app_backup_preflight.go`と`internal/application/operation_gate.go`では、終了・二重開始を防ぐ予約の後、起動時整理を行ってから通常操作を停止する。整理自身が通常ticketを取得するため、先に通常受付を止めると整理に入れない。「終了を防ぐ」と「通常操作を止める」は同じ時点である必要がない。

`ReserveBackup`で得た所有者は、`PauseAndWait`が取消で戻っても予約を持っている。待機の取消と片付けの完了を分けるためである。従来の`BeginBackup`が待機取消時に予約を戻す動作と比較し、どの関数が予約の終了責任を持つかを追ってみる。

## 結果確定まで終了を防ぐ観点（#555）

`app_backup_start_windows.go`から`finishBackup`、保持部品の`finish`へ進む順を読む。資源の解放と結果の保持は別の段階なので、予約だけを見る終了判定では、予約を戻した直後の結果を取りこぼし得る。`beforeClose`はGate内で実行中状態も確認し、開始予約との先後を保つ。

`TestAppBackupRunCloseProtectsOutcomeStorage`は、この狭い隙間を実行速度に頼らず模型にして検証する。shutdown時は結果を消すだけでなく、後から届く完了が結果を復活させない条件も必要になる。実ファイルの公開入口との結合は、この寿命試験とは別に確認する。

## 実際の処理の入口を包んで通知する（#567）

`app_backup_save_windows.go`の`backupProgressFile`を読む。保持ファイルのinterfaceを埋め込み、公開・削除・Closeの入口だけを包んでいる。通知後は元のメソッドへ処理を渡すので、所有権・返却値・エラーを変える必要がない。通知しないWriteやSync等も元のinterfaceから呼び出せる。

DB片付けの後に公開し、さらに出力を片付けるため、「片付け」という段階は複数回現れる。固定の画面順に処理を並べ替えるのではなく、実際の処理順を観測する理由を`TestAppBackupStageNotifications`で確認する。

同じ試験では、通知から実行所有者の進捗を取得している。通知前に状態ロックを解放する必要がある一方、通知先自体にも短く非ブロッキングな処理を使う契約が必要になる。合成所有者との試験は、実際のApp保存workerや公開入口の取消制御の結合を代替しない。

## 進捗の通知と実行制御を分ける（#565）

`app_backup_progress_windows.go`の`reportStage`と、`BackupExecutions.BeginPublication`を比較する。「保存確定の段階を通知した」という値だけでは、取消と保存確定の先後を保証できない。画面の段階と取消可否は、別の役割を持つ情報として読む。

`backupRunState`の`start`・`finish`・`snapshot`では、時計を取得してからロックを取る。試験用の時計も関数なので、ロック内で呼ぶと待機や再入の原因になり得る。`TestBackupProgressClockOutsideLock`で、時計が所有者のロックを取れることを確認する。取得時刻とロック取得には隙間があるため、厳密な時刻の保証ではない。

`TestBackupProgressLifetime`は、取消後もworkerを待たせ、経過が増え続けることと、結果保持後に固定されることを合成時計で確認する。実時間のSleepに頼らず、この区別を再現できる理由を考えてみる。内部保存処理の通知は#567で追加し、実保存workerとの結合・公開API/UIは後続である。

## 成果物と観測を別々に残す（#559）

`app_backup_save_windows.go`から`observeBackupOmissions`、`cloneBackupSaveRunResult`の順に読む。保存に使える目録・画像一覧と、「除外を確認した」という事実は役割が異なる。公開後の同期で失敗すると、準備成果物は破棄しても、除外理由や保存時の作品名を診断用に残せる。

`TestAppBackupOmissionOutcomes`では、作品名が読めない場合とSQL解放が未確認の場合を比較する。どちらも画面に作品名を出せないが、後者を警告だけにすると通常操作を安全に再開できる根拠まで失う。`DetailError`と外側へ返すエラーを分ける理由を説明してみる。

保持時と取得時にスライスをコピーすることも確認する。値を観測用として分離しても、元配列を共有すると呼出し側から過去の結果を書き換えられる。この部品の検証だけで、公開APIや実行workerとの接続まで完了したとは扱わない。

## 本文を受け取る前に長さを調べる（#558）

`internal/storage/database_copy_cover_works.go`の`copyCoverWorks`で、SQLの`CASE`から`rows.Scan`、合計サイズの検査へ読む。受信後に`len(title)`だけを検査すると、極端に長いタイトルは検査前にGoへ渡ってしまう。SQL側で長さに応じて本文をNULLにし、Goでは長さから上限超過を判別する。

SQLiteの`length(TEXT)`は文字数を扱い、途中のNULにも注意が必要になる。ここでは`length(CAST(title AS BLOB))`でバイト数を扱う。CASEの遅延評価は[SQLite公式仕様](https://www.sqlite.org/lang_expr.html#the_case_expression)を参照する。これはGoへ渡す本文の制限であり、SQLite内部の全メモリ使用量を8MiB以内に保証する仕組みではない。

`TestCopyCoverWorksByteBoundaries`と`TestCopyCoverWorksReadAndCleanupFaults`を比べ、「上限に達した」と「接続を解放できたか不明」を同じ警告にまとめてはいけない理由を説明してみる。#558は読取部品の実装であり、上記#559で結果保持と内部保存経路の判断を追加した。実行workerとの接続・公開API・画面表示は後続である。

## 詳細が見えないことと、保存できないことを分ける（#557）

除外画像の作品名は、保存後に対象を探すための付加情報である。作品名を表示できないだけなら、本体と資源の安全性を確認して退避を続けられる。一方、SQL接続を閉じられたか不明な場合は、付加情報の不足と同じ警告へまとめられない。失敗の場所だけでなく、何を確認できたかを読む必要がある。

ページ分割は一度の転送を減らすが、Go側に全件を保持するなら保持量は減らない。件数・合計バイト数・1作品名の長さを別々に制限する理由を、[設計正本](../backup-restore.md#結果詳細の可用性分割取得上限5572026-11-14)の表で確認する。上限超過時に一部だけを完全な一覧に見せないことも、数値制限と同じ契約の一部である。この節は設計の説明であり、読取や分割取得の実装成功を示すものではない。
