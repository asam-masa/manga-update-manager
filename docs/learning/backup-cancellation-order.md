# 取消要求と処理完了を分ける

## 読む入口

#549の`internal/application/backup_execution.go`と対応する試験を読む。仕様の正本は[バックアップ設計](../backup-restore.md#実行制御部品549)と[ADR-0022](../adr/0022-manual-backup-and-replacement-restore.md)である。部品は既存保存経路へ未接続であり、ここでの合成試験を実ファイルの安全性保証と扱わない。

## 読む順番と観点

1. `Cancel`と`BeginPublication`を比較する。「先にcontextを取り消し、後で公開可否を確認する」だけでは、確認直後に別のgoroutineが公開する隙間ができる。同じロック内で状態を変えると、どちらが先だったかを1か所で決められる。
2. `Cancel`のロック解放後を見る。状態を取消受付済みにしてから、その実行の取消関数を呼ぶ。取消関数の実行前でも公開は拒否され、次回実行へ古い取消が届くことも防ぐ。
3. `Finish`と`Begin`を見る。取消受付はI/Oや片付けの完了ではない。所有者が解放の試行を終えるまでは次の開始を止める。完了状態も、解放成功や通常操作の再開許可を意味しない。
4. `TestBackupExecutionCancelPublicationRace`を見る。どちらが勝つかは固定せず、「取消を受け付けたのに公開を開始した」という組合せを禁止している。Sleepで順序を推測せず、チャネルで同時要求を始めて両方の終了を待つ。

## 自分で考える問い

- 取消時にすぐ完了状態へ変えると、片付け中に次のバックアップが始まらないか。
- 古いIDの`Finish`を許可すると、次回の実行表示に何が起こるか。
- 状態確認のロックを保持したままファイル書込をすると、状況取得や取消は応答できるか。
- 部品の試験が成功しても、実際の公開呼出しがこの制御を通らなければ何を保証できないか。

## 結果を保持するときの観点（#551）

`app_backup_run_windows.go`の`start`→`finish`→`snapshot`も読む。完了状態だけが先に見えると「完了なのに結果がない」という矛盾が生じるため、同じロックで結果を対応付ける。一方、処理の実行と大きな目録のコピーはロック外へ置き、観測や取消をI/O待ちに巻き込まない。

Goの構造体をコピーしても、スライスの元配列やポインターの指す先は共有される。`cloneBackupSaveRunResult`と`TestBackupRunRetainsOutcomes`で、保持時・取得時の両方で分離する理由を確かめる。エラーの診断チェーンは内部で読み取り専用とし、任意のオブジェクトを複製できる仕組みに広げない。公開APIのDTO変換と実保存への接続は別の検証である。
