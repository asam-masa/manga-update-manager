# 仕様の記録と検証状態の更新を分ける

文書確認には二つの問いがあります。「今回の変更の説明があるか」と「以前の説明が今も正しいか」です。

前者は差分レビューで確認します。新しい仕様や重要な判断の記録がなければ、コードが正しくてもレビューの根拠が不足します。マージ後の確認を理由に先送りしません。

後者はマージ後や外部設定後に関連文書を照合します。例えばCIが成功しても、同じADRで必要とする実機確認が残っていれば、CIの結果だけを追記し、全体のPendingは維持します。過去の調査結果を誤りとして消すのではなく、日付や後続の結果への参照で現在との違いを説明します。

読み取り専用の照合と修正を分けると、確認中の推論がそのまま確定した仕様になることを防げます。漏れは小さなIssue・PRで直し、根拠が取得できない項目は未確認として残します。

正本は[ADR-0012](../adr/0012-check-documentation-after-merge.md)と[PR・レビュー運用](../develop/workflow/pull-request-review.md)です。

最終照合では「部品がエラーを返した」と「取り込み全体で旧画像と参照を保全した」を分ける必要がある。残存状態を用意した整理テストも、実際に処理途中でプロセスが終了した後の再起動とは別の証拠になる。テストが多数成功しても、合格条件へ対応しない部分を件数で埋めることはできない。[ADR-0013の照合例](../verification/cover-validation-audit.md)では不足を後続Issueへ残し、仕様や既知制約を変更せずPendingを維持した。

Issue #192では、部品で書込/同期エラーが返ることと、そのエラーを受けた取り込みが参照変更へ進まないことを別々に確認した。また、PNGの全バイトが残っていても保存確認が終わっていなければ、起動整理は削除の所有根拠にしない。失敗時の「消して片付ける」より「確認できないものを保持する」が必要な場面である。[検証記録](../verification/cover-failure-preservation.md)は実OS故障と境界注入を区別している。

Issue #193では、本番処理の区切りに達したことを子から通知してから終了させる。再接続時の結果は、旧参照のまま、新参照へ確定済み、旧実ファイルだけ削除済みなど、終了した位置で異なる。常に旧状態へ戻すことを正解にせず、現在参照を守り、確認できた未参照物だけ整理する。[途中終了の検証記録](../verification/cover-interrupted-recovery.md)は、状態を手作業で作る試験と実際のプロセス終了、さらに電源断を分けている。

## 完了条件と既知の制約を分ける

ADR-0013では検証の追記ごとにPendingを維持し、残る作業の全体像が見えにくくなった。履歴は残しつつ、現在の合格条件と根拠の対応を一か所へまとめると、未検証と過去の未実装を混同しにくくなる。進捗はGitHub Issuesで管理し、設計文書へ作業管理を複製しない。

既知制約を分ける判断は、未解決の問題を直したことにはならない。今回は特殊な自動前面化の終了だけを、利用者の承認後に必須修正から分けた。通常操作で再現したら必須へ戻す条件も残す。他の停止・保全・終了の検証まで免除する判断ではない。正本は[ADR-0013の完了判定](../adr/0013-define-cover-operation-boundaries.md#現在の完了判定issue-178)とする。
