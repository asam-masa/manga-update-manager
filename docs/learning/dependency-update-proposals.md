# 更新提案と採用判断を分ける

Renovateは更新案を作る道具であり、その変更を採用してよいと判断する道具ではありません。判断の正本は[ADR-0010](../adr/0010-propose-dependency-updates-with-renovate.md)、手順は[依存更新運用](../develop/workflow/dependency-updates.md)です。

## 対象にする基準

継続的に追う価値があり、更新案を機械的に作れて、検証方法を持てる依存を対象にします。Go直接依存・npm・Actionsはこの条件を満たします。更新提案を受け取ることと、最新版への移行を承認することは別です。

間接依存まで通常の個別PRにすると、採用したライブラリの更新との関係を追いにくくなります。一方、脆弱性修正では間接依存も必要になる場合があるため、通常更新の対象外を「永遠に更新しない」と読み替えません。

## 関連する変更をまとめる理由

無関係な依存をまとめると失敗原因を切り分けにくくなります。しかしWails本体とCLIを別々にすると、異なる版の組み合わせを検証する恐れがあります。変更量を減らすことだけではなく、一緒に成立させる条件を基準にPRを分けます。

## 自動化にも境界がある

設定validatorは項目と形式を確認します。検出テストは想定した文字列に一致するかを確認します。CIは変更後のテストとビルドを確認します。どれも実際のBot運用や全GUI操作の代わりにはなりません。

スケジュールはBotを起動する予約ではなく、実行時に新規更新を許可する条件です。PR数の制限も通常更新の予算であり、脆弱性修正は別扱いです。保証できることと、外部サービス・アラート・実行頻度に依存することを分けて記録します。
