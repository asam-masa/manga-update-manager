# 更新提案と採用判断を分ける

Renovateは更新案を作る道具であり、その変更を採用してよいと判断する道具ではありません。判断の正本は[ADR-0010](../adr/0010-propose-dependency-updates-with-renovate.md)、手順は[依存更新運用](../develop/workflow/dependency-updates.md)です。

## 対象にする基準

継続的に追う価値があり、更新案を機械的に作れて、検証方法を持てる依存を対象にします。Go直接依存・npm・Actionsはこの条件を満たします。更新提案を受け取ることと、最新版への移行を承認することは別です。

間接依存まで通常の個別PRにすると、採用したライブラリの更新との関係を追いにくくなります。一方、脆弱性修正では間接依存も必要になる場合があるため、通常更新の対象外を「永遠に更新しない」と読み替えません。

## 関連する変更をまとめる理由

無関係な依存をまとめると失敗原因を切り分けにくくなります。しかしWails本体とCLIを別々にすると、異なる版の組み合わせを検証する恐れがあります。変更量を減らすことだけではなく、一緒に成立させる条件を基準にPRを分けます。

### Viteのメジャー移行

[Issue #72](https://github.com/asam-masa/manga-update-manager/issues/72)では、Reactプラグイン6がVite 8を要求するため、両方を同じPRで更新します。TypeScript 7への移行は別に扱い、失敗原因を切り分けます。`--force`や`--legacy-peer-deps`で互換性チェックを省略しません。

Vite 8はビルド・変換にRolldownとOxcを使用します。lockfileの差分が大きくても、行数だけで問題とは判断せず、直接依存と推移依存の関係を確認します。React Compilerは任意機能であり、今回導入しません。アプリのデータ形式と画面仕様も変更しません。

ビルド成功だけでは、開発用サーバーとWailsの接続を確認できません。DOMテスト、配布用ビルド、WebView2での起動、画像配信Spikeの開発版・配布版を分けて検証し、結果と未実施項目をPRへ記録します。Vite 8の既定ビルド対象はEdge 111などへ変わるため、現在のWebView2での成功を古いランタイム全体の互換性保証とは扱いません。[公式移行ガイド](https://vite.dev/guide/migration)を参照してください。

## 自動化にも境界がある

### TypeScriptの型検査と画面の変換

[Issue #73](https://github.com/asam-masa/manga-update-manager/issues/73)ではTypeScript 7へ移行します。Viteがモジュールを解決するため、型検査も`moduleResolution: Bundler`へ合わせ、廃止された`esModuleInterop: false`を除きます。`tsc`は`noEmit`で型検査を担当し、配布するJavaScriptの変換はViteが担当します。コンパイラーの更新が、そのまま画面の実行コード変更を意味するわけではありません。

アプリ用の`tsc`だけでは、参照先のVite設定用プロジェクトまで検査したとは言えません。ビルドでは`tsconfig.node.json`も明示的に検査します。この設定はNode.jsで実行するため、開発依存の`@types/node`と`types: ["node"]`、必要なESライブラリを指定します。型エラーを避けるために`any`へ置き換えたり、検査を新たに無効化したりしません。再生成できる`*.tsbuildinfo`はGit対象外です。

TypeScript 7は従来のコンパイラーAPIを提供しません。今回のコードではCLIの`tsc`を利用し、APIの直接利用は確認されていません。エディターの言語サーバーはCLIと別の境界なので、ビルド成功からエディターの補完まで検証済みとは判断しません。移行の根拠は[公式リリース説明](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)を参照してください。

設定validatorは項目と形式を確認します。検出テストは想定した文字列に一致するかを確認します。CIは変更後のテストとビルドを確認します。どれも実際のBot運用や全GUI操作の代わりにはなりません。

スケジュールはBotを起動する予約ではなく、実行時に新規更新を許可する条件です。PR数の制限も通常更新の予算であり、脆弱性修正は別扱いです。保証できることと、外部サービス・アラート・実行頻度に依存することを分けて記録します。
