# 表示の成功と設定保存の成功を分ける

## 題材

Issue [#27](https://github.com/asam-masa/manga-update-manager/issues/27)のフォーム開閉設定を題材に、非同期の保存、初期値、失敗時の扱いを整理する。判断の正本は[ADR-0006](../adr/0006-persist-display-settings.md)、現在の契約は[画面設計](../work-screen.md)と[データ仕様](../データ仕様.md)である。

## 画面を閉じることと保存すること

フォームはReactの状態だけでも閉じられる。一方、再起動後の復元には保存が必要になる。DB書き込みの失敗で操作を戻すと、一覧を広く見ることもできなくなる。そこで画面操作を先に反映し、保存できなかった場合は次の起動で以前の状態へ戻る可能性を伝える。

## 非同期は完了順が変わり得る

閉じる要求と開く要求を同時に送ると、最初の要求が後から完了する可能性がある。今回の画面はPromiseの列へ明示操作を追加し、一つの保存が完了または失敗してから次を送る。最初の保存が失敗しても列を止めない。

画面は保存完了を待たず変えるため、古い応答で最新の警告状態を上書きしない。これは複数アプリ全体の順序を保証する仕組みではない。

## 初期値は保存済み値とは違う

未登録の初回と、設定を読み込めない異常では、どちらもフォームを表示する。しかし初回には警告せず、異常なら警告する。初期値を返すことと保存することは分ける。

起動時の値をそのまま保存するuseEffectを使うと、保存済み値の取得前や取得失敗時に上書きする恐れがある。保存は利用者の開閉操作からだけ呼ぶ。StrictModeの再実行や古い応答もテストする。

## 型の範囲を小さくする

保存対象のDisplayはフォーム開閉だけを持つ。検索文字と途中入力を一緒にJSON化しない。保存対象を増やすときは必要な項目だけ追加する。未知の設定を何でも保存する仕組みを先に作る必要はない。

## 境界ごとの検証

保存後の再オープンは一時SQLite、操作とエラーはApplication・Wails、連続クリックと初期化はDOMテストで確認する。DOMの再マウントは実アプリの再起動そのものではない。実WebView2の復元は手動確認として別に残す。
