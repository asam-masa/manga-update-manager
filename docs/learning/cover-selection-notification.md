# 選択完了と取り込み完了を分ける

ファイルを選んだ直後にも、画像の読み取り、変換、保存、DB更新、後始末が残る。APIのPromiseだけでは「選択画面が閉じた」と「取り込み全体が終わった」を区別できない。

今回の追加APIでは、全体の選択枠を解放した直後にイベントを送り、最後の結果は従来どおりPromiseで返す。選択完了を知らせても同作品の操作権は最後の解放まで持ち続ける。これにより別作品の選択と、同作品の二重操作防止を両立する。

作品IDだけでイベントを照合すると、前回の遅い通知が次回の選択中状態を解除する恐れがある。そこで要求ごとの操作IDも照合する。イベントは進捗の手掛かりであり、確定結果の代わりにはしない。イベントが届かなくてもPromise完了で状態を解放し、通知の到着順を前提にしない。

Applicationのコールバックは要求ごとの引数として渡す。共有のImporterへ「今の操作ID」を書き込む方法だと、別作品の取り込みが並行する際に値を取り違える恐れがある。パスを知っている処理からもコールバックへパスを渡さないことで、画面への公開情報を狭く保つ。

正本は[選択完了通知](../cover-persistence.md#選択完了通知)と[ADR-0013](../adr/0013-define-cover-operation-boundaries.md)。この段階では画面を接続せず、テストで選択処理を差し替えて契約を確認する。実OSダイアログやイベント受信の実WebView2確認とは区別する。

## 段階の観測と処理結果を分ける

Issue #184では、要求ごとのコールバックで処理段階も観測できるようにする。「保存」を通知したことは保存成功ではなく、その処理へ入る直前の観測にすぎない。待機アニメーションや経過時間が動いていても、裏側の処理が進んでいる証明にはならない。

停止判定を通過した段階だけを通知し、解放は停止後も必要な後始末として扱う。同じ操作の途中で元画像を解放してから保存準備へ進むこともあるため、「解放」を操作全体の完了と解釈してはいけない。コールバック自体は軽く保ち、結果や制御を変えない。[正本の通知契約](../cover-persistence.md#長時間処理の案内)と[検証の限界](../verification/cover-progress-stages.md)を参照する。画面と10秒計測は後続で接続する。

Issue #186では、段階コールバックから画面へ送信せず、最新の観測状態だけをメモリへ記録する。画面から定期取得すれば、配送キューや通知の再送を増やさずに済む。ただし取得が空でも、処理終了と通信の遅れを区別できない。段階の観測と最終結果を別経路に保ち、完了は操作APIで判断する。[ADR-0017](../adr/0017-poll-cover-progress-snapshots.md)を参照する。
