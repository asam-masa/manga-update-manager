# 画像を展開する前に検査する

画像の読み取りは、拡張子の確認だけでは終わらない。今回の正本は[画像生成の契約](../thumbnail-processing.md)と[ADR-0011](../adr/0011-generate-png-cover-thumbnails.md)である。

## なぜ二つの上限が必要か

圧縮した画像は、少ないバイト数から大量の画素へ展開できる。入力の20 MiB制限だけでは巨大な画像を防げない。寸法を先に取得し、`width > MaxPixels / height`で検査する。先に幅と高さを掛けると、値が大きい場合の整数オーバーフローを検査へ持ち込む。

WebPにはコンテナのキャンバス寸法と、圧縮画像自体の寸法がある。外側だけを確認すると、内側に異なる巨大寸法を置ける。両方を検査して一致を確認してからデコードする。

## 読めることと静止画であること

標準PNGデコーダーはアニメーション制御チャンクを無視して静止画を返す場合がある。そのため、Decodeの成功だけでアニメーション非対応の契約を満たしたとはいえない。チャンクの長さと境界から種類を読み、制御チャンクを拒否する。本文に偶然同じ文字列が含まれる場合は拒否しない。

DecodeConfigは寸法を取得する処理であり、本文すべての検証ではない。ヘッダーだけ残したPNGは寸法を読めても、完全デコードには失敗する。この差をテストで残す。

## 大きな中間画像を増やさない

方向補正後の画像をもう一枚確保する代わりに、元画像の座標へ変換する`image.Image`のビューを作った。8方向を小さな番号付き画素で確認すると、回転と反転の取り違えを見つけやすい。そのビューから600px以下の画像へ縮小する。

インターフェースは将来のために抽象化したものではなく、Goの画像処理APIが必要とする`Bounds`・`At`・`ColorModel`に合わせている。ファイル保存やDB更新のインターフェースを今回先行追加しない。

## どこまで検証したかを分ける

今回の合成画像テストは容量、寸法、透過、方向、破損入力を再現する。実際の表紙の色再現や、WebView2での表示、容量不足時のファイル・DBの整合性は証明しない。独立した敵対的レビューと変異入力のテストも使うが、確認範囲を画像管理全体へ広げて報告しない。
