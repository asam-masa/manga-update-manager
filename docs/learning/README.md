# 学習資料

## 目的

設計と実装で得た知識を、後から理解し直せる教材として残します。ADR、要件、設計文書とは分離し、設計や意思決定の参照時に学習用の説明がノイズにならないようにします。

## 正本との関係

学習資料は、現在有効な仕様やDecisionの正本ではありません。

| 場所 | 役割 |
| --- | --- |
| GitHub Issue | 解決する問題、受け入れ条件、対象外、依存関係、未決定事項 |
| ADR | 判断時点の事実、選択肢、Decision、Consequences、Validation |
| 要件・設計文書 | 現在有効な仕様と制約 |
| PR | 実際の変更、実装理由、確認結果、未実施項目、後続作業 |
| `docs/learning/` | 背景の噛み砕き、比較の考え方、つまずき、確認方法 |

学習資料と正本が異なる場合は、ADR、要件、設計文書を優先します。学習資料から新しいDecisionを確定しません。

## 記録する内容

題材に応じて、次のうち学習に必要な内容を記録します。

- 何を理解するための資料か
- 問題をどのように分解したか
- 判断時点で重要だった制約は何か
- 代替案をどの観点で比較したか
- 実装中に起きた問題と、原因をどう切り分けたか
- テストまたは手動確認で何が分かったか
- どの条件では同じ判断が当てはまらないか
- 正本となるADR、設計文書、Issue、PR

結論や仕様をそのまま複製せず、なぜそう判断できるのかを説明します。未検証の項目を成功として扱わず、事実、推論、提案、実施後の結果を区別します。

## PR・学習資料・会話の使い分け

PR本文は変更内容・実装理由・検証結果・残課題など、レビューに必要な説明を扱います。詳しい読む順番や学習用の問いは本文へ入れず、関連する学習資料がある場合にリンクで案内します。

学習資料は毎PRで機械的に作りません。判断の比較、失敗から得た知識、安全性や責務の境界など、学ぶ価値のある変更に絞ります。既存資料への追記や参照で足りる場合は、新しいPR別教材を増やしません。

コードを読む教材では、必要に応じて次を含めます。

- 学ぶ題材と、今回それを読む理由
- 読む順番と対象のファイル・関数・行。履歴のコードを指す場合は対象コミットも示す
- 「この確認を省くと何が起こるか」など、読むうえで持つ観点
- 自分の言葉で説明してみる問いなど、理解を確認する方法
- 実測・模型・静的確認の区別と、未検証の条件

Codexの完了報告では、適した題材がある場合に学習ポイントと読む入口を短く紹介します。学習案内は、人間の確認が必要なレビュー項目とは分けます。学習の完了や、新しい教材の作成そのものを一律のマージ条件にはしません。ただし、今回の変更に必要な既存資料の更新は従来どおり確認します。

文書がなくても、会話でPR番号と「読む順番・観点・考える問いを教えて」と依頼できます。その際は対象差分と関連文書を確認して説明し、会話での解説を未検証事項の解消や新しいDecisionの承認とは扱いません。

## クイズでの利用

`.agents/skills/quiz-project-decisions`は、Git履歴、GitHub Issues、PR、ADR、設計文書を正本として確認し、学習資料を解説の補助に使います。

クイズのために架空の正解を作りません。回答、成績、出題履歴はリポジトリや外部サービスへ保存しません。
