# ファイルの存在とロックの寿命を分ける

「ロック用ファイルがあるから起動中」と判断すると、異常終了でファイルが残り、次の起動を止めてしまいます。PIDを保存する方法も、PIDの再利用や古いファイルをいつ消すかという判断が必要です。

今回はWindowsが管理するファイルのハンドルを保持します。同じ実体のファイルを共有なしで開くため、次の起動は開けません。ファイルそのものは残しますが、ハンドルを閉じた後やプロセスが終了した後は再び開けます。ロックファイルを削除しないのは、削除と再作成で別の実体をロックする競合を増やさないためです。

重要なのは取得する場所と解放する順番です。DBを開く前に排他を取得し、DBを閉じた後に解放します。途中で失敗してもこの順序を保ち、取得を確認できない場合は保存データへ触れません。

初回の実装では、Wailsが起動コールバックを別処理で動かす点を見落とし、独立レビューで指摘されました。終了処理を二回呼んでも、その後に初期化が始まればDBを開いてしまいます。終了済み状態も同じmutexで守り、遅延した初期化を拒否する必要がありました。順番のテストでは、普段成功する順序だけでなく、終了後に起動処理が届く順序も作ります。

HTTPやSQLiteのテストだけでは、プロセス終了後にOSが排他を解放することは確かめられません。そのため一時保存先を使う別プロセスを起動し、正常終了と強制終了の両方で再取得を確認しました。これは画面の案内やネットワークファイルシステムまで確認したことにはなりません。
