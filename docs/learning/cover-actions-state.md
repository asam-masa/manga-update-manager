# カードの寿命と操作の寿命を分ける

## Reactの作り直しと画像の再取得は別である

Reactのkeyを変えると画像要素は作り直されるが、同じsrcの画像をWebView2が再利用することまでは防げない。no-storeはHTTPの保存制御であり、要素を作り直せば必ず通信が起こるという保証ではない。HTML仕様にも[文書内の利用可能な画像の一覧](https://html.spec.whatwg.org/multipage/images.html#the-list-of-available-images)がある。

今回は、保存済みPNGと別HTTP応答は新画像なのに、利用者の実画面には旧画像が残り、変更UIだけの操作では配信要求数が増えなかった。この観測を根拠に、再取得時だけURLの目印を変えた。通常の再描画でも変えると不要な取得が増えるため、画像要素の寿命に合わせて一度生成する。目印は画像の版ではなく、サーバーは常に現在画像を読む。[正本と実機結果](../verification/cover-image-refresh.md)を参照する。

## カードが消えても操作状態を保持する

検索でカードが消えても、Go側の画像処理は続く。カード内だけに処理中状態を持たせると、再表示した時に処理を忘れ、同じ作品を再操作できるように見えてしまう。今回は一覧を所有するAppからフックを使い、作品IDごとの処理・結果を保持する。

Reactのstate更新はクリック直後に同期反映されるとは限らない。refでも受付状態を持ち、二重クリックの間隙を閉じる。表示用のstateと受付用のrefの役割を分け、同じ処理の開始・終了で両方を更新する。

画像操作、最終アクセス、一覧は同じ作品DTOを返しても、応答の到着順はDB更新順と一致しない。応答で作品全体を置き換えると、古いアクセス応答が新しい画像を戻すことがある。画像操作は画像の項目、アクセス操作は最終アクセスだけを統合し、取得中に完了した変更は世代番号で一覧にも反映する。

テストではPromiseを手動で解決し、イベントも任意の順で発生させる。速い処理の通常操作だけでは再現しにくい、古い通知や非表示中の完了を確認できる。一方、フォーカスやOS選択画面の本番動作は実WebView2で別に確かめる必要がある。

正本は[画面設計](../work-screen.md#登録済み作品の画像操作issue-43)、[通知契約](../cover-persistence.md#選択完了通知)。検証範囲は[画像操作UI](../verification/cover-actions-ui.md)を参照する。

## 操作受付と通知の識別は同じとは限らない

#247では、同作品の受付は従来のIDで保ち、通知はID・登録日時・操作種別で分ける。SQLiteのIDが再利用されても、旧作品の結果を新しい登録の名前で表示したり、通知閉鎖後に別登録へ戻ったりしないためである。画面が隠れていても開始時の作品名を保持すれば、一覧から作品名を引けなくても案内できる。

また、通知を閉じて別作品へ戻った直後に、編集ダイアログの遅延した復帰が割り込む例を追加テストで検出した。予定した復帰先が存在するだけでは不十分で、実行時に利用者がすでに移動していないことも確認する。画像要素は再取得のため作り直すので、テストでもDOM要素の同一性と作品参照の保持を混同しない。[現在の契約](../work-screen.md#作品ごとの共通通知issue-247親236)と実画面未検証の範囲を分けて扱う。

#236の[実WebView2確認](../verification/work-actions-notices.md)では、展開状態のあるボタンがUIAのInvokeではなくExpandCollapseを公開していた。操作補助が失敗しても、製品のボタンが動かないとは限らない。操作方式・対象名を確認し、模擬矩形の計算、実ウィンドウの配置、利用者のキー操作をそれぞれの観測として記録した。拡大キーで寸法が変わらなかった結果も、文字拡大の成功に読み替えない。

## 保存・配信・撮影を別の観測として扱う

開発モードの検証では、配信画像の内容や保存済みPNGが切り替わっていても、ウィンドウ撮影には旧画像が残るケースがあった。保存、HTTP応答、WebView2表示、撮影画像は同じ観測ではない。ここで保存失敗やキャッシュ不具合と決めつけると、正常な層を変更する恐れがある。

逆に、HTTP応答が変わっただけで利用者の画面も正しいとはいえない。実画面と撮影方法の切り分けを残し、確認できた範囲だけを記録する。また、検証補助の強制前面化中にWebView2のフォーカスエラー終了も観測した。補助ツールの条件と通常利用での再現性を分ける必要がある。原因は未特定であり、[開発モードの検証記録](../verification/dev-cover-operations.md)を現在の根拠とする。

後続の[フォーカス終了の切り分け](../verification/webview-focus-exit.md)では、画像選択中の無効な親へ自動前面化した場合に終了し、手動Alt+Tabと取消では終了しなかった。同じ「アプリを前に出す」でも、対象が親か選択画面か、親が有効かによって条件が異なる。補助操作が再現に関わると分かっても、ライブラリ内部の理由や通常操作全体の安全性まで証明したことにはならない。観測条件・終了するコード経路・未確定の理由を分けて残す。
