# レビュー対象と独立性を分けて考える

レビューで大切なのは、詳しく読むことだけではなく、何を読んだかを確定することである。

Gitの作業ツリーとindexは同じとは限らない。画面上のファイルに修正があっても、ステージしていなければコミットに入らない。作業ツリーのテスト成功だけでステージ版を正しいと判断すると、古い不具合をコミットする場合がある。そこでコミット前にはindexを読み、対象のtree IDを記録する。PRでは複数コミットの結果を固定したベースとheadで確認する。

敵対的レビューは、問題があるという結論を先に決める作業ではない。仕様から反例を探し、反例が成立しない条件も確かめる。実装担当の説明だけを渡すと同じ前提を共有しやすいため、別担当へは差分と仕様を渡す。指摘なしも有効な結果であり、AIの指摘は一次根拠を確認してから採用する。

独立性には実行時間の負担がある。全変更に追加する代わりに、データ・外部境界・競合などの影響で適用を判断する。文書でも権限や安全手順を変更するなら、単なる文章修正とは区別する。担当を増やし続けず、解決できない重大な判断は利用者へ戻す。

AGENTS.md方式はCodexが守る手順であり、Git操作を制限するプログラムではない。今回の選択は自動化を小さく保つためのものなので、手動操作での漏れが問題になれば別途見直せる。
