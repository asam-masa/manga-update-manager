# 入口の変更と作品の同一性を分ける

タグ管理の再取得に失敗したとき、「前回の表示を見せる」と「その内容で変更してよい」は別の判断になる。表示を残せば入力や確認内容を見返せるが、最新と誤認させない表示と、変更を止める状態が必要である。改名競合でも、自分の入力を残すことと現在名を確認したことを分ける。確認ボタンで保存まで実行すると、確認のつもりで別の名前を上書きしかねない。[明示確認と再開の契約](../tag-management.md#読込失敗と確認変化からの再開)を参照する。

Issue #322では、編集対象の行と、操作結果の通知を別の寿命で考える。タグ名を変えると検索条件に一致しなくなり、その行が消えることがある。変更した行だけ例外表示する代わりに、通知を行の外へ置き、操作を続けられる場所へフォーカスを戻す。さらに通知をダイアログの内側だけに置くと、閉じたときに確定後の停止警告も消える。通知の所有を一覧側へ分ける理由である。

画面サンプルで配置を承認しても、非同期応答・競合時の入力保持・実WebView2のキー操作まで確かめたことにはならない。承認された操作、サンプルの見た目、まだ製品へ接続していない振る舞いを分けて記録することで、外出先とローカルの引き継ぎでも検証を先取りせずに済む。[設計正本と残る確認](../tag-management.md#管理画面の合意issue-322未接続)を参照する。

Issue #320では、削除確認用のIDと登録日時を文字列のまま往復させる。表示のための型変換でIDや日時の桁を失うと、利用者が変更していなくても確認条件が変わるためである。既存の作品表示DTOを一括変更せず、新規の確認情報で正確な表現を使う。JSONと生成TypeScriptモデルの両方を通す試験で、タグID・作品ID・日時を確認する。

Issue #317の削除確認用データは、タグ名と対象作品を1回のSQLで読む。名前を読んだ後に別のSQLで作品を読む方式では、その間の変更で「古い名前と新しい対象」を表示する可能性がある。読取時の情報を揃えることと、後から安全に削除することは別の保証である。削除の確定時には、その時点で確認条件を照合し直す必要がある。

Issue #313では、その再確認と削除を同じTxで行う。途中の別接続の変更で書けなくなったときは、その呼出しを自動でやり直さない。やり直した新しいTxで削除を通すと、利用者が見ていない対象まで変更する可能性があるためである。またCommit成功後の後片付け失敗は、保存失敗と区別する。確定結果を維持することで、失敗したと思って同じ変更を再送することを避けられる。[契約と試験の限界](../tag-management.md#改名削除の内部確定issue-313)を参照する。

Issue #312のタグ管理では、「使用数が同じ」と「対象が同じ」を区別する。3作品から1作品を外して別作品へ付けても件数は3のままである。件数だけを削除条件にすると、確認しなかった作品からタグを外す可能性がある。作品IDの再利用も含めて何を同じ対象とするかを決め、確認画面の表示と保存時の照合を対応させる必要がある。

一方、改名はタグの同じIDと関連を保って名前を変える。付け外しのたびに改名まで止めるかは、削除と同じ判断ではない。確認したタグ名の変化だけを競合にする方針なら、別の改名を上書きせず、関連の増減だけで入力をやり直す負担も避けられる。[正本の比較と採用理由](../adr/0020-confirm-tags-with-work-edits.md)と[管理の設計](../tag-management.md)を参照する。設計を記録したことは実装・故障検証の成功を意味しない。

Issue #310の削除確認では、作品情報とタグを二つのAPIから読み取る。片方だけ先に反映すると、別々の確認時点を最新の全体として見せるため、両方の成功と検証を待って表示を更新する。それでも同じ瞬間のDB状態を読んだ保証にはならない。取得後の変更は、削除APIが削除と同じTxで正確な作品項目・タグ集合を照合して拒否する。画面の「確認できた」と、DBで「削除してよい」が成立する境界を分ける理由である。[画面契約](../work-screen.md#削除確認のタグ接続issue-310親295)を参照する。

編集・削除は段階的に接続し、現在の検証完了判断は[条件別の照合](../verification/work-edit-delete-completion.md)に集約した。以下の未実装・後続という説明は各設計段階の学習記録であり、現在の作業状態を管理するものではない。層ごとの成功と実機確認を合わせて判断し、合成故障を物理OS故障へ読み替えない。

最新側の話数一覧を開くためにURLを変えたくても、別作品として登録し直すと画像や最終アクセスが分かれる。URLは起動先、作品IDはアプリ内の同じ作品を指すものとして役割を分けると、入口だけを差し替えられる。

Issue #306のタグ編集では「保存済みの候補」「選択の途中状態」「新規作成の意図」を分ける。改名後の候補を読み直しても選択全体を置換すると、利用者が外したタグや作りかけの名前まで戻ってしまう。初回だけ保存済みの選択を採用し、再取得では選択したIDの名前が変わった部分を確認する。正確なIDを文字列で運び、検索用の表記変換は保存名へ適用しない。

また、二つの読取は同時に成功・失敗するとは限らない。先に失敗した一方だけで判断すると、後から返ったDB停止を隠す可能性がある。各読取の停止を観測し、両方の成功と内容の整合を確認してから保存を許可する。これは読取失敗を結果不明の書込失敗として扱うこととは異なる。[画面契約](../work-screen.md#タグ編集の画面接続issue-306)と[実機確認の限界](../verification/work-tag-editor.md)を参照する。

編集対象の4項目だけを保存することも大切である。ダイアログを開いた時点の作品全体を送り返すと、その間に更新された画像や最終アクセスを古い値へ戻す恐れがある。操作受付の排他と、保存する項目の限定は別々の対策になる。

作品行を削除できたことと画像ファイルの削除許可も別である。元画像や共有ファイル、所有を確認できないファイルは消さない。完全削除でUndoを省く判断は、DBとファイルを一つの原子的操作にできることを意味しない。失敗や結果不明の契約は実装前に具体化する。

正本は[ADR-0018](../adr/0018-edit-and-delete-works.md)と[編集・削除設計](../work-edit-delete.md)である。ここでは設計の考え方を説明し、排他・削除の実装や検証が完了したとは扱わない。

Issue #224では、カードを消すだけでなく、削除前に始まった一覧取得が後から作品を戻すことを防ぐ。数値IDだけを永久に除外するとSQLiteが再利用したIDの新規作品まで隠れるため、画面内では登録日時も合わせて識別する。結果通知をカード外へ置くと、消えた作品の警告も伝えられる。モーダルで背景を止めても開始済みPromiseは止まらないため、表示上の停止と応答の整合は別の対策になる。

Issue #223では「DBから作品が消えた」と「削除操作を受け付け直してよい」を分ける。画像の後処理や保護のCloseが残る間に作品予約を解くと、同じ対象の操作や終了判断が先行してしまう。Applicationが戻り、結果をAPIへ変換するまで予約を保持する。一方、Appのmutexを保持したまま終了案内を表示せず、拒否を判断してからロックを外す。安全な順序と利用者への案内は別の責務である。

Issue #227では、画像機能の停止と参照の排他を分ける。画像の安全性を確認できないときでも、参照を変えるDB処理まで必ず止めるとは限らない。ただし排他を省いてよいわけではない。DB削除と後処理を同じ参照排他の内側に置き、画像を操作する段階だけは既存の停止判断を通す。画像の整理を省略したことを警告すれば、削除確定とファイル回収の保証を混同しない。

資源の解放も処理の一部である。ファイル整理の本体が終わっても、保護のCloseに失敗する場合がある。解放結果を次の操作へ伝える前に排他を解くと、安全性を確認できない状態で別の操作が始まる。後処理の成功だけでなく、解放・停止通知・ticket返却・参照排他返却の順序をテストする理由である。App全体の終了判断との接続は、Application単体とは別に確認する。

Issue #222では「現在の内容が確認時と同じか」と「途中で一度でも変更されたか」を区別する。前者を採るなら、全変更を追うrevisionを追加せず確認した5項目を比較できる。確認情報は新規入力ではないので、前後空白を除去して一致扱いに変えない。照合後に別の変更を削除しないよう、読取と条件付きDELETEを同じTxに置く。画像パスの一致は作品が選んだ参照の一致であり、そのパスのファイルを消してよい証明ではない。

Commitが失敗したテストも一種類では足りない。読取ロックによるCommit競合では作品が残り、実Commit後に合成エラーを返すdriverでは作品が消える。それでも本番側の返却はどちらも結果不明となる。テストで再接続して結果を観測できることと、本番で安全に自動再試行できることは別である。

Issue #221では、削除の結果と画像整理の結果を分ける。作品行を消した後でファイル整理に失敗しても、作品を消せなかったことにはならない。「失敗」だけでは利用者に再削除を促すため、確定済みの削除と残った整理を別に伝える。逆にCommitの結果が不明なら、画像まで消すと作品が残っていた場合に参照を壊す。確認できない結果を成功か失敗へ無理にまとめないことが重要になる。

確認画面は、確認した時点の対象を示すものであり、削除時も同じ内容とは限らない。モーダルで背景操作を止めても開始済みの処理は完了し得る。確認対象の照合と実際の削除を競合なく結び、変化があれば確認し直す必要がある。ただし閲覧日時だけの変化まで止めると不要な再確認が増えるため、何を確認対象とするかを先に決める。この方針は設計合意であり、削除での実装検証は後続に残る。

Issue #219では、短い保存を無理に遅いディスクで再現せず、検証用だけの保存境界で待機する。重要なのは待機点が共通受付の内側にあること、実Storeへ委譲すること、古いマーカーや期限切れを今回の待機と誤認しないことである。実画面で終了案内を見ても、実OS故障や通常版の長時間保存まで検証できたことにはならない。解除後に保存し、通常ビルドで読み直す観測を分けて根拠を残す。

Issue #215では入力の寿命と一覧の寿命を分ける。入力は開いた時点で固定し、保存が成功した4項目だけを一覧へ反映する。保存前に始まった一覧取得にはrevisionで保存結果を重ね、画像やアクセスの応答で作品DTO全体を置き換えない。通知もカードから分けることで、タイトル変更で検索から消えても成功を伝えられる。標準モーダルで背景を止めても、開始済みPromiseは止まらないため、この順序対策は必要である。

Issue #213では、APIが成功したことと、その後も安全にDBを使えることを分ける。Commit済みで接続の解放だけを確認できないなら、入力を再送すると保存を重ねてしまう。作品付きの成功に停止警告を添え、Commit自体が不明な場合だけ専用エラーにする。画面の停止判定にも専用コードを加えるが、それだけで入力保持や警告表示のUIが完成したことにはならない。

Issue #209では、入力型から画像と日時を除外し、SQLの更新列も4項目と更新日時に限定する。さらにDBの現在行を読み、過去の画面DTO全体を保存しない。変更なしならUPDATEだけでなくCommitも避ける。一方、Commitエラーを「保存されなかった」と決めつけず、実際には保存済みでも結果不明としてDBを止めるテストを用意する。再接続して結果を調べるのはテストの観測であり、本番が自動回復する方式ではない。

Issue #211では「同じ作品で他の操作を始めてよいか」と「画像やDBの次の段階を始めてよいか」を分ける。作品の予約は画像の後始末まで保持するが、画像だけの停止を全作品機能へ広げない。終了を拒否したときも、受付を閉じたり未開始整理を取消したりしない順序が必要になる。拒否は単にfalseを返すだけでなく、拒否前に何を変更したかまで確認する。

Issue #314では、タグIDと作品IDが同じ数字でも同じ操作対象ではないため、受付集合を分ける。一方で終了を決める瞬間は共通のmutexへ集約する。別々の受付を順番に閉じる方式では、一方を閉じた後で他方が終了を拒否し、アプリが開いたまま一部操作だけ使えなくなるおそれがある。共通の判定で拒否したときは受付を変更せず、案内ダイアログを出す前にAppの寿命ロックも外す。公開APIの成功は確定したタグをそのまま返し、画面更新のための再取得とは分ける。詳しい契約と検証限界は[タグAPI](../tag-api.md#管理用の変更apiissue-314)を参照する。

Issue #327では、管理機能を「見る」と「変える」に分ける。読み取りだけでも、読込失敗を空一覧へ置き換えると「以前のタグが消えた」と誤認しやすい。前回の表示を残すことと、その情報を最新と扱うことを分ける必要がある。また、マウント中かの真偽だけではStrictModeで再開した画面へ旧応答が入るため、要求番号も照合する。DB停止はダイアログだけに所有させず、閉じた後も親で保持する。読み取りの復旧と、停止解除の許可は別である。[契約](../tag-management.md#管理一覧の接続issue-327親315)と[検証範囲](../verification/tag-management-list.md)を参照する。
