# 画像を保存する前に境界を分ける

「ファイルをコピーする」だけでも、入力、展開、保存、DB参照、画面配信は別の失敗を持つ。

容量が小さい画像でも、展開後の画素が多ければメモリーを使う。ファイル容量と画素数を別々に制限し、画像を全部展開する前に寸法を確認する。ただしヘッダーだけが正常な画像もあるため、寸法確認をデコード成功の代わりにはできない。

アニメーション非対応も、PNGやWebPという形式名を許可するだけでは守れない。今回の小さな検証では、GoのPNGデコーダーがアニメーション制御チャンクを含む合成PNGを受理した。これはアニメーション対応の証明ではなく、静止画かどうかを別途確認する必要性を示す。

画像ファイルとSQLiteは同時にコミットできない。旧画像を先に削除すると、新しい画像の保存やDB更新に失敗したとき戻せなくなる。新しい画像を準備して参照を切り替える方法にも、未参照ファイルが残る問題がある。「操作は成功したが後処理に失敗した」を分けて考える必要がある。

GoのHTTPハンドラーで成功しても、WailsのWebView2やViteのプロキシを通るとは限らない。今回の検証はGo側の契約だけを確認した。アプリ配信、保存障害、見え方の確認は後続で行い、技術調査の成功を製品の完成と混同しない。
