# 画像を保存する前に境界を分ける

「ファイルをコピーする」だけでも、入力、展開、保存、DB参照、画面配信は別の失敗を持つ。

容量が小さい画像でも、展開後の画素が多ければメモリーを使う。ファイル容量と画素数を別々に制限し、画像を全部展開する前に寸法を確認する。ただしヘッダーだけが正常な画像もあるため、寸法確認をデコード成功の代わりにはできない。

アニメーション非対応も、PNGやWebPという形式名を許可するだけでは守れない。今回の小さな検証では、GoのPNGデコーダーがアニメーション制御チャンクを含む合成PNGを受理した。これはアニメーション対応の証明ではなく、静止画かどうかを別途確認する必要性を示す。

画像ファイルとSQLiteは同時にコミットできない。旧画像を先に削除すると、新しい画像の保存やDB更新に失敗したとき戻せなくなる。新しい画像を準備して参照を切り替える方法にも、未参照ファイルが残る問題がある。「操作は成功したが後処理に失敗した」を分けて考える必要がある。

GoのHTTPハンドラーで成功しても、WailsのWebView2やViteのプロキシを通るとは限らない。今回の検証はGo側の契約だけを確認した。アプリ配信、保存障害、見え方の確認は後続で行い、技術調査の成功を製品の完成と混同しない。

正本: [ADR-0008](../adr/0008-manage-imported-cover-images.md)、[技術確認](../verification/image-management-investigation.md)、[Issue #40](https://github.com/asam-masa/manga-update-manager/issues/40)。

## 子の保持と領域全体の保護を分ける

フォルダーのハンドルを保持して名前変更を防げても、そこへ到達する途中の親まで同じ条件で守れるとは限りません。Issue #103では固定した合成起点から一階層ずつ確認し、親を保持したまま子を開きました。全階層を保持した状態と解放後を比較すると、単に権限が不足していたため移動できなかった場合と区別しやすくなります。

この環境では子だけの保持でも親の移動が拒否されました。それを一般化せず、観測と保証を分けて記録します。最初の起点を開くまでの安全性はまだ証明していないため、固定階層のテスト成功だけで実アプリの保存先全体が安全だとは扱いません。確認範囲は[祖先保持Spike](../verification/cover-ancestor-handles.md)を参照してください。

Issue #105では、属性を取得する権限と、共有制御によって名前変更を防ぐ条件を分けて比較しました。属性専用での初回の失敗と後の観測差から、属性が読めたことだけを移動防止の根拠にしません。通常読取と読み書き共有の候補では、移動拒否だけでなく、二重の取得・子の読み書き・解放後の移動も確認します。都合のよい拒否結果だけで結論せず、観測と保証を分ける題材です。[ドライブルートSpike](../verification/cover-drive-root.md)に失敗と限界を記録しています。

## 保護範囲と検証の完了を分ける

「悪意ある別プロセスへの完全防御は保証しない」と決めることと、通常の失敗を無視することは別です。共有違反でフォルダーを開けないときに保護を外して続けると、操作ミスや普段の同時操作に対する目標まで失います。対象外は保証の境界であり、リンク拒否や削除前照合を省略する許可ではありません。

Issue #107では、保護範囲は合意済み、通常読取方式は候補、未作成領域や終了待ちとの接続は未検証、と分けて記録します。小さなSpikeの成功から本番採用や全体のVerifiedまで飛ばさず、次の実装で確かめる条件を具体化するためです。正本は[保護範囲と本番化の条件](../cover-persistence.md#保護範囲と本番化の条件)と[ADR-0013](../adr/0013-define-cover-operation-boundaries.md)です。

Issue #109では、既存保存先を先に保持してから、固定名covers一階層だけを準備します。作成できたことと安全に保持できたことは別なので、既存だった場合も同じハンドルで属性を検証します。失敗時に作成済みフォルダーを消さないのは、作成と失敗の間に入った未知の内容まで削除しないためです。Closeも一件の失敗で打ち切らず全件を試しますが、エラーがあれば解放完了と断定しません。[境界の契約](../verification/cover-directory-boundary.md)を参照してください。

Issue #111は、書き込み成功と「閉じた後も同じファイルを読めること」を分けます。CREATE_NEWで既存物を上書きせず、同期とCloseを確認した後、識別情報・サイズ・SHA-256を照合します。同じ内容の別ファイルはハッシュだけでは区別できず、同じファイルの内容変更はIDだけでは区別できません。両方を合わせます。短い書き込みや同期失敗を合成注入するテストは実ドライブを満杯にせず分岐を確認する方法であり、電源断耐久性の証明ではありません。[保存境界の契約](../verification/new-cover-file.md)に未確認事項を残します。
