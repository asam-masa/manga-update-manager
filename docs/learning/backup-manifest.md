# JSONを読めることと、形式を検証できることを分ける

バックアップはアプリ自身が作ったように見えても、読み込み時には外部入力となる。まず目録の形だけを検証し、実DBや画像の安全性は後段へ分ける。[形式契約](../backup-format.md)、[検証範囲](../verification/backup-manifest.md)、Issue #390が正本である。

Goの`encoding/json`は、通常のデコードでは同じキーが複数回現れることをエラーにしない。構造体へ読み込めただけでは、未知キー・欠落・重複をすべて検出したことにはならない。今回はTokenでキーの出現を確認してから、必要なキーと値の型を検証する。キーのUnicodeエスケープは復号後に比較するので、同じ名前を別表記にして重複を隠す入力も拒否できる。

サイズも浮動小数へ変換せず、`json.Number`から整数として解釈する。これにより巨大な整数の精度低下や、小数を丸めて制限内に見せる扱いを避ける。合計の判定は加算前に残容量と比較する。入力を読む段階でも上限+1バイトで止め、宣言されたサイズの正しさには依存しない。

ただし、この段階で分かるのは「目録が契約に沿う」ということだけである。ハッシュに64桁の文字列が入っていても、その画像を読んで照合したことにはならない。移行名が既知でも、DBの実構造が同じとは限らない。後続の限定読込と意味的検証を省略できない理由がここにある。

## ZIPの宣言値も検証対象にする

#391では、目録と実際に読んだ本文のサイズ・ハッシュを照合する。ただし、本文の前にも境界がある。ZIPの終端記録に巨大な件数が書かれていると、本文を展開しなくても、ライブラリのメタ情報の割当てが増える場合がある。先に宣言件数と実際の中央ディレクトリーを上限付きで検査するのはこのためである。

本文のCRC検査は最後まで読んだ時点で失敗することもある。必要なバイト数を受け取れただけでは成功にせず、EOFまたはエラーまで確認する。今回は本文をファイルへ保存せず破棄するので、途中失敗で半端な出力を残さない。[限定読込の検証範囲](../verification/backup-archive.md)と、将来の準備保存・意味的検証は別の責務として扱う。

独立レビューでは、標準ライブラリが格納CRCの0を未設定として検査を省略する条件が見つかった。EOFまで読むだけで今回の厳密なCRC契約を満たすとは限らないため、アプリ側でもCRCを計算して常に比較する。ライブラリの正常終了と、自分たちが保証したい条件を区別する具体例になった。
