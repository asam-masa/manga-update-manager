# 復元準備物の意味的検証

親Issue #651。形式v1のバイト照合と[読取専用SQLセッション](./restore-sql-session.md)に続き、復元の切替前にDBと画像を検証する。

## 現行DBの受入条件

初回は埋込み移行一覧で定まる現行版を対象とする。目録の移行一覧、実DBの適用履歴と埋込み一覧の完全一致を求める。未知・未来・旧版、欠落、重複、目録との不一致は拒否する。対応する旧版は、版ごとの移行手順と移行前後の合成試験を用意して個別に判断する。

埋込みの現行移行SQLを適用した独立した基準DBを作る。保持中の準備DBの `main.sqlite_schema` から得たオブジェクトの種別・名前・所属テーブル・定義文を基準DBと照合する。定義文のNULLを区別し、欠落・追加・定義の差を拒否する。配置に依存する `rootpage` は比較から除く。基準DBは信頼済みの移行SQLから作成し、復元入力の定義文は比較対象として扱う。

移行履歴に加えて定義を比較することで、履歴名が同じでも制約や索引の欠落を検出できる。新規作成DBと過去版から通常移行した合成DBを既存バックアップ経路に通し、正規の入力が通ることを確かめる。正規経路で定義文の差が出た場合は、原因と必要な許容条件を別途判断する。

## データと画像

SQLiteの整合性検査と外部キー検査を行う。作品・タグ・作品とタグの関連を全件読み、日時や保存値、関連先について通常の読込で必要な規則を検証する。検査に失敗した値は修復せず、切替前に停止する。

登録作品が参照する管理画像のID集合と、目録の含有・除外画像のIDの和集合の一致を求め、対応するDB管理記録とパスを照合する。含有画像はDB管理記録・目録・準備本文のサイズとハッシュの一致に加え、PNGの内容と寸法を確認する。除外画像の本文は不要とし、参照を保持して仮表示へつなぐ。元環境で記録した物理識別は復元先の所有確認に使わない。

含有画像は準備ファイルの識別を保持し、最終配置で同じファイルであることを照合してから復元先DBの管理記録を確定する。確認と記録の確定後に通常起動時の画像整理へ引き渡す。具体的な配置・書込み・異常時の復旧順序は切替工程で設計する。

## 実装の分割

1. 現行版の履歴判定と基準DBとの構造照合。
2. SQLite整合性・外部キーと、通常の読込に必要なデータ規則の検査。
3. DB参照・含有と除外の記録・PNG内容と寸法の照合。
4. 切替工程での最終配置・物理識別・管理記録の確定。

#663では現行版判定と構造照合を読取専用セッションへ接続する。既存の移行処理でメモリー内の基準DBを作り、保持中の準備DBでは履歴の照合とRowsの終了を確認してから構造へ進む。新規・通常移行の合成DBをコピーとZIP展開に通し、索引欠落、追加ビュー、履歴の不一致と区別できることを確認する。

途中失敗と取消では検査結果を採用せず、SQL資源を全て解放したと確認できる場合だけ既存Cleanupに進める。解放未確認時は既存の保全契約を適用する。元ZIP・現在データ・退避データは検査工程で変更しない。ADR-0022の検証状態はPendingとする。
